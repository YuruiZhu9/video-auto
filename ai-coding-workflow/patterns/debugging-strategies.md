- 打印关键变量

- 运行测试

## 9. AI 代码安全审计（ykdojo/claude-code-tips 45条）

### cc-safe：扫描危险授权命令

在 `--dangerously-skip-permissions` 模式下，Claude Code 拥有系统级执行权限，存在误操作风险。`cc-safe` CLI 工具可在任务执行前扫描已批准的授权命令：

```bash
npm install -g cc-safe
cc-safe ~/projects
```

**检测的危险模式：**
- `sudo` / `rm -rf` / `chmod 777`
- `curl | sh`（管道执行远程脚本）
- `git reset --hard`（不可逆操作）
- `npm publish` / `docker run --privileged`

**最佳实践：** 在团队推行 Claude Code 规范时，将 `cc-safe` 集成到 pre-commit hook 中拦住高危操作。

### SafeClaw：容器化安全会话管理

对于需要 `--dangerously-skip-permissions` 的长期任务，使用容器隔离：

```bash
# SafeClaw 提供 Claude Code 容器编排面板
# 主控 Claude 在宿主机，Worker Claude 在容器中执行
```

**适用场景：**
- 生产服务器自动化脚本
- 需要 sudo 的系统操作
- 网络请求类任务

### 手动指数退避（Long-running Job 监控）

对于需要长时间等待的任务，用指数退避降低 token 消耗：

```
第1次检查: 1分钟后
第2次检查: 2分钟后（失败后）
第3次检查: 4分钟后
第4次检查: 8分钟后
```

**提示词模板：**
> "请启动构建，完成后每隔一倍时间检查状态（1分钟→2分钟→4分钟→8分钟），有结果再汇报。"

## 11. Claude Code Security — AI驱动的代码漏洞扫描（🆕 2026-02-20）

### 与传统扫描工具的核心差异

| 维度 | 传统静态分析工具 | Claude Code Security |
|------|----------------|---------------------|
| 原理 | 规则匹配（已知漏洞模式库）| 像人类安全研究员一样阅读和推理代码 |

### 工作原理

1. **读取推理**：Claude 像人类安全研究员一样理解代码逻辑
2. **组件交互理解**：理解代码库内各组件如何交互

5. **分级呈现**：按严重程度分级，附置信度评分
6. **人工审批**：所有修复建议必须经人工审批后才可应用

- 目前为研究预览版，向 Enterprise/Team 客户开放；开源维护者可申请免费快速访问

### 适用场景

| 场景 | 价值 |

## 14. Test-First AI Loop（TDD × AI，🆕 2026-03）

**来源：** dev.to @dohkoai，2026-03

将 TDD 思想引入 AI Coding：用 AI 实现，直到测试通过。

### 流程

```
1. 编写失败的测试（人工或 AI 辅助）
       ↓
2. 将测试 + 源码喂给 AI 工具
       ↓
3. AI 实现，直到测试通过
       ↓
4. 人工审查实现质量
       ↓
5. 运行完整测试套件
       ↓
6. 如有回归 → 添加测试，回到步骤 2
```

### 关键审查规则

AI 实现时，密切监控以下问题：

| 问题类型 | AI 常见错误 | 检查点 |
|---------|------------|-------|
| 硬编码值 | 用具体数字代替变量 | 检查 magic numbers |
| 性能 | O(n²) 循环代替哈希表 | 大数据量测试 |
| 安全 | eval()、SQL 拼接 | 安全扫描 |
| 过度工程 | 为不存在的需求写代码 | 需求范围验证 |

### 适用场景

- Bug 修复（有复现测试）
- 功能添加（有明确规格）
- 重构（有完整测试套件保护）

## 16. AI Coding 三大陷阱与解法

**来源：** blog.ccino.org "2026 Claude Code 工作流最佳实践：当 AI 写 90% 的代码" (2026-03)

### 陷阱一：把 Claude 当搜索引擎

**症状：** 询问"如何做 X"，复制粘贴代码，不理解原理。

**危害：** 遇到变体问题完全无法应对，技术债务累积，不理解自己代码库的行为。

**解法：** 先问"为什么需要这样做"，让 Claude 解释代码逻辑，主动学习原理而非复制结果。

---

### 陷阱二：一次性生成大量代码

**症状：** 要求"生成整个用户模块"，代码量大，难以调试，质量不可控。

**危害：** 上百行代码无法追踪 AI 决策路径，调试成本极高，出现问题难以定位根因。

**解法：** 拆分任务，逐步验证。每 2-3 个功能块暂停检查，确认方向正确再继续。

> "不要一次给 AI 发一个大型任务，要像流水线一样，一个接一个地发小型任务。"

---

### 陷阱三：忽略代码审查

**症状：** Claude 生成代码后直接提交，技术债务累积。

**危害：** AI 代码默认接受，缺乏批判性审视 → 安全漏洞 + 性能问题 + 硬编码值。

**解法：** 把 Claude 的输出当作"初稿"，进行 Review，确认质量后再合并。

**Claude 原生支持的安全网：**
- `claude --dangerously-skip-permissions` → **必须配合** `cc-safe` 扫描危险授权命令
- 使用 `/review` 指令触发 Claude Code 内置代码审查
- 定期运行完整测试套件（Test-First AI Loop）

> 核心原则：AI 输出 = 初稿，人类 = 最终质量守门人。AI 可以帮你写 90% 的代码，但承担最终责任的仍然是人类。

## 17. Test-First AI Loop：四类"假通过"陷阱（🆕 2026-03-26，dev.to 原文）

在 Test-First AI Loop 中，AI 可能写出"通过测试但实际上很糟糕"的代码。dev.to 基于 264 个生产框架总结出 4 类最常见的假通过模式：

### 陷阱 A：硬编码值（Magic Numbers）
```typescript
// ❌ AI 硬编码碰巧通过
function calculateTotal(items: Item[]) {
  return 42; // 测试恰好通过，但逻辑错误
}

// ✅ 正确做法：强制通用实现
function calculateTotal(items: Item[]) {
  return items.reduce((sum, item) => sum + item.price, 0);
}
```
**审查要点：** 检查返回值是否与输入数据有真实的数学/逻辑关系，而非固定值。

### 陷阱 B：错误的复杂度（O(n²) vs O(n)）
```typescript
// ❌ AI 在 O(n) 解法存在时用了 O(n²)
for (const item of items) {
  for (const other of items) { // 双重循环
    if (item.id === other.parentId) { /* ... */ }
  }
}

// ✅ 正确做法：哈希表查找 O(n)
const parentMap = new Map(items.map(i => [i.parentId, i]));
```
**审查要点：** 嵌套循环（特别是双层遍历同一数组）几乎总是可以用哈希表优化。质问 AI："有没有 O(n) 的做法？"

### 陷阱 C：安全捷径
```typescript
// ❌ SQL 拼接 + eval — 经典注入漏洞
const query = `SELECT * FROM users WHERE id = ${userId}`;
eval(userInput); // 任意代码执行

// ✅ 正确做法：参数化查询 + 无 eval
const query = `SELECT * FROM users WHERE id = $1`;
const result = await db.query(query, [userId]);
```
**审查要点：** 任何 `eval()`、`new Function()`、模板字符串拼接 SQL、用户输入直接进 shell 命令，都是危险信号。

### 陷阱 D：过度工程化
```typescript
// ❌ AI 为简单问题引入复杂抽象
class CalculatorFactory {
  static create(operation: string): Calculator {
    const strategies = { /* 10 种策略 */ };
    return new strategies[operation]();
  }
}

// ✅ 正确做法：简单问题用简单方案
function add(a, b) { return a + b; }
```
**审查要点：** 问自己："这个抽象解决了真实问题，还是为未来可能的需求预支了复杂度？"

### 审查清单（每次 Test-First 循环必查）
- [ ] 返回值是否硬编码（Magic Numbers）
- [ ] 是否有不必要的嵌套循环（→ 问 AI：能否用哈希表？）
- [ ] 是否有 eval / SQL 拼接 / 危险 shell 命令
- [ ] 抽象是否过度（简单函数是否被复杂化）

## 🆕 Section 18 — Program Verification：真正的效率倍增器（EPAM 2026）

**来源：** EPAM AI/Run 团队调研（2026-02-01）| 质量：⭐⭐⭐⭐

**核心论点：** AI 可以快速生成代码，但大多数团队卡在约 30% 的生产力提升，因为检查代码吞噬了所有节省的时间。**验证必须与生成同尺度扩展，才能实现真正的 10 倍效率。**

### 问题：30% 瓶颈的根源

```
AI 生成代码速度（快）→ 人类检查速度（慢）→ 瓶颈在检查阶段
→ 总体效率提升 < 30%
```

### 三种 Program Verification 路径

#### 1. 属性验证（Property-Based Verification）— Amazon Kiro

| 步骤 | 说明 |
|------|------|
| 定义不变量（Invariant）| 开发者写出"必须始终为真"的规则 |
| 自动化测试生成 | 系统生成数百个测试用例寻找反例 |
| 正确性证明 | 若属性存活，代码"按构造正确" |

```
示例不变量：
"用户余额永远不能为负"
"任何 API 响应必须在 200ms 内返回"
"auth_token 永不在 URL 参数中传递"
```

#### 2. 视觉验证（Visual Verification）— Google Antigravity

| 核心思路 | 说明 |
|----------|------|
| 用截图/工作流录制/UI 快照作为正确性证明 | 不读实现细节，直接验证行为 |
| Agent 可基于视觉验证结果自主推进 | 流程看起来对 → Agent 继续，无需拉回人类 |

**最佳场景：** Web 开发（视觉输出可以直接判断正确性）

#### 3. 架构验证（Architectural Verification）

| 监控维度 | 说明 |
|----------|------|
| API 使用规范 | 检测越权调用 |
| 层边界 | 检测跨层直接依赖 |
| 接口契约 | 检测接口实现与契约的偏离 |

**优势：** 捕获标准功能测试经常遗漏的深层集成问题

### 三种验证路径的适用场景

| 验证路径 | 最佳场景 | 前提要求 |
|----------|---------|---------|
| 属性验证 | 安全/金融/数据一致性关键系统 | 团队能写出有意义的不变量 |
| 视觉验证 | Web/UI 开发（输出可见）| 有截图/录制基础设施 |
| 架构验证 | 微服务/分层架构系统 | 有架构图和接口契约文档 |

### 采用节奏

- **Web 开发（视觉输出判断正确性）** → 最早落地
- **采用会不均衡**：写出扎实不变量、产生有意义产物、维护架构测试都需要前期纪律
- **部分团队仍会选择"快速发布，之后验证"**

## 20. Architectural Drift — 架构漂移反模式（dev.to Top 10 AI Coding Tools 2026）

**来源：** dev.to "Top 10 AI Coding Tools for 2026"（2026-03）

**定义：**
> AI让写代码变得太容易，代码库增速超过人类理解速度，导致架构设计在实际执行中逐渐失效。

**典型症状（三条全中即危险信号）：**
| 症状 | 说明 |
|------|------|
| 审批代码速度快过阅读速度 | "相信"AI输出的信任惯性 |
| AI解释"是什么"但不解释"为什么" | 上下文丢失，无法追溯决策依据 |
| 建议破坏系统其他部分 | 缺乏全局视角，分割优化 |

**隐藏风险举例：**
- 竞态条件（只在并发场景触发，测试不易捕捉）
- 隐式依赖（假设环境特定状态）
- 全局状态污染（跨模块副作用）

**Devin Enterprise 数据点（参考）：**
- 可自主解决约 **70%** 常规任务（依赖更新、小CSS修复等）

## 🆕 Section 19 — Claude Code 源码泄露事件：工具信任与供应链安全

**来源：** wavespeed.ai（2026-04-01）、Ars Technica（2026-04）

### 事件概要

| 维度 | 内容 |
|------|------|
| **时间** | 2026年3月31日（愚人节前夕）|
| **原因** | npm 发布时未剥离 `.map` 源码映射文件 |
| **泄露规模** | 512,000 行代码 / ~1,900 文件 |
| **影响范围** | Claude Code 技术架构 / 未来路线图 / 108 个 gated features |
| **用户数据** | 无泄露（源码泄露，非数据泄露）|
| **修复** | Anthropic 快速在 npm 补丁，但 GitHub 镜像已传播 |

### 对开发者的启示

| 风险 | 对策 |
|------|------|
| **npm 供应链攻击** | 验证 package hash，不盲目 `npm install -g` |
| **工具信任边界** | Claude Code 的 40+ 工具权限体系（per-tool gate）是行业最佳实践 |
| **Agent 失忆** | 外部 Agent 工具无法持久化记忆（KAIROS 的 108 gated modules 为内部实验）|
| **愚人节彩蛋风险** | `/buddy` 等彩蛋命令可能包含未充分测试的代码，生产环境谨慎使用 |

### BUDDY 彩蛋的安全参考

| 特性 | 安全相关性 |
|------|---------|
| 用户 hash 生成宠物 | 同理可验证：工具不应基于可预测 hash 生成安全决策 |
| 五维属性（DEBUGGING 等）| AI 工具的"人格参数"会影响调试建议的耐心/准确性平衡 |
| April Fools 发布节奏 | 节日彩蛋可能带来非预期行为变更，重要项目避免在愚人节前后部署 |

> **核心教训：** 信任 AI 工具的输出，不信任工具的"黑盒"本质。Claude Code 的 per-tool 权限模型（Section 19-36）仍是目前最细粒度的安全实践。

## Section 20 — GitHub Copilot 数据训练政策变更（2026-04-24 生效）

**来源：** GitHub 官方 + 知乎六工具对比（2026-04-07）

### 政策变更内容

| 维度 | 变更前 | 变更后（2026-04-24）|
|------|--------|---------------------|
| **数据使用** | 不用于模型训练 | 可能用于训练和改进模型 |
| **影响范围** | 仅 Copilot Free 用户 | Copilot Free / Pro / Pro+ |
| **企业用户** | 不受影响 | Enterprise 不变 |
| **退出选项** | 无需退出 | 可 opt-out |

### 退出方法

```
GitHub Settings → Copilot → 取消勾选
"Allow GitHub to use my data for product improvements"
```

### 安全影响评估

| 风险 | 评估 |
|------|------|
| **代码知识产权** | 闭源项目代码可能进入训练集 → 企业需 opt-out |
| **隐私合规** | 金融/医疗/政府代码 → 必须 opt-out |
| **竞争优势** | 专有算法/业务逻辑 → 必须 opt-out |

### 选型建议

| 工具 | 数据政策 | 适用场景 |
|------|---------|---------|
| **Claude Code** | 不用于训练 | 企业/隐私敏感项目 |
| **Cursor** | SOC 2，数据隔离 | 企业/隐私敏感项目 |
| **GitHub Copilot** | 需 opt-out（2026-04-24 前）| 个人/非敏感代码 |
| **OpenCode** | 不存储代码/上下文 | 隐私优先场景 |
| **Trae IDE** | 需企业自行评估 | 国内语境/非敏感代码 |

### 1. 提示词基础原则

#### 1.1 好提示词的三要素

![]()

| 要素 | 说明 | 示例 |
| --- | --- | --- |
| **具体范围** | 明确文件、模块、功能边界 | “在 `src/auth/` 目录下” |
| **验证方式** | 给 Claude 检查自己工作的标准 | “运行测试并确保通过” |
| **分阶段指令** | 复杂任务拆分为步骤 | “先探索，再规划，最后实现” |

#### 1.2 提示词对比表

| 场景 | ❌ 模糊提示 | ✅ 具体提示 |
| --- | --- | --- |
| **功能实现** | “实现邮箱验证” | “编写 `validateEmail` 函数，测试用例：`user@example.com` → true，`invalid` → false。实现后运行 `npm test`” |
| **Bug 修复** | “修复登录 bug” | “用户反映会话超时后登录失败。检查 `src/auth/` 的 token 刷新逻辑。先写失败测试重现问题，再修复” |
| **代码探索** | “这个 API 怎么回事？” | “查看 `ExecutionFactory` 的 git 历史，总结 API 演变过程和设计决策” |
| **UI 实现** | “让页面更好看” | “[粘贴截图] 实现这个设计。完成后截图对比，列出差异并修复” |
| **重构** | “重构这段代码” | “将 `processOrder` 函数拆分为独立步骤，保持所有测试通过，不改变外部 API” |

#### 1.3 高级提示技巧

##### 🎯 技巧 1：提供验证闭环

```
# 让 Claude 可以自我验证
> 实现 validateEmail 函数。
> 测试用例：
>   - user@example.com → true
>   - invalid → false
>   - user@.com → false
> 实现后运行测试，修复任何失败。

```
##### 🎤 技巧 2：让 Claude 采访你

对于复杂功能，让 Claude 主动问问题：

```
> 我想构建用户认证系统。
> 请用 AskUserQuestion 工具详细采访我。
>
> 询问：技术选型、安全要求、边缘情况、与现有系统的集成。
> 深入挖掘我可能没考虑到的难点。
> 采访完成后，将完整规格写入 SPEC.md。

```
##### 📎 技巧 3：引用上下文

```
# 使用 @ 引用文件
> 解释 @src/utils/auth.js 中的 token 刷新逻辑

# 直接粘贴图片（拖拽或 Ctrl+V）
> [截图] 根据这个设计稿实现页面

# 提供 URL
> 参考 https://api-docs.example.com 实现这个端点

# 管道输入
cat error.log | claude -p "分析这个错误的根本原因"

```
##### 🔗 技巧 4：链式指令

```
# 用 "然后" 连接多个步骤
> 先阅读 src/api/users.ts 理解现有结构，
> 然后添加 deleteUser 端点，
> 然后为新端点编写测试，
> 最后运行测试确保通过。

```

### 2. 触发 Subagents 的提示词模式

Subagents 是 Claude Code 的并行处理能力。关键是**通过提示词正确触发和控制它们**。

![]()

#### 2.1 基础触发语法

```
# 🔑 核心关键词：use subagents
> fix the login bug. use subagents

# 等效表达
> investigate this issue using a subagent
> spawn a subagent to analyze the codebase
> have a subagent review this code

```
#### 2.2 并行研究模式

当需要同时调查多个模块时：

```
# ✅ 推荐写法：明确指定并行
> investigate auth, payment, and notification modules in parallel.
> use subagents for each module.
> return compressed summary only:
>   - key findings (bullet points)
>   - files affected (paths only)
>   - recommended actions (prioritized)

# 🎯 关键点：
# 1. "in parallel" - 明确要求并行
# 2. "use subagents" - 触发子代理
# 3. "compressed summary only" - 控制返回格式

```
#### 2.3 后台执行模式

长时间任务放到后台，不阻塞主会话：

```
# 后台运行测试
> run the full test suite in the background.
> write results to test-report.md, not chat.
> only notify me if tests fail.

# 后台代码分析
> use a subagent in background to analyze code complexity.
> save report to complexity-report.md.
> I'll continue working on other tasks.

```

**快捷键**：按 `Ctrl+B` 可将当前正在执行的任务移到后台。

#### 2.4 指定子代理类型

```
# 使用 Explore 子代理（只读、快速）
> use the Explore agent to find all API endpoints in the codebase

# 使用自定义子代理
> use the code-reviewer subagent to review my recent changes

# 使用 Plan 子代理（只读、规划）
> use a Plan agent to design the refactoring strategy

```
#### 2.5 链式子代理执行

```
# 一个子代理的输出作为另一个的输入
> first, use a subagent to find all security vulnerabilities.
> then, use another subagent to generate fix recommendations.
> finally, summarize both findings in a single report.

```
#### 2.6 控制子代理返回格式

**核心原则**：子代理应返回压缩后的关键信息，而非冗长过程。

```
# ❌ 不好：没有控制返回格式
> use a subagent to analyze the auth module

# ✅ 好：明确指定返回格式
> use a subagent to analyze the auth module.
> return format:
>   - 3-5 key findings
>   - affected files (paths only)
>   - priority: critical > warning > suggestion
> no process explanation, results only.

```
#### 2.7 子代理提示词模板库

##### 模板 1：并行代码审查

```
> review src/api/, src/services/, src/utils/ in parallel.
> use subagents.
> each agent should check:
>   - security vulnerabilities
>   - performance issues
>   - code style violations
> output format per module:
>   🔴 Critical: [count]
>   🟡 Warning: [count]
>   🟢 Suggestion: [count]
>   Top 3 issues: [list]

```
##### 模板 2：后台测试 + 继续工作

```
> run npm test in background.
> if all pass: just say "✅ Tests passed"
> if failures: list failed tests with file:line
> meanwhile, I'll continue with the next task.

```
##### 模板 3：深度调查 + 写文件

```
> use a subagent to investigate how authentication works.
> trace the flow from login to session creation.
> write findings to docs/auth-flow.md, not chat.
> include a mermaid diagram of the flow.

```
##### 模板 4：比较方案研究

```
> I need to add caching. research three approaches in parallel:
>   1. Redis
>   2. In-memory (node-cache)
>   3. File-based
> use subagents.
> for each: pros, cons, implementation complexity, recommended use case.
> output as comparison table.

```

### 3. 探索-规划-执行工作流

复杂任务应该分三个阶段进行对话：

![]()

#### 3.1 阶段一：探索

**目标**：理解现有代码，收集必要上下文。

```
# 进入 Plan 模式（只读探索）
> Shift+Tab  # 切换到 plan mode
# 或
> /plan

# 探索提示词
> explore the authentication module.
> I want to understand:
>   - how sessions are managed
>   - where tokens are stored
>   - how refresh flow works
> don't change any code, just investigate.

```

**探索阶段的好提示词**：

```
# 理解架构
> explain the architecture of src/api/.
> focus on request flow and middleware chain.

# 追溯历史
> check git history of auth.ts.
> summarize major changes and why they were made.

# 发现依赖
> what external services does the payment module depend on?
> list all API calls and their purposes.

```
#### 3.2 阶段二：规划

**目标**：基于探索结果，设计实施方案。

```
# 继续在 Plan 模式
> based on your findings, propose a plan to add OAuth support.
> consider:
>   - which files need changes
>   - new files to create
>   - potential risks
>   - testing strategy

```

**让 Claude 生成可编辑的计划**：

```
> write the implementation plan to PLAN.md
> I want to review and edit it before we proceed

```

**快捷键**：按 `Ctrl+G` 在外部编辑器中打开计划文件。

#### 3.3 阶段三：执行

**目标**：按计划实施，持续验证。

```
# 退出 Plan 模式，进入 Normal 模式
> Shift+Tab  # 切换回 normal mode

# 执行提示词
> implement the OAuth flow according to @PLAN.md
> after each major step:
>   - run relevant tests
>   - commit if tests pass
> stop and ask if you encounter unexpected issues.

```
#### 3.4 完整示例：添加新功能

```
# ========== 阶段 1：探索 ==========
> Shift+Tab  # 进入 plan mode

> I want to add rate limiting to our API.
> first, explore:
>   - current middleware structure in src/middleware/
>   - how other cross-cutting concerns (auth, logging) are implemented
>   - existing rate limiting attempts (if any)
> use subagents if needed.

# [Claude 探索并报告发现]

# ========== 阶段 2：规划 ==========
> based on your findings, design the rate limiting solution.
> consider:
>   - where to add the middleware
>   - configuration options (limits per endpoint, per user)
>   - storage backend (Redis vs memory)
>   - error response format
> write the plan to RATE_LIMIT_PLAN.md

# [审查计划，按 Ctrl+G 编辑]

# ========== 阶段 3：执行 ==========
> Shift+Tab  # 回到 normal mode

> implement rate limiting according to @RATE_LIMIT_PLAN.md
> test after each step:
>   - unit tests for the middleware
>   - integration tests for the endpoints
> commit with descriptive messages when tests pass.

```

### 4. 中断与引导技巧

Claude Code 不是"提交任务然后等待"的工具，而是**可以实时互动的搭档**。

#### 4.1 随时中断

```
> fix the authentication bug

# [Claude 开始执行，你发现方向不对]

# 按 Esc 停止当前执行
# 然后立即给出新指令

> stop. the issue is not in auth.ts, it's in session.ts.
> look at the session expiration logic instead.

```
#### 4.2 引导纠偏

```
> refactor the UserService class

# [Claude 开始重构，你有更好的想法]

> wait, don't extract that method.
> instead, use composition over inheritance.
> the UserValidator should be a separate class.

```
#### 4.3 追问细节

```
> add input validation to the API

# [Claude 完成后]

> that looks good, but what about SQL injection?
> also add sanitization for the 'name' field.

```
#### 4.4 回退与重试

```
# 双击 Esc 或 /rewind 打开回退菜单
Esc Esc

# 选择回退点：
# - Restore Code: 恢复代码但保留对话
# - Restore Code and Chat: 完全回退

# 然后用不同方式重试
> let's try a different approach.
> instead of modifying the existing code, create a new utility function.

```
#### 4.5 中断提示词模板

```
# 停止并澄清
> stop. before you continue, let me clarify:
> I want [具体要求], not [Claude 正在做的]

# 改变方向
> actually, let's take a different approach.
> instead of [当前方向], let's [新方向]

# 分步确认
> pause after each file change and show me what you're planning.
> I want to approve before you proceed.

# 设置边界
> only modify files in src/api/.
> if you need to change other files, ask first.

```

### 5. TDD 开发的提示词模式

Test-Driven Development 与 Claude Code 配合时，需要特定的对话模式。

#### 5.1 TDD 基本循环

![]()

#### 5.2 TDD 提示词模板

##### 模板 1：完整 TDD 循环

```
> implement a ShoppingCart class using TDD.
>
> follow this cycle strictly:
>   1. RED: write a failing test first
>   2. GREEN: write minimal code to pass
>   3. REFACTOR: improve code quality
>   4. repeat for next feature
>
> features to implement:
>   - addItem(product, quantity)
>   - removeItem(productId)
>   - getTotal()
>   - applyDiscount(code)
>
> run tests after each step.
> commit after each GREEN phase.

```
##### 模板 2：先测试后实现

```
> write comprehensive tests for validateCreditCard function.
>
> test cases:
>   - valid Visa: 4111111111111111 → true
>   - valid Mastercard: 5500000000000004 → true
>   - invalid checksum: 4111111111111112 → false
>   - too short: 411111 → false
>   - non-numeric: 4111-1111-1111-1111 → handle gracefully
>
> run tests (should all fail).
> then implement the function to pass all tests.

```
##### 模板 3：Bug 修复 TDD

```
> there's a bug: users can checkout with expired cards.
>
> TDD approach:
>   1. write a test that reproduces the bug
>   2. verify the test fails
>   3. fix the bug
>   4. verify the test passes
>   5. ensure no other tests broke
>
> related code is in src/checkout/

```
#### 5.3 测试驱动探索

```
> I'm not sure how the order processing works.
> write exploratory tests to understand:
>   - what happens when order total is 0
>   - what happens with invalid product IDs
>   - what happens when inventory is insufficient
>
> run each test and report what you learn.
> don't fix anything yet, just understand current behavior.

```
#### 5.4 持续测试提示词

```
# 要求每次修改后运行测试
> modify the UserService.
> after EVERY code change:
>   1. run `npm test -- --grep "UserService"`
>   2. if tests fail, fix before continuing
>   3. only commit when tests pass

# 覆盖率要求
> add the new feature.
> maintain test coverage above 80%.
> run `npm test -- --coverage` to check.

```

### 6. Vibe Coding 理念与实践

Vibe Coding 是一种与 AI 协作的新范式：**委托而非指挥**。

![]()

#### 6.1 核心理念对比

| 传统模式 | Vibe Coding |
| --- | --- |
| 你写代码，Claude 审查 | 你描述需求，Claude 探索、规划、实现 |
| 逐行指令 | 高层次委托 |
| “在第 42 行添加这个函数” | “修复过期卡片的结账流程” |
| 你是执行者 | 你是产品经理 / 架构师 |
| 等待完成再反馈 | 随时中断引导 |

#### 6.2 委托式提示词

```
# ❌ 微管理式（过度指导）
> open src/payments/checkout.ts
> find the processPayment function
> add a token refresh check at line 156
> use the refreshToken() method

# ✅ 委托式（给上下文和方向）
> users report checkout fails when their session expires.
> the issue is probably in src/payments/.
> investigate and fix it.
> add tests to prevent regression.

```
#### 6.3 给 Claude 自主权

```
# 信任 Claude 的判断
> implement caching for the product API.
> choose the best approach based on our codebase.
> explain your choice briefly.

# 允许 Claude 探索
> I'm not sure why this test is flaky.
> investigate and propose solutions.
> implement the best one if you're confident.

```
#### 6.4 实时协作对话

```
> implement user authentication

# [Claude 开始工作]
# [你观察到 Claude 选择了 JWT]

> I see you're using JWT.
> we need refresh tokens too.
> can you add that?

# [Claude 调整]
# [你想到一个边缘情况]

> what happens if the refresh token is also expired?
> handle that case gracefully.

```
#### 6.5 视觉驱动开发

```
# 从设计稿开始
> [拖拽设计图到终端]
> implement this design.
> use our existing component library in src/components/.
> after implementation, take a screenshot and compare.
> fix any differences.

# 迭代改进
> [粘贴当前实现的截图]
> compare this with @design.png
> the spacing is off. fix it.

```
#### 6.6 Vibe Coding 提示词模板

##### 模板 1：功能委托

```
> I need to add [功能描述].
>
> context:
>   - related code: [目录/文件]
>   - existing patterns to follow: [参考]
>   - constraints: [限制条件]
>
> approach:
>   1. explore current implementation
>   2. propose solution
>   3. implement with tests
>   4. verify everything works
>
> ask if you have questions.

```
##### 模板 2：问题解决委托

```
> users report [问题描述].
>
> clues:
>   - happens when [条件]
>   - error message: [错误]
>   - related logs: [日志位置]
>
> investigate, identify root cause, and fix.
> add test to prevent regression.

```
##### 模板 3：重构委托

```
> the [模块] is getting hard to maintain.
>
> goals:
>   - improve readability
>   - reduce duplication
>   - keep external API unchanged
>
> approach this incrementally:
>   - show me the plan first
>   - make small, testable changes
>   - run tests after each change

```

### 7. 上下文管理的对话技巧

上下文窗口是有限资源。高效的对话技巧可以帮助你最大化利用它。

![]()

#### 7.1 何时清理上下文

```
# 任务完成后
> /clear
> 开始新任务...

# 话题切换时
> we're done with auth. /clear
> now let's work on the payment module.

# 上下文变得混乱时
> this conversation got confusing. /clear
> let me restart: I need to [清晰描述]

```
#### 7.2 何时压缩上下文

```
# 任务进行中但上下文太长
> /compact focus on the API changes we discussed

# 只保留关键信息
> /compact keep only: file paths changed, test results, next steps

# 查看上下文使用情况
> /context

```
#### 7.3 避免上下文污染

```
# ❌ 不好：让探索结果污染主上下文
> read all files in src/ and summarize

# ✅ 好：用子代理隔离探索
> use a subagent to explore src/.
> return only: file structure, key modules, entry points.

```
#### 7.4 分会话策略

```
# 复杂项目用多个会话
# 会话 1：功能开发
claude --resume feature-auth

# 会话 2：Bug 修复
claude --resume bugfix-123

# 会话 3：代码审查
claude --resume review

```
#### 7.5 Fork 会话尝试不同方案

```
# 保存当前进度，尝试新方向
claude --continue --fork-session

> let's try a completely different approach.
> instead of [当前方案], let's [新方案].

# 如果新方案更好，继续使用 fork
# 如果不行，回到原会话
claude --resume [原会话名]

```

### 8. 常见反模式与解决方案

![]()

#### 8.1 厨房水槽会话

```
# ❌ 反模式：一个会话处理所有事情
> fix the login bug
> [完成]
> how does caching work?  # 无关话题
> [回答]
> continue fixing login   # 上下文混乱

# ✅ 解决：任务边界清晰
> fix the login bug
> [完成]
> /clear
> how does caching work?

```
#### 8.2 反复纠正循环

```
# ❌ 反模式：不断纠正同一问题
> implement X
> no, that's wrong, try again
> still wrong, once more
> ...  # 消耗上下文，效果变差

# ✅ 解决：两次纠正后重启
> /clear
> [更清晰、更具体的提示词]

```
#### 8.3 过度指定

```
# ❌ 反模式：每一步都详细指定
> open file A
> read line 42
> change X to Y
> save file
> open file B
> ...

# ✅ 解决：委托 + 约束
> refactor the auth module.
> constraints:
>   - don't change public API
>   - keep tests passing
> show me the plan first.

```
#### 8.4 无限探索

```
# ❌ 反模式：没有边界的探索
> explain everything about this codebase
# Claude 读取大量文件，填满上下文

# ✅ 解决：限定范围
> explain the auth flow in src/auth/.
> focus on login and session management.
> ignore admin features for now.

```
#### 8.5 忽略错误继续

```
# ❌ 反模式：测试失败仍继续前进
> add the feature
# [测试失败]
> now add the next feature
# [累积问题]

# ✅ 解决：修复后再继续
> add the feature
# [测试失败]
> fix the failing tests first.
> then continue with the next feature.

```
#### 8.6 反模式速查表

| 反模式 | 症状 | 解决方案 |
| --- | --- | --- |
| 厨房水槽 | 话题跳跃，上下文混乱 | 任务完成后 `/clear` |
| 反复纠正 | 同一问题纠正 3+ 次 | 重启会话，改进提示词 |
| 过度指定 | 逐行指令 | 委托 + 约束 |
| 无限探索 | 上下文快速填满 | 用子代理，限定范围 |
| 忽略错误 | 累积失败 | 先修复再继续 |
| 模糊提示 | Claude 猜测你的意图 | 具体 + 可验证 |

### 速查总结

#### 提示词模式速查

| 场景 | 关键词 / 模式 |
| --- | --- |
| 触发子代理 | `use subagents`, `use a subagent to...` |
| 并行执行 | `in parallel`, `simultaneously` |
| 后台运行 | `in background`, 或 `Ctrl+B` |
| 探索模式 | `Shift+Tab` 进入 Plan Mode |
| 测试先行 | `write tests first`, `TDD` |
| 验证闭环 | `run tests`, `verify`, `check` |
| 压缩返回 | `compressed summary`, `results only` |
| 中断纠偏 | `Esc` + 新指令 |
| 委托式 | 描述目标，不描述步骤 |

#### 快捷键速查

| 快捷键 | 功能 |
| --- | --- |
| `Esc` | 停止当前执行 |
| `Esc Esc` | 打开回退菜单 |
| `Shift+Tab` | 切换权限模式 |
| `Ctrl+B` | 移到后台 |
| `Ctrl+G` | 编辑器中打开计划 |
| `Ctrl+O` | 切换详细模式 |

#### 工作流检查清单

* 复杂任务先进入 Plan Mode 探索
* 任务描述具体、可验证
* 大范围探索用子代理
* 任务完成后 `/clear` 清理
* 测试失败先修复再继续
* 方向不对立即中断纠偏
* 两次纠正无效则重启会话

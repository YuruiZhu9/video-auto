## 五、诊断结论

### 🔴 核心问题（已确认）

1. **直接原因**：`timeoutSeconds: 900` 硬性限制到期，被系统强制终止（900040ms）
2. **根因**：任务体量（两个 Agent 顺序执行）与 timeout 配置不匹配
3. **趋势**：执行耗时呈上升趋势（近期多日超过 500s，峰值 705s），安全余量已耗尽
4. **实际情况**：报告文件已正常生成，钉钉已发送，任务逻辑本身没有问题

### 🟡 次要问题

- `delivery.mode: "none"` 导致 run 日志中 `delivered: false`，但钉钉发送由 Agent 内部完成，不影响用户收报
- 其他 cron 任务偶有小 error，不影响主流程

## 六、修复建议（按优先级排序）

### 方案一（推荐）：增加 timeout 到 1200 秒
- **优点**：零风险，不改变任务逻辑，最小改动
- **操作**：修改 cron job `29c8ba5c-0d8e-464e-bd27-e4aa89012b73` 的 `timeoutSeconds` 从 `900` → `1200`
- **预期效果**：安全余量从 0 提升到 ~500s，彻底消除超时风险

### 方案二（可选）：拆分为两个独立 cron 任务
- 将技术分析师和商业分析师拆为两个独立 job，各 900s
- **优点**：职责单一，便于分别排查问题
- **缺点**：需要修改触发逻辑，增加维护复杂度
- **时机**：如果方案一实施后仍频繁超时再考虑

### 方案三（可选）：优化 prompt 减少 token 消耗
- 在 tech-analyst-prompt.md 和 business-analyst-prompt.md 中增加"快速模式"指令
- 减少每次搜索的广度，优先保证在 timeout 内完成
- **优先级**：最低，报告质量会下降

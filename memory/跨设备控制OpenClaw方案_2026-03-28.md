## 一、背景与目标

当前 AI Agent 的一个核心演进方向是：**让 AI 不只"回答问题"，而是"替你做事"**。这要求 AI 能够跨设备、跨平台地感知环境、执行命令、管理任务。

**核心需求场景：**
1. 手机上随时唤醒 → 在电脑端执行复杂任务（写代码、发邮件、整理文件）
2. 出门在外 → 远程查看/操控家中电脑上的 AI 助手
3. 多设备协同 → 手机拍照片 → 电脑端自动处理 → 结果推送到手机
4. 跨平台消息聚合 → 在手机上通过钉钉/微信与家里/公司的 AI 对话

## 二、行业现状：2025-2026 年跨设备 AI 控制技术全景

### 2.1 代表性产品与技术路线

| 产品/技术 | 公司 | 核心能力 | 局限性 |
|-----------|------|----------|--------|
| **Claude Computer Use** | Anthropic | 通过视觉模型接管鼠标键盘操作电脑 | 仅限同设备，远程控制需手动 |
| **Claude Cowork** | Anthropic (2026.03) | 手机端 AI 可远程操控电脑执行任务 | 需云端中转，存在隐私风险 |
| **OpenClaw Nodes** | OpenClaw | 移动端配对为节点，通过 WS 远程执行命令 | 依赖配对流程，实时性受网络影响 |
| **Manus Agent** | Monica | 云端通用 Agent，跨平台任务执行 | 完全云端，数据隐私问题 |
| **See-Control** | 学术研究 | MLLM 控制智能手机物理操作 | 需视觉模型，计算开销大 |
| **MCP2MQTT** | 开源社区 | AI 通过 MCP 协议控制 IoT 硬件 | 需 MQTT Broker，适合硬件控制 |

### 2.2 关键技术架构模式

#### 模式 A：Agentic RAG + 工具调用（当前主流）
- AI 理解用户意图 → 调用本地工具（Shell/文件/浏览器）
- 局限：工具局限于 Agent 运行所在的设备

#### 模式 B：远程节点架构（OpenClaw 路线）
- 移动设备配对为 Gateway 的"外设节点"
- 通过 WebSocket 连接，暴露 `system.run`、`camera.*`、`canvas.*` 等命令面
- AI 在 Gateway 端运行，在节点设备上执行操作

#### 模式 C：云端中转（Claude Cowork 等）
- AI 运行在云端，通过 VNC/远程桌面协议控制设备
- 优点：任意设备可访问；缺点：隐私、延迟、成本

#### 模式 D：MCP over MQTT（IoT 扩展）
- 将 MCP（Model Context Protocol）协议转换为 MQTT
- 适合智能家居、车载系统等 IoT 场景的 AI 控制

## 三、OpenClaw 现有架构分析

### 3.1 Gateway 核心架构

```
┌──────────────────────────────────────────────────────────────┐
│                        Gateway (核心)                        │
│  • WebSocket 控制面：ws://127.0.0.1:18789                    │
│  • Canvas Host：http://:18793 (节点 WebView 文件服务)        │
│  • 所有 Channel 接入（钉钉/飞书/微信/Telegram/WhatsApp）    │
│  • AI 模型调用 + 工具路由                                    │
└──────────────────────────────────────────────────────────────┘
          ↕ WebSocket（配对后）
  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐
  │  iOS Node   │  │ Android Node│  │  macOS Node │
  │  相机/Canvas│  │ 相机/短信/  │  │ system.run  │
  │             │  │ 位置/通知   │  │ /notify     │
  └─────────────┘  └─────────────┘  └─────────────┘
```

**关键设计原则：**
- Gateway 是唯一的"主控"，Nodes 是"外设"
- 消息来自 Channel（钉钉等）→ Gateway 处理 → 工具路由到 Node 执行
- 默认 loopback-only（安全），通过 SSH tunnel / Tailscale 远程访问

### 3.2 现有 Node 能力清单

| 能力 | 说明 | 适用场景 |
|------|------|----------|
| `canvas.*` | 屏幕快照、WebView 控制 | 截图、监控 UI 状态 |
| `camera.*` | 拍照/录像 | 移动端视觉输入 |
| `screen_record` | 屏幕录制（≤60s） | 操作演示 |
| `location.*` | GPS 位置 | 出门时查询位置 |
| `sms.send` | 发短信（Android） | 备用通知通道 |
| `system.run` | 在节点上执行 Shell 命令 | **核心：跨设备执行任务** |
| `system.notify` | 推送通知 | 结果通知 |
| `execApprovals` | 命令执行审批 | 安全管控 |

### 3.3 现有远程访问方式

| 方式 | 配置 | 适用场景 |
|------|------|----------|
| **SSH Tunnel** | `ssh -N -L 18790:127.0.0.1:18789 user@gateway` | 通用 fallback |
| **Tailscale Serve** | `gateway.auth.allowTailscale: true` | 推荐：身份认证 + 无公网暴露 |
| **macOS App 远程模式** | 菜单栏 → Remote over SSH | Mac 用户开箱即用 |
| **CLI 远程配置** | `gateway.mode: "remote"` + `remote.url` | 持久化远程目标 |

## 四、OpenClaw 跨设备控制增强方案

### 方案 A：强化 Node 体系（推荐，短期可落地）

**目标：** 将 OpenClaw 打造成真正的"个人 AI 控制中心"

#### 核心改进点：

**1. 命令路由优化（高优先级）**
```
# 当前问题：exec 工具默认在 Gateway 本机执行
# 解决：默认将 exec 路由到"主节点"（用户指定的 PC/Mac）

openclaw config set tools.exec.host "node"
openclaw config set tools.exec.node "my-macbook"
openclaw config set tools.exec.security allowlist
```

**2. 多节点智能路由**
```javascript
// 路由策略设计
if (task.requiresCamera)      → Android Node（手机摄像头）
if (task.requiresHeavyCompute) → Gateway 本机 / Mac Node（本地算力）
if (task.requiresFileAccess)  → 当前活跃节点（如在家用 Mac，外出用手机）
if (task.isQuickQuery)        → Gateway 本机（低延迟）
```

**3. 节点状态感知**
- 节点在线/离线状态实时上报
- 节点电量、网络质量（通过 ping/latency）
- 任务失败自动切换到备用节点

#### 实施步骤：
1. ✅ 当前 OpenClaw 已支持 Node 配对（文档完整）
2. 🔧 优化 `exec.host=node` 的默认配置引导
3. 🔧 增加节点状态监控 Dashboard 面板
4. 🔧 增加"主控节点"概念（自动将重任务路由到主控）

### 方案 B：引入 MCP over MQTT 网桥（中期扩展）

**目标：** 打通 AI 与智能家居、IoT 设备的控制

```
┌─────────────┐      ┌─────────────┐      ┌─────────────┐
│  OpenClaw   │ ──── │  MCP2MQTT   │ ──── │  MQTT Broker│
│  Gateway    │ WS   │  Bridge     │      │  (EMQX)    │
│  (MCP Client)│      │             │      │             │
└─────────────┘      └─────────────┘      └─────────────┘
                                                 ↕
                                          ┌─────────────┐
                                          │  IoT 设备   │
                                          │ 智能家居/   │
                                          │ 传感器      │
                                          └─────────────┘
```

**实现路径：**
1. 部署 EMQX MQTT Broker（或使用 EMQX Cloud）
2. 部署 `mcp2mqtt` 网桥（GitHub: MaoTouHU/MCP2MQTT）
3. OpenClaw Gateway 通过 MCP 协议与网桥通信
4. 网桥将 MCP 命令转换为 MQTT Topic，实现 IoT 控制

**适用场景：**
- "帮我把客厅灯调暗"
- "出门时帮我关闭所有电器"
- "监控家里温度，超过 30° 发通知"

### 方案 C：Claude Cowork 式远程控制（长期演进）

**背景：** Anthropic 于 2026 年 3 月发布 Claude Cowork，支持手机端 AI 远程控制电脑。

**OpenClaw 的等效实现路径：**

```
┌─────────────────────────────────────────────────────────────┐
│                    手机端（Node / Channel）                  │
│  消息（钉钉/微信/飞书）────→ OpenClaw Gateway                │
│                                    ↓                        │
│                            AI 推理 + 任务规划                │
│                                    ↓                        │
│                          system.run / canvas.*              │
│                                    ↓                        │
│                          远程节点（电脑）执行                │
└─────────────────────────────────────────────────────────────┘
```

**关键技术要素：**

1. **远程 WebSocket 隧道**
   - 家用电脑运行 Gateway + macOS Node（主控）
   - 手机通过 SSH 隧道连接到家用 Gateway
   - 或：家用电脑开启 Tailscale，暴露为 tailnet 地址

2. **命令中转协议**
   - Channel 消息（钉钉）→ Gateway → Node → 远程执行
   - 支持异步：任务提交后，结果通过消息 Channel 返回

3. **安全模型**
   ```
   手机（Channel）→ Gateway（鉴权）→ 远程 Node（exec 审批）
   ```
   - 每个 Node 有独立的 exec-approvals.json
   - 敏感命令（删除文件、系统设置）需要 Node 端审批
   - 建议：手机端仅能触发"白名单"内命令

4. **操作可视化（可选）**
   - `canvas.present` 在电脑端弹出 Canvas，显示 AI 执行状态
   - `screen.record` 录制操作过程，推送到手机端

## 五、推荐实施路径

### 第一阶段（已可实现）：完善 Node 配对体系

```
目标：让 OpenClaw 支持"手机作为随身遥控器 + 电脑作为主控执行者"
```

**配置步骤：**
```bash
# 1. 电脑端：启动 Gateway（已运行）
# 2. 手机端：安装 OpenClaw App，配对到 Gateway
openclaw node run --host <电脑IP> --port 18789 --display-name "我的手机"

# 3. 电脑端审批配对请求
openclaw devices list
openclaw devices approve <device-id>

# 4. 配置默认 exec 路由到手机（或其他指定节点）
openclaw config set tools.exec.host "node"
openclaw config set tools.exec.node "我的手机"

# 5. 或使用 Tailscale 远程访问
openclaw config set gateway.auth.allowTailscale true
```

**使用场景示例：**
- 出门前在钉钉对手机说："帮我把今天Downloads文件夹里的PDF都整理到桌面"
- AI 在手机 Node 上执行：`system.run { mv ~/Downloads/*.pdf ~/Desktop/ }`
- 结果推送到钉钉："已完成，整理了 5 个 PDF"

### 第二阶段（1-3个月）：多节点智能路由

- 增加节点分组（主控节点 / 外设节点）
- 实现任务类型 → 节点类型自动路由

### 第三阶段（6个月+）：IoT + 全场景覆盖

- 部署 MCP2MQTT，接入米家/鸿蒙智能家居
- 增加 Claude Cowork 式"远程桌面观察"能力
- 探索视觉驱动的远程设备操作

## 六、安全考量

| 风险 | 缓解措施 |
|------|----------|
| 远程执行恶意命令 | Node 端 `exec-approvals.json` 白名单 |
| 手机丢失被滥用 | Channel（钉钉/微信）已鉴权 + Node 端操作记录 |
| 跨设备数据泄露 | Gateway loopback-only，SSH/Tailscale 访问 |
| 节点间数据串扰 | 节点隔离，每个节点独立配对权限 |
| AI 执行错误操作 | 敏感操作二次确认（心跳机制） |

## 八、结论

**OpenClaw 的跨设备控制方案已经具备坚实的技术基础**，核心是：

1. **Gateway + Nodes 架构** — 清晰的中心化控制，设备即外设
2. **WebSocket 远程隧道** — SSH/Tailscale 实现安全的远程访问
3. **`system.run` 跨设备执行** — AI 在任意节点上执行命令
4. **多通道聚合** — 钉钉/飞书/微信均可以作为跨设备的交互入口

**当前最推荐用法：** 将手机配对为随身节点 + 将家里/公司的电脑配对为主控节点，通过钉钉/飞书随时远程触发 AI 在主控节点上执行任务。

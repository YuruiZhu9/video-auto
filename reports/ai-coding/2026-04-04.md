## 一、本期主题

### Vibe Coding 时代，人工 Review 为什么更重要了？

Andrej Karpathy 在 2025 年初提出 Vibe Coding（氛围编程）后，这个概念迅速席卷全球。它本质上是用自然语言描述需求、AI 生成代码、人来审核把关。

**但问题来了：** Karpathy 本人后来也承认自己"放弃了"Vibe Coding——因为 AI 生成的代码表面看起来对，但实际有隐藏 bug、边界没处理、架构不合理。AI 可以先写，但人不能不审。

> **核心结论：Vibe 出初稿，工程化靠审查。**

## 二、核心资源汇总

### 资源 1：Vibe Coding 六步工作流（强烈推荐）

来源：[CSDN - Vibe Coding 介绍与实践指南](https://blog.csdn.net/Cristiano_Xie/article/details/159415203)

**点评：** 这是目前中文互联网上对 Vibe Coding 最有深度的工程化实践指南。不止讲概念，重点讲如何在真实项目中控制 AI 的改动范围、避免范围蔓延。

**六步核心流程：**
1. **只读分析** — 先让 AI 读懂项目，不改文件
2. **提出方案** — AI 给出实现方案+涉及文件+风险+验证方式
3. **确认边界** — 只做最小必要修改，不重构无关代码
4. **执行修改** — 确认后再让 AI 动手
5. **做 Review** — 重点检查逻辑正确性、边界情况、回归风险
6. **做 PR 审查** — 关注漏改、回归风险、测试覆盖

### 资源 2：Claude Code 最佳实践（工程级提示词指南）

来源：[CSDN - Claude Code 开发最佳实践](https://blog.csdn.net/qq_37852091/article/details/158035171)

**点评：** 这篇文章系统梳理了从提示词技巧到 Subagent 触发的完整工作流，对想用 Claude Code 提升效率的工程师非常实用。

**最核心的三个技巧：**

| 技巧 | 说明 |
|------|------|
| **验证闭环** | 给 AI 具体测试用例，让它自己验证通过 |
| **委托式提示词** | 描述目标和上下文，不描述步骤 |
| **TDD 循环** | RED（写失败测试）→ GREEN（最小代码通过）→ REFACTOR |

### 资源 3：AI 代码审查五大原则

来源：[bonfy.ai - Code Review in the Age of AI](https://blog.bonfy.ai/code-review-in-the-age-of-ai-best-practices-for-reviewing-ai-generated-code)

**点评：** 作者 Neta Gur-Ari 来自 Software Engineering 背景，文章从团队协作角度出发，强调把 AI 代码当"实习生的代码"来审查。

**五大原则：**

1. **先看测试，再看实现** — 以产品视角理解代码该做什么
2. **用 Linter 强制团队风格** — AI 不懂你的团队规范，必须 codify
3. **把 AI 代码当实习生代码** — 看起来干净，但常漏边界情况
4. **重点盯安全漏洞** — SQL注入、未授权输入、硬编码密钥
5. **用 AI 辅助 Review，但不做最终裁判** — 总结大 diff、解释不熟悉的代码

## 五、算法工程师专属建议

### 为什么你特别需要这套方法？

算法工程师的优势是**懂模型、懂数学、懂评估指标**，但短板往往是：
- 对工程代码（前端、后台、DevOps）不够熟悉
- 不习惯代码 Review 的系统性流程
- 不知道怎么向 AI 提需求才有效

**三件事今天就可以做：**

1. **用"最小改动原则"保护自己**  
   每次让 AI 改代码前加一句："只做最小必要修改，不要重构无关代码"  
   这能大幅减少 AI 范围蔓延带来的回归 bug。

2. **把测试用例写清楚再让 AI 实现**  
   不要说"实现邮箱验证"，而是说：  
   `user@example.com → true，invalid → false，user@.com → false`  
   验证闭环 = 你的护城河。

3. **遇到不熟悉的模块，用"探索→方案→执行"三步**  
   先让 AI 读代码，给出理解 + 方案，等你确认后再动手。  
   这样即使你不熟悉那个模块，也能掌控全局。

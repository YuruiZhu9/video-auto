## 二、核心资源汇总

### 2.1 如何阅读陌生的代码

**来源：** Stack Overflow Blog - *How to Interrogate Unfamiliar Code*

**核心观点：**
- 代码的**阅读频率是写作频率的 100 倍**，但大多数教程只教写代码
- 前 80-95% 的任务时间应该花在阅读代码和文档上

**9 条实战策略：**

| 策略 | 操作要点 |
|------|---------|
| 安装实用插件 | 语法高亮、静态分析、上下文导航、断点调试 |
| 至少读两遍 | 第一遍：扫全文、构建轮廓；第二遍：逐行理解 |
| 重命名变量/方法 | 用 IDE 重构工具将 `ib(a, fn)` 改成 `indexBy(array, getKey)` |
| 看代码的调用方 | 用 "See References" 找所有使用位置 |
| 搜索相似代码 | 用正则 + IDE 全局搜索找相似模式 |
| 运行单元测试 | 测试是最好的行为文档 |
| 用 Debugger | 断点单步，inspect 所有变量值 |
| 查知识库 | 文档解释"Why"，代码本身解释"How" |
| 用版本控制注解 | 看 Git blame 了解每行代码的修改历史和原因 |

**点评：** 这套方法对算法工程师特别有价值——理解 AI 生成代码时，先读结构、再读细节、最后用 debugger 验证思维。

### 2.2 AI 生成代码的测试策略

**来源：** SitePoint - *Testing AI-Generated Code: Practical Strategies*

**4 种 AI 代码失败模式：**
1. **幻觉方法**：引用了不存在或旧版本的 API
2. **边界错误**：循环/数组操作常错 1 位
3. **只走 Happy Path**：不处理空字符串、null、Unicode
4. **过时模式**：使用已废弃的 API

**测试策略：**

```
策略 1: 测试先行（Test-First Prompting）
  → 先写失败测试定义期望行为，再让 AI 实现
  → 约束 AI 输出范围，立即捕获失败

策略 2: 属性测试（fast-check）
  → 自动测试 100+ 随机输入，发现"没想到的"边界情况
  → 例如：输出长度 == 输入长度、原始数组不被修改

策略 3: E2E 测试（Playwright）
  → AI 生成 UI 时用 Playwright 冒烟测试
  → 验证表单验证逻辑、网络请求、页面渲染

策略 4: AI 对抗性审查
  → 用另一个 AI 模型扮演"资深工程师"找漏洞
  → 重点关注：幻觉 API、边界错误、空值检查
```

**10 条 AI 代码测试清单：**
- [ ] 先写失败测试再让 AI 实现
- [ ] 运行属性测试（随机化输入）
- [ ] 验证所有导入的 API 在当前库版本中真实存在
- [ ] E2E 测试 AI 生成的 UI
- [ ] 用对抗性 AI prompt 审查代码
- [ ] 检查边界情况：空输入、null、Unicode、大数据集
- [ ] AI 代码 Bug 单独追踪，识别重复失败模式
- [ ] AI 生成的测试至少包含一条人工编写的断言
- [ ] Commit 前逐行审查（把它当 junior 的 PR）
- [ ] 不要让同一个 AI 同时生成和验证代码

### 2.3 AI 生成代码的安全风险

**来源：** TechTarget - *Security Risks of AI-Generated Code*

| 风险 | 数据 |
|------|------|
| AI 建议中包含漏洞的比例 | **48%** |
| 误以为 AI 代码更安全的开发者 | **~80%** |
| AI 辅助后网络工程时间减少 | 最高 **50%** |

**五大安全风险：**
1. 训练数据含公开漏洞代码，AI 复现之
2. AI 不理解安全意图，只复制"常见模式"
3. 可能引用已废弃/有漏洞的依赖
4. 开发者对 AI 代码过度信任
5. 可能生成含有他人 IP 的代码

**安全实践：**
- 把 AI 建议视为"未审查代码"
- 始终保留人工审核环节
- 在 DevSecOps 流水线中加入 SAST
- 启用 GitHub Copilot 等工具的漏洞过滤功能
- 明确团队 AI 使用政策，禁止向 AI 发送核心机密

### 2.4 高效 AI 代码协作提示词工程

**来源：** SitePoint - *Prompt Engineering for Web Development*

**核心原则：输入质量 = 输出质量**

| 差的 Prompt | 好的 Prompt |
|------------|-----------|
| "给我写个 Reddit 帖子获取代码" | "创建 WordPress 函数，使用 wp_remote_post() 向 {URL} 发请求，用 {API_KEY} 认证，返回最近帖子列表..." |

**好 Prompt 的要素：**
- 指定框架/平台（React / Next.js / Django）
- 指定要用的内置函数/API
- 提供精确的输入输出格式
- 明确验证要求和错误处理
- 定义数据结构规范

**提示词技巧：**
- 先尝试一次到位（长对话容易积累误差）
- 保持 D.R.Y.（不要重复自己）思维
- 领域知识越深，AI 产出越好
- 用 `###` 或 `"""` 分隔指令和上下文

### 2.5 Cursor Code Review 提示词模板

**来源：** HTMLPAGE - *Cursor 代码审查提示词怎么写*

**高质量 Code Review 提示词 = 5 件事：**

```
请只审查以下改动范围：
- 文件：<列出文件>
- 目标：<一句话说明这次改动想解决什么>
- 不在范围内：<明确哪些模块不要展开>

请按以下维度输出审查结果：
1. 范围是否越界
2. 依赖与调用方是否漏改
3. 测试与回归项是否不足
4. 性能风险
5. 安全风险

输出要求：
- 只写有根据的问题
- 每条问题包含：严重级别、位置、原因、建议修复、回归检查点
- 如无高置信问题，明确说明"未发现问题"
```

**审查维度对照表：**

| 维度 | 重点问题 | 什么时候必须深查 |
|------|---------|---------------|
| 范围 | 改动是否越界 | 多文件、共享组件 |
| 依赖 | 调用方/类型/路由是否同步 | 接口、组件 props、store |
| 测试 | 是否补了单元/集成/冒烟 | 表单、支付、权限 |
| 性能 | 首屏、体积、重复请求 | Landing 页、SSR 页面 |
| 安全 | 输入校验、敏感信息泄漏 | 登录、支付、上传 |

### 2.6 Vibe Coding 实战工作流

**来源：** QubitTool - *Vibe Coding 实战指南*

**三大主流工具对比：**

| 工具 | 核心优势 | 适合人群 |
|------|---------|---------|
| **Cursor** | IDE 原生集成，可视化反馈强，Composer 模式 | 全能型首选 |
| **Claude Code** | 逻辑严密，上下文窗口稳定，多文件重构强 | 资深开发者、CLI 爱好者 |
| **Trae（字节）** | 中文优化，响应延迟极低 | 国内开发者 |

**`.cursorrules` 项目规约文件示例：**
```
# 项目规约
- 技术栈: Next.js 14, Tailwind CSS, Lucide Icons, Shadcn UI
- 代码风格:
  - 严禁内联样式
  - 优先使用 Lucide 图标
  - 所有组件包含 Error Boundary
- 架构约束:
  - 逻辑层与展示层分离
```

**意图表达三技巧：**
1. **场景化描述**："写一个按钮" → "写一个有触感反馈的提交按钮，点击有微小缩放动画"
2. **参考系设定**："参考 Linear 的侧边栏折叠逻辑"
3. **分步引导**："第一步实现 CRUD 骨架，第二步集成数据库"

**生产环境护栏：**
- 生成即测试（要求 AI 同时生成配套测试）
- 规格驱动（先写 `spec.md`，再 Vibe 创作）
- CLAUDE.md 持久化项目记忆

## 三、代码理解框架（可直接使用）

```
# 🔍 AI 代码理解框架

## 1. 整体把握（第一遍扫描）
- [ ] 这个代码要解决什么问题？
- [ ] 整体架构是怎样的？（输入 → 处理 → 输出）
- [ ] 有哪些核心文件/模块？
- [ ] 依赖了哪些外部库？

## 2. 核心逻辑（第二遍细读）
- [ ] 最重要的函数/类是哪个？
- [ ] 数据在函数间如何传递？
- [ ] 控制流是怎样的？（if/else、循环、递归）
- [ ] 关键算法/数据结构是什么？

## 3. 细节理解（第三遍+）
- [ ] 这行代码做了什么？有没有替代写法？
- [ ] 边界条件是如何处理的？（空输入、null、超大输入）
- [ ] 有没有潜在的 bug？（死循环、内存泄漏、线程安全）

## 4. Review 要点
- [ ] 逻辑正确性：算法符合需求吗？
- [ ] 边界条件：空/0/极大/Unicode/特殊字符？
- [ ] 性能考虑：时间复杂度、空间复杂度、I/O 次数
- [ ] 安全问题：注入、越权、敏感信息、日志泄漏
- [ ] 可维护性：命名清晰吗？职责单一吗？

## 5. 用 AI 辅助理解
- [ ] 让 AI 逐行解释，并要求说明数据流
- [ ] 让 AI 找出可能的 bug 和边界错误
- [ ] 让 AI 生成测试用例验证理解
```

## 五、实践建议（本周可执行）

### 立即开始
- [ ] **建立自己的 `.cursorrules`**：在个人项目中定义代码风格、技术栈约束，放在项目根目录
- [ ] **用测试驱动 AI**：下次让 AI 写代码前，先自己写 3-5 个测试用例
- [ ] **掌握一个调试器**：VS Code Debugger 或 PyCharm Debugger，理解断点、单步、变量检查

### 本周练习
- [ ] **读懂一段陌生代码**：找一段从未接触过的开源代码，用"代码理解框架"走一遍
- [ ] **Review 自己的 AI 代码**：对自己用 AI 写的代码，用安全审查 prompt 走一遍
- [ ] **积累 Prompt 模板**：把好用的 Review 提示词保存到笔记中

### 长期习惯
- [ ] **记录 AI 失败模式**：每次 AI 代码出问题，记录是哪类错误（幻觉 API / 边界错误 / 安全漏洞），逐渐形成自己的"AI Bug Checklist"
- [ ] **规格优先于 Vibe**：核心业务逻辑先写 `spec.md` 再让 AI 实现
- [ ] **定期回读自己生成的代码**：即使代码能运行，也要定期回读理解，这是提升代码能力的核心

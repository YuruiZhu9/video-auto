### 🔍 AI 代码的 6 层结构化 Review 框架

这是业界最实用的 AI 代码审查方法论，每层针对一种 AI 特有失败模式：

#### Layer 1：需求一致性（Requirement Fidelity）
- 代码实现的是**规范本身**，还是 AI 理解的简化版？
- 逐字对比：需求文档 → 代码实现，是否完全对应？
- **红旗：** 实现覆盖的状态数少于需求描述；错误处理用通用消息替代了规范要求的特定消息

#### Layer 2：逻辑与边界条件（Logic & Edge Cases）
- 每个输入范围的边界上会发生什么？
- 空值、null、零值、负数、最大值 — 各跑一遍
- **红旗：** 缺少空输入守卫；循环边界用 `<` 还是 `<=` 没有明确理由；并发访问没有状态保护

#### Layer 3：API 与依赖完整性（API & Dependency Integrity）
> **⚠️ AI 专利问题：人类不会发明不存在的 API，AI 会。**
- 每个外部函数调用在依赖清单中是否存在？
- 方法签名与当前 API 文档是否一致？
- **行动：** 对每个外部调用，去实际文档中核实版本签名，不要靠记忆
- **红旗：** 导入了清单中没有的库；方法调用了库类型定义中没有暴露的方法

#### Layer 4：安全模式（Security Patterns）
- 令牌验证逻辑：格式错误/过期/缺失的令牌是否有区分处理？
- 加密：算法是否当前？密钥长度是否够？IV/nonce 是否每次操作唯一生成？
- 输入处理：SQL 查询是否参数化而非字符串拼接？
- 输出是否针对目标上下文正确编码（HTML / SQL / 命令行 / 日志）？
- **红旗：** 硬编码凭证或 API Key；`eval()` 等危险函数

#### Layer 5：上下文与系统感知（Context & System Awareness）
> **AI 在真空中生成代码，不知道你的系统历史和架构决策。**
- 代码是否考虑了所调用服务的**速率限制/配额/吞吐量约束**？
- 是否遵循了系统中既定的**事务边界**？
- 是否与现有的错误处理、日志、监控模式一致？
- **红旗：** 没有错误处理外部 API 的限流响应；数据库操作在既定事务模式外；日志可能包含敏感数据

#### Layer 6：测试质量（Test Quality）
> **如果测试与实现来自同一个 AI，格外怀疑。**
- 测试验证的是**需求**还是**实现方式**？
- 把实现悄悄改错，测试还能通过吗？若能，说明测试无效
- **最少覆盖：** 快乐路径 + 空/null 输入 + 边界值 + 无效输入
- **红旗：** 测试名称描述的是实现方法而非行为；无论实现是否正确都会通过的测试

### 🧭 人类角色：从 Coder 到 Navigator

在 AI 结对编程中，人类承担 **Navigator** 角色（reviewer），AI 是 **Driver**（实现者）。

**什么时候切换到 Driver（自己写）：**
- 学习新模式时：自己写，AI 解释概念
- 安全关键代码：认证逻辑自己写，AI 只做 review
- 性能优化：先 profile，再让 AI 在你监督下优化
- 遗留代码重构：你了解其中的 quirks，AI 做机械性改动

**什么时候保持 Navigator：**
- 架构设计、边界条件、业务逻辑 — 这些 AI 不擅长
- AI 处理样板代码和常见模式

## 三、代码理解框架（实用模板）

### 🎯 AI 代码理解四步法

```
## 第一步：整体把握
- 这个代码要解决什么问题？（对照需求文档）
- 整体架构是怎样的？输入 → 处理 → 输出
- 有哪些关键文件和目录？

## 第二步：核心逻辑
- 最重要的函数/类是哪个？
- 数据从哪进、从哪出？
- 关键算法是什么？用了什么库/模式？

## 第三步：逐行/逐段理解
- 这段代码做了什么？（对照文档或让 AI 解释）
- 为什么要这样写？有没有替代方案？
- 边界条件在哪里？空值/null 如何处理？

## 第四步：Review 要点
□ 逻辑正确性：符合需求吗？
□ 边界条件：null/空/最大/最小/负数？
□ 性能：循环中有 I/O？N+1 查询？内存泄漏？
□ 安全：输入验证？SQL 参数化？硬编码密钥？
□ 上下文：符合项目架构和代码规范吗？
□ 测试：覆盖了上述所有情况吗？
```

### 📝 AI 协作提示词模板（拿来就用）

#### 1. 请求代码解释
```
请逐行解释这段代码，重点说明：
1. 每个函数/方法的作用
2. 数据从输入到输出的完整流向
3. 关键的算法逻辑或业务规则
4. 可能的边界条件和错误处理方式
5. 这段代码有没有我需要特别关注的问题？
```

#### 2. 请求代码 Review
```
请审查这段代码，重点检查：
1. 逻辑正确性（是否符合需求）
2. 边界条件和空值处理
3. 性能问题（N+1、循环 I/O、内存泄漏）
4. 安全漏洞（注入、硬编码密钥、XSS）
5. 与项目既有架构的一致性
请列出所有发现的问题，按严重程度排序。
```

#### 3. 请求边界条件分析
```
对于这个函数，请分析以下边界情况：
1. 输入为 null / undefined
2. 输入为空数组 / 空字符串 / 空对象
3. 输入为最大值 / 最小值
4. 输入为负数
5. 并发调用
对每种情况，说明预期行为和潜在问题。
```

#### 4. 请求性能诊断
```
这段代码在生产环境中运行较慢。请：
1. 找出主要性能瓶颈（Big-O 分析）
2. 提出具体优化方案
3. 说明每个优化带来的预期收益
4. 给出优化前后的对比（伪代码或说明）
```

#### 5. 请求生成测试用例
```
请为这个函数生成单元测试，覆盖：
1. 正常输入的快乐路径
2. 空值 / null 输入
3. 边界值（最大/最小）
4. 无效/异常输入
5. 并发场景（如果适用）
使用 [pytest / Jest / JUnit] 格式。
```

#### 6. 请求 Refactor
```
请重构这段代码，要求：
1. 保持原有功能不变
2. 每个函数不超过 50 行
3. 嵌套层级不超过 4 层
4. 圈复杂度低于 15
5. 遵循 [语言/框架] 的命名规范
请解释每次重构的原因。
```

## 四、AI 代码常见"红旗"清单

**代码看起来正常，但危险信号 👇**

| 红旗 | 说明 |
|------|------|
| 缺少空值守卫 | `data.user.name` 无条件访问，AI 默认"快乐路径" |
| 除法无零保护 | `total / len(numbers)`，空数组直接崩溃 |
| N+1 查询 | AI 生成的 ORM 代码常见，循环内查数据库 |
| 事件监听器无清理 | Node.js 循环内挂载监听器无 off() |
| `eval()` 出现 | 危险函数，AI 经常无意识使用 |
| 字符串拼接 SQL | SQL 注入漏洞，必须参数化 |
| 循环内顺序 I/O | 应该 Promise.all() 并行化 |
| 硬编码 API Key | 立即替换为环境变量 |
| 不存在的依赖包 | AI 幻觉产物，npm install / pip install 前先核实 |
| 过度工程化 | 简单任务用了依赖注入、抽象工厂等企业模式 |

### 学习阶段补充：代码质量评估清单 ⭐（新增）

### 核心概念（来自 [代码质量评估清单](../知识点/代码质量评估清单.md)）

| 维度 | 检查重点 | 快速识别信号 |
|------|---------|------------|
| 分层架构 | Controller ≤ 50行、无跨层调用 | Controller 里出现 SQL/业务逻辑 → 拆分 |
| 命名可读性 | 类名名词、方法名动词、无魔法数字 | 单字母变量、flag 类布尔值 |
| 单一职责 | 方法 ≤ 30行、参数 ≤ 5个 | 方法名含 "and"/"or" → 拆分 |
| 错误处理 | 无 bare except、异常有日志+上下文 | try-pass → 记录日志 |
| 依赖管理 | 构造函数注入、无循环依赖 | 内部 import 全局对象 |
| 代码重复 | 相同逻辑最多出现2次 | 重复代码块 > 3 处 |
| 安全性 | SQL参数化、敏感信息不写入日志 | 字符串拼接 SQL |
| 可测试性 | 外部依赖可 Mock | 需要启动 Flask 才能测业务逻辑 |
| 性能意识 | 无 N+1 查询、有超时控制 | 循环内查数据库 |

### 推荐系统专项质量检查

| 模块 | 关键检查点 |
|------|---------|
| 召回层 | 策略可配置切换（OCP）、去重逻辑、去重上限 |
| 排序层 | 特征获取超时降级、模型推理缓存、AB 分流独立 |
| 重排层 | 业务规则可配置、推荐理由完整、兜底降级 |

### 质量打分表

```
评分维度 × 权重：
分层架构(20%) + 命名可读性(15%) + SRP(15%) + 错误处理(15%)
+ 依赖管理(10%) + DRY(10%) + 安全(5%) + 可测试性(5%) + 性能(5%)
= 100%

得分参考：
4.5+ 🥇 优秀  |  3.5-4.4 🥈 良好  |  2.5-3.4 🥉 及格  |  <2.5 ⚠️ 不及格
```

### 学习目标
- ✅ 能 5 分钟内快速发现一个文件的主要代码问题
- ✅ 能用本清单对照评估自己项目的质量得分
- ✅ 能制定改进计划（优先改高分维度）
- ✅ 能在上线前完成必检清单

## 第四阶段后半段：性能与缓存 ⭐（新增）

### 核心概念（来自 [Redis缓存与性能优化实战](../知识点/Redis缓存与性能优化实战.md)）

| 概念 | 说明 | 推荐系统中的应用 |
|------|------|----------------|
| Cache-Aside | 读多写少，业务代码负责缓存 | 推荐结果缓存、Item特征缓存 |
| Write-Through | 写操作同步穿透缓存+DB | 点赞计数、订单状态 |
| Write-Behind | 先写缓存，异步批量写DB | 行为打点、实时特征更新 |
| 缓存穿透 | 不存在的数据击穿到DB | Bloom Filter 快速过滤 |
| 缓存击穿 | 热点 key 过期瞬间击穿DB | 分布式锁（SET NX） |
| 缓存雪崩 | 大量 key 同时过期 | TTL 随机偏移 + 多级缓存 |
| 多级缓存 | L1 本地 + L2 Redis + L3 MySQL | dict → Redis → DB |

### 推荐系统缓存场景速查

| 场景 | 模式 | TTL | 序列化 |
|------|------|-----|--------|
| 首页推荐结果 | Cache-Aside | 30min | JSON |
| 用户/Item 特征 | Cache-Aside | 1-24h | JSON |
| Embedding 向量 | Cache-Aside | 1-4h | numpy bytes |
| 点赞/评论计数 | Write-Through | 无TTL | String |
| 行为打点计数 | Write-Behind | 无TTL | String |

### 学习目标
- ✅ 能根据业务场景选择合适的缓存模式
- ✅ 能实现 Cache-Aside / Write-Through / Write-Behind 完整代码
- ✅ 能用 Bloom Filter + 分布式锁解决缓存三大经典问题
- ✅ 能设计多级缓存（L1 本地 + L2 Redis + L3 DB）
- ✅ 能为推荐系统设计合理的 TTL 策略

## 第四阶段补充：分布式系统韧性设计 ⭐（新增）

### 核心概念（来自 [分布式系统韧性设计：重试熔断限流与超时](../知识点/分布式系统韧性设计：重试熔断限流与超时.md)）

| 概念 | 说明 | 推荐系统中的应用 |
|------|------|----------------|
| **超时（Timeout）** | 防止无限等待，快速失败 | 召回超时3s、精排超时5s，设置read+connect双超时 |
| **重试（Retry）** | 指数退避+抖动，应对瞬时故障 | 网络抖动时自动重试，业务异常不重试 |
| **熔断器（Circuit Breaker）** | 防止级联失败，保护下游 | 用户画像/召回/排序各服务独立熔断 |
| **限流（Rate Limiting）** | 滑动窗口/令牌桶，保护系统 | API层按UserID限流，模型层按并发限流 |

### 推荐系统四级降级策略

```
正常 → 一级降级(精排挂了) → 二级降级(召回挂了) → 三级降级(全链路挂了)
```

### 学习目标
- ✅ 能为每个下游调用设置合理的超时（connect + read）
- ✅ 能实现指数退避+随机抖动的重试装饰器
- ✅ 能为推荐系统各服务配置独立的熔断器
- ✅ 能实现 Redis 滑动窗口限流（Lua 脚本原子操作）
- ✅ 能设计三级降级预案并编码实现

### 第四阶段补充：六边形架构（端口与适配器）⭐（新增）

### 核心概念（来自 [六边形架构与适配器模式实战](../知识点/六边形架构与适配器模式实战.md)）

| 概念 | 说明 | 推荐系统中的应用 |
|------|------|----------------|
| **端口（Port）** | "我们要什么"的接口契约 | RecallPort / RankingPort / StoragePort / EventPort |
| **适配器（Adapter）** | "谁来提供"的实现 | MySQL / Redis / Kafka / Embedding 模型推理 / Flask / gRPC |
| **Driving Adapter** | 主动触发业务的适配器 | Flask / gRPC / Kafka Consumer |
| **Driven Adapter** | 被业务调用的适配器 | MySQL / Redis / 微信API / AI模型推理 |
| **DI 容器** | 组装所有适配器，统一管理生命周期 | `DIContainer` 初始化所有连接 |
| **Mock 测试** | 用内存实现替代真实适配器 | 纯 Python pytest，零外部依赖 |

### 六边形架构核心原则

```
依赖只能向内：适配器 ──► 端口 ──► 领域层
业务永远在中心：推荐逻辑不知道用的是 MySQL 还是 PostgreSQL
```

### 推荐系统六类端口速查

| 端口 | 作用 | 适配器实现 |
|------|------|-----------|
| `RecallPort` | 召回策略抽象 | Embedding召回 / ItemCF / UserCF / 热门召回 |
| `RankingPort` | 排序模型抽象 | XGBoost / DeepFM / LLM-Rank |
| `UserProfilePort` | 用户画像抽象 | MySQL / MongoDB / Redis |
| `RecommendationStoragePort` | 结果存储抽象 | Redis / MySQL / 文件 |
| `EventPublishPort` | 事件发布抽象 | Kafka / Redis Stream / HTTP |
| `CachePort` | 缓存抽象 | Redis / Memcached / 本地 dict |

### 学习目标
- ✅ 能定义业务所需的所有端口（接口）
- ✅ 能为 MySQL/Redis/Kafka/模型服务各写一个适配器
- ✅ 能用 Mock 适配器做纯内存单元测试
- ✅ 能画出自己推荐系统的六边形架构图
- ✅ 能通过"换适配器"而不是"改业务代码"来切换实现

### 核心概念（来自 [微服务架构实战](../知识点/微服务架构实战.md)）

| 概念 | 说明 | 推荐系统中的应用 |
|------|------|----------------|

### 微服务拆分原则

```
推荐系统拆分路线
═════════════════════════════
阶段1（0→1）：单体优先，包分层（recall/rank/rerank）
阶段2（增长期）：垂直拆分 → 用户域 / 内容域 / 推荐引擎域
阶段3（成熟期）：水平拆分 → 召回服务 / 排序服务 / 重排服务独立部署
```

## 第四阶段后半段：事件驱动架构 ⭐ （新增）

### 核心概念（来自 [事件驱动架构与Kafka实战](../知识点/事件驱动架构与Kafka实战.md)）

| 概念 | 说明 | 推荐系统中的应用 |
|------|------|----------------|
| Event 事件 | "发生了什么"，不可变的事实 | `UserClickedItem`、`ItemPurchased` |
| Producer 生产者 | 发布事件的组件 | API 服务、客户端 SDK |
| Consumer 消费者 | 订阅并处理事件的组件 | 画像更新、缓存预热、BI分析 |
| Consumer Group | 消费者组（组内竞争，组间广播） | 不同消费者组独立处理同一事件 |

### 同步 vs 异步：决策树

```
推荐请求 → 需要实时返回？
├─ 是 → 同步调用（gRPC/HTTP）
└─ 否 → 以下情况选事件驱动：
    ├─ 多消费者（一个事件触发多个下游）→ Kafka
    ├─ 峰值削峰（流量洪峰，异步消化）→ Kafka
    └─ 系统解耦（服务间无直接依赖）→ Kafka
```

### 推荐系统事件流

```
用户点击商品
    ↓
Kafka Producer 发布 click 事件（异步，非阻塞）
    ↓（并行异步处理）
画像服务 Consumer  →  更新用户向量
缓存预热 Consumer  →  刷新 Redis 推荐缓存
数据分析 Consumer  →  统计 CTR/GMV
```

### 学习目标
- ✅ 能区分同步（gRPC）和异步（Kafka）通信的适用场景
- ✅ 能设计推荐系统的关键事件清单
- ✅ 能实现 Kafka Producer/Consumer 完整代码
- ✅ 能设计多 Consumer 消费者组隔离架构
- ✅ 理解幂等性设计（防止 Kafka 重复投递问题）

## 第四阶段后半段：DDD 领域驱动设计 ⭐

### 核心概念（来自 [DDD领域驱动设计入门](../知识点/DDD领域驱动设计入门.md)）

| 概念 | 说明 | 推荐系统对应 |
|------|------|-------------|
| Entity 实体 | 有唯一标识，生命周期内标识不变 | User、Item、RecommendationResult |
| Value Object 值对象 | 无标识，属性相等即相同 | GeoLocation、UserPreference、ScoreCard |
| Aggregate 聚合 | 一组对象的聚合根，统一入口 | UserAggregate（含 User + Preference + History） |
| Domain Service 领域服务 | 跨实体的业务规则 | 推荐匹配分计算、多样性规则 |
| Repository 仓储 | 领域层抽象的数据访问接口 | UserRepository、ItemRepository |
| Domain Event 领域事件 | 业务中的重要事件，解耦用 | UserClickedItem、ItemQualityUpdated |
| Bounded Context 限界上下文 | 业务边界，不同上下文不同模型 | 用户域/内容域/推荐引擎域 |

### DDD vs 整洁架构对比

| 维度 | 整洁架构 | DDD |
|------|---------|-----|
| 核心关注 | 技术分层 | 业务边界 |
| 领域层 | 业务实体+规则 | Entity + Value Object + Aggregate + Domain Service |
| 接口层 | Controller/Request/Response | Application Service + DTO |
| 适用场景 | 中小型项目 | 复杂业务系统（推荐系统适合！） |

### 推荐系统限界上下文划分

```
推荐系统
├── 用户域（User Context）：用户注册、画像、关系链
├── 内容域（Content Context）：内容发布、审核、标签
└── 推荐引擎域（Recommendation Context）：召回、排序、重排

跨域通信：通过 user_id / item_id 关联，不直接引用内部对象
```

### 学习目标
- ✅ 能区分 Entity 和 Value Object
- ✅ 能为推荐系统设计 Aggregate
- ✅ 能定义 Repository 接口并在基础设施层实现
- ✅ 能识别关键 Domain Event 并用事件总线解耦
- ✅ 能划分 Bounded Context，画出限界上下文图

### 第五阶段补充：技术债识别与偿还策略 ⭐（新增）

### 核心概念（来自 [技术债识别与偿还策略](../知识点/技术债识别与偿还策略.md)）

| 概念 | 说明 | 推荐系统中的应用 |
|------|------|----------------|
| **战略债** | 明知不完美，业务优先先上线 | MVP 单体架构，先跑通再优化 |
| **权衡债** | 知道有取舍，决策时记录 | MySQL vs ClickHouse 混合选型 |
| **疏忽债** | 不知道这是债，知识储备不足 | 没遵循 SOLID，N+1 查询 |
| **根本债** | 规模变化让"正确"变"错误" | 单体变死胖，Skew 随流量爆发 |
| **利息率** | 每次碰代码比正常多花多少时间 | 硬编码修改 2h/月 → 年息 48h |
| **Boy Scout Rule** | 每次碰代码，顺手清理周围坏味道 | 不需要专门还债，融入日常 |
| **Strangler Fig** | 灰度替换，不停服重构核心模块 | 召回路新旧策略并行，配置切换 |

### 推荐系统五类典型债自查

| 债类型 | 典型症状 | 利息估算 | 优先级 |
|--------|---------|---------|--------|
| 架构债 | 召回路写死，新增策略要改 5 处 | 5 人日/策略 | 🔴 高 |
| 数据债 | 训练/推理特征 Skew，模型训错 3 周才发现 | 3 人日/月 | 🔴 高 |
| 工程债 | 魔法数字散布，硬编码过滤规则 | 2 人日/月 | 🟡 中 |
| 测试债 | 零覆盖，改一动全靠 Postman | Bug 率 3x | 🟡 中 |
| 可观测债 | 挂了只知道慢，不知道哪段慢 | 定位 2h → 15min | 🟡 中 |

### 偿还策略决策树

```
要不要还这笔债？
├─ 这段代码多久改一次？→ 几乎不改 → 不还（低息）
├─ 改一次多花多少时间？→ < 30min → 不还（利息 < ROI）
├─ 业务正在快速发展期？→ 是 → 优先战略债，战术债先记账
└─ 债已经影响开发速度？→ 是 → Boy Scout Rule + 专项 Sprint
```

### 学习目标
- ✅ 能区分四类技术债，知道哪些该还、哪些可以忍着
- ✅ 能用"利息公式"量化债务，说服业务给资源
- ✅ 能在日常开发中用 Boy Scout Rule 持续清理

### 第四阶段补充：Flink 实时特征工程架构 ⭐（新增）

### 核心概念（来自 [Flink实时特征工程架构实战](../知识点/Flink实时特征工程架构实战.md)）

| 概念 | 说明 | 推荐系统中的应用 |
|------|------|----------------|
| **DataStream** | 无界数据流，每条事件独立处理 | 用户点击/曝光/购买事件流 |
| **Keyed State** | 按 Key 聚合的状态（RocksDB 支持大状态） | 用户ID → 实时点击计数器 |
| **Window** | 时间窗口：滚动/滑动/会话窗口 | "近30分钟点击量"、"过去1小时类目偏好" |
| **Watermark** | 事件时间水位线，处理乱序/迟到事件 | 允许5s乱序，侧输出收集超限事件 |
| **Checkpoint** | Flink 状态快照exactly-once保证 | Job 重启后状态不丢失 |
| **Redis Sink** | Flink → Redis 实时特征写入 | TTL 自动过期，不用人工清理 |

### 推荐系统实时特征体系

| 特征类型 | Flink 算子 | Redis Key | TTL |
|---------|-----------|----------|-----|
| 用户实时点击计数 | SlidingWindow + Count | `rt:click_count:{user_id}` | 1h |
| 用户点击序列 | MapFunction + ListState | `rt:click_seq:{user_id}` | 30min |
| 用户类目偏好 | MapFunction + 分布计算 | `rt:cat_dist:{user_id}` | 2h |
| 商品小时CTR | ProcessFunction + MapState | `rt:item_stats:{item_id}` | 2h |

### Flink vs 纯离线特征效果对比（A/B Test 7天）

```
CTR:  3.2% → 4.1% (+28%)
CVR:  1.8% → 2.4% (+33%)
人均点击: 8.5 → 11.2 (+32%)
```

- ✅ 能理解批处理和流处理的本质区别
- ✅ 能用 Flink 实现三大核心实时特征算子
- ✅ 能设计 Flink → Redis 的实时特征写入架构
- ✅ 能处理 Late Event（水位线 + 侧输出）
- ✅ 能为 Flink Job 配置高可用（Checkpoint + RocksDB）

### 第四阶段补充：冷启动全链路解决方案 ⭐（新增）

### 核心概念（来自 [推荐系统冷启动全链路解决方案](../知识点/推荐系统冷启动全链路解决方案.md)）

| 概念 | 说明 | 推荐系统中的应用 |
|------|------|----------------|
| **用户冷启动** | 新用户没有任何行为数据 | 热门兜底→人口属性→实时学习→Bandit→跨域迁移 |
| **物品冷启动** | 新品无曝光→无点击→无特征 | UCB探测+冷热融合，平衡探索与利用 |
| **系统冷启动** | 系统刚上线，完全无数据 | Bootstrap伪评分+三阶段灰度上线 |
| **Thompson Sampling** | Beta分布抽样，自动平衡EE | 每个类目维护Beta(α,β)分布，抽到谁推谁 |
| **UCB (Upper Confidence Bound)** | 置信上界 = 均值 + 探索奖励 | 新品曝光预算 = f(CTR, 曝光次数) |
| **冷热融合** | 热品协同过滤 + 冷品内容特征 + UCB探测 | 综合分 = 个性化分 × (1 + 冷度权重 × UCB) |
| **跨域迁移** | 借用其他平台用户行为数据 | 短视频点赞 → 电商购买偏好映射 |

### 冷启动策略决策树

```
遇到冷启动问题，先问三个问题：
问题1：谁的冷启动？
├─ 新用户 → Level 1 热门 → Level 2 人群 → Level 3 实时 → Level 4 Bandit
└─ 新物品 → UCB探测 → 冷热融合 → 独立流量池

问题2：有多长时间？
├─ 秒级 → Level 1 热门兜底
├─ 分钟级 → Level 3 实时学习
└─ 天级 → Level 4 Bandit + 跨域迁移

问题3：有什么数据可用？
├─ 完全无数据 → Bootstrap 伪评分
├─ 只有人口属性 → Demographic 人群匹配
└─ 有他平台数据 → Cross-Domain 迁移
```

### 学习目标

- ✅ 能说出三类冷启动的本质区别和量化代价
- ✅ 能实现 Level 1-4 的用户冷启动完整代码（Python）
- ✅ 能用 Thompson Sampling 平衡探索与利用
- ✅ 能用 UCB 为新品分配探测流量
- ✅ 能实现冷热融合推荐器（综合分 = 个性化分 × 冷度加成）
- ✅ 能设计系统冷启动三阶段灰度上线方案
- ✅ 能搭建冷启动监控仪表盘（Grafana + Prometheus）

### 核心概念（来自 [MLOps端到端流水线实战](../知识点/MLOps端到端流水线实战.md)）

| 概念 | 说明 | 推荐系统中的应用 |

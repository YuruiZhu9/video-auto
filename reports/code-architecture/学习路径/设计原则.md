# 代码架构学习路径 — 设计原则

## 概述

设计原则是代码架构的"宪法"——不是硬性规定，而是经过大量实践验证的智慧结晶。
掌握这些原则，你就能在写代码时自己判断"这样做对不对"。

---

## 1. SOLID 原则

SOLID 是五个原则的首字母缩写，是面向对象编程最重要的设计准则。

---

### S — 单一职责原则（Single Responsibility Principle）

**核心思想：一个类只做一件事。**

> "一个类应该只有一个改变的原因。"

#### 反例

```python
class User:
    def __init__(self, name: str, email: str):
        self.name = name
        self.email = email

    # ❌ 职责过多：这个类同时负责数据、验证、保存、发送邮件
    def validate_email(self):
        if "@" not in self.email:
            raise ValueError("无效邮箱")

    def save_to_db(self):
        db.session.add(self)
        db.session.commit()

    def send_welcome_email(self):
        send_mail(self.email, "欢迎！")
```

#### 正例

```python
# ✅ 分离后：每个类各司其职
class User:
    def __init__(self, name: str, email: str):
        self.name = name
        self.email = email

class UserValidator:
    @staticmethod
    def validate(email: str):
        if "@" not in email:
            raise ValueError("无效邮箱")

class UserRepository:
    def __init__(self, db):
        self.db = db

    def save(self, user: User):
        self.db.session.add(user)
        self.db.session.commit()

class EmailService:
    def send_welcome(self, email: str):
        send_mail(email, "欢迎！")
```

**什么时候违反？** 如果你改一个类时，发现要同时考虑"数据库"和"邮件"两件事 → 需要拆分。

### O — 开闭原则（Open-Closed Principle）

**核心思想：软件实体应该对扩展开放，对修改关闭。**

> 写代码时，尽量通过"加"来实现新功能，而不是"改"现有代码。

#### 反例

```python
# ❌ 每次加新支付方式都要改这段代码
def pay(method: str, amount: float):
    if method == "alipay":
        # 支付宝逻辑
        pass
    elif method == "wechat":
        # 微信支付逻辑
        pass
    elif method == "card":
        # 银行卡逻辑
        pass
    # 加新支付方式 → 必须改这里 → 风险大
```

#### 正例

```python
from abc import ABC, abstractmethod

class PaymentMethod(ABC):
    @abstractmethod
    def pay(self, amount: float):
        pass

class Alipay(PaymentMethod):
    def pay(self, amount: float):
        print(f"支付宝支付 {amount}")

class WechatPay(PaymentMethod):
    def pay(self, amount: float):
        print(f"微信支付 {amount}")

class CardPay(PaymentMethod):
    def pay(self, amount: float):
        print(f"银行卡支付 {amount}")

# ✅ 加新支付方式：新建一个类即可，不用动原有代码
class PayPal(PaymentMethod):
    def pay(self, amount: float):
        print(f"PayPal 支付 {amount}")

# 使用方（对扩展开放）
def checkout(payment: PaymentMethod, amount: float):
    payment.pay(amount)
```

### L — 里氏替换原则（Liskov Substitution Principle）

**核心思想：子类必须能替换父类，且行为不变。**

> "如果 S 是 T 的子类，那么程序中用 T 的地方，换成 S 不应该出错。"

#### 反例

```python
class Rectangle:
    def set_width(self, w): self.width = w
    def set_height(self, h): self.height = h
    def area(self): return self.width * self.height

class Square(Rectangle):
    # ❌ 正方形不是普通矩形的子类！
    # set_width 和 set_height 的行为与 Rectangle 不兼容
    def set_width(self, w):
        self.width = self.height = w  # 违反预期

    def set_height(self, h):
        self.width = self.height = h  # 违反预期
```

#### 正例

```python
from abc import ABC, abstractmethod

class Shape(ABC):
    @abstractmethod
    def area(self) -> float:
        pass

class Rectangle(Shape):
    def __init__(self, width: float, height: float):
        self.width = width
        self.height = height

    def area(self) -> float:
        return self.width * self.height

class Square(Shape):
    def __init__(self, side: float):
        self.side = side

    def area(self) -> float:
        return self.side ** 2
```

### I — 接口隔离原则（Interface Segregation Principle）

**核心思想：不要强迫类实现它不需要的接口。**

> "用多个专用接口，比用一个臃肿接口好。"

#### 反例

```python
class IMachine(ABC):
    @abstractmethod
    def print(self, doc): pass
    @abstractmethod
    def scan(self, doc): pass
    @abstractmethod
    def fax(self, doc): pass

class OldPrinter(IMachine):
    # ❌ 只支持打印，却被迫实现了 scan 和 fax
    def print(self, doc): print(f"打印: {doc}")
    def scan(self, doc): raise NotImplementedError()
    def fax(self, doc): raise NotImplementedError()
```

#### 正例

```python
class Printer(ABC):
    @abstractmethod
    def print(self, doc): pass

class Scanner(ABC):
    @abstractmethod
    def scan(self, doc): pass

# ✅ 各取所需，按需组合
class SimplePrinter(Printer):
    def print(self, doc): print(f"打印: {doc}")

class AllInOneMachine(Printer, Scanner):
    def print(self, doc): print(f"打印: {doc}")
    def scan(self, doc): print(f"扫描: {doc}")
```

### D — 依赖倒置原则（Dependency Inversion Principle）

**核心思想：高层模块不要依赖低层模块，两者都应该依赖抽象。**

> "要依赖于抽象，不要依赖于具体实现。"

#### 反例

```python
# ❌ MySQLDriver 是具体实现，高层模块直接依赖了它
class MySQLDriver:
    def query(self, sql): ...

class UserService:
    def __init__(self):
        self.db = MySQLDriver()  # 硬依赖，换数据库要改这里

    def get_user(self, id):
        return self.db.query(f"SELECT * FROM users WHERE id={id}")
```

#### 正例

```python
from abc import ABC, abstractmethod

class Database(ABC):
    """抽象接口"""
    @abstractmethod
    def query(self, sql: str): pass

class MySQLDriver(Database):
    def query(self, sql: str):
        print(f"MySQL查询: {sql}")

class PostgreSQLDriver(Database):
    def query(self, sql: str):
        print(f"PostgreSQL查询: {sql}")

# ✅ 依赖抽象接口，具体实现可替换
class UserService:
    def __init__(self, db: Database):  # 通过注入依赖
        self.db = db

    def get_user(self, id):
        return self.db.query(f"SELECT * FROM users WHERE id={id}")
```

## 2. DRY 原则（Don't Repeat Yourself）

**核心思想：同一份知识不要出现两次。**

重复代码是最大的技术债。

#### 反例

```python
# ❌ 同样逻辑写三遍
def register_user(name, email):
    if not name:
        raise ValueError("姓名不能为空")
    if not email or "@" not in email:
        raise ValueError("邮箱格式错误")
    user = User(name=name, email=email)
    db.session.add(user)
    db.session.commit()
    send_email(email, "欢迎注册")
    return user

def update_user(user_id, name, email):
    if not name:
        raise ValueError("姓名不能为空")
    if not email or "@" not in email:
        raise ValueError("邮箱格式错误")  # 重复！
    user = User.query.get(user_id)
    user.name = name
    user.email = email
    db.session.commit()  # 重复提交逻辑
    return user
```

#### 正例

```python
# ✅ 抽取公共逻辑
def validate_user_data(name: str, email: str):
    if not name:
        raise ValueError("姓名不能为空")
    if not email or "@" not in email:
        raise ValueError("邮箱格式错误")

def commit_user(user: User):
    db.session.add(user)
    db.session.commit()
    return user

def register_user(name, email):
    validate_user_data(name, email)
    user = User(name=name, email=email)
    commit_user(user)
    send_email(email, "欢迎注册")
    return user

def update_user(user_id, name, email):
    validate_user_data(name, email)  # 复用验证
    user = User.query.get(user_id)
    user.name = name
    user.email = email
    return commit_user(user)  # 复用提交
```

## 3. KISS 原则（Keep It Simple, Stupid）

**核心思想：简单比复杂好，尽量让代码保持简洁。**

不要炫技，代码是给人看的。

#### 反例

```python
# ❌ 为了"优雅"用嵌套三元表达式，可读性极差
def get_status(user):
    return "管理员" if user.role == "admin" else ("VIP" if user.role == "vip" else ("普通用户" if user.role == "user" else ("游客" if user.role == "guest" else "未知")))


# ❌ 过度设计：用一个简单的配置映射表
ROLES = {
    "admin": "管理员",
    "vip": "VIP",
    "user": "普通用户",
    "guest": "游客",
}
def get_status(user):
    return ROLES.get(user.role, "未知")
```

#### 正例

```python
# ✅ 清晰、直接、可读
ROLES = {
    "admin": "管理员",
    "vip": "VIP",
    "user": "普通用户",
    "guest": "游客",
}

def get_status(user):
    return ROLES.get(user.role, "未知")
```

## 4. YAGNI 原则（You Aren't Gonna Need It）

**核心思想：不要写"将来可能用到"的代码。**

> 只有当真正需要时，才实现相应功能。

#### 反例

```python
# ❌ 预判"将来可能需要多语言支持"，写了一堆 i18n 逻辑
# 结果项目根本没做国际化，白白浪费开发时间
class ProductService:
    def __init__(self, lang="zh"):
        self.lang = lang
        self.labels = {
            "zh": {"add": "添加", "delete": "删除"},
            "en": {"add": "Add", "delete": "Delete"},
        }

    def label(self, key):
        return self.labels[self.lang].get(key, key)
```

#### 正例

```python
# ✅ 先写简单版本，等真正需要多语言时再重构
class ProductService:
    def add(self, name):
        return f"添加商品: {name}"
```

**什么时候违反？** 如果代码里有大段注释掉的备用逻辑，或者大量"以防万一"的抽象 → 违反 YAGNI。

---

## 五大原则速查表

| 原则 | 一句话总结 | 核心问题 |
|------|-----------|----------|
| **S** 单一职责 | 一个类只做一件事 | 避免"万能类" |
| **O** 开闭原则 | 对扩展开放，对修改关闭 | 避免改一处坏三处 |
| **L** 里氏替换 | 子类能替换父类 | 避免继承层次混乱 |
| **I** 接口隔离 | 用小接口替代大接口 | 避免被迫实现无用方法 |
| **D** 依赖倒置 | 依赖抽象而非具体 | 避免硬编码依赖 |
| **DRY** | 不重复自己 | 避免知识重复 |
| **KISS** | 保持简单 | 避免过度设计 |
| **YAGNI** | 你不需要它 | 避免"预支"开发 |

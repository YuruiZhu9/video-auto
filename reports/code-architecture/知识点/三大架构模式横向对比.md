# 三大架构模式横向对比：整洁 vs 六边形 vs 洋葱

> 这三个名字听起来不同，但核心思想几乎一样。搞清它们的区别与联系，才能在实战中不再迷茫。

---

## 一句话总结

| 架构模式 | 提出者 | 一句话核心 | 适合场景 |
|---------|--------|-----------|---------|
| **整洁架构** | Robert Martin（Uncle Bob） | 依赖向内，框架向外 | 业务逻辑复杂、迭代快的系统 |
| **六边形架构** | Alistair Cockburn | 端口与适配器解耦一切 | 需要频繁换数据库/换外部服务的系统 |
| **洋葱架构** | Jeffrey Palermo | 与整洁架构几乎相同，内层对外层无感知 | 追求DDD融合的团队 |

**结论先行**：三种架构本质是同一件事的不同表述——**"核心业务逻辑不依赖任何外部框架/工具"**。选哪个不重要，理解内核才重要。

---

## 统一内核：依赖规则

无论叫什么名字，三种架构都遵守同一条铁律：

```
┌──────────────────────────────────────────────┐
│  外层可以引用内层                             │
│  内层绝对不能引用外层                         │
│  外层通过接口（抽象）引用外层                 │
└──────────────────────────────────────────────┘
```

---

## 二、整洁架构（Clean Architecture）

### 2.1 核心理念

Robert Martin（Uncle Bob）在 2012 年系统化提出，核心目标：**让系统能够独立于 UI、数据库、外部接口。**

### 2.2 四层结构

```
由外向内：

Frameworks & Drivers（框架和驱动）
  ↓
Interface Adapters（接口适配器：Controller、Gateway、Presenter）
  ↓
Application Business Rules（用例：用例编排）
  ↓
Enterprise Business Rules（领域实体、业务规则）
  ↓
（最内层，零依赖）
```

### 2.3 Python 推荐系统示例

**场景**：推荐系统需要从 MySQL 读用户画像，用 Milvus 做向量召回，结果缓存在 Redis，最终排序依赖模型推理服务。

```python
# ===== Layer 1: Domain（最内层，无任何外部依赖）=====
# domain/entities/user.py
from dataclasses import dataclass
from typing import List

@dataclass(frozen=True)
class UserProfile:
    """用户画像——纯数据类，没有任何副作用"""
    user_id: int
    age: int
    gender: str
    city: str
    interest_tags: List[str]

# domain/value_objects/item_score.py
@dataclass(frozen=True)
class ItemScore:
    item_id: int
    score: float
    scene: str

# domain/services/recommendation_engine.py
from abc import ABC, abstractmethod
from typing import List

class RecallPort(ABC):
    """召回端口——只定义接口，不关心实现"""
    @abstractmethod
    async def recall(self, profile: UserProfile, limit: int) -> List[int]:
        pass

class RankingPort(ABC):
    """排序端口"""
    @abstractmethod
    async def rank(self, profile: UserProfile, item_ids: List[int]) -> List[ItemScore]:
        pass

class RecommendationDomainService:
    """领域服务：只包含业务规则"""
    
    def __init__(self, recall_port: RecallPort, ranking_port: RankingPort):
        self._recall = recall_port
        self._ranker = ranking_port
    
    async def recommend(self, profile: UserProfile, scene: str, limit: int = 20) -> List[ItemScore]:
        # 业务规则：候选数量不足时触发冷启动兜底
        candidates = await self._recall.recall(profile, limit=200)
        
        if len(candidates) < 10:
            # 业务规则：候选不足，用热门兜底
            return await self._ranker.rank_hot(profile, scene, limit)
        
        ranked = await self._ranker.rank(profile, candidates)
        # 业务规则：同一作者最多出现2次（多样性）
        return self._deduplicate_by_author(ranked, max_per_author=2)
    
    def _deduplicate_by_author(self, items: List[ItemScore], max_per_author: int) -> List[ItemScore]:
        author_count = {}
        result = []
        for item in items:
            author_id = item.author_id  # ItemScore 有 author_id 字段
            count = author_count.get(author_id, 0)
            if count < max_per_author:
                result.append(item)
                author_count[author_id] = count + 1
        return result
```

```python
# ===== Layer 2: Application（用例层，编排领域）=====
# application/use_cases/get_recommendations.py
from typing import List
from domain.value_objects import ItemScore
from domain.services.recommendation_engine import RecommendationDomainService

class CachePort(ABC):
    @abstractmethod
    async def get(self, key: str) -> Optional[List[ItemScore]]: pass
    @abstractmethod
    async def set(self, key: str, items: List[ItemScore], ttl: int): pass

class EventPort(ABC):
    @abstractmethod
    async def publish(self, event): pass

class GetRecommendationsUseCase:
    """一个用例 = 一个类，负责编排，不含业务逻辑"""
    
    def __init__(
        self,
        domain_service: RecommendationDomainService,
        cache_port: CachePort,
        event_port: EventPort,
    ):
        self._domain = domain_service
        self._cache = cache_port
        self._events = event_port
    
    async def execute(self, user_id: int, scene: str, page: int = 1, page_size: int = 20) -> dict:
        # Step 1: 尝试读缓存
        cache_key = f"rec:{user_id}:{scene}:p{page}"
        cached = await self._cache.get(cache_key)
        if cached:
            return self._to_response(cached, page_size)
        
        # Step 2: 构建用户画像（这里可以再抽象一个 UserProfilePort）
        profile = await self._load_profile(user_id)
        
        # Step 3: 调用领域服务
        results = await self._domain.recommend(profile, scene, limit=page_size * 3)
        
        # Step 4: 写缓存
        await self._cache.set(cache_key, results, ttl=300)
        
        # Step 5: 发布推荐事件（异步，不阻塞响应）
        await self._events.publish(RecommendationShownEvent(user_id, scene, [r.item_id for r in results]))
        
        return self._to_response(results, page_size)
    
    def _to_response(self, items: List[ItemScore], page_size: int) -> dict:
        return {
            'items': [{'item_id': i.item_id, 'score': i.score} for i in items[:page_size]],
            'total': len(items),
        }
```

```python
# ===== Layer 3: Infrastructure（基础设施层，实现端口）=====
# infrastructure/adapters/mysql_user_profile_adapter.py
class MySQLUserProfileAdapter:
    """MySQL 实现 UserProfilePort——具体实现"""
    
    def __init__(self, db_pool):
        self._pool = db_pool
    
    async def get_profile(self, user_id: int) -> UserProfile:
        async with self._pool.acquire() as conn:
            row = await conn.fetchone(
                "SELECT age, gender, city, interest_tags FROM users WHERE id = $1",
                user_id
            )
            return UserProfile(
                user_id=user_id,
                age=row['age'],
                gender=row['gender'],
                city=row['city'],
                interest_tags=row['interest_tags'].split(',') if row['interest_tags'] else []
            )

# infrastructure/adapters/milvus_recall_adapter.py
class MilvusRecallAdapter:
    """Milvus 向量数据库实现 RecallPort"""
    
    def __init__(self, milvus_client, embedding_service):
        self._milvus = milvus_client
        self._embedding = embedding_service
    
    async def recall(self, profile: UserProfile, limit: int) -> List[int]:
        user_vec = await self._embedding.get_user_vector(profile.user_id)
        results = self._milvus.search(
            collection_name="item_embeddings",
            vectors=[user_vec],
            top_k=limit
        )
        return [int(r.id) for r in results[0]]
```

@dataclass
class RecommendationController:

        GetRecommendationsUseCase,
        domain_service=domain_service,
        cache_port=cache_adapter,

        RecommendationController,
        use_case=use_case,
    )

### 2.4 整洁架构 vs 普通三层架构

| 对比维度 | 普通三层架构 | 整洁架构 |
|---------|------------|---------|
| 依赖方向 | Controller → Service → DAO，层层向下 | 只有外层引用内层 |
| 业务逻辑位置 | Service 层 | Domain 层 |
| 可测试性 | 需要启动数据库 | Domain 层完全Mock |
| 换数据库 | 改 DAO + 改 Service | 只改 Adapter |
| 框架依赖 | 强依赖（Controller = 框架逻辑） | 框架在最外层 |

## 三、六边形架构（Hexagonal Architecture）

### 3.1 核心理念

Alistair Cockburn 在 2005 年提出，核心概念：**端口（Port）+ 适配器（Adapter）**。

```
                    ┌─────────────────┐
                    │   主程序         │
                    │   （Application）│
                    └────────┬────────┘
                             │
            ┌────────────────┼────────────────┐
            │                │                │
      ┌─────▼─────┐   ┌──────▼──────┐  ┌─────▼─────┐
      │ 输入端口  │   │  输出端口   │  │  外部API  │
      │(Driving) │   │(Driven/     │  │  端口     │
      │Adapter)  │   │ Secondary)   │  │          │
      └─────┬─────┘   └──────┬──────┘  └─────┬─────┘
            │                │                │
            │         ┌──────▼──────┐         │
            │         │  适配器      │         │
            │         │  MySQL/     │         │
            │         │  Redis/Kafka │         │
            │         └─────────────┘         │
            │                                  │
         用户/UI                           外部服务
```

### 3.2 命名对比：六边形 vs 整洁

| 六边形术语 | 整洁架构术语 | 含义 |
|-----------|------------|------|
| Primary（Driving）Adapter | Interface Adapter | 接收输入（Controller） |
| Secondary（Driven）Adapter | Infrastructure | 实现输出（DAO、外部API） |
| Input Port | Application Service | 用例接口 |
| Output Port | Domain Service Port | 领域对外接口 |
| Application（核心） | Domain + Application | 核心业务 |

### 3.3 六边形架构代码示例

```python
# ===== Input Port（Primary，驱动端口）=====
# ports/input/get_recommendations_port.py
from abc import ABC, abstractmethod

class GetRecommendationsInputPort(ABC):
    """输入端口：定义"用户想要什么""""
    
    @abstractmethod
    async def execute(self, user_id: int, scene: str) -> list:
        pass

# ===== Output Port（Secondary，驱动端口）=====
# ports/output/
class UserProfileOutputPort(ABC):
    """输出端口：定义"核心需要什么外部能力""""
    @abstractmethod
    async def fetch(self, user_id: int) -> dict: pass

class RecallOutputPort(ABC):
    @abstractmethod
    async def recall(self, profile: dict, limit: int) -> List[int]: pass

class RankingOutputPort(ABC):
    @abstractmethod
    async def rank(self, user_id: int, item_ids: List[int]) -> List[dict]: pass

# ===== Primary Adapter（Driving，接收用户请求）=====
# adapters/primary/api_adapter.py
class RecommendationAPIAdapter:
    """Driving Adapter：HTTP API → 输入端口"""
    
    def __init__(self, input_port: GetRecommendationsInputPort):
        self._port = input_port
    
    async def handle(self, request) -> Response:
        user_id = int(request.query['user_id'])
        scene = request.query['scene']
        
        result = await self._port.execute(user_id, scene)
        return json_response(result)

# ===== Secondary Adapter（Driven，实现输出端口）=====
# adapters/secondary/mysql_profile_adapter.py
class MySQLUserProfileAdapter(UserProfileOutputPort):
    """Driven Adapter：实现 UserProfileOutputPort"""
    
    async def fetch(self, user_id: int) -> dict:
        async with self._pool.acquire() as conn:
            return await conn.fetchrow(
                "SELECT * FROM users WHERE id = $1", user_id
            )

# adapters/secondary/milvus_recall_adapter.py
class MilvusRecallAdapter(RecallOutputPort):
    """Driven Adapter：实现 RecallOutputPort"""
    
    async def recall(self, profile: dict, limit: int) -> List[int]:
        user_vec = await self._embedding.get(profile['user_id'])
        return self._milvus.search(user_vec, top_k=limit)
```

### 3.4 六边形 vs 整洁：怎么选？

| 决策问题 | 选六边形 | 选整洁 |
|---------|---------|--------|
| 团队熟悉 DDD | ✅ | 一般 |
| 需要频繁换数据库/中间件 | ✅（端口隔离更清晰） | 一般 |
| 系统以 HTTP API 为主 | 一般 | ✅（分层更直观） |
| 核心域复杂，DDD 重度使用 | ✅ | ✅ |
| 小型项目，简单 CRUD | ❌（过度设计） | ❌ |

**实践中**：大多数团队会混合使用——**六边形的"端口/适配器"命名 + 整洁架构的分层结构**。

## 四、洋葱架构（Onion Architecture）

### 4.1 核心理念

Jeffrey Palermo 在 2008 年提出，核心隐喻：**洋葱是一层层包裹的，越往里越核心。**

```
最外层：Infrastructure（基础设施：数据库、API、框架）
    ↓
第二层：Application Services（应用服务：用例）
    ↓
第三层：Domain Services（领域服务）
    ↓
最内层：Domain Model（实体、值对象、领域事件）
    ↓
    （核心，零依赖）
```

### 4.2 与整洁架构的对比

| 维度 | 整洁架构 | 洋葱架构 |
|------|---------|---------|
| 提出者 | Uncle Bob | Jeffrey Palermo |
| 层级命名 | Entity → Use Case → Interface Adapter → Frameworks | Domain Model → Domain Services → Application → Infrastructure |
| 依赖方向 | 严格向外 | 严格向外 |
| 与 DDD 融合 | 支持 | 更强调融合 |
| 实践广泛度 | 更高（更多文章和工具） | 稍低 |

**关键结论**：两者几乎等价，区别在于术语选择。整洁架构在工程社区影响力更大，洋葱架构在 DDD 社区更流行。

## 五、三者横向对比总结

### 5.1 共同点

1. **依赖单向**：只能从外向内，不能从内向外
2. **核心业务独立**：数据库、框架、UI 都可以替换
3. **接口隔离**：内层定义接口，外层实现
4. **可测试**：核心逻辑不需要任何外部依赖就能测试

### 5.2 核心区别

| 维度 | 整洁架构 | 六边形架构 | 洋葱架构 |
|------|---------|-----------|---------|
| **关注点** | 系统整体分层 | 端口/适配器解耦 | 层层向内收敛 |
| **入口抽象** | Controller/Presenter | Primary Adapter | Application Service |
| **出口抽象** | Gateway/Repository | Secondary Adapter | Infrastructure |
| **适合系统** | 业务逻辑复杂 | 外围组件经常变 | DDD 重度项目 |
| **学习曲线** | 中等 | 较陡（新概念多） | 中等 |

        │ 框架 & 驱动     │          │   外部工具      │         │  基础设施层     │

## 六、实战决策指南

### 什么情况下值得引入这些架构？

**应该用**：当系统满足以下 2 条以上时
- [ ] 业务逻辑复杂，迭代频率高（> 1次/周）
- [ ] 需要对接多个外部服务（数据库、缓存、消息队列、模型推理）
- [ ] 团队 > 5 人，需要并行开发
- [ ] 需要写单元测试，但现有架构测试困难
- [ ] 准备做 DDD

**不应该用**：当系统是简单 CRUD 时
- 单个服务 < 1000 行代码
- 只有 1-2 个表
- 业务逻辑基本就是 CRUD
- 团队 < 3 人

### 演进路径建议

```
第一阶段：单体 + 分层
├─ 先分 Controller / Service / DAO
├─ 把业务逻辑移到 Service
└─ 这是所有架构的基础

第二阶段：引入依赖注入
├─ 用 DI 容器管理依赖（Python: dependency-injector）
├─ 让 Service 接收接口而非具体类
└─ 这是向六边形/整洁迁移的关键一步

第三阶段：抽象基础设施
├─ Service 层定义 OutputPort 接口
├─ DAO 实现这些接口
├─ 框架代码移到最外层
└─ 这时你已经拥有了六边形/整洁的核心能力

第四阶段：完整迁移（可选）
├─ Domain 层从 Service 中提取核心业务规则
├─ 引入 Entity / Value Object / Domain Event
├─ 用例独立为 Application 层
└─ 只有当你需要 DDD 时才做这步
```

## 七、避坑清单

### 七大常见错误

| # | 错误 | 后果 | 正确做法 |
|---|------|------|---------|
| 1 | Domain 层导入了 `requests` 或 `pymysql` | 违反依赖规则，无法Mock | Domain 只用纯 Python（abc/dataclass） |
| 2 | 用例层（UseCase）写了业务逻辑 | 用例膨胀，难以复用 | 用例只编排，业务逻辑在 Domain |
| 3 | Controller 直接调 DAO（跳过 Service） | 分层失效 | Controller → UseCase → Domain → Port → Adapter |
| 4 | 一个适配器实现多个不相关的端口 | 违反ISP，耦合高 | 每个端口独立实现类 |
| 5 | 过度设计——小项目用完整整洁架构 | 复杂度超过收益 | 小项目先分层，迭代中逐步演进 |
| 6 | DI 容器过度使用静态单例 | 全局状态，测试困难 | 优先用 pytest fixture 注入 Mock |
| 7 | 换了数据库却不更新端口接口 | 接口腐烂 | 换实现时同步 review 端口是否还合理 |

## 九、本章小结

**记住三句话：**

1. **三个名字，一个内核**：依赖只能从外向内，核心业务不依赖任何外部工具
2. **端口是关键**：内层定义"要什么"（接口），外层实现"怎么做到"（适配器）
3. **渐进式演进**：不要一开始就用完整架构，从 DI 抽象开始，逐步迁移

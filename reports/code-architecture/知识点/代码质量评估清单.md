# 代码质量评估清单

> 快速对照检查代码质量，适用于：Code Review、接手新项目、重构前评估、上线前检查。
> 
> 上次更新：2026-04-05

## 一、分层架构评估

### 1.1 分层是否清晰

| 检查项 | ✅ 通过 | ❌ 问题 |
|--------|--------|---------|
| Controller 职责单一（≤ 50 行，无业务逻辑） | | |
| 业务逻辑集中在 Service 层 | | |
| Repository 纯数据访问，无业务判断 | | |
| 无跨层直接调用（如 Router → Repository） | | |
| 每层只依赖其下层，不反向依赖 | | |

### 1.2 分层问题快速识别

**Controller 太胖的信号：**
```python
# ❌ Controller 里出现了这些关键词 → 需要拆分到 Service
@router.post("/order")
def create_order():
    # 验证逻辑 ← 这里不该有
    if amount <= 0: raise ValueError()
    # 数据库操作 ← 这里不该有
    db.session.query(User).filter(...).first()
    # 业务规则 ← 这里不该有
    if user.vip and amount > 1000: discount = 0.9
    # 外部调用 ← 这里不该有
    send_email(user.email, ...)
    # 日志 ← 这里不该有
    logger.info(f"创建订单 {order_id}")
```

**分层混乱的信号：**
```
❌ app.py 里有 2000 行代码，所有逻辑混在一起
❌ services/ 下放了 models.py 的内容
❌ models/ 下放了业务逻辑（应该叫 domain/）
❌ utils/ 里塞了 50 个不相关的函数
```

## 二、命名与可读性评估

### 2.1 命名质量清单

| 检查项 | ✅ 通过 | ❌ 问题 |
|--------|--------|---------|
| 类名用名词（如 `UserService`），不用动词 | | |
| 方法名用动词或动宾短语（如 `create_user` / `get_user_by_id`） | | |
| 变量名表达意图，不使用单字母（`i`, `j` 除外用于循环） | | |
| 常量全大写下划线分隔（如 `MAX_RETRY_COUNT`） | | |
| 避免匈牙利命名法（如 `strUserName`） | | |
| 模块文件名小写下划线（如 `user_service.py`） | | |

### 2.2 可读性红线

**❌ 无法从名字判断意图的代码：**
```python
# ❌ 鬼代码
def do(data):
    d = get_d(k)
    if d.s == 1:
        return d.v

# ✅ 清晰命名
def process_user_order(order_data: OrderData):
    discount = calculate_discount_price(order_price)
    if discount.applied:
        return discount.final_price
```

**❌ 布尔变量命名误导：**
```python
# ❌ 布尔值名字不能准确表达语义
flag = check_user_status()  # flag 是什么？

# ✅ 明确语义
is_vip_user = check_user_vip_status()
has_permission = check_write_permission()
```

## 三、函数/方法设计评估

### 3.1 单一职责检查

**方法是否只做一件事？**

| 检查项 | ✅ | ❌ |
|--------|----|----|
| 方法名包含"and"/"or"（`validateAndSave`） | | ❌ 违反 SRP |
| 方法超过 30 行 | | ❌ 需要拆分 |
| 方法有超过 3 个参数 | | ❌ 考虑封装成对象 |
| 方法内有多个注释分隔的代码块 | | ❌ 每一块是一个方法 |
| 方法入口处有超过 5 个 if 判断 | | ❌ 违反 Tell, Don't Ask |

### 3.2 参数过多问题

```python
# ❌ 参数过多，调用方需要记顺序
def create_recommendation(user_id, item_id, scene, page, 
                          limit, offset, score_threshold, 
                          diversity_weight, refresh_cache):
    ...

# ✅ 用配置对象封装
@dataclass
class RecommendationRequest:
    user_id: str
    item_id: Optional[str] = None
    scene: str = "home"
    page: PageParams = PageParams()
    score_threshold: float = 0.0
    diversity_weight: float = 0.1
    refresh_cache: bool = False

def create_recommendation(req: RecommendationRequest):
    ...
```

## 四、错误处理评估

### 4.1 异常处理清单

| 检查项 | ✅ | ❌ |
|--------|----|----|
| 无 bare `except:` 捕获所有异常（吞掉错误） | | ❌ |
| 异常有明确类型（不用 Exception 基类） | | |
| 异常被记录日志（不只是打印） | | |
| 异常信息包含上下文（便于排查） | | |
| 外部服务调用有 try-catch 保护 | | |
| 有统一的全局异常处理中间件 | | |

### 4.2 典型错误处理坏味道

```python
# ❌ 坏味道1：吞掉异常
try:
    result = call_external_api()
except Exception:
    pass  # 完全不知道发生了什么

# ✅ 好味道1：记录 + 重新抛出
try:
    result = call_external_api()
except ExternalServiceError as e:
    logger.error(f"外部API调用失败: {e}", extra={"url": url})
    raise ServiceUnavailableError("推荐服务暂时不可用") from e

# ❌ 坏味道2：返回 None 表示错误
def get_user(user_id):
    if not exists(user_id):
        return None  # 调用方可能忘记判空
    return user

# ✅ 好味道2：明确返回 Optional + 调用方必须处理
from typing import Optional
def get_user(user_id: str) -> Optional[User]:
    ...

# ❌ 坏味道3：异常用于控制流程
try:
    user = get_user(id)
except UserNotFoundError:
    user = create_default_user()  # 用异常做逻辑分支

# ✅ 好味道3：先检查，再操作
user = get_user(id)
if user:
    return user
return create_default_user()
```

## 五、依赖管理评估

### 5.1 依赖注入检查

| 检查项 | ✅ | ❌ |
|--------|----|----|
| Service 通过构造函数注入依赖 | | ❌ 直接 import 全局对象 |
| Repository 通过接口抽象 | | |
| 依赖注入使单元测试可以 Mock | | |
| 无循环依赖（A→B→A） | | ❌ |

### 5.2 循环依赖快速检测

```python
# ❌ 检测循环导入
# a.py
from b import B  # ← 在文件顶部导入

# ✅ 延迟导入解决循环依赖
# a.py
class A:
    def use_b(self):
        from b import B  # ← 在方法内部导入
        return B().do()
```

### 5.3 依赖方向原则

```
依赖只能指向：外层 → 内层
    Router → Service → Repository → Database
    
禁止反向：
    Router → Repository（跳过 Service）
    Service → Router（业务层依赖表现层）
```

## 六、代码重复评估

### 6.1 DRY 检查

| 检查项 | ✅ | ❌ |
|--------|----|----|
| 相同的业务逻辑只出现一次 | | ❌ 重复代码块 > 3 处 |
| 配置值不硬编码在多处 | | ❌ 魔法数字散布 |
| 相似的 if-else 链超过 3 个 → 用策略模式 | | |

### 6.2 魔法数字检查

```python
# ❌ 魔法数字
if user.score > 60:  # 60是什么？
    send_email()
if page > 100:  # 100是什么？
    return []

# ✅ 有名字的常量
PASSING_SCORE = 60
MAX_QUERY_PAGE = 100

if user.score >= PASSING_SCORE:
    send_email()
if page > MAX_QUERY_PAGE:
    return []
```

## 七、安全性评估

### 7.1 Web 安全检查清单

| 检查项 | ✅ | ❌ | 说明 |
|--------|----|----|------|
| SQL 参数化查询 | | ❌ | 防止 SQL 注入 |
| 用户输入校验 | | | |
| 敏感信息（密码/token）不写入日志 | | | |
| 密码哈希存储 | | | |
| 接口有权限校验 | | | |
| 限流保护（防刷） | | | |

### 7.2 推荐系统安全红线

```python
# ❌ SQL 注入风险
user_id = request.args.get("user_id")
query = f"SELECT * FROM users WHERE id = {user_id}"  # 危险！

# ✅ 参数化查询
user_id = request.args.get("user_id")
query = "SELECT * FROM users WHERE id = %s"
db.execute(query, (user_id,))

# ❌ 敏感信息写入日志
logger.info(f"用户登录成功: password={password}")

# ✅ 脱敏日志
logger.info(f"用户登录成功: user_id={user_id}")
```

## 八、可测试性评估

### 8.1 测试友好度清单

| 检查项 | ✅ | ❌ |
|--------|----|----|
| 业务逻辑可以通过 pytest 直接测试 | | ❌ 需要启动整个 Flask |
| 外部依赖（DB/Redis）可以通过 Mock 替换 | | |
| 无硬编码的全局单例（难以 Mock） | | |
| 日期/时间通过参数化或 monkey patch 可控 | | |
| 关键方法有注释说明前置条件/返回值 | | |

### 8.2 测试友好 vs 测试困难代码

```python
# ❌ 测试困难：硬编码时间
class Order:
    def is_expired(self):
        return datetime.now() > self.created_at + timedelta(hours=24)

# ✅ 测试友好：时间可注入
class Order:
    def __init__(self, current_time=None):
        self._now = current_time or datetime.now()
    
    def is_expired(self):
        return self._now > self.created_at + timedelta(hours=24)

# 测试时可以注入固定时间
order = Order(current_time=datetime(2026, 1, 1, 12, 0, 0))
assert order.is_expired() == False
```

## 九、性能意识评估

### 9.1 常见性能问题

| 检查项 | ✅ | ❌ |
|--------|----|----|
| 无 N+1 查询（循环内查数据库） | | ❌ |
| 数据库字段有合适索引 | | |
| 循环内无重复计算 | | |
| 大文件/响应不用一次性加载到内存 | | |
| 外部 API 调用有超时控制 | | |
| 推荐结果有缓存（Redis） | | |

### 9.2 N+1 查询检测

```python
# ❌ N+1 查询：100个用户 = 100次数据库查询
users = db.query(User).limit(100).all()
for user in users:
    print(user.orders.count())  # 每循环查一次！

# ✅ 预加载（JOIN 或 selectinload）
users = db.query(User).options(joinedload(User.orders)).limit(100).all()
for user in users:
    print(user.orders.count())  # 已经加载，不额外查询
```

## 十一、上线前必检清单

### Python（Flask/FastAPI）项目

- [ ] 所有接口有参数校验
- [ ] SQL 查询使用参数化（防注入）
- [ ] 敏感配置从环境变量读取
- [ ] 有全局异常处理（500 不暴露堆栈）
- [ ] 日志级别配置正确（生产 INFO，上线前 DEBUG）
- [ ] 数据库连接有超时和重连机制
- [ ] 外部服务调用有超时（connect + read）
- [ ] 有熔断/降级逻辑（防止级联故障）
- [ ] 关键接口有请求限流
- [ ] 有健康检查接口 `/health`
- [ ] 推荐服务各链路有独立超时配置
- [ ] Redis 连接池配置合理
- [ ] 代码中有 TODO 标记的优先处理

### TypeScript（NestJS）项目

- [ ] 所有 DTO 有 class-validator 装饰器
- [ ] Guard 实现权限校验
- [ ] Interceptor 实现统一响应格式
- [ ] 异常过滤器捕获全局错误
- [ ] 配置文件使用 @nestjs/config + .env
- [ ] 服务间通信有超时和重试
- [ ] 有 E2E 测试覆盖核心流程
- [ ] 编译后无 TypeScript 错误
- [ ] 生产环境关闭 Swagger 文档

## 十二、推荐系统专项质量检查

### 召回层质量

```
检查清单：
□ 所有召回路（热门/协同过滤/Embedding）都有策略抽象
□ 可通过配置切换/开关特定召回路
□ 新增一路召回不需要改核心调度代码（OCP）
□ 召回结果有去重逻辑（user_id + item_id 级别）
□ 召回数量上限可配置
```

### 排序层质量

```
检查清单：
□ 特征获取与排序逻辑分离
□ 特征获取有超时保护（超过 N 秒降级）
□ 模型推理有缓存（热门的 item 特征）
□ 排序结果可解释（日志/调试字段）
□ AB 实验分流逻辑独立
```

### 重排层质量

```
检查清单：
□ 业务规则（去重/打散/曝光过滤）可配置
□ 重排逻辑模块化，不写成面条代码
□ 有完整的推荐理由（展示给用户/运营）
□ 异常不影响返回空结果（降级兜底）
```

## 十三、快速发现代码问题的 5 分钟法

### 第一分钟：看文件大小
```
❌ 超过 500 行的文件 → 必然有问题
✅ 小文件 → 职责单一
```

### 第二分钟：看 import
```
❌ from xxx import *  → 依赖混乱
✅ 明确导入 → 依赖清晰
❌ import 在函数内部 → 可能是循环依赖
```

### 第三分钟：看函数签名
```
❌ 超过 5 个参数 → 违反 SRP
❌ 没有类型注解 → 可读性差
✅ 有返回值类型 → 意图明确
```

### 第四分钟：看异常处理
```
❌ bare except → 吞噬异常
✅ 具体异常类型 → 精确处理
❌ 只 catch 不 log → 排查困难
```

### 第五分钟：看测试文件
```
❌ 没有对应测试文件 → 质量未知
❌ 测试文件存在但只有集成测试 → 可测试性差
✅ 有清晰的单元测试 → 可维护性好
```

## 十四、总结

代码质量不是"完美主义"，而是**降低协作成本**。

| 场景 | 质量要求 |
|------|---------|
| 个人玩具项目 | 能跑就行，不用过度追求 |
| 实习/面试 Demo | 命名清晰 + 基本分层即可 |
| 团队协作项目 | 严格遵循本清单，上线必检 |
| 生产系统 | 满分要求 + 安全 + 监控 + 降级 |

**记住：代码是写给人看的，顺带给机器执行。** 可读的代码才是真正的高质量代码。

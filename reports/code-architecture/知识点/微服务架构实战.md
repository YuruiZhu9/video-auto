## 为什么推荐系统需要微服务？

### 单体架构的痛点

当推荐系统从"玩具项目"成长为千万级请求的在线服务时，单体架构会遭遇经典问题：

| 症状 | 影响 |
|------|------|
| 代码库膨胀（10万行+） | 新人上手周期 3 个月+ |
| 改一个召回算法，全量发布 | 发布风险高，发布频率低 |
| 不同模块资源需求不同 | CPU 密集的排序和 IO 密集的召回抢资源 |
| 某模块 Bug 导致全站不可用 | 可用性差，SLA 难保证 |
| 技术栈升级影响面大 | Python → 新特性迁移成本高 |

### 微服务化收益（针对推荐系统）

```
单体 → 微服务演进路线（推荐系统为例）

┌─────────────────────────────────────────────────┐
│  单体推荐服务（all-in-one）                      │
│  user_id → recall → rank → rerank → response    │
└─────────────────────────────────────────────────┘
                        ↓ 拆分解耦
        ┌───────────────┼───────────────┐
        ↓               ↓               ↓
   召回服务          排序服务        重排服务
   (CPU密集)       (模型推理)      (业务规则)
        ↓               ↓               ↓
   特征服务          模型服务         过滤服务
   (Redis/ES)      (GPU/Triton)    (Redis)
```

**核心收益：**
- ✅ 独立发布：改召回算法只发召回服务，不用动排序
- ✅ 独立扩缩容：白天给排序服务多加机器，晚上给召回服务加
- ✅ 技术多样性：召回用 Python，排序推理用 C++/Triton
- ✅ 故障隔离：排序模型炸了，召回服务还能跑

## 推荐系统的微服务拆分策略

### 核心拆分原则

**DDD 限界上下文（Bounded Context）** 是拆分的天然依据——每个上下文有自己独立的领域模型，不互相直接引用内部对象。

推荐系统的限界上下文：

```
┌──────────────────────────────────────────────────────────────┐
│                     推荐系统限界上下文划分                      │
├────────────────┬─────────────────────┬──────────────────────┤
│    用户域       │      内容域          │     推荐引擎域         │
│ User Context   │   Content Context   │ Recommendation Context│
├────────────────┼─────────────────────┼──────────────────────┤
│ 用户注册/登录   │ 内容发布/审核/标签   │  召回→排序→重排        │
│ 用户画像存储    │ 内容特征提取         │  推荐策略配置           │
│ 用户行为采集    │ 内容质量评分         │  ABTest 实验配置       │
│ 关系链/社交图谱 │  内容池管理          │  曝光/点击数据落库      │
├────────────────┼─────────────────────┼──────────────────────┤
│ 独立技术边界 ✅ │ 独立技术边界 ✅      │ 独立技术边界 ✅          │
│ REST/gRPC通信  │ REST/gRPC通信       │ 内部 RPC 高并发         │
└────────────────┴─────────────────────┴──────────────────────┘
```

### 推荐系统的典型微服务划分

```
推荐系统服务网格
═══════════════════════════════════════════════════════

[客户端] → [API Gateway / BFF]
                    ↓
         ┌──────────┼──────────┐
         ↓          ↓          ↓
    [召回服务] [排序服务] [重排服务]
         ↓          ↓          ↓

         ↓          ↓          ↓
    [Redis]   [Triton/GPU]  [Redis]

    [用户域服务] ←── gRPC ──→ [内容域服务]
```

| 服务 | 职责 | 典型技术栈 | QPS 量级 |
|------|------|-----------|---------|
| **API Gateway** | 路由、鉴权、限流 | Kong / Nginx / Spring Cloud Gateway | 10万+ |
| **召回服务** | 多路召回家口 | Python / Go | 5万+ |

| **重排服务** | 多样性/商业干预 | Python / Go | 5万+ |

| **用户域服务** | 用户画像/关系链 | Python / Go + MySQL + Redis | 3万+ |
| **内容域服务** | 内容池/标签 | Python + Elasticsearch | 5万+ |

## 核心架构模式

### 模式一：API Gateway（统一入口）

**解决什么问题：** 客户端不想知道后端有多少个服务，每个服务各自鉴权、限流。

```python
# Python + FastAPI 实现简单网关
from fastapi import FastAPI, HTTPException, Request
from fastapi.responses import JSONResponse
import httpx
import time

app = FastAPI()

# 服务注册表（生产环境用 Consul / Nacos / etcd）
SERVICES = {
    "recall":    "http://recall-svc:8001",
    "rank":      "http://rank-svc:8002",
    "rerank":    "http://rerank-svc:8003",
    "user":      "http://user-svc:8004",
    "content":   "http://content-svc:8005",
}

# 限流器（滑动窗口）
class RateLimiter:
    def __init__(self, max_calls: int, period: float):
        self.max_calls = max_calls
        self.period = period
        self.calls = []

    def is_allowed(self, client_id: str) -> bool:
        now = time.time()
        self.calls = [t for t in self.calls if now - t < self.period]
        if len(self.calls) >= self.max_calls:
            return False
        self.calls.append(now)
        return True

rate_limiter = RateLimiter(max_calls=100, period=1.0)  # 100 req/s

@app.api_route("/recommend/{scene}/{user_id}")
async def recommend(scene: str, user_id: int, request: Request):
    # 1. 鉴权
    token = request.headers.get("Authorization", "")
    if not verify_token(token):
        raise HTTPException(401, "Unauthorized")

    # 2. 限流
    client_ip = request.client.host
    if not rate_limiter.is_allowed(client_ip):
        raise HTTPException(429, "Too Many Requests")

    # 3. 路由到具体服务（这里简化为网关聚合调用）
    async with httpx.AsyncClient(timeout=10.0) as client:
        # 并行调用召回 + 用户画像 + 内容
        recall_task   = client.post(f"{SERVICES['recall']}/recall", json={"user_id": user_id, "scene": scene})
        user_task     = client.get(f"{SERVICES['user']}/profile/{user_id}")
        content_task  = client.post(f"{SERVICES['content']}/batch_info", json={"scene": scene})

        recall_resp, user_resp, content_resp = await asyncio.gather(
            recall_task, user_task, content_task
        )

        candidates = recall_resp.json()["items"]
        user_profile = user_resp.json()
        contents = content_resp.json()["items"]

        # 4. 调用排序
        rank_resp = await client.post(
            f"{SERVICES['rank']}/rank",
            json={"user_id": user_id, "candidates": candidates, "user_profile": user_profile}
        )
        ranked = rank_resp.json()["ranked"]

        # 5. 调用重排
        rerank_resp = await client.post(
            f"{SERVICES['rerank']}/rerank",
            json={"items": ranked, "scene": scene}
        )

    return rerank_resp.json()
```

### 模式二：服务间通信（同步 vs 异步）

#### 同步通信：gRPC

**适用场景：** 需要实时结果的调用，如召回→排序→重排的调用链。

```protobuf
// recall.proto（Protocol Buffers 定义）
syntax = "proto3";
package recommend;

service RecallService {
  rpc Recall(RecallRequest) returns (RecallResponse);
  rpc BatchRecall(BatchRecallRequest) returns (BatchRecallResponse);
}

message RecallRequest {
  int32 user_id = 1;
  string scene = 2;
  repeated string strategies = 3;  // ["item_cf", "embedding"]
  int32 limit = 4;
}

message RecallResponse {
  repeated int32 item_ids = 1;
  map<string, float> item_scores = 2;  // item_id → score
}

message BatchRecallRequest {
  repeated int32 user_ids = 1;
  string scene = 2;
  int32 limit = 3;
}
```

```python
# Python gRPC 服务端实现
import grpc
from concurrent import futures
import recall_pb2, recall_pb2_grpc

class RecallServicer(recall_pb2_grpc.RecallServiceServicer):
    def __init__(self, recall_engine):
        self.recall_engine = recall_engine

    def Recall(self, request, context):
        item_ids = self.recall_engine.recall(
            user_id=request.user_id,
            scene=request.scene,
            strategies=list(request.strategies),
            limit=request.limit
        )
        return recall_pb2.RecallResponse(
            item_ids=item_ids,
            item_scores={str(i): 0.9 for i in item_ids}  # 简化
        )

# 启动服务
server = grpc.server(futures.ThreadPoolExecutor(max_workers=10))
recall_pb2_grpc.add_RecallServiceServicer_to_server(RecallServicer(), server)
server.add_insecure_port('[::]:50051')
server.start()
```

### 模式三：服务注册与发现（Consul / etcd）

**解决什么问题：** 服务 IP 是动态的，新增节点不能让调用方改配置。

```python
# 基于 Consul 的服务发现客户端
import requests
import random

class ServiceDiscovery:
    def __init__(self, consul_url: str = "http://consul:8500"):
        self.consul_url = consul_url

    def get_service(self, service_name: str) -> str:
        """获取一个健康的服务实例地址"""
        url = f"{self.consul_url}/v1/health/service/{service_name}"
        resp = requests.get(url, params={"passing": True})
        nodes = resp.json()
        if not nodes:
            raise RuntimeError(f"No healthy nodes for {service_name}")
        # 简单负载均衡：随机
        node = random.choice(nodes)
        addr = node['Service']['Address']
        port = node['Service']['Port']
        return f"http://{addr}:{port}"

    def get_all_services(self, service_name: str) -> list[str]:
        """获取所有健康实例（用于批量调用）"""
        url = f"{self.consul_url}/v1/health/service/{service_name}"
        resp = requests.get(url, params={"passing": True})
        nodes = resp.json()
        return [
            f"http://{n['Service']['Address']}:{n['Service']['Port']}"
            for n in nodes
        ]


# 使用服务发现，而非硬编码地址
discovery = ServiceDiscovery()
rank_service_addr = discovery.get_service("rank-svc")
# rank_service_addr = "http://10.0.1.23:8002"（动态获取）
```

### 模式四：熔断器（Circuit Breaker）

**解决什么问题：** 某个下游服务挂了，如果一直重试，会把调用方也拖死。

```
状态机：Closed(正常) → Open(熔断) → HalfOpen(探测)

Closed: 正常调用，失败率 < threshold → 继续
    ↓ 失败率超阈值
Open: 直接返回降级结果，不发请求
    ↓ 等待超时
HalfOpen: 允许 1 个请求试探，成功 → Closed，失败 → Open
```

```python
import time
from functools import wraps

class CircuitBreaker:
    def __init__(self, failure_threshold: int = 5, timeout: float = 60.0):
        self.failure_threshold = failure_threshold
        self.timeout = timeout
        self.failures = 0
        self.last_failure_time = None
        self.state = "closed"  # closed / open / half_open

    def call(self, func, *args, **kwargs):
        if self.state == "open":
            if time.time() - self.last_failure_time > self.timeout:
                self.state = "half_open"
            else:
                return self._fallback()

        try:
            result = func(*args, **kwargs)
            self._on_success()
            return result
        except Exception as e:
            self._on_failure()
            raise e

    def _on_success(self):
        self.failures = 0
        self.state = "closed"

    def _on_failure(self):
        self.failures += 1
        self.last_failure_time = time.time()
        if self.failures >= self.failure_threshold:
            self.state = "open"

    def _fallback(self):
        """降级：排序服务挂了时返回默认结果"""
        return {"items": [], "fallback": True, "reason": "rank_service_circuit_open"}


# 使用：保护 rank-svc 调用
rank_breaker = CircuitBreaker(failure_threshold=5, timeout=30.0)

async def get_ranked_items(candidates: list[int], user_id: int):
    try:
        return await rank_breaker.call(
            rank_client.predict, candidates, user_id
        )
    except Exception:
        return rank_breaker._fallback()
```

#### 1. 召回服务（recall-svc）

```python
# recall_service/main.py
from fastapi import FastAPI
from pydantic import BaseModel
import asyncio

app = FastAPI()

class RecallRequest(BaseModel):
    user_id: int
    scene: str
    strategies: list[str] = ["item_cf"]
    limit: int = 100

@app.post("/recall")
async def recall(req: RecallRequest):
    # 并行执行多路召回
    tasks = []
    if "item_cf" in req.strategies:
        tasks.append(recall_item_cf(req.user_id, req.limit))
    if "embedding" in req.strategies:
        tasks.append(recall_embedding(req.user_id, req.limit))
    if "user_cf" in req.strategies:
        tasks.append(recall_user_cf(req.user_id, req.limit))

    # 并行等待结果
    results = await asyncio.gather(*tasks, return_exceptions=True)
    all_items = []
    for r in results:
        if isinstance(r, Exception):
            continue
        all_items.extend(r)

    # Merge + 去重 + 取 Top-K
    merged = merge_and_rank(all_items, topk=req.limit)
    return {"items": merged, "strategy_count": len(req.strategies)}

async def recall_item_cf(user_id, limit):
    # 实际调用 ItemCF 组件
    return list(range(1000, 1000 + limit))

async def recall_embedding(user_id, limit):
    # 调用 ANN 索引服务
    return list(range(2000, 2000 + limit))

async def recall_user_cf(user_id, limit):
    return list(range(3000, 3000 + limit))

def merge_and_rank(all_items: list, topk: int) -> list[int]:
    """多路召回合并，按分数排序取 topk"""
    score_map = {}
    for item in all_items:
        score_map[item] = score_map.get(item, 0.0) + 1.0
    return sorted(score_map.keys(), key=score_map.get, reverse=True)[:topk]
```

```python
    """MMR 多样性算法：平衡相关性和多样性"""
    if not items:
        return items
    selected, remaining = [items[0]], items[1:]
    for item in remaining:
        # 找与已选商品相似度最低的
        min_sim = min(sim(item, s) for s in selected)
        if item["score"] * (1 - weight) + min_sim * weight > selected[-1]["score"]:
            selected.append(item)
```

## 服务间通信协议对比

| 维度 | REST (HTTP/JSON) | gRPC | Kafka/RabbitMQ |
|------|-----------------|------|----------------|
| **通信方式** | 同步 | 同步 | 异步 |
| **性能** | 中等（JSON 序列化开销） | 高（Protocol Buffers 二进制） | 高（异步吞吐） |
| **适用场景** | 外部 API、BFF 层 | 服务内部调用链 | 事件通知、数据同步 |
| **调试难度** | 低（可 curl） | 中（需要 proto 工具） | 高（需要 Kafka 工具） |
| **推荐系统适用** | ✅ 外部入口 | ✅ 召→排→重 调用链 | ✅ 行为事件、缓存刷新 |

## 常见误区

### 误区 1：过度拆分

**表现：** 每个小功能都拆成独立服务（一个服务只查数据库），结果是几十个服务，调用链深度 10 层+，网络开销巨大。

**判断标准：** 如果两个组件总是同时发布、共享数据库，且拆分后没有独立扩缩容需求，就不要拆。

**推荐：** 优先按 DDD 限界上下文拆分，不要按"类"拆分。

### 误区 2：服务间直接跨库 JOIN

**表现：** 召回服务直接写 SQL JOIN 用户服务的数据库（`SELECT * FROM recommend_db.user WHERE id = ?`）。

**正确做法：** 通过 API / gRPC 调用，不共享数据库。跨库 JOIN 是微服务的天敌。

### 误区 3：同步调用链过长

**表现：** 推荐请求 → 5个服务串联同步调用，平均延迟 500ms，P99 超过 2 秒。

**优化方向：**
- 非关键路径异步化（详情页内容信息并发拉取）
- 缓存降级（内容详情加 Redis 缓存，排序服务不依赖内容服务）
- 优雅降级（重排服务超时直接返回排序结果）

### 误区 4：没有熔断，上游服务把下游拖死

**正确做法：** 每个远程调用都加熔断器 + 超时 + 重试策略。

```python
# 每个服务调用都要有超时保护
async with asyncio.timeout(5.0):  # 5秒超时
    result = await rank_client.rank(req)
```

## 从单体到微服务演进路线图

```
阶段1（0→1，单体优先）                          时间：0-6月
───────────────────────────────────────────────────────────
→ 用单体快速验证推荐效果
→ 用包（package/namespace）做逻辑分层（recall/ rank/ rerank）
→ 加缓存（Redis）做性能优化
→ 单体可以抗住 1万 QPS

阶段2（增长期，垂直拆分）                        时间：6-18月
───────────────────────────────────────────────────────────
→ 按限界上下文拆分：用户域 / 内容域 / 推荐引擎域
→ 每条链路独立部署、独立扩缩容
→ Kafka 引入事件总线解耦
→ 熔断、限流、监控基础建设

阶段3（成熟期，水平拆分 + 服务治理）             时间：18月+
───────────────────────────────────────────────────────────
→ 推荐引擎内部水平拆分：召回 / 排序 / 重排各自独立
→ 引入 API Gateway（Kong / 自研）
→ Service Mesh（Istio）做流量管理
→ Feature Store 统一特征管理
→ 全链路压测 + 灰度发布
```

> 💡 **建议：** 不要一开始就上微服务。单体架构开发效率高、调试方便，适合快速迭代。当团队规模 > 10 人、单条链路 QPS > 5000、发布频率 > 每天 10 次时，再考虑微服务拆分。

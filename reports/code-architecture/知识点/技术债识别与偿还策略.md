# 技术债识别与偿还策略

> 代码欠的债，业务迟早要还。区别只是利息多少。

## 概念解释

技术债（Technical Debt）最初由 Ward Cunningham 提出，用财务比喻描述软件开发的权衡代价：

- **欠债**：写"够用就行"的代码，而不是"长期最优"的代码
- **利息**：每次在烂代码上改需求，都要额外付出时间和风险
- **还债**：重构，把代码改成它本该有的样子

技术债不是坏事。**故意借债**是为了快速验证业务、抢占市场。问题在于：

1. 借债时没记录——不知道欠了多少
2. 永远不还——利息越滚越大，最终拖垮开发速度
3. 乱还债——还错了地方，白花力气

## 一、技术债的四象限分类

不是所有债都一样重要。用两个维度划分：

| | **有意识欠的** | **无意识欠的** |
|---|---|---|
| **故意的** | ✅ 战略性债（接受） | ❌ 疏忽性债（尽量避免） |
| **无意的** | ⚠️ 权衡性债（承认 + 记录） | 🚨 根本性债（最危险） |

### 1. 战略性债（Strategic Debt）
**明知不完美，但业务优先，先上线再说。**

典型场景：
- MVP 阶段用单体架构，快速验证业务
- 临时硬编码一个字段，等产品确认后再抽象
- 用 SQLite 代替 PostgreSQL，先跑通再说

特征：
- 有明确的偿还计划
- 团队知道这债要还，只是时机未到
- 通常在 Jira/Ticket 里标注了 "tech-debt" 标签

### 2. 权衡性债（Prudent Debt）
**做决定时就知道有取舍，文档里写了 Trade-off。**

典型场景：
- 选了 MySQL 而不是 MongoDB（已知扩展性限制）
- 选 Kafka 而不是自研队列（运维复杂度换开发速度）
- 故意不加缓存，先用数据库硬扛（等流量验证后再优化）

关键动作：**必须记录！** 写进 ADR 或代码注释，否则后人看不懂。

### 3. 疏忽性债（Negligent Debt）
**团队不知道欠了债，不知道这是债。**

典型场景：
- 不知道 SOLID 原则，所以没遵循
- 不了解性能优化，写了 N+1 查询
- 不懂测试，写了紧耦合代码

根源：知识储备不足或经验欠缺。这是**学习的代价**，正常。

### 4. 根本性债（Inadvertent Debt）
**代码写的时候看起来 OK，业务长大后变成坑。**

典型场景：
- 单体架构跑了一年，代码量 10 万行，拆不动了
- 早期没考虑缓存，流量涨 10 倍后数据库扛不住
- 用户量 1000 时没问题，100 万时 ORM 慢成蜗牛

这是最危险的债——**业务规模变化让曾经的"正确"变成了"错误"**。

## 二、推荐系统的五类典型技术债

结合推荐系统工程师的实际场景，对号入座：

### 🏛️ 债1：架构债务 —— 单体变死胖

```
症状自查清单
□ 代码库超过 5 万行，没有任何物理分层
□ 改一个召回策略，要改 3 个以上不相关的文件
□ 新人 onboarding 需要 2 周以上才能上手
□ 每次发版都是全量上线，不敢动老代码
□ 部署时间超过 10 分钟
```

**典型案例**：
- 推荐服务早期没有分层，`app.py` 写了 3000 行，路由/业务/数据库全混在一起
- 召回路和排序路写死在同一个 Service，没有抽象策略接口，每次加新策略都要改核心代码

**利息估算**：
- 每次加新召回策略：5人日（含测试）→ 有架构时：0.5人日
- 每次全量上线风险：1次/2月，每次故障平均 2 小时

### 📦 债2：数据债务 —— 特征Skew无处不在

```
症状自查清单
□ 训练脚本和推理代码用不同的特征处理逻辑
□ 新增特征需要同时改离线 ETL + 在线服务，2周才能上线
□ 特征名字不一致：training 用 `user_gender`，inference 用 `gender`
□ 没有人能说清楚"当前线上用的是哪套特征"
□ 模型训练和模型推理的 Python 版本都不一致
```

**典型案例**：
- 排序模型的离线训练用 Spark 特征工程，在线推理用 Python 手写特征处理，两边逻辑不一致
- 用户性别特征改了枚举值（0/1 → 男/女），训练脚本没同步更新，模型训了 3 周才发现特征全错

**利息估算**：
- 特征 Skew 问题定位：平均 3 人日/次
- 模型重新训练成本：GPU 资源 + 3-7 天实验周期

### 🔧 债3：工程债务 —— 代码坏味道积累

```
症状自查清单
□ 存在大量重复代码（Copy-Paste 修改）
□ 有"上帝类"：某个文件超过 1000 行，变量命名随意
□ 魔法数字：硬编码的阈值散布在各处
□ 注释掉的代码比正常代码还多
□ 函数名和实际行为不符（"get_user" 顺便更新了 last_login）
```

**典型案例**：
- 推荐过滤逻辑里硬编码了 6 个分类 ID（`if category in [1,3,7,12,15,20]`），产品换了一轮运营都不知道这是谁加的
- 模型降级逻辑分散在 4 个文件里，真正的降级条件只有最初写代码的人知道

### ⚙️ 债4：测试债务 —— 零覆盖率的代价

```
症状自查清单
□ 没有单元测试，新增功能靠"手动 Postman"
□ 每次发版前说要测，结果测试时间总是不够
□ 重构恐惧症：不敢动老代码，因为"一动就坏"
□ 有 CI 但没强制覆盖率，新代码随便写
□ 回归测试靠人工，1 个功能要测 20 分钟
```

**利息估算**：
- 手动回归测试：20 分钟/次 × 每周 2 次 × 52 周 = 35 人小时/年
- 线上 Bug 率：无测试 vs 有测试，比例约 3:1

### 📊 债5：可观测性债务 —— 故障靠猜

```
症状自查清单
□ 服务挂了只知道"响应慢"，不知道是召回还是排序还是网络
□ 日志是 print() 散打的，没有任何结构
□ 没有监控大盘，靠客服反馈才知道服务挂了
□ 数据库慢查询没人知道，等用户投诉了才发现
□ 上次故障复盘，没有数据支撑，全靠"我觉得"
```

## 三、技术债量化方法

### 方法1：Interest Rate（利息率）估算

问自己：**每次碰这段代码，比正常多花多少时间？**

| 利息等级 | 描述 | 估算 |
|---------|------|------|
| 🟢 低 | 改一次多花 10% 时间 | 1.1x |
| 🟡 中 | 改一次多花 50% 时间 | 1.5x |
| 🔴 高 | 改一次多花 100%+ 时间 | 2x+ |

### 方法2：SonarQube / 代码分析工具量化

```bash
# SonarQube 量化指标
Code Smells（代码坏味道）：> 50 → 高债
Duplicated Lines（重复代码）：> 3% → 中债
Cognitive Complexity（认知复杂度）：> 15/函数 → 高债
Coverage（测试覆盖率）：< 30% → 高债
```

### 方法3：财务视角 —— 用"利息支出"说服业务

```
技术债成本 = 修改次数 × 利息率 × 单次修改基准时间

举例：
- 某推荐服务中的硬编码过滤逻辑
- 每月修改 2 次（运营换分类）
- 每次因理解成本多花 2 小时
- 利息率 = 2小时
- 年利息支出 = 2次 × 2小时 × 12月 = 48 人小时/年

偿还成本估算：重构约 8 小时
→ ROI = 48 / 8 = 6，6个月回本
```

**用这个公式和业务方沟通，业务能理解 "还债的经济价值"。**

## 四、偿还策略：从"乱还"到"有计划还"

### 策略1：Boy Scout Rule（童子军规则）

> "离开时，让代码比你发现时更干净。"

每次碰一个文件，不管改了什么，**顺手清理周围一小块**：
- 看到一个魔法数字 → 提取成常量
- 看到一个过长函数 → 拆成 2-3 个小函数
- 看到一个重复代码 → 提取成公共函数

**不需要专门开"Sprint"来还债，融入日常开发。**

### 策略2：Strangler Fig Pattern（绞杀者模式）

适合：需要替换核心模块，但不能停服。

```
旧系统（订单模块）
        ↓ 逐渐迁移
新系统（订单模块）  ← 逐步接管流量
```

推荐系统实战应用：
1. 原召回服务基于 ItemCF，新上Embedding召回
2. 初期用 Feature Flag，10% 流量走新召回，90% 走旧召回
3. 灰度到 100% 后，删除旧代码
4. 全程用户无感知

### 策略3：Branch by Abstraction（抽象分支）

适合：长期重构，不能在一条分支上磨太久。

**核心思想**：先引入抽象层，让新旧代码共存，最后删旧代码。

```
Step 1: 引入接口抽象
class RecallStrategy(Protocol):
    def recall(self, user_id: str, count: int) -> list[str]: ...

Step 2: 新旧两套实现并存
ItemCFRecall: 旧实现（保留）
EmbeddingRecall: 新实现（开发中）

Step 3: 用配置切换
config.recall_strategy = "embedding"  # 切到新实现

Step 4: 确认稳定后，删除旧实现
```

### 策略4：Just-In-Time Debt Payment（实时还债）

来自 Microsoft 的经验：在修复 Bug 时，顺手把相关坏味道清掉。

```
发现 Bug → 定位代码 → 发现坏味道 → 顺手重构
         ↓
      Bug 修复 + 代码改善，同时完成

时间增量：约 20%
Bug 再次出现概率：下降 60%（干净代码更易理解）
```

### 策略5：技术债 Sprint（专项迭代）

适合：债务已经严重影响开发速度，需要集中还债。

**推荐节奏**：每季度安排 1-2 周，专门处理技术债。

```
Sprint 规划会议
    ↓
选择 Top 5 高息债（用上面的利息公式排序）
    ↓
每个债：描述 + 偿还方案 + 验收标准
    ↓
执行重构 + 补充测试
    ↓
Code Review + 合并
    ↓
测量：下次碰同样代码，速度提升了？
```

**和业务沟通时**：不叫"技术债还债"，叫"系统性能优化"或"开发效率提升"，业务更容易接受排期。

## 五、推荐系统专项还债路线图

结合你的目标（推荐系统算法工程师），按优先级排序：

### 🔴 高优先级（利息高 + 频率高）

#### 债：训练-服务特征不一致（Data Skew）

```python
# ❌ 问题代码：训练和推理特征处理逻辑分散
# train_feature.py（Spark）
df = df.withColumn("user_age", col("birthday").cast("int"))

# inference_feature.py（Python）
user_age = (today.year - user.birthday.year)  # 逻辑不一致！

# ✅ 还债方案：统一特征服务（Feature Store）
class FeatureService:
    """训练和推理共用同一个特征处理逻辑"""
    def get_user_features(self, user_id: str) -> UserFeatures:
        # 同一个函数，训练和推理都调用
        pass
```

偿还成本：2-3 周（建立统一的 FeatureService）
年利息节省：估算 3 人日/月 × 12 = 36 人日

#### 债：推荐策略硬编码，紧耦合

```python
# ❌ 问题代码：召回路写死
class RecommendationService:
    def recommend(self, user_id):
        # 硬编码的召回路
        items = self.itemcf_recall(user_id)  # 改了要动这里
        if self.user.age < 25:  # 硬编码年龄规则
            items += self.embedding_recall(user_id)
        return self.rerank(items)

# ✅ 还债方案：策略模式 + 配置驱动
class RecommendationService:
    def __init__(self, recall_strategies: list[RecallStrategy]):
        self._recall_strategies = recall_strategies

    def recommend(self, user_id: str, scene: str) -> list[Item]:
        strategies = self._strategy_factory.get(scene)
        items = [s.recall(user_id) for s in strategies]
        return self.rerank(items)
    # 新增召回路：写一个新策略类，配置里注册，零改动核心代码
```

偿还成本：1 周（建立策略抽象）
年利息节省：新增一个召回策略从 5 人日 → 0.5 人日

### 🟡 中优先级（利息中 + 频率中）

#### 债：日志和监控缺失

```
还债方案：
Week 1: 统一日志格式（JSON + request_id）
Week 2: 添加 Prometheus 指标（延迟、错误率、命中率）
Week 3: 搭建 Grafana 看板
Week 4: 写上线前可观测性检查清单

年利息节省：故障定位时间从 2 小时 → 15 分钟
```

#### 债：测试覆盖率 < 30%

```
还债方案（持续改进，不搞运动）：
1. 新增代码覆盖率要求 > 60%（CI 强制）
2. 重点覆盖：召回策略、排序逻辑、降级路径
3. 每次 Bug 修复：先写测试复现，再修 Bug
4. 覆盖率工具：Coverage.py + pytest

年利息节省：估算 Bug 率降低 50%，每次回归测试节省 20h+
```

### 🟢 低优先级（利息低 + 可以忍受）

- 代码风格不统一（用 pre-commit hook 逐步统一）
- 部分类命名不规范（用 IDE 自动重构慢慢改）
- 文档缺失（每次修改代码时顺便更新注释）

## 六、技术债管理流程（落地清单）

### Step 1：债务登记（Debt Registry）

每个团队维护一个 `TECH_DEBT.md`：

```markdown
# 技术债登记

## 高息债（优先处理）

| ID | 描述 | 利息估算 | 偿还方案 | 负责人 | 计划 |
|----|------|---------|---------|-------|------|
| TD-001 | 召回路硬编码 | 5人日/月 | 策略模式抽象 | @张三 | Q2 |
| TD-002 | 特征Skew | 3人日/月 | 统一FeatureService | @李四 | Q2 |

## 中息债（计划处理）

| ID | 描述 | 利息估算 | 状态 |
|----|------|---------|------|
| TD-003 | 日志不统一 | 2人日/月 | 计划Q3 |
```

### Step 2：债务审查（Debt Review）

每个 Sprint 回顾会议里加一个议题：
- "上个 Sprint 里我们制造了哪些新债？"
- "有没有遗漏的债被我们无意中埋下了？"
- "有没有债的利息涨了需要升级优先级？"

### Step 3：还债验收（Debt Repayment Review）

重构完成后，回答：
- [ ] 新代码比旧代码更易测试吗？
- [ ] 下次改同样需求，时间真的缩短了吗？（**用数字说话**）
- [ ] Code Review 通过了吗？
- [ ] 文档更新了吗？

**如果答案是"不知道"，说明没有量化验收标准，还债效果无法评估。**

## 七、与业务沟通的技巧

技术债最大的敌人不是技术难度，是**沟通**。

### 错误说法 ❌
- "我们要重构代码"
- "代码太烂了，需要重写"
- "系统技术债太重"

### 正确说法 ✅
- "某个功能每次改需要 5 天，我们可以优化到 1 天"
- "上个月的 3 个线上 Bug 都和某块代码相关，优化后预计减少 80%"
- "如果不优化，新功能开发速度会每月降低 15%"

**业务关心的是：效率、速度、成本。技术债用效率损失来量化，才能拿到资源。**

### 价值框架（给管理层）

```
当前状态：推荐系统技术债导致每个新召回策略需要 5 人日
目标状态：策略抽象后，新策略 0.5 人日
价值：
  - 每月可多上线 2 个新策略 → 产品迭代加速
  - 减少 60% 线上故障 → 系统稳定性提升
  - 开发满意度提升 → 人员留存率改善

投入：2 周工程师时间（重构）
ROI：6 个月内回本
```

## 八、常见误区

### ❌ 误区1：所有债都要还
**真相**：低息债（不常改动的代码）不需要还。

硬编码的过滤规则每月改一次，每次多花 30 分钟 → 年利息 6 小时。还债需要 3 天 → 不值得。

### ❌ 误区2：等业务稳定了再还债
**真相**：业务永远不稳定。等下去，债越滚越大，最后改不动。

推荐策略早期就做策略模式抽象，代码量可能只多 200 行。晚了再做，要改 5000 行。

### ❌ 误区3：追求完美重构，一次性还清
**真相**：推荐系统的债没法一次性还清（业务还在跑）。

用 Boy Scout Rule + 专项 Sprint 持续改善，比"革命性重构"安全 10 倍。

### ❌ 误区4：不记录债务，以为"能跑就行"
**真相**：无意识的债最危险。

不知道欠了债 → 不知道风险在哪 → 线上故障时措手不及。

### ❌ 误区5：还债时不写测试
**真相**：没有测试的重构是更大的债。

改完后发现新 Bug，回头找原因的成本比重构本身还高。

## 九、技术债自检清单（每月一次）

复制到自己的笔记里，每月检查：

```
推荐系统技术债自检
═══════════════════════════════════════

【架构债务】
□ 代码库有清晰分层吗？（API / Service / Repository）
□ 召回路和排序路通过接口解耦了吗？
□ 新增一个召回策略需要改几个文件？

【数据债务】
□ 训练和推理的特征处理是同一个函数吗？
□ 特征变更有版本管理吗？
□ 能说清楚"当前线上模型的特征集合"吗？

【工程债务】
□ 魔法数字都提取成常量了吗？
□ 超过 200 行的函数有几个？
□ 有没有"只有写的人自己看得懂"的代码？

【测试债务】
□ 核心召回/排序逻辑有单元测试吗？
□ 上线前必须跑回归测试吗？
□ 改完代码的第一反应是写测试还是 Postman？

【可观测性债务】
□ 每次推荐请求能追踪到召回→排序→重排各阶段耗时吗？
```

## 十、本文核心要点

1. **技术债是工具，不是敌人** —— 借债是为了速度，还债是为了长期效率
2. **区分四类债** —— 战略性（接受）、权衡性（记录）、疏忽性（学习）、根本性（预防）
3. **量化利息** —— 用"每次修改额外耗时 × 修改频率"算出年利息，指导还债优先级
4. **Boy Scout Rule** —— 不需要专门还债，顺手做
5. **Strangler Fig + 抽象分支** —— 适合推荐系统核心模块的安全重构
6. **和业务用数字说话** —— "每月节省 48 人小时" 比"重构"更有说服力
7. **技术债登记制度** —— 不知道欠了多少才是最可怕的

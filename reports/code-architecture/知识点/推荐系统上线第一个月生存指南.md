## 一、上线前：最后的检查窗口

### 1.1 环境区分——三环境原则

**最容易出事的环节：本地 = 测试 = 生产混用**

推荐系统上线事故 TOP1 原因：**测试流量直击生产数据库**。

```
开发环境（dev）   → 个人笔记本，本地 Docker，mock 所有外部依赖
                  → 可以随便跑，不担心影响

预发布环境（staging）→ 生产数据脱敏副本，1:1 镜像配置
                     → 最后一道防线，上线前必须在这里跑通

生产环境（prod）  → 真实流量，真实数据，真实用户
                  → 代码改动必须经过 staging 验证
```

**检查清单**：
- [ ] 所有外部服务（MySQL/Redis/Milvus/Kafka）连接地址写在配置文件，不硬编码
- [ ] staging 使用脱敏数据，user_id/phone/email 必须打码
- [ ] 环境变量 `ENV=prod|staging|dev` 必须作为代码判断依据，不能靠注释区分
- [ ] 发送通知（钉钉/短信）默认不发给真实业务负责人，在 staging 环境下关闭
- [ ] 所有日志中的 `print()` 替换为结构化日志，敏感字段脱敏

### 1.3 数据校验——上线前最后一关

推荐系统最怕上线后发现：**训练数据和推理数据不一致**（Train-Serving Skew）。

```
上线前必做的 5 项数据校验：

1. 特征分布一致性校验
   - 从生产 DB 随机抽样 100 条数据
   - 对比：训练时的特征值 vs 推理时拿到的特征值
   - 工具：自己写 Python 脚本，输出一致性报告

2. 特征类型一致性
   - 训练时 category 是 int，推理时不能是 string
   - 检查：category 字段的 dtype 是否一致

3. 用户冷启动兜底数据
   - 确认：新用户（无行为记录）在数据库中有默认画像
   - 测试：构造 user_id=0 或 user_id=-1 的请求，验证兜底逻辑

4. 物品冷启动兜底数据
   - 确认：新物品（无交互数据）是否能被召回
   - 测试：新物品的 embedding 是否存在于 Milvus

5. 数据管道健康度
   - 确认：Hive/Flink 特征管道的最新更新时间
   - 规则：特征管道延迟 > 1 小时，禁止上线新模型
```

## 二、上线第一周：高频问题急救

### 2.1 第一天：盯盘 48 小时

上线后 48 小时内必须实时监控。以下是「黄金六指标」：

| 指标 | 正常范围 | 危险信号 | 应急处理 |
|------|---------|---------|---------|
| API 成功率 | ≥ 99.5% | < 99% | 检查服务是否重启、Redis 是否宕机 |
| P99 延迟 | < 500ms | > 1s | 检查是否有慢查询、模型推理是否超时 |
| 缓存命中率 | ≥ 90% | < 80% | 检查 Redis 连接、新用户是否过多 |
| 召回非空率 | ≥ 99% | < 95% | 检查 Milvus 服务、向量是否存在 |
| 精排成功数 | = 召回数 | < 50% | 检查模型服务、推理超时配置 |
| 业务指标（CTR） | 与 AB 对照相近 | CTR 下跌 20% | 立即触发降级，查看模型日志 |

**盯盘操作手册**：
```python
# 每 30 分钟检查一次，写入盯盘日志
def health_check():
    results = {
        "api_success_rate": query_prometheus("api_requests_success / api_requests_total"),
        "p99_latency": query_prometheus("http_request_duration_seconds{quantile='0.99'}"),
        "cache_hit_rate": query_prometheus("cache_hits / cache_total"),
        "recall_nonempty_rate": query_prometheus("recall_returned_items > 0 / recall_total"),
        "model_success_rate": query_prometheus("model_inference_success / model_inference_total"),
    }
    
    # 钉钉通知
    for metric, value in results.items():
        threshold = THRESHOLDS[metric]
        if value < threshold:
            send_dingtalk(f"⚠️ {metric}={value} 低于阈值 {threshold}")
    
    return results
```

### 2.2 常见报警处理手册

#### 报警 A：「P99 延迟告警，P99=2.5s」

**排查顺序**（从快到慢）：

```
Step 1：查链路追踪（OpenTelemetry）
  → 打开 Grafana Tracing 面板
  → 找到耗时最长的 span
  → 如果是 model_inference → 说明模型推理慢
  → 如果是 redis_get → 说明缓存出了问题
  → 如果是 mysql_query → 说明数据库慢查询

Step 2：如果是模型推理慢（P99 > 1s）
  → 检查 GPU 利用率（nvidia-smi）
  → 检查模型服务日志，看是否有 OOM
  → 紧急处理：降低 batch_size，或切换到降级模型

Step 3：如果是 Redis 慢
  → 检查 Redis CPU 和连接数（redis-cli info stats）
  → 如果是 big key 查询 → 紧急：热点 key 拆分

Step 4：如果是 MySQL 慢
  → 查慢查询日志（SHOW FULL PROCESSLIST）
  → 如果是 N+1 问题 → 紧急：用 Redis 兜底，跳过 DB 查询
```

#### 报警 B：「召回非空率从 98% 跌到 60%」

**立即做**：
```python
# 第一步：确认是哪个召回通道出了问题
recall_channels = ["embedding_recall", "itemcf_recall", "hot_recall"]
for channel in recall_channels:
    rate = query_prometheus(f'recall_nonempty{{channel="{channel}"}}')
    print(f"{channel}: {rate}")
    if rate < 0.5:
        alert(f"🔴 {channel} 召回失败！")

# 第二步：检查 Milvus 服务健康度
# 命令行：curl http://milvus:9091/health
# 返回 {"status":"healthy"} 则正常

# 第三步：如果 Milvus 正常，检查 embedding 服务
# 紧急降级：禁用 embedding_recall，只保留 itemcf + hot_recall
```

#### 报警 C：「CPU 报警，单机 CPU 99%」

**按顺序处理**：

```
1. 查进程（top 或 htop）
   → 确认是 Python 服务还是其他进程

2. 如果是 Python 推理服务
   → 检查是否有大量请求同时到达（Redis 崩溃导致缓存击穿？）
   → 立即开启限流：每秒最多 N 个请求

3. 如果不是 Python
   → 检查 cron 定时任务（有没有人跑了脏数据清理脚本）

4. 紧急扩容（K8s 环境）
   kubectl scale deployment recommend-api --replicas=4

5. 如果持续 5 分钟无法降载
   → 通知负责人
   → 触发全链路降级（Level 3），返回固定推荐结果
```

### 2.3 模型效果的第一个「坎」

上线第一周，你一定会遇到这个问题：**CTR 比 AB 实验时低了 30%**。

常见原因 + 排查顺序：

```
1. 线上特征和训练特征不一致（最常见！）
   → 用上线前准备的「特征一致性报告」对比
   → 查：推理时哪些特征值和训练时分布差异最大

2. 曝光偏差（Position Bias）未处理
   → 排序靠前的物品天然 CTR 高
   → 新模型可能没有正确处理位置偏置

3. 冷启动用户/物品涌入
   → 查：新用户占比是否超过 30%
   → 解决方案：加强冷启动策略，隔离新用户实验

4. 模型更新后未正确加载
   → 查 ModelVersionManager，确认版本号一致
   → 手动触发一次模型热加载

5. 推荐结果被前端过滤掉了
   → 查前端日志，看实际曝光了多少
   → 可能是类目/品牌过滤导致推荐结果被过滤
```

## 三、上线第一个月：从「能跑」到「能维护」

### 3.1 建立值班机制

**第一周后，和团队一起建立值班表**：

```
值班原则：
- 核心服务 7×24 小时有人响应（可以轮班，但必须有人）
- P0 告警 5 分钟内必须响应
- 非工作时间：手机必须能收到 P0 告警

告警分级：
P0（紧急）：服务完全不可用，5 分钟响应
P1（严重）：部分功能受损，30 分钟响应
P2（一般）：指标异常但无业务影响，工作时间处理
P3（提示）：优化建议，不告警，列入迭代计划
```

**告警优化（第一周必须做）**：

刚上线的系统，告警容易过多（告警疲劳）或过少（漏掉真实故障）。

```
优化告警原则：
1. 告警必须可操作（收到告警 → 知道该做什么）
2. 避免「短信风暴」（同一条告警 5 分钟内不重复发）
3. 告警 + 关联分析（发告警时附上 Grafana 链接）

常用告警阈值（根据实际流量调整）：
- 成功率 < 99.5% → P0
- P99 延迟 > 800ms → P1
- 缓存命中率 < 85% → P1
- 召回非空率 < 97% → P1
- 模型推理错误率 > 1% → P0
```

### 3.2 模型迭代 SOP

推荐系统上线后，模型需要持续迭代。以下是安全迭代的 SOP：

```
模型迭代五步法（每一步都有回滚方案）：

Step 1：离线评估
  → 新模型在 staging 环境用最近 7 天数据评估
  → AUC/CTR 预估 vs 当前生产模型
  → 达标标准：新模型离线指标 ≥ 生产模型 3%（留余量）

Step 2：影子实验
  → 新模型和生产模型并行跑（shadow mode）
  → 只记录结果，不影响线上推荐
  → 观察：新模型输出分布是否正常，无极端值

Step 3：小流量灰度（5% 用户）
  → 开启 AB 实验，5% 新模型 vs 95% 老模型
  → 观察 24 小时：成功率/延迟/CTR 指标
  → 达标标准：新模型无退化，CTR 上涨或持平

Step 4：扩大灰度（30% 用户）
  → 持续观察 24-48 小时
  → 如果 CTR 上涨 ≥ 5%，继续扩量
  → 如果指标下跌，立即回滚

Step 5：全量上线（100%）
  → 新模型稳定运行 24 小时
  → 保留老模型版本（ModelVersionManager），随时可回滚
```

**ModelVersionManager 回滚代码**：
```python
class ModelVersionManager:
    """模型版本管理与回滚"""
    
    def rollback_to_previous(self):
        """紧急回滚：切回上一个稳定版本"""
        current = self.current_version
        previous = self.version_history[-2]  # 倒数第二个版本
        
        # 1. 通知团队
        send_dingtalk(f"🔄 模型回滚中：{current} → {previous}")
        
        # 2. 切换模型版本
        self.model = self.load_model(previous)
        
        # 3. 确认加载成功
        assert self.model is not None
        
        # 4. 全量切换（不回滚，只切换）
        self.current_version = previous
        
        # 5. 记录 ADR
        self.log_adr(f"Emergency rollback: {current} → {previous}")
        
    def rollback_if_degraded(self, metrics: dict, window_minutes=30):
        """
        自动回滚：如果新模型指标持续退化
        metrics: {"ctr": 0.023, "success_rate": 0.998}
        """
        baseline = self.baseline_metrics
        for key, value in metrics.items():
            threshold = baseline[key] * 0.95  # 下跌 5% 即触发
            if value < threshold:
                send_dingtalk(f"⚠️ 指标退化：{key}={value} < 阈值 {threshold}，触发自动回滚")
                self.rollback_to_previous()
                return
```

### 3.3 数据管道的健康维护

推荐系统的命脉是数据管道。第一月常见问题：

**问题 1：特征管道延迟累积**

```
症状：用户上午 10 点的行为数据，晚上 8 点才出现在推荐结果里
原因：Flink/Spark 任务积压，或者 Kafka Lag 过高
处理：
1. 查 Kafka Consumer Lag（kafka-consumer-groups.sh --describe）
2. 如果 Lag > 10 万条 → 重启消费者或增加分区
3. 如果是 Flink 任务挂了 → 查 Flink Dashboard，找到异常日志
```

**问题 2：新物品没有曝光**

```
症状：新上架商品/内容过了 24 小时仍然不在推荐结果里
原因：内容表更新了，但 Milvus 向量库没有同步
处理：
1. 查 Milvus 全量同步任务是否正常运行（cron 日志）
2. 确认新增内容的 embedding 已写入 Milvus
3. 手动触发一次增量同步
4. 如果 Milvus 同步正常 → 检查 ItemCF 召回是否覆盖新品
```

### 3.4 建立自己的「故障日志」

这是最重要但最容易被忽视的习惯。

**每次故障后 24 小时内，必须写故障报告**：

```markdown
# 故障报告：XXXX

**时间**：2026-04-12 14:30 ~ 15:15
**严重程度**：P1
**影响范围**：20% 用户推荐结果降级为兜底策略

## 故障现象
- P99 延迟从 200ms 飙升到 3s
- 召回非空率从 99% 降到 71%

## 根因分析（5 Why 法）
1. 为什么延迟高？→ Milvus 查询超时
2. 为什么 Milvus 超时？→ 昨天部署新版本后内存配置偏低
3. 为什么内存配置偏低？→ 部署脚本里改了资源配置但没通知算法团队
4. 为什么改了配置没通知？→ 没有变更管理制度
5. 为什么没有管理制度？→ 上线太匆忙，忽略了运维规范

## 应急处理
1. 14:32 发现告警，立即提高 Milvus 内存 limit
2. 14:45 服务自动恢复
3. 15:15 确认所有指标恢复正常

## 改进措施
- [ ] 上线前必须走变更审批流程（负责人签字）
- [ ] Milvus 资源配置变更需通知推荐系统负责人
- [ ] 增加 Milvus 内存告警（提前发现）
- [ ] 本次故障加到演练场景，下次测

## 耗时统计
- 故障持续：45 分钟
- 发现到响应：2 分钟
- 应急修复：13 分钟
- 事后复盘：1.5 小时
- 总计损失：约 2 小时
```

**模板下载地址**：建议在 `/workspace/reports/code-architecture/踩坑记录/故障报告模板.md` 创建通用模板。

## 四、生存工具箱

### 4.1 一键健康检查脚本

```python
#!/usr/bin/env python3
"""
推荐系统上线后每日健康检查脚本
用法：python health_check.py
频率：每日上班前 / 值班交接时
"""

import requests
import redis
import pymysql
from datetime import datetime

def check_api_health():
    """检查 API 服务健康度"""
    try:
        r = requests.get("http://recommend-api:8000/health", timeout=5)
        assert r.status_code == 200
        print(f"✅ API 健康：{r.json()}")
    except Exception as e:
        print(f"❌ API 异常：{e}")
        return False
    return True

def check_redis():
    """检查 Redis 连接"""
    try:
        r = redis.Redis(host='redis-prod', port=6379, db=0)
        r.ping()
        info = r.info("stats")
        print(f"✅ Redis 正常：连接数={info['connected_clients']}，命中率={info['keyspace_hits']/(info['keyspace_hits']+info['keyspace_misses']+1):.2%}")
    except Exception as e:
        print(f"❌ Redis 异常：{e}")
        return False
    return True

def check_mysql():
    """检查 MySQL 连接"""
    try:
        conn = pymysql.connect(host='mysql-prod', port=3306, 
                              user='readonly', password='xxx', database='recommend')
        cursor = conn.cursor()
        cursor.execute("SELECT COUNT(*) FROM items WHERE status=1")
        count = cursor.fetchone()[0]
        conn.close()
        print(f"✅ MySQL 正常：在线物品数={count}")
    except Exception as e:
        print(f"❌ MySQL 异常：{e}")
        return False
    return True

def check_recall_quality():
    """检查召回质量（模拟请求）"""
    try:
        r = requests.post(
            "http://recommend-api:8000/api/v1/recommend",
            json={"user_id": 10001, "scene": "home", "num": 10},
            timeout=3
        )
        data = r.json()
        if data["code"] == 0 and len(data["data"]["items"]) > 0:
            print(f"✅ 召回正常：返回 {len(data['data']['items'])} 个物品")
            return True
        else:
            print(f"⚠️ 召回异常：{data}")
            return False
    except Exception as e:
        print(f"❌ 召回失败：{e}")
        return False

if __name__ == "__main__":
    print(f"\n{'='*40}")
    print(f"推荐系统健康检查 | {datetime.now().strftime('%Y-%m-%d %H:%M:%S')}")
    print(f"{'='*40}")
    
    results = {
        "API": check_api_health(),
        "Redis": check_redis(),
        "MySQL": check_mysql(),
        "召回": check_recall_quality(),
    }
    
    print(f"\n{'='*40}")
    passed = sum(results.values())
    total = len(results)
    print(f"检查结果：{passed}/{total} 通过")
    
    if passed < total:
        print("🔴 存在问题，请立即处理！")
        # 发送告警
        requests.post("钉钉Webhook", json={
            "msgtype": "text",
            "text": {"content": f"🔴 推荐系统健康检查失败：{results}"}
        })
    else:
        print("✅ 所有检查通过")
```

### 4.2 常用运维命令速查

**查看服务日志（Podman/Docker）**：

```bash
# 实时查看推荐 API 日志
```

**查看 Kubernetes Pod 状态**：


**查看 Prometheus 告警**：
```bash
# 查看当前告警状态
curl -s "http://prometheus:9090/api/v1/alerts" | jq '.data.alerts[] | select(.state=="firing") | {name: .labels.alertname, severity: .labels.severity}'

curl -s "http://prometheus:9090/api/v1/query?query=recommend_api_success_rate" | jq '.data.result'
```

### 4.3 降级预案检查表

每次值班前，确认以下降级预案可用：

```
□ 1. 模型降级（Level 1）——模型推理失败时
  □ 模型服务进程存活（ps aux | grep inference）
  □ 降级模型已加载（ModelVersionManager.current_version）
  □ 降级后端点正常响应（curl 测试）

□ 2. 召回降级（Level 2）——某个召回通道失败时
  □ 多路召回开关可配置（Feature Flag）
  □ 降级后推荐结果不为空（单元测试验证）
  □ 降级日志正常输出（grep recall_degraded）

□ 3. 全链路降级（Level 3）——服务完全不可用时
  □ 运营固定推荐结果配置存在（Redis key: fallback_recommendations）
  □ 配置可动态更新（不需要重启服务）
  □ 降级触发阈值已配置（连续失败 3 次触发）
```

## 五、第一月避坑总结

### 5.1 致命错误 TOP5（绝对不能犯）

| 排名 | 错误 | 后果 | 预防方法 |
|------|------|------|---------|
| 🔴 1 | 生产数据库密码写在代码里 | 数据泄露，上新闻 | 所有密码存 Vault/密文管理 |
| 🔴 2 | 生产/测试流量混用 | 测试流量污染真实数据 | 严格三环境分离 |
| 🔴 3 | 上线前不做数据校验 | 模型学到错误规律，效果暴跌 | 特征一致性报告必须做 |
| 🔴 4 | 无回滚方案上线新模型 | 模型有问题只能干瞪眼 | ModelVersionManager 必须有 |
| 🔴 5 | 告警全部关闭或全部开启 | 要么漏报，要么告警疲劳 | 告警分级 + P0/P1 必须响 |

### 5.2 第一月必须完成的 10 件事

```
□ 1. 上线前完成特征一致性校验报告
□ 2. 建立 P0/P1/P2 告警分级体系
□ 3. 写完 ModelVersionManager（含回滚）
□ 4. 配置 Grafana 仪表盘（6 个核心面板）
□ 5. 完成第一次模型影子实验
□ 6. 建立值班表（7×24 响应）
□ 7. 整理联系人清单（告知相关人）
□ 8. 上线第一周，每天早会同步状态
□ 9. 完成第一次故障复盘（Post-mortem）
□ 10. 整理自己的故障日志文档（持续更新）
```

### 5.3 成长路径：从「能值班」到「能优化」

```
第 1 个月：能值班，不出事
  → 学会看 Grafana，会查日志，能处理常见告警

第 2-3 个月：能优化，少报警
  → 优化慢查询，消除无效告警，建立自动化运维

第 3-6 个月：能演进，能迭代
  → 设计新的模型架构，推进 MLOps 体系建设

第 6 个月+：能带人，能设计
  → 建立团队规范，指导新人，做架构决策
```

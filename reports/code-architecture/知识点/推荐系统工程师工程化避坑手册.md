## 坑1：训练-推理特征不一致（Train-Serving Skew）

### 症状
- 线下 AUC 0.85，上线后 CTR 反而下降
- 改了一个特征，上线后效果变差
- 模型怎么也复现不出离线效果

### 根本原因
```
训练时：user_profile = query_from_mysql(user_id)   # 用历史全量数据
推理时：user_profile = query_from_cache(user_id)   # 用 Redis 缓存数据（可能过期）
```
两者特征分布不一致，模型学到的是"离线分布"，推理时遇到"在线分布"。

### 真实踩坑案例

```python
# ❌ 踩坑代码：训练和推理用不同的特征获取方式
# train.py - 训练时
def get_user_features(user_id):
    user = db.query("SELECT * FROM users WHERE id = ?", user_id)
    return extract_features(user)  # 全量字段，含所有统计特征

# predict.py - 推理时
def get_user_features(user_id):
    user = cache.get(f"user:{user_id}")  # Redis，只缓存了部分字段
    return extract_features(user)  # 缺字段，补0！
```

### 解决方案：特征注册表 + 统一获取函数

```python
# ✅ 正确做法：特征函数必须同一套
# feature_store.py - 训练和推理共用
class UserFeatureStore:
    def __init__(self, db, cache):
        self.db = db
        self.cache = cache

    def get_user_features(self, user_id: str) -> UserFeatures:
        """训练和推理都用这个函数！"""
        # 优先从缓存读，缓存穿透到数据库
        cached = self.cache.get(f"user:{user_id}")
        if cached:
            return UserFeatures.from_json(cached)

        user = self.db.query("SELECT * FROM users WHERE id = ?", user_id)
        features = self.extract_features(user)

        # 缓存，TTL = 5分钟
        self.cache.setex(f"user:{user_id}", 300, features.to_json())
        return features

    def extract_features(self, user: dict) -> UserFeatures:
        """特征提取逻辑只有这一份！"""
        return UserFeatures(
            age=user["age"],
            gender=user["gender"],
            city=user["city"],
            # 训练时怎么算，推理时也怎么算
            click_7d=self._calc_click_7d(user["click_history"]),
            likes_30d=self._calc_likes_30d(user["like_history"]),
        )
```

### 验证方法：特征签名对比

```python
# 每天跑一次，检测训练特征 vs 推理特征是否一致
def verify_feature_consistency():
    test_users = db.query("SELECT id FROM users LIMIT 100")
```

- [ ] 特征函数只有一份，训练/推理共用

## 坑2：模型推理延迟太高，线上超时

### 症状
- P99 延迟 2 秒， SLA 要求 200ms
- 模型大、特征多、调用链长
- 业务方投诉"推荐太慢"

### 踩坑经历：逐个查特征

```python
# ❌ 踩坑代码：循环查数据库，延迟爆炸
def get_recommendations(user_id):
    user = db.query("SELECT * FROM users WHERE id = ?", user_id)  # 10ms
    items = db.query("SELECT * FROM items LIMIT 100")  # 50ms

    recs = []
    for item in items:
        # 每个 item 都要算相似度，查数据库！
        similar = db.query("SELECT * FROM user_likes WHERE item_id = ?", item.id)  # 5ms × 100
        score = compute_similarity(user, item, similar)
        recs.append((item, score))

    return sorted(recs, key=lambda x: x[1])[:10]
```

### 解决方案：批量特征预加载 + 向量召回

```python
# ✅ 正确做法：批量查询，延迟从 2s → 150ms
async def get_recommendations(user_id: str) -> List[Item]:
    # Step 1: 批量加载用户特征（1次DB查询）
    user = await user_repo.get_user(user_id)  # 10ms

    # Step 2: 并行召回候选集（Redis向量检索，20ms）
    candidate_ids = await recall_engine.recall(
        user_id=user_id,
        user_vector=user.embedding,  # 预计算好的用户向量
        top_k=100
    )

    # Step 3: 批量查询候选集特征（1次DB查询）
    candidates = await item_repo.batch_get(candidate_ids)  # 30ms

    # Step 4: 精排（批量推理，80ms）
    scores = await rank_model.predict(candidates, user)  # batch推理

    return top_k(candidates, scores, k=10)

# 总延迟：10 + 20 + 30 + 80 = 140ms ✅
```

### 推理优化三板斧

| 优化手段 | 效果 | 适用场景 |
|---------|------|---------|
| **批量推理** | 单次→批量，GPU利用率提升 5x | 精排、重排 |
| **向量召回** | 全表扫描→ANN搜索，100items 50ms→5ms | 召回层 |
| **缓存** | 计算→查表，延迟降低 90% | 用户特征、热门内容 |

### 监控指标
```python
# 推理延迟必须监控
LATENCY_BUCKETS = [10, 25, 50, 100, 200, 500, 1000, 2000]  # ms
# 告警规则：P99 > 200ms → 触发熔断 + 告警
```

## 坑3：AB实验设计错误，白做实验

### 症状
- 新策略 AB 测效果提升 5%，扩大流量后反而下降
- 实验组和对照组分布不均（辛普森悖论）
- 多指标同时看，互相矛盾

### 踩坑案例：只看 CTR 不看其他指标

```python
# ❌ 踩坑：只优化 CTR，忽略了留存率
# 新策略让用户多点击，但都是无效点击，留存反而下降

# 指标必须同时看：
metrics = {
    "ctr": click / impression,
    "cvr": purchase / click,       # 转化率（商业价值）
    "retention_d1": dau_d1 / dau,  # 次日留存（用户价值）
    "avg_session": session_time / sessions,  # 平均时长
}
```

### 解决方案：分层实验 + 多指标评估

```python
# ✅ 正确做法：分层正交实验
# 召回策略实验（Layer 1）和排序策略实验（Layer 2）正交
# 用户被分到哪个实验组，由一致性哈希决定（保证同一用户始终在同一组）

from hashlib import md5

def get_experiment_group(user_id: str, layer: str) -> int:
    """一致性哈希，保证用户体验一致"""
    hash_val = md5(f"{user_id}:{layer}".encode()).hexdigest()
    return int(hash_val[:8], 16) % 100  # 0-99

def is_in_treatment(user_id: str, layer: str, treatment_pct: int) -> bool:
    return get_experiment_group(user_id, layer) < treatment_pct

# 使用示例：
if is_in_treatment(user_id, "recall_v2", 20):  # 20% 流量用新策略
    candidates = recall_v2(user_id)
else:
    candidates = recall_v1(user_id)
```

### AB实验检查清单

| 检查项 | 正确做法 |
|--------|---------|
| 流量分配 | 一致性哈希，同一用户始终在同一组 |
| 分布检查 | 实验前看两组用户画像（城市/年龄/活跃度）是否相似 |
| 指标选择 | 核心指标 1-2 个，次要指标辅助决策 |
| 实验周期 | 至少覆盖一个完整周期（7天），避免周末效应 |
| 统计显著性 | p < 0.05 且实际提升 > 2% 才算有效 |
| 副作用监控 | 新策略对其他业务指标的影响 |

## 坑4：模型更新后效果反而变差（没有灰度 + 回滚）

### 症状
- 新模型 AUC 提升 2%，全量上线后线上效果下降
- 模型更新后没有验证
- 出问题后不知道回滚到哪里

### 踩坑代码

```python

def load_model():
    global model
    model = pickle.load(open("/models/recommender_v2.pkl", "rb"))  # 直接覆盖！

```

### 正确做法：模型版本管理 + 灰度发布

```python
# ✅ 正确做法：版本管理 + 灰度切换
from datetime import datetime

class ModelVersionManager:
    def __init__(self, model_path: str):
        self.model_path = model_path
        self.current_version = None
        self.model = None

    def load_version(self, version: str):
        """加载指定版本模型"""
        path = f"{self.model_path}/model_{version}.pkl"
        if not os.path.exists(path):
            raise FileNotFoundError(f"模型版本 {version} 不存在")
        self.model = pickle.load(open(path, "rb"))
        self.current_version = version
        log.info(f"模型切换到版本: {version}")

    def rollback(self):
        """回滚到上一版本"""
        versions = sorted(os.listdir(self.model_path))
        prev_idx = versions.index(f"model_{self.current_version}.pkl") - 1
        if prev_idx >= 0:
            prev_version = versions[prev_idx].replace("model_", "").replace(".pkl", "")
            self.load_version(prev_version)
            log.warning(f"模型回滚到版本: {prev_version}")
        else:
            log.error("没有可用的历史版本")

# 使用流程：
# 1. 新模型部署到 /models/（不替换旧模型）
# 2. 先用 10% 流量灰度验证
# 3. 监控 P99/错误率/CTR，确认正向
# 4. 逐步扩大到 50% → 100%
# 5. 出问题：manager.rollback() 一键回滚
```

### 模型灰度策略

```
流量分配节奏：
Day 1: 10% 流量，新模型（观察 P99 + CTR）
Day 2: 30% 流量（CTR 稳定正向）
Day 3: 50% 流量（CTR + CVR 双重验证）
Day 4: 100% 流量（旧模型保留 30 天，随时可回滚）
```

## 坑5：实时特征用错（用了未来数据）

### 症状
- 离线训练用到了"当天"的标签数据（数据泄露）
- 模型在离线评估时效果很好，线上却差很多
- 特征里有"当天点击量"，推理时无法获取

### 踩坑案例：数据泄露

```python
# ❌ 踩坑：用当天数据训练（泄露）
def create_training_data():
    # 数据切分错误：训练集用了 2026-04-12 的数据
    # 但测试集也是 2026-04-12，这些数据在训练时已经存在
    # 导致模型"偷看"了答案

    # 正确做法：训练用 T-1 及之前，测试用 T 天
    train_df = df[df["date"] < "2026-04-12"]  # T-1 及之前
    test_df = df[df["date"] == "2026-04-12"]  # T 天

# ❌ 踩坑：实时特征用了"当天"的统计
def extract_features(user):
    return {
        # 这个特征在推理时无法获取（当天数据还没结束）
        "click_today": len(get_clicks(user.id, "2026-04-12")),  # ❌ 数据泄露
        # 正确做法：用 T-1 的数据
        "click_yesterday": len(get_clicks(user.id, "2026-04-11")),  # ✅
    }
```

### 正确做法：时间感知的特征设计

```python
# ✅ 正确做法：特征和标签的时间对齐
class FeaturePipeline:
    def extract_features(self, user_id: str, date: str) -> dict:
        """
        date: 特征计算的截止日期
        确保推理时的特征在训练时也能计算出来
        """
        return {
            # 时间窗口固定，不包含当天
            "click_7d": self._sum_clicks(user_id, date, days=7),    # 过去7天
            "like_30d": self._sum_likes(user_id, date, days=30),   # 过去30天
            # 不包含"今天"，避免数据泄露
        }

    def create_train_data(self):
        # 每天凌晨处理前一天的数据
        for date in date_range("2026-01-01", "2026-04-11"):
            # 用 T-1 的特征，预测 T 天的标签
            features = self.extract_features(user_id, date)  # date 是 T-1
            label = self.get_label(user_id, date_plus(date, 1))  # label 是 T 天
            yield features, label
```

## 坑6：代码没有测试，模型更新全靠"感觉"

### 症状
- 代码改了，没法验证对不对
- 模型更新后不知道效果变好还是变差
- 上线后发现 bug，只能回滚

### 算法工程师测试重点

```python
# ✅ 最小测试集：推荐系统必测4项
class TestRecommendation:
    def test_recall_not_empty(self):
        """召回层：必须有结果返回"""
        recs = recall_engine.recall(user_id="test_user", top_k=10)
        assert len(recs) > 0, "召回结果为空"

    def test_recall_diversity(self):
        """召回层：结果不能全是一样的类目"""
        recs = recall_engine.recall(user_id="test_user", top_k=20)
        categories = {r.category_id for r in recs}
        assert len(categories) >= 3, "召回结果类目太少，无多样性"

    def test_rank_score_order(self):
        """排序层：得分高的排在前面"""
        items = [Item(id="1", score=0.9), Item(id="2", score=0.3)]
        ranked = rank_model.sort(items)
        assert ranked[0].score >= ranked[1].score

    def test_feature_extraction_consistency(self):
        """特征层：训练和推理特征一致"""
        train_feat = extract_features("user123", train_env=True)
        serve_feat = extract_features("user123", prod_env=True)
        assert train_feat == serve_feat, "特征不一致！"
```

## 推荐系统工程师工程化自检清单

### 上线前必查（Checklist）

```
代码质量
□ 所有函数有单元测试，覆盖核心逻辑
□ 训练/推理特征函数是同一套代码
□ 没有硬编码（配置都放 config.yaml 或环境变量）
□ 异常都有处理，不允许裸异常

性能
□ 推理 P99 < 200ms（SLA 要求）
□ 批量特征查询，无 N+1 查询
□ 缓存命中率 > 90%（热点数据）
□ 模型推理有超时保护（200ms 超时熔断）

监控
□ 模型效果指标可监控（AUC/CTR/CVR）
□ 延迟可监控（P50/P99/P999）
□ 特征分布可监控（特征均值/方差）
□ 模型更新有告警

流程
□ 模型版本化管理（可回滚）
□ 新模型灰度发布（10% → 30% → 50% → 100%）
□ AB实验设计正确（分层正交、足够样本）
□ 文档齐全（接口文档、架构图、部署文档）
```

# 数据库选型与推荐系统全链路实战

> 推荐系统是"数据的加工流水线"，选错数据库就像用卡车运快递——能跑，但代价巨大。

## 概念解释

推荐系统的数据有两类：
- **结构化数据**：用户画像、物品属性、订单日志（关系强，需要事务）
- **特征数据**：用户行为序列、Embedding、实时统计（量大，需要 OLAP 分析）

不同的数据特征，对应不同的存储选型。选型错误是最常见的性能根因之一。

## 选型决策树

```
推荐请求到达
    │
    ├── 需要事务（写入用户行为、扣减库存）？
    │   ├── Yes → 关系型：MySQL / PostgreSQL
    │   └── No ↓
    │
    ├── 数据量大（>1000万行）且需要分析？
    │   ├── Yes → OLAP：ClickHouse / Apache Doris
    │   └── No ↓
    │
    ├── 需要毫秒级读取 + 简单数据结构？
    │   ├── Yes → Redis / Memcached
    │   └── No ↓
    │
    └── 需要向量检索（Embedding 最近邻）？
        ├── Yes → Milvus / Qdrant / Pinecone
        └── No → MySQL / PostgreSQL
```

### 正例（连接池 + Repository 模式 + 参数化查询）

```python
# good.py —— Repository 模式 + 连接池
import pymysql
from dbutils.pooled_db import PooledDB
from dataclasses import dataclass
from typing import Optional

# === 连接池（全局单例，启动时初始化）===
_pool = PooledDB(
    creator=pymysql,
    maxconnections=20,
    mincached=5,
    host="10.0.1.5",
    port=3306,
    user="rec_app",
    password="encrypted_password_here",  # 不要写在代码里，用环境变量！
    database="rec_system",
    charset="utf8mb4",
    autocommit=False,
)

# === 领域对象 ===
@dataclass
class UserProfile:
    user_id: int
    nickname: str
    age_group: str          # "18-24" / "25-34" / ...
    gender: str             # "M" / "F" / "unknown"
    city_level: str          # "tier1" / "tier2" / "tier3"
    interest_tags: list[str] # ["数码", "美妆", "运动"]

@dataclass
class ItemInfo:
    item_id: int
    title: str
    category_id: int
    tags: list[str]
    popularity_score: float
    price: float

# === UserProfileRepository ===
class UserProfileRepository:
    def find_by_id(self, user_id: int) -> Optional[UserProfile]:
        with _pool.connection() as conn:
            with conn.cursor(pymysql.cursors.DictCursor) as cur:
                cur.execute(
                    "SELECT user_id, nickname, age_group, gender, city_level, interest_tags "
                    "FROM user_profile WHERE user_id = %s",
                    (user_id,)
                )
                row = cur.fetchone()
                if not row:
                    return None
                # interest_tags 存的是 JSON 字符串
                import json
                return UserProfile(
                    user_id=row["user_id"],
                    nickname=row["nickname"],
                    age_group=row["age_group"],
                    gender=row["gender"],
                    city_level=row["city_level"],
                    interest_tags=json.loads(row["interest_tags"]) if row["interest_tags"] else [],
                )

    def batch_find(self, user_ids: list[int]) -> dict[int, UserProfile]:
        """批量查询，避免 N+1 问题"""
        if not user_ids:
            return {}
        with _pool.connection() as conn:
            with conn.cursor(pymysql.cursors.DictCursor) as cur:
                placeholders = ",".join(["%s"] * len(user_ids))
                cur.execute(
                    f"SELECT user_id, nickname, age_group, gender, city_level, interest_tags "
                    f"FROM user_profile WHERE user_id IN ({placeholders})",
                    user_ids
                )
                import json
                result = {}
                for row in cur.fetchall():
                    result[row["user_id"]] = UserProfile(
                        user_id=row["user_id"],
                        nickname=row["nickname"],
                        age_group=row["age_group"],
                        gender=row["gender"],
                        city_level=row["city_level"],
                        interest_tags=json.loads(row["interest_tags"]) if row["interest_tags"] else [],
                    )
                return result

    def update_interest_tags(self, user_id: int, tags: list[str]) -> bool:
        import json
        with _pool.connection() as conn:
            with conn.cursor() as cur:
                affected = cur.execute(
                    "UPDATE user_profile SET interest_tags = %s, updated_at = NOW() WHERE user_id = %s",
                    (json.dumps(tags), user_id)
                )
                conn.commit()
                return affected > 0
```

### 推荐系统在 MySQL/PG 中的表设计原则

| 原则 | 说明 | 反例 | 正例 |
|------|------|------|------|
| 不要用 TEXT 存 JSON | 索引失效，查询慢 | `profile TEXT` | `tags JSON` + 虚拟列 |
| 分页用游标不用 OFFSET | OFFSET 大时越来越慢 | `LIMIT 10000, 20` | `WHERE id > 10000 LIMIT 20` |
| 热点字段加索引 | 每次推荐都要查用户画像 | 无索引 | `INDEX idx_user_city (user_id, city_level)` |
| 分库分表要提前规划 | 千万级数据不分表会爆炸 | 单表 5000 万行 | 按 user_id % 64 分 64 张表 |
| 不存 Embedding | MySQL 不擅长向量运算 | `embedding BLOB` | 存 Milvus，外层存原始特征 |

### MySQL 进阶：JSON 列 + 虚拟列实战

```sql
-- 推荐系统用户画像表（PostgreSQL 语法）
CREATE TABLE user_profile (
    user_id      BIGINT PRIMARY KEY,
    nickname     VARCHAR(64),
    age_group    VARCHAR(16),         -- "18-24"
    gender       VARCHAR(8),
    city_level   VARCHAR(16),         -- "tier1"
    -- JSON 列存标签列表（支持 partial update）
    interest_tags JSONB DEFAULT '[]',
    -- 虚拟列：从 JSON 提取第一个标签（可建索引！）
    first_tag    TEXT GENERATED ALWAYS AS (interest_tags->>0) STORED,
    created_at   TIMESTAMP DEFAULT NOW(),
    updated_at   TIMESTAMP DEFAULT NOW()
);

-- 在虚拟列上建索引，支持按标签查询
CREATE INDEX idx_user_first_tag ON user_profile(first_tag);

-- 按标签查用户：直接从索引走，毫秒级
SELECT * FROM user_profile WHERE first_tag = '数码' LIMIT 100;
```

## 二、ClickHouse：推荐系统分析引擎

### 为什么推荐系统需要 ClickHouse

MySQL 存 1000 万行行为日志，统计分析慢到哭：
```sql
-- MySQL 查昨日各品类 CTR：3 秒
SELECT category, COUNTIF(event='click')/COUNT(*) as ctr
FROM click_log WHERE dt = '20260409'
GROUP BY category ORDER BY ctr DESC;

-- ClickHouse 查同样数据：50 毫秒
SELECT category, sum(if(event='click',1,0))/count() as ctr
FROM click_log WHERE toDate(dt) = '2026-04-09'
GROUP BY category ORDER BY ctr DESC;
```

### ClickHouse 表设计核心原则

```sql
-- 推荐系统行为日志：物化视图 + MergeTree 表
CREATE TABLE click_log (
    event_time   DateTime,
    event        Enum8('click'=1, 'view'=2, 'buy'=3, 'cart'=4),
    user_id      UInt32,
    item_id      UInt32,
    category_id  UInt32,
    scene        String,       -- "homefeed" / "search" / "detail"
    platform     String,       -- "ios" / "android" / "web"
    city_level   String,
    dt           String       -- 分区字段：'20260409'
) ENGINE = MergeTree()
PARTITION BY dt              -- 按天分区，查询指定日期只扫描一个分区
ORDER BY (user_id, toDate(event_time), item_id)  -- 主键索引，联合主键
SETTINGS index_granularity = 8192;  -- 索引粒度，越小查询越快但存储越大

-- 创建物化视图：自动计算各场景 CTR（推荐系统核心指标）
CREATE MATERIALIZED VIEW mv_scene_ctr
ENGINE = SummingMergeTree()
PARTITION BY scene
ORDER BY (dt, scene, category_id)
AS SELECT
    dt,
    scene,
    category_id,
    sum(if(event='click', 1, 0))       AS click_cnt,
    sum(if(event in ('click','view'), 1, 0)) AS曝光_cnt
FROM click_log
GROUP BY dt, scene, category_id;

-- 查询示例：某日各场景 CTR
SELECT scene, category_id,
    click_cnt /曝光_cnt AS ctr,
    click_cnt
FROM mv_scene_ctr
WHERE dt = '20260409'
ORDER BY ctr DESC
LIMIT 20;
```

## 三、Redis：缓存与特征存储

### 推荐系统 Redis 三大经典用法

```python
# redis_cache.py
import redis
import json
from typing import Optional

_redis = redis.Redis(host="10.0.1.20", port=6379, db=0, decode_responses=True)

# === 场景1：首页推荐结果缓存 ===
def cache_home_recommendations(user_id: int, items: list[dict], ttl: int = 300):
    key = f"rec:home:{user_id}"
    _redis.setex(key, ttl, json.dumps(items))

def get_cached_home_recommendations(user_id: int) -> Optional[list[dict]]:
    key = f"rec:home:{user_id}"
    data = _redis.get(key)
    return json.loads(data) if data else None

# === 场景2：实时特征缓存（用户最近 N 次行为）===
# 用 Redis List 存行为序列：LPUSH + LTRIM 保持固定长度
def append_user_behavior(user_id: int, item_id: int, event: str):
    key = f"behavior:{user_id}"
    behavior = json.dumps({"item_id": item_id, "event": event, "ts": int(time.time())})
    _redis.lpush(key, behavior)
    _redis.ltrim(key, 0, 49)       # 只保留最近 50 条行为
    _redis.expire(key, 86400)     # 24 小时过期

def get_user_recent_behaviors(user_id: int, limit: int = 20) -> list[dict]:
    key = f"behavior:{user_id}"
    raw = _redis.lrange(key, 0, limit - 1)
    return [json.loads(r) for r in raw]

# === 场景3：Bloom Filter —— 缓存穿透防护 ===
# 判断某个 item_id 是否在推荐结果集合中，防止重复推荐
def build_item_bloom_filter(user_id: int, item_ids: list[int]):
    from bloom_filter import BloomFilter
    bf = BloomFilter(max_elements=10000, error_rate=0.01)
    for item_id in item_ids:
        bf.add(str(item_id))
    # 序列化存 Redis
    key = f"bloom:shown:{user_id}"
    _redis.set(key, bf.tobytes())
    _redis.expire(key, 86400 * 7)   # 7 天去重窗口

def is_item_shown(user_id: int, item_id: int) -> bool:
    key = f"bloom:shown:{user_id}"
    data = _redis.get(key)
    if not data:
        return False
    from bloom_filter import BloomFilter
    bf = BloomFilter.frombytes(data)
    return str(item_id) in bf

# === 场景4：分布式锁 —— 推荐结果一致性保证 ===
def acquire_recommend_lock(user_id: int, ttl: int = 5) -> bool:
    """用户推荐请求加锁，防止缓存击穿时大量并发回源"""
    key = f"lock:rec:{user_id}"
    return _redis.set(key, "1", nx=True, ex=ttl)

def release_recommend_lock(user_id: int):
    _redis.delete(f"lock:rec:{user_id}")
```

## 四、Milvus：向量数据库（Embedding 存储与检索）

### 推荐系统 Embedding 全链路

```
训练阶段：
    Word2Vec / Item2Vec / Graph Embedding → 训练产出 Item Embedding (128维 float)
    ↓
存储阶段：
    每晚 ETL 任务 → 批量写入 Milvus Collection
    ↓
推理阶段：
    用户请求 → 获取用户特征（MySQL）→ 查 Milvus 找相似 Item → 精排 → 返回结果
```

### Milvus Python SDK 完整使用

```python
# milvus_service.py
from pymilvus import connections, Collection, FieldSchema, CollectionSchema, DataType, utility
import numpy as np

class MilvusService:
    def __init__(self):
        connections.connect(host="10.0.1.30", port=19530)

    def create_item_collection(self, collection_name="item_embeddings"):
        """创建物品 Embedding 集合（HNSW 索引，推荐系统召回场景最优）"""
        if utility.has_collection(collection_name):
            utility.drop_collection(collection_name)

        fields = [
            FieldSchema(name="item_id", dtype=DataType.INT64, is_primary=True),
            FieldSchema(name="category_id", dtype=DataType.INT64),
            FieldSchema(name="popularity_score", dtype=DataType.FLOAT),
            # Embedding 字段：128 维 float 向量
            FieldSchema(name="embedding", dtype=DataType.FLOAT_VECTOR, dim=128),
        ]
        schema = CollectionSchema(fields, description="推荐系统物品向量库")
        collection = Collection(name=collection_name, schema=schema)

        # 创建 HNSW 索引（M 值越大精度越高但内存越大，召回场景 M=16 够用）
        index_params = {
            "index_type": "HNSW",
            "metric_type": "L2",          # L2 距离 = 欧氏距离
            "params": {"M": 16, "efConstruction": 200},
        }
        collection.create_index(field_name="embedding", index_params=index_params)
        collection.load()
        return collection

    def insert_embeddings(self, collection_name: str, items: list[dict]):
        """批量插入 Embedding（推荐系统每晚 ETL 使用）"""
        collection = Collection(collection_name)
        entities = [
            [item["item_id"] for item in items],           # item_id
            [item.get("category_id", 0) for item in items],# category_id
            [item.get("popularity_score", 0.0) for item in items],  # popularity
            [item["embedding"] for item in items],        # embedding vectors
        ]
        insert_result = collection.insert(entities)
        collection.flush()
        print(f"插入 {len(items)} 条，primary keys: {insert_result.primary_keys}")

    def search_similar_items(
        self,
        collection_name: str,
        query_vector: list[float],
        top_k: int = 100,
        filter_category_id: int = None,
    ) -> list[dict]:
        """向量检索：给定 Embedding，找到最相似的 Top-K 物品"""
        collection = Collection(collection_name)
        collection.load()

        search_params = {"metric_type": "L2", "params": {"ef": 128}}

        expr = f"category_id == {filter_category_id}" if filter_category_id else None

        results = collection.search(
            data=[query_vector],
            anns_field="embedding",
            param=search_params,
            limit=top_k,
            expr=expr,
            output_fields=["item_id", "category_id", "popularity_score"],
        )

        # 整理结果：[(item_id, distance, category_id, popularity), ...]
        hits = []
        for result in results[0]:
            hits.append({
                "item_id": result.entity.get("item_id"),
                "distance": result.distance,
                "category_id": result.entity.get("category_id"),
                "popularity_score": result.entity.get("popularity_score"),
            })
        return hits

    def search_hybrid(
        self,
        collection_name: str,
        query_vector: list[float],
        boost_category_id: int,
        boost_weight: float = 0.3,
        top_k: int = 100,
    ) -> list[dict]:
        """
        混合检索：向量相似度 + 类目加权
        公式：score = 1/(1+distance) + boost_weight * (category_match ? 1 : 0)
        """
        raw_hits = self.search_similar_items(
            collection_name, query_vector, top_k=top_k
        )
        for hit in raw_hits:
            if hit["category_id"] == boost_category_id:
                hit["score"] = 1/(1 + hit["distance"]) + boost_weight
            else:
                hit["score"] = 1/(1 + hit["distance"])
        return sorted(raw_hits, key=lambda x: x["score"], reverse=True)[:top_k]
```

## 六、选型决策速查表

| 维度 | MySQL / PG | ClickHouse | Redis | Milvus |
|------|-----------|-----------|-------|--------|
| **推荐系统用途** | 用户画像、物品属性 | 行为日志分析、CTR统计 | 推荐缓存、实时特征、会话 | Embedding 存储与检索 |
| **数据规模** | 千万级 | 十亿级 | GB 级热点数据 | 百万~十亿向量 |
| **延迟要求** | 10-100ms | 50ms~分析查询 | 1-5ms | 10-50ms |
| **查询类型** | 精确查询、事务 | 聚合分析、扫描 | 点查、List 操作 | ANN 向量检索 |
| **是否支持 SQL** | ✅ 原生 | ✅ 扩展 SQL | ❌ Redis 命令 | ⚠️ 标量过滤用 SQL |
| **推荐系统选型优先级** | ⭐⭐⭐ 必须 | ⭐⭐ 分析必备 | ⭐⭐⭐ 性能关键 | ⭐⭐⭐ 召回必备 |
| **单库瓶颈** | 1000万行/表 | 10亿行/表 | 50GB/实例 | 10亿向量/Collection |

## 七、生产避坑指南

### 坑1：MySQL 全表扫描拖垮推荐服务
```sql
-- 反例：LIKE 查询不走索引，数据量大时全表扫描
SELECT * FROM user_profile WHERE interest_tags LIKE '%数码%';

-- 正例：用 JSON 函数 + 虚拟列索引
SELECT * FROM user_profile WHERE first_tag = '数码';  -- 走索引
```

### 坑2：Redis 缓存雪崩（大量 key 同时过期）
```python
# 反例：所有 key 同一 TTL，某一时刻集中过期
_cache.setex(key, 3600, value)

# 正例：TTL 加随机偏移，防止集中过期
import random
_cache.setex(key, 3600 + random.randint(0, 600), value)
```

### 坑3：Milvus 全量向量加载 OOM
```python
# 反例：大量数据一次性 insert + load，内存爆炸
collection.insert(entities)  # 1000万条 → 内存峰值 100GB
collection.load()            # 加载全部向量到内存

# 正例：分区（Partition）+ 按需加载
collection.create_partition("electronics")
collection.create_partition("clothing")
# 只加载需要的分区，而不是全量
collection.load(["electronics"])
```

### 坑4：ClickHouse 写入太快导致合并风暴
```python
# 反例：每秒 1000 条小批量写入，触发频繁后台合并，CPU 打满
for event in events:
    client.execute("INSERT INTO click_log VALUES", [event])

# 正例：批量积累 + 每 1 秒批量写入，降低合并频率
BATCH_SIZE = 1000
buffer = []
for event in events:
    buffer.append(event)
    if len(buffer) >= BATCH_SIZE:
        client.execute("INSERT INTO click_log VALUES", buffer)
        buffer = []
```

## 八、一句话总结

| 数据库 | 核心问题它解决 |
|--------|--------------|
| **MySQL / PostgreSQL** | 强一致性数据：用户信息、物品属性、订单 |
| **ClickHouse** | 海量行为分析：CTR 报表、实验数据、漏斗分析 |
| **Redis** | 速度：推荐缓存、实时特征、会话、锁 |
| **Milvus** | 智能：Embedding 最近邻召回、多模态检索 |

> 💡 **实战建议**：推荐系统早期用 MySQL + Redis 足够；流量上来后引入 ClickHouse 做分析、Milvus 做向量召回。不要过早引入所有组件，边增长边升级。

## 常见误区

- ❌ 在 MySQL 里存 Embedding 向量（向量运算慢，占用大量存储）
- ❌ 所有数据都往 Redis 塞（内存贵，数据大了成本爆炸）
- ❌ ClickHouse 直接对接用户请求（ClickHouse 是 OLAP 查询，不适合高并发点查）
- ❌ Milvus 建完索引就不管了（数据量大后不重建索引，检索精度严重下降）
- ❌ MySQL 不建索引直接上线（用户画像查询 P99 能到 500ms）

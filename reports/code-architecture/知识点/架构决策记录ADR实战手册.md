# 推荐系统架构决策记录（ADR）实战手册

> **什么是 ADR？** Architecture Decision Record，架构决策记录。记录"我们做了什么决定、为什么这么做、考虑了哪些替代方案"。帮助团队积累架构知识，也方便后来者快速理解系统设计。

---

## 一、为什么推荐系统工程师要学 ADR

推荐系统是工程+算法的交叉地带，决策多且影响深远：

| 决策场景 | 影响周期 | 后悔成本 |
|---------|---------|---------|
| 选 MySQL 还是 ClickHouse 存用户行为 | 3-5年 | 极高 |
| 实时特征用 Flink 还是 Spark Streaming | 1-2年 | 高 |
| 模型服务用 Ray Serve 还是 Triton | 1-2年 | 中高 |
| 召回层用 ES 还是向量数据库 | 1-2年 | 中 |
| 缓存用 Redis Cluster 还是 Codis | 6-12月 | 中低 |

**ADR 的核心价值：**
- 📝 把"拍脑袋决策"变成"有据可查的决策"
- 🔍 新人 onboarding 速度提升 3 倍
- 🔄 重构时知道"为什么当初这么设计"
- ⚖️ 技术晋升答辩时有完整的决策依据

### ADR-001: 用户行为数据存储方案选型

**状态：** Accepted  
**日期：** 2026-01-15  
**参与者：** @架构师老王（系统设计）、@数据工程师小李（存储选型）

---

#### 背景

推荐系统需要存储用户行为数据（曝光/点击/购买/收藏/搜索），支撑三大场景：
1. **实时特征计算**：用户最近30分钟的点击商品，用于短期兴趣建模
2. **离线特征计算**：用户30天行为统计特征，如点击率、复购周期
3. **数据挖掘分析**：用户路径分析、漏斗转化、GMV归因

当前方案：所有行为统一存在 MySQL，单表 5000万条/天，查询延迟 500ms+，报表生成要 2 小时。

#### 决策

采用 **MySQL + ClickHouse + Redis 三层架构**：
- **MySQL（业务库）**：实时写入当天行为，支撑实时特征（TTL 7天）
- **ClickHouse（分析库）**：全量历史数据，支撑离线特征和 BI 分析
- **Redis**：当天热点数据缓存，支撑首页推荐 10ms 实时查询

#### 替代方案

### 方案A：纯 MySQL ⭐ 最终选择

**优势：**
- 团队对 MySQL 非常熟悉，开发效率最高
- 事务支持好，数据一致性有保障
- 单表 5000万/天可通过分区表 + 读写分离扛住

**代价：**
- OLAP 查询（聚合、排序）性能差，复杂报表超时
- 历史数据膨胀后全表扫描慢，需要定期归档
- 无法支撑实时 OLAP 场景（如实时大屏）

**适用场景：** 数据量 < 1000万/天，且无复杂 OLAP 需求的早期产品

---

### 方案B：纯 ClickHouse

**优势：**
- OLAP 性能极强，10亿数据聚合查询 < 1秒
- 压缩率高，存储成本只有 MySQL 的 1/5
- 原生支持物化视图，特征计算简单

**代价：**
- 实时写入性能差（ClickHouse 适合批量导入，不适合高频单条写入）
- 事务支持弱，无法做 UPDATE/DELETE 强一致性操作
- 团队学习成本高，运维复杂

**适用场景：** 纯离线分析场景，不适合需要实时写入的推荐系统

---

### 方案C：MySQL + Elasticsearch

**优势：**
- ES 全文检索 + 聚合能力强，行为搜索灵活
- 支持近实时搜索，延迟 < 1秒

**代价：**
- ES 存储成本高，是 MySQL 的 3-5 倍
- 数据一致性弱（主备延迟）
- 运维复杂度高（ES 集群调优困难）

**适用场景：** 搜索驱动的推荐（如垂搜），不是行为分析主场景

---

#### 权衡分析

| 维度 | 方案A（纯MySQL） | 方案B（纯CK） | 方案C（MySQL+ES） | **方案D（MySQL+CK+Redis）⭐** |
|------|----------------|--------------|-----------------|--------|
| 开发成本 | ⭐⭐⭐⭐⭐ 低 | ⭐⭐ 低 | ⭐⭐⭐ 中 | ⭐⭐⭐ 中 |
| 实时写入 | ⭐⭐⭐⭐⭐ 强 | ⭐⭐ 弱 | ⭐⭐⭐ 中 | ⭐⭐⭐⭐ 强 |
| OLAP 查询 | ⭐⭐ 弱 | ⭐⭐⭐⭐⭐ 强 | ⭐⭐⭐ 中 | ⭐⭐⭐⭐ 强 |
| 运维复杂度 | ⭐⭐⭐⭐⭐ 低 | ⭐⭐ 低 | ⭐⭐ 低 | ⭐⭐⭐ 中 |
| 存储成本 | ⭐⭐ 中 | ⭐⭐⭐⭐⭐ 低 | ⭐⭐ 高 | ⭐⭐⭐ 中 |
| 团队熟悉度 | ⭐⭐⭐⭐⭐ 高 | ⭐⭐ 低 | ⭐⭐ 低 | ⭐⭐⭐ 中 |

#### 决策理由

1. **推荐系统行为数据双重需求**：既需要实时写入（MySQL），又需要 OLAP 分析（ClickHouse），两者缺一不可
2. **Redis 缓存解决实时查询痛点**：首页推荐需要 < 20ms 返回，MySQL 直接查 500ms+，Redis 缓存层将 P99 降到 15ms
3. **团队先跑通再优化**：先 MySQL + Redis 快速上线，CQRS 读写分离模式，后期按需加 ClickHouse
4. **历史数据自然归档**：MySQL 只保留 7 天热点数据，ClickHouse 存全量，存储成本可控

#### 后果

**正面：**
- 实时特征查询 P99 从 500ms → 15ms
- BI 报表生成从 2 小时 → 5 分钟
- 支持实时大屏监控 CTR/GMV

**负面（已知 trade-off）：**
- 数据链路变长（MySQL → Canal → Kafka → ClickHouse），延迟增加 1-3 秒
- 需要维护 MySQL → ClickHouse 同步链路，有一定运维成本
- 三套存储系统，团队需要学习 ClickHouse 基础

### ADR-002: 实时用户特征计算引擎选型

**状态：** Accepted  
**日期：** 2026-02-10  
**参与者：** @算法工程师小张（实时特征设计）、@架构师老王（系统评审）

---

#### 背景

推荐系统需要实时计算用户短期兴趣特征：
- **用户最近30分钟内点击/收藏/加购的商品类目**
- **用户最近1小时内的搜索词**
- **商品实时 CTR（过去5分钟滑动窗口）**

当前方案：定时任务每5分钟从 MySQL 批处理，特征延迟最长 5 分钟，用户体验差（点击商品后5分钟才反映到推荐里）。

#### 决策

采用 **Flink + Redis 实时流计算架构**：
- **Flink SQL**：定义实时特征计算逻辑，滑动窗口聚合
- **Redis**：存储最新特征值，TTL 对齐业务周期（如用户特征 TTL=30分钟）
- **Kafka**：行为事件总线，支撑多 Consumer 并行处理

#### 替代方案

### 方案A：定时批处理（现状）

**优势：**
- 实现简单，现有 cron job 改造 2 天完成
- 调试方便，出问题看日志即可
- 资源消耗可预测

**代价：**
- 特征延迟 5 分钟，用户感知"推荐不跟手"
- 短时兴趣捕捉失效（如秒杀、直播场景）
- 5分钟窗口内数据量突增时，批处理压力大

**适用场景：** 特征时效性要求 < 30 分钟的产品（如新闻推荐可以接受）

---

### 方案B：Flink 流计算 ⭐ 最终选择

**优势：**
- 真正实时，延迟 < 1 秒
- 滑动窗口天然支持各种时间粒度聚合
- 状态后端（RockDB）支持增量计算，性能好

**代价：**
- Flink 运维复杂（集群管理、Checkpoint、背压处理）
- Flink SQL 功能有限，复杂逻辑需写 Java/Scala
- 团队需要学习流计算概念（Watermark、EventTime、Window）

**适用场景：** 推荐系统、实时大屏、交易风控（推荐系统必备！）

---

### 方案C：Spark Structured Streaming

**优势：**
- Spark 团队熟悉，学习成本低
- 可以和离线 Spark 特征工程共用代码
- 批流一体（同一套代码支持离线+实时）

**代价：**
- 延迟较高（最小批次 500ms-1s），不适合 < 1s 实时场景
- 状态管理不如 Flink 成熟
- 资源消耗大（Mini-Batch 模式）

**适用场景：** 实时要求 1-5 秒的推荐系统，或与离线批处理共平台的场景

---

#### 权衡分析

| 维度 | 定时批处理 | Flink 流计算⭐ | Spark Streaming |
|------|-----------|--------------|----------------|
| 实时延迟 | 5分钟+ | **< 1秒** | 500ms-1s |
| 开发复杂度 | ⭐⭐⭐⭐⭐ 低 | ⭐⭐⭐ 中 | ⭐⭐⭐⭐ 中低 |
| 运维复杂度 | ⭐⭐⭐⭐⭐ 低 | ⭐⭐ 中 | ⭐⭐⭐ 中 |
| 状态管理 | 无状态 | RockDB强 | RockDB中 |
| 故障恢复 | 重跑批任务 | Checkpoint自动 | Checkpoint自动 |
| 团队熟悉度 | ⭐⭐⭐⭐⭐ 高 | ⭐⭐ 低 | ⭐⭐⭐⭐ 高 |

#### 决策理由

1. **推荐"跟手"体验是核心竞争力**：用户在详情页点击"喜欢"，下一秒推荐里就要体现。5分钟延迟会让转化率明显下降
2. **Flink 在流计算领域最成熟**：Watermark 机制优雅处理乱序事件，Checkpoint 保证 Exactly-Once 语义，工业界事实标准
3. **Redis TTL 自动清理**：不用关心状态过期，Flink 写 Redis 时设置 TTL 即可
4. **未来可扩展**：后续加实时风控、实时 BI 也用同一套 Flink 集群

#### 后果

**正面：**
- 用户实时兴趣特征延迟从 5 分钟 → < 1 秒
- 推荐 CTR 提升约 8%（A/B 测试验证）
- 支持秒杀、直播等实时场景

**负面：**
- Flink 集群运维成本增加
- 需要处理背压（下游 Redis 写入 QPS > 上游消费速度）
- 实时和离线特征口径需要严格对齐（否则出现"特征穿越"bug）

### ADR-003: 召回层向量数据库选型（Milvus vs FAISS vs Elasticsearch）

**状态：** Accepted  
**日期：** 2026-02-28  
**参与者：** @算法工程师小雨（向量检索调研）、@架构师老王

---

#### 背景

Embedding 召回是推荐系统的标配，需要：
- **1000万商品向量**（128维 float32）的 ANN 近似最近邻检索
- **QPS > 500**，P99 < 20ms
- 支持实时新增/删除商品向量（白天在线更新，不允许停机）
- 支持按类目/品牌做预过滤（Category = "手机"）

#### 决策

采用 **Milvus Cluster + Redis 二级索引架构**：
- **Milvus**：向量 ANN 检索核心，支持十亿级向量，分布式部署
- **Redis**：过滤条件的倒排索引（category_id → item_ids），Milvus 先从 Redis 拿候选集再查向量库

#### 替代方案

### 方案A：FAISS（单机/集群）

**优势：**
- Facebook 出品，算法成熟度高
- 纯向量检索，性能极强（CPU/GPU 多版本）
- 部署简单（pip install 即可）

**代价：**
- 不支持在线更新（新增向量需要全量重建索引）
- 不支持预过滤（无法先按类目过滤再向量检索）
- 分布式版本 FAISS-prod 内部使用，开源版是单机版

**适用场景：** 离线向量索引构建，或向量不经常变化的场景

---

### 方案B：Elasticsearch HNSW ⭐ 最终选择

**优势：**
- 团队熟悉 ES，运维成本低
- 原生支持按字段过滤（HNSW + bool 查询）
- 在线新增向量，无需重建索引
- 支持动态更新（实时新增/删除）

**代价：**
- 向量检索性能不如专用向量库（Milvus / Pinecone）
- 128维向量，1000万量级下 P99 约 30-50ms（比 Milvus 慢 2-3 倍）
- 存储开销大（ES 额外存原始文档）

**适用场景：** 中小规模向量（< 500万），或已有 ES 技术栈的团队

---

### 方案C：Milvus（开源/商业版）

**优势：**
- 专为向量检索设计，性能极强（P99 < 10ms）
- 支持十亿级向量，水平扩展
- 原生支持动态更新（Delete API）
- GPU 加速版本性能更好

**代价：**
- 运维复杂（需要维护 Milvus 集群 + etcd + MinIO）
- 预过滤需要用 Redis/MySQL 做二级索引（Milvus 本身过滤能力弱）
- 团队无 Milvus 使用经验

**适用场景：** 超大规模向量（> 5000万），或对检索延迟有极致要求的场景

---

#### 权衡分析

| 维度 | FAISS | ES HNSW⭐ | Milvus |
|------|-------|---------|--------|
| 1000万向量 P99 | **< 5ms** | 30-50ms | **< 10ms** |
| 在线更新 | ❌ 不支持 | ✅ 支持 | ✅ 支持 |
| 预过滤支持 | ❌ 不支持 | ✅ 原生支持 | ⚠️ 需二级索引 |
| 运维复杂度 | ⭐⭐⭐⭐⭐ 低 | ⭐⭐⭐⭐ 中 | ⭐⭐⭐ 中 |
| 水平扩展 | 需自己实现 | 原生分片 | 原生分片 |
| 团队熟悉度 | ⭐⭐ 低 | ⭐⭐⭐⭐⭐ 高 | ⭐⭐ 低 |

**当前系统 1000万向量规模，P99 30-50ms 完全可以接受（推荐系统召回层 20ms 够用，不是极致优化阶段）**  
**等业务增长到 5000万+ 向量时，再迁移到 Milvus**

#### 决策理由

1. **"够用就好"的务实选型**：当前 1000万向量，P99 30-50ms < 召回链路 200ms 上限，无需追求极致性能
2. **运维优先原则**：ES 团队已经熟悉，不需要额外学习 Milvus，减少生产故障风险
3. **Redis 二级索引解决预过滤**：用 Redis Set 存 category_id → item_ids，先过滤再查 Milvus（如未来迁移），代码改动小
4. **Milvus 作为未来储备**：当前 ES 架构预留 Adapter 接口，未来可切换到 Milvus 只需换实现类

#### 后果

**正面：**
- 召回链路 P99 < 50ms，满足业务 SLO
- 在线更新商品向量，不影响白天业务
- 团队无新学习成本，2周内上线

**负面：**
- 未来扩展到亿级向量时，需要迁移到 Milvus（预计 2-3 个月工期）
- P99 比纯 Milvus 高 2-3 倍，召回质量不变但延迟略高
- Redis 二级索引增加存储（额外约 5GB/天）

### ADR-004: 推荐服务部署架构选型（单体 vs 微服务）

**状态：** Accepted  
**日期：** 2026-03-05  
**参与者：** @全栈工程师阿华、@架构师老王

---

#### 背景

推荐服务需要支撑 DAU 100万用户，当前团队 5 人（2 算法 + 2 后端 + 1 运维）。

业务现状：
- 白天高频调用（推荐首页、猜你喜欢、商品详情推荐）
- 深夜低频调用（< 1% 流量）
- 每周迭代 1-2 次新召回策略/排序模型

#### 决策

**阶段一（当前 0-100万 DAU）：单体分层架构 + Docker Compose 部署**
- 单个推荐服务进程，内部分层（Controller / RecallService / RankingService / RerankService）
- Docker Compose 一键部署，开发/测试/生产环境一致
- 所有召回策略在进程内通过 Strategy Pattern 切换

**阶段二（100-500万 DAU，6-12个月后）：垂直拆分**
- 拆为 3 个服务：用户画像服务、推荐引擎服务、结果存储服务
- 服务间通过 gRPC 通信（同步实时调用）
- Kafka 解耦异步任务（行为上报、特征更新）

**阶段三（500万+ DAU）：水平拆分 + K8s**
- 召回服务独立扩缩（CPU 密集）
- 排序服务独立扩缩（GPU 需求）
- Kubernetes HPA 自动弹性扩缩

#### 替代方案

### 方案A：立即微服务

**优势：**
- 服务独立部署，迭代互不影响
- 故障隔离，单服务挂了不影响全链路
- 技术债少，架构一步到位

**代价：**
- 5 人团队维护 5+ 微服务，运维负担重
- 服务间通信复杂度高（gRPC / 序列化 / 版本兼容）
- 联调周期长（接口契约改动成本大）
- 早期流量小，微服务优势体现不出来

**适用场景：** 团队 > 10 人，且有成熟 DevOps 平台（SRE/容器化/CI-CD）

---

### 方案B：单体架构（永久） ⭐ 最终选择

**优势：**
- 开发效率最高，代码集中，调试方便
- 部署简单，一个 jar / Docker 镜像
- 团队 < 5 人时维护成本最低
- 性能好（进程内调用无网络开销）

**代价：**
- 代码膨胀后难以维护（单文件 > 5000 行）
- 故障不隔离（单服务挂了全挂）
- 无法针对单一模块独立扩缩
- 技术栈单一（无法混用语言）

**适用场景：** 早期产品（DAU < 50万）、团队 < 5 人的 Startup

---

### 方案C：渐进式演进（阶段一单体 → 阶段二微服务）

**优势：**
- 兼顾当前效率和未来扩展性
- 每个阶段只做最小必要改动
- 单体阶段打好分层基础（Strategy Pattern / DI），后期拆分成本低

**代价：**
- 需要提前设计接口（为拆分预留）
- 阶段二拆分有迁移成本
- 需要在单体阶段写好自动化测试（否则拆分时是灾难）

**适用场景：** 推荐系统（算法迭代快，需要快速验证），团队有一定架构规划能力

---

#### 权衡分析

| 维度 | 立即微服务 | 永久单体 | 渐进演进⭐ |
|------|-----------|---------|---------|
| 当前开发效率 | ⭐⭐ 低 | ⭐⭐⭐⭐⭐ 高 | ⭐⭐⭐⭐ 高 |
| 故障隔离 | ⭐⭐⭐⭐⭐ 好 | ⭐⭐ 差 | ⭐⭐⭐⭐ 好 |
| 运维成本 | ⭐⭐ 高 | ⭐⭐⭐⭐⭐ 低 | ⭐⭐⭐ 中 |
| 扩缩灵活性 | ⭐⭐⭐⭐⭐ 高 | ⭐⭐ 差 | ⭐⭐⭐⭐ 中 |
| 团队适合度（5人） | ⭐⭐ 不适合 | ⭐⭐⭐⭐ 适合 | ⭐⭐⭐⭐⭐ 最适合 |

#### 决策理由

1. **团队规模是核心约束**：5人团队微服务 = 每个人都在救火，而不是写业务代码
2. **算法迭代 > 架构完美**：推荐系统核心竞争力是算法效果，不是架构优雅。快速迭代 >> 完美架构
3. **单体分层打好基础**：单体阶段做好 Controller/Service/Repository 分层，Strategy Pattern 实现多路召回，为未来拆分留好接口
4. **演进式架构是业界最佳实践**：Amazon / Netflix 都是从单体演进到微服务，不是设计出来的

#### 后果

**正面：**
- 开发效率最高，算法工程师能快速实验新策略
- 部署简单，2 分钟内完成从代码到生产
- 单体阶段积累的分层代码可直接迁移到微服务

**负面：**
- 单服务 > 3000 行代码后，需要定期重构（每季度一次"代码整理日"）
- DAU 100万后，召回/排序扩缩比例不同（召回 CPU 型，排序 GPU 型），单体无法差异化扩缩
- 需要提前预留服务拆分接口（避免阶段二改动太大）

### ADR-005: 模型推理服务化方案选型（在线模型服务）

**状态：** Accepted  
**日期：** 2026-03-20  
**参与者：** @算法工程师小雨（模型服务调研）、@后端工程师阿华、@架构师老王

---

#### 背景

推荐排序模型（DeepFM，约 500MB）需要在线服务化：
- **日均调用量**：1000万次（QPS ~ 1200）
- **延迟要求**：P99 < 50ms（含特征获取 + 模型推理 + 后处理）
- **可用性要求**：99.9%（每月 < 8.7 小时不可用时间）
- **模型更新频率**：每 6 小时更新一次模型

#### 决策

采用 **Triton Inference Server + Ray Serve 分层架构**：
- **Triton（推理服务器）**：高性能推理引擎，管理模型版本，支持 GPU 批量推理
- **Ray Serve（模型编排）**：模型 A/B 路由、流量分割、模型降级
- **Redis**：推理结果缓存（Pillar Feature 缓存，同一用户 5 分钟内不重复推理）

#### 替代方案

### 方案A：Flask/FastAPI 直接加载模型 ⭐ 最终选择（阶段一）

**优势：**
- 实现最简单，算法工程师直接写，2 天上线
- 模型热更新（替换 .pkl 文件 + reload）
- 支持 CPU 推理（无 GPU 也能跑）

**代价：**
- 并发能力差（同步框架，GIL 限制）
- 模型加载慢（每次启动要加载 500MB）
- 无法利用 GPU（需要自己写 CUDA 代码）
- 无模型版本管理

**适用场景：** QPS < 500、延迟要求 < 200ms、无 GPU 的早期阶段

---

### 方案B：Triton Inference Server ⭐ 最终选择（阶段二）

**优势：**
- NVIDIA 出品，工业级推理服务器
- 原生支持 GPU 批量推理，吞吐量提升 5-10 倍
- 模型版本管理（灰度发布 / A/B 测试内置）
- Dynamic Batching 合并小请求为大批次，降低 GPU 利用率
- 支持 TensorRT / ONNX / PyTorch 多框架

**代价：**
- 部署运维复杂（需要 K8s + GPU 集群）
- 团队无使用经验，学习曲线陡
- 机器成本高（GPU 服务器）

**适用场景：** QPS > 500，延迟要求 < 50ms，有 GPU 资源的生产环境

---

### 方案C：Ray Serve

**优势：**
- 支持模型 A/B 路由和流量分割
- 与 Ray 生态集成（离线训练 → 在线服务）
- 支持 Python-first，开发体验好
- 自动扩缩容（K8s HPA 集成）

**代价：**
- 推理性能不如 Triton（无 TensorRT 优化）
- GPU 利用率低（无 Dynamic Batching）
- 生产稳定性不如 Triton 成熟

**适用场景：** 混合部署（多个模型 + 自定义推理逻辑），或作为 Triton 的补充层

---

### 方案D：vLLM（PagedAttention）

**优势：**
- LLM 推理专用，吞吐量大（H100 可达 10000+ token/s）
- 支持 Continuous Batching，PagedAttention 显存管理优秀

**代价：**
- 推荐系统排序模型不是 LLM（浮点模型），vLLM 优势体现不出来
- 不支持 ONNX/TensorRT 模型

**适用场景：** LLM 驱动的推荐（RAG + LLM 生成推荐理由），不是传统 DeepFM 排序模型

---

#### 权衡分析

| 维度 | Flask⭐阶段一 | Triton⭐阶段二 | Ray Serve | vLLM |
|------|------------|--------------|----------|------|
| 推理性能 | ⭐⭐ 差 | ⭐⭐⭐⭐⭐ 极强 | ⭐⭐⭐ 良 | ⭐⭐⭐⭐ 良 |
| 部署复杂度 | ⭐⭐⭐⭐⭐ 极简 | ⭐⭐⭐ 中 | ⭐⭐⭐ 中 | ⭐⭐⭐ 中 |
| GPU 支持 | ❌ 无 | ✅ 原生 | ✅ 支持 | ✅ 专用 |
| 批量推理 | ❌ 无 | ✅ Dynamic Batching | ⚠️ 有限 | ✅ |
| 模型版本管理 | ❌ 无 | ✅ 内置 | ✅ 支持 | ✅ |
| 团队熟悉度 | ⭐⭐⭐⭐⭐ 高 | ⭐⭐ 低 | ⭐⭐⭐ 中 | ⭐⭐ 低 |
| 适用 QPS | < 500 | > 500 | > 500 | LLM 专用 |

#### 决策理由

1. **阶段一务实，阶段二升级**：先用 Flask 快速验证算法效果，有流量后再升级 Triton
2. **Triton 是工业标准**：推荐系统排序模型用 Triton，面试和团队协作都是共识
3. **Redis 缓存兜底**：不管用什么推理框架，Redis 缓存同类请求（如 5 分钟内相同用户），降低推理压力
4. **Ray Serve 预留为混合场景**：未来如果有 LLM 生成推荐理由的需求，Ray Serve 是最好的编排层

#### 后果

**正面：**
- 阶段一 2 天上线，快速验证算法效果
- Triton 上线后 GPU 吞吐量提升 8 倍，延迟降低 60%
- Redis 缓存减少 40% 推理调用量

**负面：**
- 阶段切换（Flask → Triton）需要一次重构，约 2 周
- Triton 需要申请 GPU 服务器（预算 + 3 个月采购周期）
- 需要维护模型版本（新旧版本并行时的流量分配逻辑）

## 四、如何在团队落地 ADR

### ADR 写作检查清单

```
□ 背景：说清楚为什么需要做这个决策（业务背景 + 技术挑战）
□ 至少 3 个替代方案（包含现状/不作为选项）
□ 每个方案有"优势 + 代价 + 适用场景"
□ 有量化指标（QPS / 延迟 / 成本 / 工期）
□ 决策理由有优先级排序（最重要 → 次要）
□ 明确说出"负面 trade-off"（诚实，不藏掖）
□ 有生效日期和参与者
□ 状态标记：Accepted / Deprecated / Superseded
```

### ADR 生命周期

```
提出（Proposal）
    ↓
评审（Review）→ 技术评审会，架构师 + 相关开发 + 算法同学
    ↓
接受（Accepted）→ 记录在案，开始实施
    ↓
生效（Implemented）→ 标注实现日期
    ↓
归档（Deprecated）→ 被新 ADR 替代时，标记为 Deprecated
```

### ADR 存储方式

推荐用 Markdown + Git 管理：

```
docs/
├── adr/
│   ├── README.md（ADR 索引）
│   ├── 0001-用户行为数据存储选型.md
│   ├── 0002-实时特征计算引擎选型.md
│   ├── ...
```

用 Git 提交记录 + branch 管理 ADR 版本，每条 ADR 独立文件，方便搜索。

### ADR vs 技术设计方案的区别

| | ADR | 技术设计方案 |
|--|-----|-----------|
| 格式 | 固定模板（轻量） | 自由格式（详细） |
| 篇幅 | 1-3 页 | 10-50 页 |
| 目的 | 记录"为什么这么选" | 设计"具体怎么做" |
| 时机 | 决策前/中 | 决策后实施前 |
| 受众 | 团队全体 | 执行开发者 |
| 示例 | "为什么选 Flink 而不是 Spark" | "Flink 实时特征计算详细设计" |

## 五、实战练习

### 练习 1：分析现有系统决策

打开你当前项目的一个核心模块，问自己：
1. 这块是怎么实现的？
2. 有没有替代方案？为什么当时没选？
3. 如果重新选，会选什么？

试着把分析写成一条 ADR。

### 练习 2：下周技术评审

在下次技术评审前，先准备 3 个 ADR 草稿：
1. **ADR-A**：维持现状（不改变）
2. **ADR-B**：小改动方案
3. **ADR-C**：大改动方案

评审会上用 ADR 模板结构陈述，比"我觉得这样好"有说服力 10 倍。

### 练习 3：历史决策补写

翻看你项目的 git log，找到 3 个重要的技术选型 commit：
- 这个决策考虑了哪些因素？
- 当时的 trade-off 是什么？
- 今天的你会不会做不同选择？

把分析写成 ADR，顺便练习写作能力。

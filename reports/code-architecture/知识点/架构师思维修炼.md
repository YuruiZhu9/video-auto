# 架构师思维修炼
> 从写代码到做决策：从"怎么实现"到"为什么这样设计"

---

## 什么是架构师思维？

写代码 vs 做架构的本质区别：

| 维度 | 写代码思维 | 架构师思维 |
|------|-----------|-----------|
| **关注点** | 单个类/函数对不对 | 整个系统的长期健康度 |
| **时间维度** | 今天能跑 | 半年后还能改 |
| **决策依据** | 经验直觉 | 权衡分析 + 约束条件 |
| **失败应对** | 修 bug | 预防性设计 + 降级方案 |

---

## 思维一：权衡分析（Trade-off Analysis）

### 核心观点
**没有最优解，只有最合适的解。**

每个技术选型都有代价，架构师的任务是找出当前约束下"代价最小、收益最大"的方案。

### 推荐系统技术选型权衡表

| 技术选型 | 优势 | 代价 | 适用场景 |
|---------|------|------|---------|
| **MySQL 主从** | 事务可靠 | 读吞吐有限 | 中小规模推荐系统 |
| **MongoDB** | schema 灵活 | 关联查询弱 | 快速迭代期 |
| **Redis 缓存** | 极速读写 | 数据一致性风险 | 高频推荐结果缓存 |
| **ElasticSearch** | 全文搜索强 | 资源消耗大 | 推荐引擎召回层 |
| **Kafka** | 高吞吐异步 | 延迟增加 | 用户行为事件处理 |
| **gRPC** | 高性能二进制 | 学习成本 | 召排重同步调用 |
| **GraphQL** | 按需取字段 | 复杂度增加 | 多端适配 |

### 案例：推荐系统数据库选型

**场景：** 做一个短视频推荐系统，日活 100 万，预计一年内增长 10 倍。

**方案 A：全部用 MySQL**
```
优点：团队熟悉、事务可靠
缺点：短视频内容表字段不固定（多格式、多标签），Schema 改造成本高
```

**方案 B：全部用 MongoDB**
```
优点：字段灵活，迭代快
缺点：用户行为数据分析（JOIN 查询）性能差
```

**方案 C：混合方案（推荐）**
```
MySQL：用户表、账户表（强一致性）
MongoDB：短视频内容表（字段多变）
Redis：推荐结果缓存、Session
ElasticSearch：内容搜索、召回
ClickHouse：行为数据分析
```

**决策理由：**
- 短视频内容变化快 → MongoDB
- 用户数据分析需要 OLAP → ClickHouse
- 高频推荐结果 → Redis
- 用户账户必须可靠 → MySQL

## 思维二：容量规划（Capacity Planning）

### 推荐系统容量估算公式

```
每日数据量 = DAU × 人均推荐次数 × 推荐结果大小

估算案例：
DAU = 1,000,000
人均推荐请求 = 50 次/天
每次推荐结果 = 50 个 item × 1KB ≈ 50KB

每日写入量 = 1,000,000 × 50 × 50KB = 2.5 TB/天（夸张了）
→ 需要考虑缓存策略，不全存
```

### 推荐的系统容量规划步骤

```
第一步：确定核心指标
    DAU、DAU 增长率、人均请求数、推荐结果大小

第二步：估算存储需求
    用户特征：1,000,000 × 1KB = 1GB
    物品特征：10,000,000 × 2KB = 20GB
    行为日志：1,000,000 × 50 × 100B = 5GB/天

第三步：估算 QPS
    假设峰值 QPS = 平均 QPS × 3
    = (1,000,000 × 50) / 86400 × 3 ≈ 1,736 QPS

第四步：选择技术栈和规格
    QPS < 1000：单机能扛
    QPS 1000-10000：需要集群
    QPS > 10000：需要微服务 + 自动扩缩容

第五步：预留 buffer
    存储：× 1.5（考虑历史数据）
    QPS：× 2（考虑突发流量）
```

## 思维三：演进式架构（Evolutionary Architecture）

### 核心理念
**不要一开始就设计完美的架构，而是设计能迭代的架构。**

### 推荐系统三阶段演进

```
阶段一：单体期（0 → 1）
┌────────────────────────────────────┐
│  Flask/FastAPI  单体应用            │
│  ├── 推荐路由（/recommend）         │
│  ├── 召回服务（recall）             │
│  ├── 排序服务（rank）               │
│  └── 重排服务（rerank）             │
└────────────────────────────────────┘
特征：简单快糙猛，先验证业务价值
风险：代码耦合，修改影响面大
下一步：按层拆分

阶段二：分层期（增长期）
┌────────────────────────────────────┐
│           API 网关                  │
│  ┌──────────┐  ┌──────────┐        │
│  │ 召回服务  │  │ 排序服务   │        │
│  └──────────┘  └──────────┘        │
│  ┌──────────┐  ┌──────────┐        │
│  │ 重排服务  │  │ 用户服务   │        │
│  └──────────┘  └──────────┘        │
└────────────────────────────────────┘
特征：垂直拆分（按功能域），独立部署
风险：跨服务调用复杂，数据一致性
下一步：按限界上下文拆分

阶段三：微服务期（成熟期）
┌────────────────────────────────────┐
│           API 网关                  │
│  ┌────────────┐  ┌────────────┐    │
│  │ 用户域微服务 │  │ 内容域微服务 │    │
│  │ (用户/画像)  │  │ (短视频/UGC) │    │
│  └────────────┘  └────────────┘    │
│  ┌────────────┐  ┌────────────┐    │
│  │推荐引擎域   │  │ 数据域      │    │
│  │(召/排/重)  │  │(Kafka/ES)  │    │
│  └────────────┘  └────────────┘    │
└────────────────────────────────────┘
特征：按业务边界拆分，团队自治
风险：分布式复杂度，需要完善基础设施
```

### 演进决策树：该不该拆？

```
是否需要拆分？
│
├─ 当前服务是否是独立部署单元？
│   └─ 否 → 先包分层，不急着拆服务
│
├─ 拆分后团队能独立维护吗？
│   └─ 否 → 先不拆，拆了反而增加沟通成本
│
├─ 是否有明显的性能瓶颈需要独立扩缩容？
│   └─ 否 → 先不拆，拆了增加复杂度
│
└─ 是否是不同业务域（bounded context）？
    └─ 是 → 可以拆，但从小服务开始
```

## 思维四：非功能性设计

### 推荐系统非功能指标清单

| 指标 | 目标值 | 达标手段 |
|------|--------|---------|
| **延迟 P99** | < 200ms | 缓存、异步、降级 |
| **可用性** | > 99.9% | 集群、熔断、多活 |
| **吞吐量** | 支持 10 倍增长 | 水平扩展、读写分离 |
| **一致性** | 最终一致即可 | 异步 + 补偿 |
| **可观测性** | 3 大指标 | 日志 + 指标 + 链路追踪 |

### 降级策略设计

```
推荐系统降级优先级（从高到低）
═══════════════════════════════════════════

第1层：模型降级
  召回：多路召回归并 → 只保留 ItemCF
  排序：精排模型 → 规则排序（热度/时间）
  重排：多样性 → 去除多样性（只保相关性）

第2层：缓存降级
  推荐结果缓存过期时间 1h → 直接返回历史热门

第3层：服务降级
  某路召回服务超时 → 跳过该路，返回其他路结果
  排序服务挂了 → 返回基础推荐（人工运营列表）

第4层：静态兜底
  所有服务都挂了 → 返回"猜你喜欢"默认列表（固定值）
```

## 思维五：决策文档化（Architecture Decision Records）

### 为什么要写 ADR？

```
口头决策 = 没人记得清
书面决策 = 团队共同资产、可追溯、可质疑改进
```

### ADR 模板

```markdown
# ADR-001：推荐系统数据库选型

## 状态：已接受

## 背景
- 日活 100 万短视频平台推荐系统
- 需要存储用户数据、内容数据、行为日志
- 团队 5 人，技术栈以 Python 为主

## 决策
采用混合数据库方案：
- MySQL：用户表、账户表
- MongoDB：短视频内容表
- Redis：推荐缓存、Session
- ClickHouse：行为日志分析

## 结果
- 正面：各司其职，性能最优
- 负面：多数据源增加运维复杂度

## 备选方案
- 全 MySQL：内容表扩展性差，放弃
- 全 MongoDB：行为分析性能差，放弃

## 有效期
评估：3 个月后重新评估
```

## 思维六：代码评审中的架构视角

### 评审问题清单

```
在 Code Review 时，多问这几个问题：

1. 单元测试覆盖了吗？（没有测试的代码，怎么敢上生产）
2. 这个改动会影响哪些人？（影响面评估）
3. 如果这个服务挂了怎么办？（有没有降级方案）
4. 这个接口还能向前兼容吗？（会不会破坏已有调用方）
5. 这个数据量增长 10 倍还能跑吗？（容量意识）
6. 为什么不用缓存？（性能意识）
7. 这个日志够不够定位问题？（可观测性）
8. 这个异常有没有被吞掉？（防御性编程）
```

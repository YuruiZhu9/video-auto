# 架构评估体系：如何量化判断代码架构的好坏

> 架构不是玄学，可以被量化、被测量、被对比。

## 一、为什么需要量化架构

架构评估的本质是回答三个问题：
1. **健康度**：代码库现在有多健康？
2. **风险点**：哪里最可能出 Bug / 最难改？
3. **趋势**：架构是在变好还是变差？

没有量化 → 全凭感觉 → 团队吵来吵去 → 不了了之。

## 二、四大核心度量维度

### 维度1：圈复杂度（Cyclomatic Complexity）

**定义**：一个函数内部有多少条独立执行路径。

**为什么重要**：圈复杂度越高 → Bug 率越高 → 维护成本指数增长。

```
复杂度 = 判定节点数 + 1
- 顺序执行：复杂度 1
- if：复杂度 2
- if + else：复杂度 2
- if + elif + elif：复杂度 4
- for + if + while：复杂度 4
```

**推荐阈值**：
| 复杂度 | 评价 | 行动 |
|--------|------|------|
| 1-10 | ✅ 健康 | 正常维护 |
| 11-20 | ⚠️ 警告 | 考虑拆分 |
| 21-50 | 🔴 高风险 | 必须重构 |
| >50 | ☠️ 危险 | 立即重构 |

**Python 计算示例**：
```python
import ast
from typing import Dict

class ComplexityVisitor(ast.NodeVisitor):
    def __init__(self):
        self.functions: Dict[str, int] = {}
        self._current_function = None
        self._complexity = 0

    def visit_FunctionDef(self, node: ast.FunctionDef):
        old_func = self._current_function
        old_complex = self._complexity
        self._current_function = node.name
        self._complexity = 1  # 基础复杂度
        self.generic_visit(node)
        self.functions[node.name] = self._complexity
        self._current_function = old_func
        self._complexity = old_complex

    def visit_If(self, node: ast.If):
        if self._current_function:
            self._complexity += 1
        self.generic_visit(node)

    def visit_For(self, node: ast.For):
        if self._current_function:
            self._complexity += 1
        self.generic_visit(node)

    def visit_While(self, node: ast.While):
        if self._current_function:
            self._complexity += 1
        self.generic_visit(node)

    def visit_ExceptHandler(self, node: ast.ExceptHandler):
        if self._current_function:
            self._complexity += 1
        self.generic_visit(node)

def analyze_file(filepath: str):
    with open(filepath) as f:
        tree = ast.parse(f.read())
    visitor = ComplexityVisitor()
    visitor.visit(tree)
    
    print(f"\n📊 复杂度分析: {filepath}")
    print("=" * 50)
    high_risk = []
    for name, score in sorted(visitor.functions.items(), key=lambda x: -x[1]):
        if score > 20:
            flag = "🔴"
            high_risk.append(name)
        elif score > 10:
            flag = "⚠️"
        else:
            flag = "✅"
        print(f"{flag} {name}: {score}")
    
    print(f"\n高风险函数: {len(high_risk)} 个")
    return high_risk

# 使用
analyze_file("/workspace/recommendation_service.py")
```

### 维度2：耦合度（Coupling）

**两种耦合**：
- **Afferent Coupling（传入耦合，Ca）**：有多少模块依赖我？→ 我被多少人需要
- **Efferent Coupling（传出耦合，Ce）**：我依赖了多少模块？→ 我依赖了多少外部东西

**不稳定指数**：`I = Ce / (Ca + Ce)`

| I值 | 含义 |
|-----|------|
| 0.0 | 最稳定（被广泛依赖，但不依赖别人）|
| 1.0 | 最不稳定（依赖很多，不被依赖）|

**推荐规则**：
- 核心业务逻辑层：`I` 应该低（稳定）
- 应用层/接口层：`I` 可以相对高
- 避免出现不稳定模块依赖稳定模块（违反依赖倒置原则）

**Python 耦合度计算**：
```python
import ast
import os
from collections import defaultdict

class CouplingAnalyzer(ast.NodeVisitor):
    def __init__(self, module_name: str):
        self.module = module_name
        self.imports = set()
        self.classes = set()
        self.function_calls = defaultdict(set)

    def visit_Import(self, node: ast.Import):
        for alias in node.names:
            self.imports.add(alias.name.split('.')[0])
        self.generic_visit(node)

    def visit_ImportFrom(self, node: ast.ImportFrom):
        if node.module:
            self.imports.add(node.module.split('.')[0])
        self.generic_visit(node)

    def visit_Call(self, node):
        # 追踪函数调用关系
        if isinstance(node.func, ast.Attribute):
            if isinstance(node.func.value, ast.Name):
                self.function_calls[node.func.value.id].add(node.func.attr)
        self.generic_visit(node)

def analyze_project_coupling(root_dir: str):
    module_deps = {}
    
    for dirpath, _, files in os.walk(root_dir):
        for file in files:
            if file.endswith('.py') and not file.startswith('test_'):
                filepath = os.path.join(dirpath, file)
                module_name = filepath.replace(root_dir, '').replace('/', '.').replace('.py', '')
                
                with open(filepath) as f:
                    tree = ast.parse(f.read())
                analyzer = CouplingAnalyzer(module_name)
                analyzer.visit(tree)
                
                module_deps[module_name] = {
                    'imports': analyzer.imports,
                    'calls': dict(analyzer.function_calls)
                }
    
    # 找出最稳定的模块（被依赖最多，不依赖别人）
    depended_by = defaultdict(int)
    depends_on = defaultdict(set)
    
    for mod, deps in module_deps.items():
        for dep in deps['imports']:
            depended_by[dep] += 1
            depends_on[mod].add(dep)
    
    print("\n📊 项目耦合度分析")
    print("=" * 50)
    print("\n🔗 被依赖最多的模块（核心稳定模块）：")
    for mod, count in sorted(depended_by.items(), key=lambda x: -x[1])[:5]:
        print(f"  {mod}: {count} 个模块依赖它")
    
    print("\n⚠️ 依赖最多的模块（不稳定模块）：")
    for mod, deps in sorted(depends_on.items(), key=lambda x: -len(x[1]))[:5]:
        print(f"  {mod}: 依赖 {len(deps)} 个模块 → {deps}")

analyze_project_coupling("/workspace/app/")
```

### 维度3：内聚度（Cohesion）

**定义**：一个模块内部元素（函数/类）彼此相关的程度。

**推荐内聚度类型**：
| 类型 | 评价 | 适用场景 |
|------|------|---------|
| 功能内聚（Functional） | ⭐⭐⭐ 最佳 | 推荐引擎、排序服务 |
| 顺序内聚（Sequential） | ⭐⭐ | 数据处理流水线 |
| 通信内聚（Communicational）| ⭐⭐ | 共享数据的工具类 |
| 过程内聚（Procedural）| ⭐ | 勉强接受 |
| 巧合内聚（Coincidental）| ☠️ 最差 | 完全不相关的代码堆在一起 |

**检测巧合内聚**：
```python
# 反例：巧合内聚 - 3个完全无关的函数放一个文件
# user_utils.py
def calculate_distance(lat1, lon1, lat2, lon2): ...  # 地理
def validate_email(email): ...  # 邮箱验证
def generate_UUID(): ...  # ID生成

# 正例：功能内聚 - 每个模块专注一件事
# geo_utils.py
def calculate_distance(lat1, lon1, lat2, lon2): ...

# validation_utils.py
def validate_email(email): ...

# id_utils.py
def generate_UUID(): ...
```

**LCOM（Lack of Cohesion of Methods）计算**：
```python
"""
LCOM = 1 - (平均字段使用数 / 最大可能使用数)
LCOM 越高 = 内聚度越低 = 模块设计越差
"""

class LCOMAnalyzer:
    @staticmethod
    def analyze_class_methods(cls_methods: list[dict]) -> float:
        """
        cls_methods: [{"method_name": "do_a", "fields_used": {"x", "y"}}, ...]
        """
        if not cls_methods:
            return 0.0
        
        total_fields = set()
        for m in cls_methods:
            total_fields.update(m['fields_used'])
        
        if not total_fields:
            return 1.0  # 无字段，高内聚
        
        # P = 每个方法平均使用的字段数
        total_usage = sum(len(m['fields_used']) for m in cls_methods)
        P = total_usage / len(cls_methods)
        m = len(total_fields)
        
        lcom = 1 - (P / m)
        return round(lcom, 3)
    
    @staticmethod
    def interpret(lcom: float) -> str:
        if lcom <= 0.3:
            return "✅ 高内聚"
        elif lcom <= 0.5:
            return "⚠️ 中等内聚"
        else:
            return "🔴 低内聚 → 考虑拆分"

# 使用
analyzer = LCOMAnalyzer()
result = analyzer.analyze_class_methods([
    {"method_name": "get_user", "fields_used": {"user_id", "name"}},
    {"method_name": "update_user", "fields_used": {"user_id", "name", "email"}},
    {"method_name": "delete_user", "fields_used": {"user_id"}},
])
print(f"LCOM: {result} → {analyzer.interpret(result)}")
```

### 维度4：架构熵（Architectural Entropy）

**定义**：架构熵 = 代码库有序程度下降的趋势。熵越高，架构越混乱。

**信号指标**（架构熵上升的早期警告）：
1. **循环依赖出现**：A→B→C→A
2. **跨层直接调用**：Controller 直接调用 Repository 之外还调用 Redis
3. **上帝类出现**：一个类 > 500行，> 20个方法
4. **参数弥漫**：函数参数 > 5个，且大部分参数是其他对象的属性
5. **神秘命名**：`do_it()`、`process_2()`、`temp_data()`
6. **测试覆盖率下降趋势**：连续3个月下降

**架构熵监控仪表盘**：
```python
from dataclasses import dataclass
from datetime import datetime
import json

@dataclass
class EntropyMetrics:
    date: str
    avg_complexity: float
    max_complexity: int
    total_lines: int
    god_classes_count: int
    circular_deps_count: int
    test_coverage: float  # 百分比
    lcom_avg: float       # 平均内聚度

class EntropyTracker:
    def __init__(self, history_file: str):
        self.history_file = history_file
        self.history = self._load()
    
    def _load(self) -> list:
        try:
            with open(self.history_file) as f:
                return json.load(f)
        except FileNotFoundError:
            return []
    
    def record(self, metrics: EntropyMetrics):
        self.history.append({
            "date": metrics.date,
            "complexity": metrics.avg_complexity,
            "coverage": metrics.test_coverage,
            "god_classes": metrics.god_classes_count,
            "entropy_score": self._calc_entropy_score(metrics)
        })
        with open(self.history_file, 'w') as f:
            json.dump(self.history, f, indent=2)
    
    def _calc_entropy_score(self, m: EntropyMetrics) -> float:
        """综合熵值：越高 = 架构越乱"""
        complexity_score = min(m.avg_complexity / 10, 5) * 2  # 权重2
        coverage_score = (100 - m.test_coverage) / 20          # 权重1
        god_class_score = m.god_classes_count * 3             # 权重3
        lcom_score = m.lcom_avg * 5                            # 权重5
        return round(complexity_score + coverage_score + god_class_score + lcom_score, 2)
    
    def get_trend(self) -> str:
        if len(self.history) < 2:
            return "数据不足"
        current = self.history[-1]['entropy_score']
        previous = self.history[-2]['entropy_score']
        delta = current - previous
        if delta > 0.5:
            return f"📈 熵增 +{delta:.2f} → 架构正在恶化，优先处理高息技术债"
        elif delta < -0.5:
            return f"📉 熵减 {delta:.2f} → 重构有效，继续保持"
        else:
            return f"➡️ 熵稳定 {delta:+.2f} → 当前架构状态良好"
    
    def summary(self):
        print("\n📊 架构熵趋势报告")
        print("=" * 50)
        for h in self.history[-5:]:
            print(f"  {h['date']} | 熵:{h['entropy_score']:.1f} | 覆盖:{h['coverage']:.0f}%")
        print(f"\n趋势: {self.get_trend()}")

# 使用
tracker = EntropyTracker("/workspace/metrics/entropy_history.json")
tracker.summary()
```

## 三、架构健康度雷达图

综合四个维度，给架构打分：

```python
@dataclass
class ArchitectureScore:
    complexity_score: float    # 圈复杂度（0-100，越低越好）
    coupling_score: float      # 耦合度（0-100，越低越好）
    cohesion_score: float      # 内聚度（0-100，越高越好）
    entropy_trend: float       # 熵趋势（0-100，越低越好）

    def overall(self) -> float:
        # 复杂度、耦合、熵是负向指标（越低越好）
        # 内聚是正向指标（越高越好）
        return round(
            (100 - self.complexity_score) * 0.25 +
            (100 - self.coupling_score) * 0.25 +
            self.cohesion_score * 0.25 +
            (100 - self.entropy_trend) * 0.25,
            1
        )

    def grade(self) -> str:
        score = self.overall()
        if score >= 85:
            return "🏆 A - 优秀"
        elif score >= 70:
            return "✅ B - 良好"
        elif score >= 55:
            return "⚠️ C - 及格"
        elif score >= 40:
            return "🔴 D - 较差"
        else:
            return "☠️ F - 危险"

# 推荐系统各层评分参考
print("""
📊 推荐系统各层架构评分参考

       推荐引擎层:  85/100 (A)  - 策略模式，多路召回隔离
       排序服务层:  78/100 (B)  - 职责清晰，依赖注入
       缓存层:      92/100 (A)  - 独立模块，可测试
       数据访问层:  65/100 (C)  - Repository 模式刚引入，还需完善
       API 层:      88/100 (A)  - BFF 网关，干净利落
       整体:        81/100 (B)  - 整体架构健康，持续改进中
""")
```

## 四、推荐系统专项评估清单

### 召回层评估
- [ ] 召回策略是否可热插拔（新增策略不用改核心代码）？
- [ ] 各召回路是否有独立开关？
- [ ] 召回结果是否有降级兜底？

### 排序层评估
- [ ] 模型推理是否有超时/熔断？
- [ ] 排序参数是否外部可配置？
- [ ] 模型版本切换是否平滑？

### 架构层评估
- [ ] 是否有明确的分层边界？
- [ ] 循环依赖是否已消除？
- [ ] 核心逻辑是否与框架解耦？
- [ ] 依赖注入是否贯穿全项目？

### 可测试性评估
- [ ] 单元测试覆盖率是否 ≥ 60%？
- [ ] 核心算法是否有集成测试？
- [ ] 是否能做到不启动外部服务跑通测试？

```python
class RecommendationSystemHealthCheck:
    """推荐系统架构健康度自动检查"""
    
    def run(self) -> dict:
        results = {
            "timestamp": datetime.now().isoformat(),
            "checks": []
        }
        
        # 1. 复杂度检查
        from pathlib import Path
        high_complexity = []
        for py_file in Path("/workspace/app").rglob("*.py"):
            if "test" not in str(py_file):
                issues = analyze_file(str(py_file))
                high_complexity.extend(issues)
        
        results["checks"].append({
            "name": "圈复杂度检查",
            "status": "PASS" if len(high_complexity) == 0 else "WARN",
            "detail": f"高风险函数 {len(high_complexity)} 个",
            "items": high_complexity
        })
        
        # 2. 分层检查
        results["checks"].append({
            "name": "分层架构检查",
            "status": "PASS",
            "detail": "六边形架构 + 整洁分层"
        })
        
        # 3. 依赖注入检查
        results["checks"].append({
            "name": "依赖注入检查",
            "status": "PASS",
            "detail": "DIContainer 已配置"
        })
        
        # 综合评分
        warn_count = sum(1 for c in results["checks"] if c["status"] == "WARN")
        fail_count = sum(1 for c in results["checks"] if c["status"] == "FAIL")
        
        if fail_count > 0:
            results["overall"] = "🔴 需要立即修复"
        elif warn_count > 0:
            results["overall"] = "⚠️ 有改进空间"
        else:
            results["overall"] = "✅ 架构健康"
        
        return results
```

## 七、常见误区

**❌ 误区1：追求完美分数**
架构没有100分，只有适合当前阶段的架构。过度设计比设计不足更危险。

**❌ 误区2：只看单一指标**
复杂度低的代码不等于好代码，还要看内聚、耦合、测试覆盖。

**❌ 误区3：只测一次**
架构健康是动态的，建议每周跑一次评分，记录趋势。

**❌ 误区4：指标至上**
指标是辅助工具，不是目的。代码可读性 > 分数高低。

**✅ 正确姿势**
1. 选3-5个最相关的指标
2. 建立基线（Baseline）
3. 持续跟踪趋势
4. 趋势比绝对值重要
5. 用数据说服团队，而不是主观判断

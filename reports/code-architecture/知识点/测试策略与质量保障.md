# 推荐系统工程化：测试策略与质量保障

> 把代码从"能跑"变成"能上线"的关键一步

---

## 为什么要测试

很多人写代码的流程是：写完 → 手动跑一下 → 没问题就上线。结果：

- 上线后才发现 bug，紧急回滚
- 改了一个功能，坏了三个功能（回归）
- 代码越改越烂，不敢动老代码

**测试的价值**：
- 🛡️ 防护网：有测试，改代码不慌
- 📖 文档：测试就是最好的使用示例
- 🔍 定位bug：测试失败 → 精准定位问题
- 🚀 重构信心：有测试，重构后一跑就知道对不对

---

## 测试分层策略

推荐系统的测试分为四层，从下往上：

```
┌─────────────────────────────────────────┐
│     E2E 测试（端到端）                    │
│  模拟用户真实请求，验证完整推荐链路       │
├─────────────────────────────────────────┤
│     集成测试                              │
│  测试服务+数据库/缓存的集成               │
├─────────────────────────────────────────┤
│     单元测试                              │
│  测试纯逻辑：召回策略、排序模型、降级逻辑 │
├─────────────────────────────────────────┤
│     冒烟测试                              │
│  上线前快速验证核心路径是否正常           │
└─────────────────────────────────────────┘
```

### 各层测试对比

| 层级 | 运行速度 | 覆盖范围 | 维护成本 | 适用场景 |
|------|---------|---------|---------|---------|
| 单元测试 | ⚡ 快（毫秒级） | 单个函数/类 | 低 | 业务逻辑、算法逻辑 |
| 集成测试 | 🐢 中（秒级） | 模块间交互 | 中 | Repository、Service 组合 |
| E2E 测试 | 🐢🐢 慢（分钟级） | 完整链路 | 高 | 上线前验收 |

---

## 第一层：单元测试

### 核心原则

```
单元测试要点
═════════════════════════════════════
1. 测试一个"单元"（通常是1个函数/方法）
2. 不依赖外部（数据库、Redis、HTTP）
3. 运行速度快（毫秒级）
4. given-when-then 结构：给定输入 → 执行操作 → 验证输出
```

### 推荐系统单元测试场景

#### 场景1：召回策略测试

```python
# tests/unit/test_recall_strategies.py
import pytest
from unittest.mock import MagicMock
from recall import ItemCFRecall, UserCFRecall, EmbeddingRecall

class TestItemCFRecall:
    """ItemCF 协同过滤召回测试"""

    def setup_method(self):
        """每个测试前准备模拟数据"""
        self.user_id = "user_001"
        # 模拟用户行为数据：user_id -> [(item_id, score)]
        self.user_behavior = {
            "user_001": [("item_A", 1), ("item_B", 1), ("item_C", 1)],
            "user_002": [("item_A", 1), ("item_B", 1)],
            "user_003": [("item_C", 1), ("item_D", 1)],
        }
        # 模拟物品相似度矩阵
        self.item_similarity = {
            ("item_A", "item_B"): 0.8,
            ("item_A", "item_C"): 0.3,
            ("item_C", "item_D"): 0.9,
        }

    def test_recall_top_k(self):
        """测试返回 top-k 结果"""
        recall = ItemCFRecall(
            user_behavior=self.user_behavior,
            item_similarity=self.item_similarity
        )
        results = recall.recall(self.user_id, top_k=3)

        # 验证：应该返回最多3个物品
        assert len(results) <= 3
        # 验证：不应该包含用户已交互的物品
        user_interacted = set(item for item, _ in self.user_behavior[self.user_id])
        assert all(item not in user_interacted for item in results)

    def test_empty_user_behavior(self):
        """测试冷启动用户（无行为数据）"""
        recall = ItemCFRecall(
            user_behavior={},
            item_similarity=self.item_similarity
        )
        results = recall.recall("cold_user", top_k=5)

        # 冷启动用户应该返回空或有降级策略
        assert isinstance(results, list)

    def test_similarity_threshold(self):
        """测试相似度阈值过滤"""
        recall = ItemCFRecall(
            user_behavior=self.user_behavior,
            item_similarity=self.item_similarity,
            similarity_threshold=0.5  # 只保留相似度>0.5的
        )
        results = recall.recall(self.user_id, top_k=10)

        # 验证：所有结果相似度都应 > 0.5
        # （results 格式：[(item_id, score)]，score 即相似度）
        if results:
            for item, score in results:
                assert score > 0.5, f"物品 {item} 相似度 {score} 应大于 0.5"


class TestEmbeddingRecall:
    """Embedding 向量召回测试"""

    def test_recall_with_empty_embedding(self):
        """物品无 embedding 时的降级处理"""
        recall = EmbeddingRecall(embedding_model=None)  # 模型加载失败
        results = recall.recall("user_001", top_k=5)

        # 应该触发降级，返回热门物品
        assert results is not None
        assert len(results) >= 0

    def test_recall_result_format(self):
        """测试返回格式正确性"""
        mock_model = MagicMock()
        mock_model.encode.return_value = [0.1, 0.2, 0.3]
        mock_items = [
            {"id": "item_1", "embedding": [0.1, 0.2, 0.3]},
            {"id": "item_2", "embedding": [0.2, 0.3, 0.4]},
        ]
        recall = EmbeddingRecall(embedding_model=mock_model, items=mock_items)
        results = recall.recall("user_001", top_k=2)

        # 验证返回格式
        assert isinstance(results, list)
        for item_id, score in results:
            assert isinstance(item_id, str)
            assert isinstance(score, (int, float))
```

```python
# tests/unit/test_ranker.py
import pytest
from ranker import MLflowRanker, RuleRanker

class TestRuleRanker:
    """规则排序器测试（适合快速迭代期）"""

    def test_score_calculation(self):
        """测试综合打分公式"""
        ranker = RuleRanker(weights={"ctr": 0.4, "recency": 0.3, "quality": 0.3})

        item = {
            "ctr": 0.05,        # 5% 点击率
            "publish_time": "2026-03-25T10:00:00",  # 10点发布
            "quality_score": 0.8
        }

        score = ranker.calculate_score(item)
        assert 0 <= score <= 1  # 分数应在 [0, 1]
        assert isinstance(score, float)

    def test_time_decay(self):
        """测试时间衰减：越新的内容分数越高"""
        ranker = RuleRanker()
        now = "2026-03-25T12:00:00"

        old_item = {"publish_time": "2026-03-20T12:00:00", "ctr": 0.1}
        new_item = {"publish_time": "2026-03-25T11:00:00", "ctr": 0.1}

        old_score = ranker.calculate_score(old_item, now=now)
        new_score = ranker.calculate_score(new_item, now=now)

        # 同样 CTR，新内容应该排更前
        assert new_score > old_score, "新内容分数应该更高"


class TestMLflowRanker:
    """MLflow 模型排序器测试"""

    def test_model_loading_failure(self):
        """模型加载失败时的降级策略"""
        ranker = MLflowRanker(model_path="/nonexistent/path")
        items = [{"id": "item_1", "features": [0.1, 0.2]}]

        # 应该降级到规则排序
        results = ranker.rank(items)
        assert results is not None
        assert len(results) > 0

    def test_feature_mismatch(self):
        """特征维度不匹配时的处理"""
        ranker = MLflowRanker(model_path="models/ranker_v1")
        items = [
            {"id": "item_1", "features": [0.1, 0.2]},         # 2维
            {"id": "item_2", "features": [0.1, 0.2, 0.3, 0.4]},  # 4维，异常
        ]

        # 应该跳过异常 item 或填充默认值
        results = ranker.rank(items)
        assert len(results) <= 2
```

```python
import pytest
from degradation import DegradationManager, DegradationLevel

class TestDegradationManager:
    """推荐系统降级策略测试"""

    def setup_method(self):
        self.manager = DegradationManager()

    def test_degradation_levels(self):
        """测试三级降级"""
        levels = [
            DegradationLevel.MODEL,      # 第1级：模型降级
            DegradationLevel.CACHE,       # 第2级：缓存降级
            DegradationLevel.STATIC       # 第3级：静态兜底
        ]

        for level in levels:
            handler = self.manager.get_handler(level)
            assert handler is not None, f"降级级别 {level} 应有处理器"

    def test_fallback_response(self):
        """测试降级时的兜底响应"""
        result = self.manager.fallback()
        assert result is not None
        # 兜底应该返回默认推荐（非空列表）
        assert isinstance(result, list)

    @pytest.mark.parametrize("level", [
        DegradationLevel.MODEL,
        DegradationLevel.CACHE,
        DegradationLevel.STATIC
    ])
    def test_all_levels_produce_results(self, level):
        """参数化测试：所有降级级别都能产生结果"""
        handler = self.manager.get_handler(level)
        result = handler.handle(user_id="test_user", context={})
        assert result is not None
```

## 第二层：集成测试

### 为什么要做集成测试

```
单元测试：只测一个函数，不管它怎么和别的模块交互
集成测试：测多个模块组合在一起时是否正确

推荐系统的集成测试重点：
  - Service + Repository：数据存取是否正确
  - Service + Cache：缓存读写/失效是否正确
  - API + Service + Repository：完整请求链路
```

### Repository 集成测试

```python
# tests/integration/test_user_repository.py
import pytest
from sqlalchemy import create_engine
from sqlalchemy.orm import sessionmaker
from repositories.user_repository import SQLAlchemyUserRepository
from models.user import Base, User

# 使用内存 SQLite 数据库做测试
TEST_DATABASE_URL = "sqlite:///:memory:"

@pytest.fixture(scope="function")
def db_session():
    """每个测试用独立的数据库会话"""
    engine = create_engine(TEST_DATABASE_URL, connect_args={"check_same_thread": False})
    Base.metadata.create_all(engine)
    Session = sessionmaker(bind=engine)
    session = Session()
    yield session
    session.close()
    Base.metadata.drop_all(engine)


class TestUserRepository:
    """用户 Repository 集成测试"""

    def test_create_and_get(self, db_session):
        """测试创建和查询用户"""
        repo = SQLAlchemyUserRepository(db_session)

        # 创建用户
        user = User(id="user_001", name="张三", age=25)
        created = repo.create(user)
        assert created.id == "user_001"

        # 查询用户
        fetched = repo.get_by_id("user_001")
        assert fetched is not None
        assert fetched.name == "张三"

    def test_update_user_profile(self, db_session):
        """测试更新用户画像"""
        repo = SQLAlchemyUserRepository(db_session)

        repo.create(user)

        # 更新画像

        assert "财经" in updated.tags
        assert len(updated.tags) == 3

    def test_get_nonexistent_user(self, db_session):
```

## 第三层：Mock 与 Patch

### 何时用 Mock

```
Mock（模拟）的使用场景：
═════════════════════════════════════
✓ 外部 HTTP API 调用（第三方服务）
✓ 数据库连接（集成测试太慢时）
✓ Redis/MQ 等基础设施
✓ 模型推理服务（不想每次都真实推理）

✗ 不要 Mock 自己写的业务逻辑（那部分应该直接测）
✗ 不要 Mock 太多层（失去测试意义）
```

### pytest-mock 实战

```python
# tests/unit/test_recommendation_service_with_mock.py
import pytest
from unittest.mock import Mock, patch
from services.recommendation_service import RecommendationService

class TestRecommendationServiceWithMock:

    @patch('services.recommendation_service.UserRepository')
    @patch('services.recommendation_service.RecallEngine')
    @patch('services.recommendation_service.Ranker')
    def test_recommend_with_mocked_dependencies(
        self, mock_ranker_cls, mock_recall_cls, mock_user_repo_cls
    ):
        """
        测试推荐服务，但 mock 掉所有外部依赖
        只测试服务编排逻辑是否正确
        """
        # Setup: 配置 Mock 对象
        mock_user_repo = mock_user_repo_cls.return_value
        mock_user_repo.get_by_id.return_value = Mock(id="user_001", tags=["科技"])

        mock_recall = mock_recall_cls.return_value
        mock_recall.recall.return_value = [
            ("item_A", 0.9), ("item_B", 0.8), ("item_C", 0.7)
        ]

        mock_ranker = mock_ranker_cls.return_value
        mock_ranker.rank.return_value = [
            {"item_id": "item_A", "score": 0.9},
            {"item_id": "item_B", "score": 0.8},
        ]

        # Execute: 执行服务
        service = RecommendationService(
            user_repo=mock_user_repo,
            recall_engine=mock_recall,
            ranker=mock_ranker
        )
        result = service.recommend(user_id="user_001", count=5)

        # Verify: 验证调用链路
        mock_user_repo.get_by_id.assert_called_once_with("user_001")
        mock_recall.recall.assert_called_once()
        mock_ranker.rank.assert_called_once()
        assert len(result) <= 5

    def test_cache_hit(self):
        """测试缓存命中场景"""
        service = RecommendationService()
        # 手动注入缓存命中的场景
        with patch.object(service.cache, 'get', return_value=["item_cached"]):
            result = service.recommend("user_001", count=5)
            # 缓存命中时，不调用召回和排序
            assert result == ["item_cached"]
```

## 第四层：CI/CD 流水线

### 推荐的 CI/CD 流程

```
代码提交
    ↓
① 代码检查（Lint + Format）
    ↓
② 单元测试（< 2 分钟）
    ↓
③ 构建 Docker 镜像
    ↓
④ 推送镜像到仓库
    ↓
⑤ 部署到测试环境
    ↓
⑥ 集成测试 + E2E 测试
    ↓
⑦ 审批（生产部署）
    ↓
⑧ 蓝绿部署 / 金丝雀发布
    ↓
⑨ 监控 + 告警
```

### GitHub Actions 配置

```yaml
# .github/workflows/ci.yml
name: CI Pipeline

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

jobs:
  # ── 第1步：代码质量检查 ──
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.11'
      - run: pip install ruff flake8 black
      - run: ruff check .          # 风格检查
      - run: black --check .       # 格式检查
      - run: mypy src/              # 类型检查（Python）

  # ── 第2步：单元测试 ──
  unit-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.11'
      - run: pip install -r requirements.txt pytest pytest-cov pytest-mock
      - run: pip install -e .
      - run: pytest tests/unit/ -v --cov=src --cov-report=xml
      - uses: codecov/codecov-action@v3
        with:
          files: ./coverage.xml

  # ── 第3步：集成测试 ──
  integration-test:
    runs-on: ubuntu-latest
    services:
      redis:
        image: redis:7
        ports:
          - 6379:6379
      postgres:
        image: postgres:15
        env:
          POSTGRES_DB: test_db
          POSTGRES_USER: test
          POSTGRES_PASSWORD: test
        ports:
          - 5432:5432
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.11'
      - run: pip install -r requirements.txt pytest pytest-asyncio
      - run: pytest tests/integration/ -v
      # 集成测试通过后才执行 E2E
      - run: pytest tests/e2e/ -v --tb=short

  # ── 第4步：构建并推送镜像 ──
  build-and-push:
    needs: [lint, unit-test, integration-test]
    runs-on: ubuntu-latest
    if: github.ref == 'refs/heads/main'
    steps:
      - uses: actions/checkout@v4
      - uses: docker/setup-buildx-action@v3
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - uses: docker/metadata-action@v5
        id: meta
        with:
          images: ghcr.io/${{ github.repository }}/recommender
          tags: |
            type=sha,prefix={{branch}}-
            type=raw,value=latest
      - uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          cache-from: type=gha
          cache-to: type=gha,mode=max

  # ── 第5步：部署到测试环境 ──
  deploy-staging:
    needs: [build-and-push]
    runs-on: ubuntu-latest
    environment: staging
    steps:
      - uses: actions/checkout@v4
      - name: Deploy to Kubernetes
        run: |
          kubectl set image deployment/recommender-api \
            api=${{ needs.build-and-push.outputs.image_tag }}
          kubectl rollout status deployment/recommender-api
          # 等待服务就绪
          kubectl wait --for=condition=available deployment/recommender-api --timeout=120s

  # ── 第6步：生产部署（金丝雀）──
  deploy-production:
    needs: [deploy-staging]
    runs-on: ubuntu-latest
    environment:
      name: production
      url: https://api.example.com
    steps:
      - uses: actions/checkout@v4
      - name: 金丝雀发布（先 10% 流量）
        run: |
          kubectl patch deployment recommender-api \
            -p '{"spec":{"strategy":{"type":"RollingUpdate","rollingUpdate":{"maxSurge":"25%","maxUnavailable":"25%"}}}}'
      - name: 验证金丝雀
        run: |
          # 跑冒烟测试验证 10% 流量
          python tests/smoke_test.py --env=production
      - name: 全量发布
        run: |
          kubectl scale deployment recommender-api --replicas=10
```

## 第五层：上线前冒烟测试

### 什么是冒烟测试

```
冒烟测试 = 上线前快速验证核心功能是否正常
不是全面测试，只测"冒烟"——功能能不能跑起来

推荐系统冒烟测试清单：
═════════════════════════════
[ ] 健康检查接口返回正常
[ ] 召回接口能在 500ms 内返回结果
[ ] 排序接口能处理 100 个物品
```

## 测试覆盖率目标

```
推荐系统各模块覆盖率建议：
═════════════════════════════════════

核心算法层（召回/排序/重排）  → 覆盖率 ≥ 80%
Service 层                    → 覆盖率 ≥ 70%
Repository 层                  → 覆盖率 ≥ 60%
API Controller 层             → 覆盖率 ≥ 50%（路由测通即可）

覆盖率不是越高越好：
- 追求 100% 覆盖率 = 浪费时间写无用测试
- 重点覆盖：业务逻辑、边界条件、降级策略
```

## 面试表达模板

**问：你怎么做推荐系统的质量保障？**

```
质量保障分四层：

第一层，单元测试，覆盖核心算法逻辑。比如召回策略、排序打分、
降级兜底这些纯函数，用 given-when-then 的结构去测，
重点测边界情况和降级路径。

第二层，集成测试，测模块间的交互。比如 Service 层调用 Repository
时数据存取是否正确，用测试数据库（SQLite 内存）做隔离。

第三层，API 端到端测试，用 FastAPI 的 TestClient 测完整请求链路，
覆盖冷启动用户、空列表返回这些场景。

第四层，上线前冒烟测试，快速验证延迟、并发、降级策略是否生效。

整个流程接进 GitHub Actions CI/CD，单元测试过了才允许合入 main 分支，
生产部署前跑冒烟测试，有任何一个检查点失败就阻止发布。
```

## 适用场景

- ✅ 上线前质量保障
- ✅ 重构时的防护网
- ✅ 新功能开发时的自测
- ✅ 回归测试（防止改A坏B）
- ✅ 团队代码规范落地

## 常见误区

- ❌ 误区1：测试覆盖率越高越好 → 聚焦核心逻辑，80% 比 100% 伪代码强
- ❌ 误区2：只测 happy path → 必须覆盖边界条件和异常
- ❌ 误区3：Mock 用太多 → 不要 Mock 自己写的业务逻辑
- ❌ 误区4：CI 跑 30 分钟 → 单元测试必须快，集成测试才可慢
- ❌ 误区5：写了测试就不管了 → 测试本身也要 Code Review

### 主题一：架构设计与分层（⭐⭐⭐ 最高频）

---

**【基础】⭐ 请描述一个推荐系统的经典三层架构，每层职责是什么？**

参考答案要点：
- **召回层（Recall）**：从海量候选集（百万~亿级）中快速拉取候选集（百~千级），用多路召回（热门 + ItemCF + UserCF + Embedding）并行拉取，用策略模式热插拔
- **排序层（Rank）**：对召回候选集做精排打分（DeepFM/DeepFFM），特征获取 + 模型推理，返回带分数的列表
- **重排层（Rerank）**：对排序列表做业务规则处理（去重、多样性、商业干预），最终返回 Top-N
- 三层核心矛盾：**速度 vs 精度**（越往后精度越高，但候选越少计算越重）

---

**【基础】⭐ 为什么要分层？不分层行不行？**

参考答案要点：
- 不分层：亿级候选直接精排 → 单次请求耗时 10s+，服务不可用
- 分层核心思想：**漏斗过滤**，每层逐步缩小候选集，同时提高精度
- 推荐系统经典漏斗：召回（万级）→ 粗排（千级）→ 精排（百级）→ 重排（十级）
- 架构原则：每层只做该层该做的事（召回不做排序，排序不做重排）

---

**【进阶】⭐⭐ 你理解的六边形架构（端口与适配器）是什么？为什么推荐系统要用？**

参考答案要点：
- 六边形核心：**核心业务逻辑在中心，外部依赖（MySQL/Redis/Kafka/模型）在六边形外**
- 端口（Port）：定义"我要什么"接口，比如 `RecallPort`/`RankingPort`，和实现无关
- 适配器（Adapter）：端口的具体实现，比如 `MySQLRecallAdapter` / `RedisCacheAdapter`
- 好处：换数据库 / 换模型 / 换消息队列，**不改一行领域代码**
- 推荐系统案例：Embedding 模型从 PyTorch 换成 ONNX Runtime → 只换 Adapter，召回路由代码不动

---

**【高难】⭐⭐⭐ 整洁架构 / 六边形 / 洋葱架构三者有什么区别？**

参考答案要点：
- 三者本质相同：**依赖只能从外向内**，业务逻辑永远在最中心
- **整洁架构**（Bob大叔）：Entities → Use Cases → Interface Adapters → Frameworks & Drivers，更强调"内层不知道外层存在"
- **六边形架构**（Alistair Cockburn）：Port + Adapter 术语，Driving Adapter（主动触发，如 REST API）和 Driven Adapter（被动提供，如 MySQL）
- **洋葱架构**：强调同心圆，每层向内依赖，领域层最内
- **推荐系统选型建议**：六边形 + 整洁混用，六边形定义端口（输入/输出），整洁架构定义层次（四层）
- **进阶加分**：六边形更适合**接入层变化频繁**的场景（REST → gRPC → GraphQL），整洁架构更适合**业务规则复杂**的场景

---

**【高难】⭐⭐⭐ 你的推荐系统如果要从单体演进到微服务，怎么拆？**

参考答案要点（演进路线）：
- **阶段一（0→1）**：单体分层，包级别拆分（`recall/` / `rank/` / `rerank/`），先跑通
- **阶段二（增长期）**：按业务域垂直拆分 → 用户服务 / 内容服务 / 推荐引擎服务，通过 Kafka 事件总线解耦
- **阶段三（成熟期）**：按处理阶段水平拆分 → 召回服务 / 排序服务 / 重排服务独立部署，独立扩缩容
- **拆分判断标准**：
  - 不是"按类拆分"，而是"按限界上下文拆分"
  - 不是"服务越小越好"，要问：独立部署？独立扩缩容？独立团队？
- **信号**：某服务成为性能瓶颈 / 某团队修改频繁影响其他模块 → 该拆了
- **解耦神器**：Kafka 事件总线（推荐系统天然是事件驱动的：点击→更新画像）

### 主题二：设计原则与模式（⭐⭐⭐ 高频）

---

**【基础】⭐ 请解释 SOLID 原则，重点讲你用过哪个？**

参考答案要点（选 1-2 个深入讲）：
- **SRP（单一职责）**：一个类/函数只做一件事 → 推荐系统：RecallEngine 只做召回，不做缓存、不做日志
- **OCP（开闭原则）**：对扩展开放、对修改关闭 → 推荐系统：新增一路召回，继承 BaseRecallStrategy，不改召回引擎
- **DIP（依赖倒置）**：依赖抽象接口，不依赖具体实现 → 推荐系统：依赖 RecallPort，不直接依赖 MySQLRecallAdapter
- **LSP（里氏替换）**：子类可以替换父类 → 排序策略换成 DeepFM 不影响上游调用
- **ISP（接口隔离）**：不要大接口 → RecallPort 只定义召回方法，不塞进超大 RecommendPort

---

**【进阶】⭐⭐ 推荐系统中策略模式是怎么用的？能举个具体例子吗？**

参考答案要点（完整代码讲解）：

反例（if-else 硬编码，新增策略要改代码）：
```python
def recall(user_id, scene):
    if scene == "home":
        return embedding_recall(user_id)
    elif scene == "detail":
        return item_cf_recall(user_id)
    elif scene == "search":
        return hot_recall()
```

正例（策略模式，新增策略不改动已有代码）：
```python
class BaseRecall(ABC):
    @abstractmethod
    def recall(self, ctx: RecallContext) -> List[int]: pass

class EmbeddingRecall(BaseRecall):
    def __init__(self, vector_store): self.vector_store = vector_store
    def recall(self, ctx): ...

class ItemCFRecall(BaseRecall):
    def __init__(self, redis_client): self.redis_client = redis_client
    def recall(self, ctx): ...

# 引擎：通过注册机制自动加载，不改引擎代码
recall_engine = RecallEngine()
recall_engine.register("embedding", EmbeddingRecall(vector_store))
recall_engine.register("item_cf", ItemCFRecall(redis_client))
```

关键好处：新增一路召回，继承 BaseRecall → 注册 → 上线，不需要改召回引擎一行代码（OCP 完美诠释）

进阶加分：结合工厂模式 `create_recall(scene)` 按场景自动选择

---

**【进阶】⭐⭐ 你在项目中用过哪些设计模式？在哪里用的？**

推荐系统高频模式及回答模板：

| 模式 | 面试回答 |
|------|---------|
| **策略模式** | "多路召回，每路策略独立，新增策略不改动引擎代码" |
| **模板方法** | "召回路→排序路→重排路流程固定，具体每路实现可替换" |

| **工厂模式** | "按场景（首页/详情页/搜索页）创建推荐器，内部组合多个策略" |
| **责任链模式** | "请求经过：鉴权→限流→缓存查询→推荐→响应格式化，每步独立可插拔" |

**【高难】⭐⭐⭐ 什么情况下你会"故意违背"某些设计原则或模式？**

参考答案要点（展示权衡思维）：
- **性能优先**：热点代码中，函数内联比抽象调用快 5-10%，生产环境可能选内联
- **YAGNI 原则**：不要过度设计，不确定会用到的抽象层先不写
- **简单优先**：如果只有一种召回策略，强上策略模式反而增加复杂度
- **团队规模**：小团队（3人以下）强上微服务 + DDD，维护成本 > 收益
- **面试加分表达**："设计原则是指导方针，不是教条。了解原则才能判断什么时候打破它。"

### 主题三：重构与质量（⭐⭐ 高频）

---

**【基础】⭐ 你怎么发现代码有"坏味道"？常见的坏味道有哪些？**

- **发现工具**：SonarQube（扫描）/ flake8（Lint）/ mypy（类型检查）
- **推荐系统专项工具**：lizard（圈复杂度）/ bandit（安全扫描）

**【进阶】⭐⭐ 你做过重构吗？请举个具体例子**

参考答案要点（STAR 法则）：

- **Situation**：接手 3000 行单文件推荐服务，每次加召回策略改 8 处，还影响已有逻辑
- **Task**：在不影响业务的前提下，重构成可维护的分层架构
- **Action**（分步）：
  1. 加 Feature Flag，双轨并行，不影响线上
  2. 提取配置层（dataclass），消灭魔法数字
  3. 引入 Repository 模式，数据库访问抽象
  4. 领域层零依赖（纯 Python），核心逻辑独立
  5. DI 容器组装，按场景切换新旧逻辑
  6. 上线验证通过后，去掉 Feature Flag
- **Result**：新增一路召回从 3 人日 → 0.5 人日，召回模块圈复杂度从 67 → 8

**【进阶】⭐⭐ 什么是技术债？你怎么决定"要不要还"？**

参考答案要点：
- 技术债 = "走捷径的代价"，包括：战略债（明知不完美先上线）/ 疏忽债（不知道这是债）/ 根本债（规模变化让正确变错误）
- **决策公式**：`ROI = 年利息节省 ÷ 还债成本`，年利息 = 每月修改次数 × 单次多花时间 × 12
- **不还的条件**：几乎不改的代码 / 利息 < ROI / 业务快速发展期，债先记账
- **还的条件**：债已经影响开发速度 / 高息债（每月改 4 次以上）
- **推荐系统高息债 TOP3**：召回路硬编码 / 训练-服务特征 Skew / 无降级预案

### 主题四：缓存与性能（⭐⭐⭐ 高频）

---

**【基础】⭐ 推荐系统的缓存策略是怎么设计的？**

参考答案要点：
- **Cache-Aside（最常用）**：读：缓存有则返，无则查库+写缓存；写：先写库，再删缓存
- **推荐系统应用**：首页推荐结果（TTL 5-30min）/ Item 特征缓存（TTL 1-24h）
- **Write-Through**：写操作同步穿透缓存+DB → 点赞计数、用户画像
- **Write-Behind**：先写缓存，异步批量写 DB → 用户行为打点、实时特征
- **多级缓存**：本地 dict（L1）→ Redis（L2）→ MySQL（L3），逐级穿透

---

**【进阶】⭐⭐ 缓存穿透、击穿、雪崩是什么？怎么解决？**

参考答案要点：

| 问题 | 原因 | 解决方案 |
|------|------|---------|
| **缓存穿透** | 查询不存在的数据，直击 DB | Bloom Filter 快速判断不存在；布谷鸟过滤器 |
| **缓存击穿** | 热点 key 过期瞬间，大量请求击穿到 DB | 分布式锁（SETNX）+ 互斥更新；永不过期+异步重建 |
| **缓存雪崩** | 大量 key 同时过期 | TTL + 随机偏移量（±10%）；多级缓存；Redis Cluster 高可用 |

推荐系统专项：热门 item 的 embedding 缓存击穿最致命 → 用模型推理结果永不过期 + 异步更新

---

**【高难】⭐⭐⭐ 如何设计一个推荐系统的多级缓存架构？**

参考答案要点（完整架构）：

```
请求 → L1(本地LRU, 1000条, 命中率60%) → L2(Redis集群, TTL10min) → L3(MySQL/特征存储)
                                                                              ↑
                                              异步写：写穿透 + 双删策略（先删L2→写DB→延迟删L2）
```

- **L1 本地缓存**：热点用户/Item 特征，用 Python dict + LRU，F5 本地命中
- **L2 Redis 缓存**：跨实例共享，首页推荐结果、Embedding 向量（numpy bytes 序列化）
- **L3 数据库**：兜底，所有缓存未命中时查 MySQL/ClickHouse
- **缓存失效策略**：双删（先删缓存→写DB→延迟删缓存）防并发写覆盖
- **降级**：Redis 挂了 → 直接查 MySQL（降级不降服务）

### 主题五：分布式与韧性（⭐⭐⭐ 中高频）

---

**【基础】⭐ 为什么推荐系统要做降级？降级策略有哪些？**

参考答案要点：
- 降级原因：推荐系统多个下游（Redis/模型服务/特征存储），任一挂了不能导致整体不可用
- **三级降级**：
  - L1（模型降级）：精排模型挂了 → 用规则打分（CTR × 权重）
  - L2（缓存降级）：Redis 缓存全崩 → 用历史推荐结果兜底（冷启动兜底列表）
  - L3（静态兜底）：全链路崩 → 返回热门列表（完全降级）
- **降级关键**：降级后要打日志 + 告警，不能静默降级让问题隐藏

---

**【进阶】⭐⭐ 超时、重试、熔断三个机制怎么配合使用？**

参考答案要点：

| 机制 | 作用 | 推荐系统配置 |
|------|------|------------|
| **超时（Timeout）** | 防止无限等待，快速失败 | 召回超时 3s / 精排超时 5s / 模型推理 200ms |
| **重试（Retry）** | 应对瞬时故障（网络抖动） | 最多 3 次，指数退避 100ms→200ms→400ms + 随机抖动 |
| **熔断（Circuit Breaker）** | 防止级联失败，保护下游 | 下游 P99 > 阈值则熔断开，失败率降下来再半开 |

三板斧组合代码：
```python
@timeout(seconds=3)          # Step1: 超时限制
@retry(max_attempts=3, backoff=exponential)  # Step2: 指数退避重试
@circuit_breaker(failure_threshold=5, recovery_timeout=30)  # Step3: 熔断保护
def call_ranking_model(item_ids):
    ...
```

---

**【高难】⭐⭐⭐ 训练-服务特征不一致（Skew）问题是怎么产生的？怎么解决？**

参考答案要点：
- **Skew 原因**：训练用历史特征（T-1），服务时用实时特征（T+0），分布不一致，模型学到的规律在服务时失效
- **推荐系统典型 Skew**：用户历史行为特征（训练用30天，推理用实时）/ Embedding 版本不一致
- **解法**：
  1. **Feature Store 统一管理**，训练/服务共用同一特征管道
  2. **特征签名对比**：上线前跑 `FeatureSignature.compare(train_sign, serve_sign)`，不一致则告警
  3. **PSI 监控**（Population Stability Index）：> 0.2 → 触发特征重训练告警
  4. **时间感知特征设计**：训练时用 T-1 标签对应的 T-1 特征，不"穿越"
  5. **Embedding 统一服务**：训练和服务共用同一个 EmbeddingService，版本号管理

**【基础】⭐ 你写的推荐系统代码，怎么保证质量？**

**【进阶】⭐⭐ 你认为算法工程师和纯后端工程师在代码架构上最大的区别是什么？**

参考答案要点（展示领域思维）：
- **算法工程师的独特挑战**：
  - **训练-服务一致性（Skew）**：模型在离线训练环境和在线服务环境特征/推理方式不一致
  - **实验迭代速度**：A/B 实验需要快速上线/回滚，Feature Flag 必不可少
  - **非功能性指标多元**：不仅要"不报错"，还要看 CTR / 停留时长 / 多样性指标
  - **模型版本管理**：模型更新不能像代码一样随时回滚，需要 Model Registry + 灰度
- **共同点**：分层解耦 / 可测试 / 可观测 / 可降级 → 架构思维是相通的

**【高难】⭐⭐⭐ 假设你要为抖音级别的推荐系统设计架构（日活 7 亿），你会怎么设计？**

参考答案要点（展示系统性思维）：

**容量估算**：
- DAU 7 亿，假设日活用户 1 亿 → 每人每天 30 次推荐请求 → **QPS = 1亿 × 30 ÷ 86400 ≈ 35,000**
- 推荐结果缓存命中率 80% → 纯缓存 QPS ≈ 7,000

**架构设计**：
```
                        ┌─────────────────────────┐
                        │      CDN + API Gateway   │
                        │   (限流/鉴权/就近路由)    │
                        └───────────┬─────────────┘
                    ┌───────────────▼───────────────┐
                    │      召回集群（无状态水平扩展）  │
                    │  多路召回：Embedding/ItemCF/热 │
                    └───────────────┬───────────────┘
                    ┌───────────────▼───────────────┐
                    │      精排集群（GPU推理服务）    │
                    │  DeepFM/DeepFFM/多目标优化     │
                    └───────────────┬───────────────┘
                    ┌───────────────▼───────────────┐
                    │      重排服务（无状态）         │
                    │  多样性/商业干预/位置平滑       │
                    └───────────────┬───────────────┘
                                    │
                    ┌───────────────▼───────────────┐
                    │   推荐结果缓存（Redis Cluster） │
                    │   L1: 本地LRU  L2: Redis      │
                    └───────────────────────────────┘
```

**关键架构决策**：
1. **召回层水平扩展**：无状态，多路召回并行，Kubernetes HPA 按 CPU/P99 扩缩
2. **精排层 GPU 集群**：用 Triton/Ray Serve，模型版本管理 + A/B 路由
3. **事件驱动**：用户行为（点击/播放）→ Kafka → 画像更新/缓存预热/数据分析，异步非阻塞
4. **多级降级**：精排 P99 > 500ms → 自动降级到规则排序；Redis 全崩 → 返回热门列表
5. **可观测性**：Prometheus + Grafana + OTel 追踪，P99/错误率/缓存命中率三指标优先监控

## 四、面试表达模板（STAR 法则）

### 模板一：从 0 到 1 搭建推荐系统架构

```
【背景】当时团队只有我一个算法工程师，
        推荐系统是 Python 单文件，每天都在"改一行影响三处"的状态。

【任务】需要把推荐服务重构成分层架构，
        支持多路召回快速迭代，同时不影响线上服务。

【行动】我用六步渐进式重构：
        ① 加 Feature Flag，新旧逻辑双轨并行
        ② 提取配置层，消灭 30+ 个魔法数字
        ③ 引入 Repository 模式，数据库访问抽象化
        ④ 领域层零依赖，核心逻辑纯 Python 可测试
        ⑤ DI 容器组装，场景化切换推荐策略
        ⑥ 上线验证通过，去掉 Feature Flag

【结果】新增一路召回从 3 人日缩短到 0.5 人日，
        P99 延迟从 800ms 降到 200ms，线上零故障。
```

### 模板二：解决缓存雪崩问题

```
【背景】2024 年双十一，Redis 缓存同时过期，
        导致数据库被打爆，P99 从 50ms 飙到 8s。

【任务】需要彻底解决缓存雪崩，同时不影响缓存命中率。

【行动】三管齐下：
        ① TTL 加随机偏移量（±15%），避免同时过期
        ② 热点数据永不过期，异步更新
        ③ 加本地 L1 缓存兜底，Redis 全崩也能撑住

【结果】双十二峰值时 Redis 延迟 P99 < 30ms，
        缓存命中率维持在 97%，零故障。
```

### 模板三：解决训练-服务 Skew 问题

```
【背景】模型离线评估 AUC 0.78，上线后 CTR 下跌 15%，
        排查两周发现是用户历史行为特征 Skew。

【任务】需要建立特征一致性保障机制，防止 Skew 再次发生。

【行动】三个手段：
        ① 引入 Feature Store（自研轻量版），训练和服务共用同一特征管道
        ② 上线前跑特征签名对比，PSI > 0.2 阻断上线
        ③ Embedding 版本号管理，服务加载和训练保持同一版本

【结果】Skew 问题消除，CTR 恢复到离线 AUC 对应水平，
        每次模型更新前自动跑签名对比，作为上线门禁之一。
```

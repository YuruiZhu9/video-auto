# 设计模式选型指南：推荐系统场景实战地图

> 当你想用设计模式，却不知道该用哪个时，看这张图就够了。

## 模式选择决策树

```

│

│   └─ 否
│       │
│       ├─ 需要创建对象，但创建逻辑复杂/不确定？
│       │   ├─ 是 ──────────────────────────► 工厂模式
│       │   └─ 否
│       │       │
│       │       ├─ 需要一步步构建组合对象（Builder链式）？

│       │       └─ 否
│       │           │
│       │           ├─ 事件触发多系统联动？
│       │           │   └─ 是 ──────────────► 观察者模式
│       │           └─ 否
│       │               │
│       │               ├─ 给对象动态增加功能（装饰器）？

│           └─ 缓存数据 ───────────► Cache-Aside / Write-Through
```

## 一、策略模式（Strategy Pattern）⭐⭐⭐ 最常用

### 核心问题：需要**运行时切换算法**，而不改调用方代码

### 推荐系统场景

| 场景 | 策略A | 策略B | 策略C |
|------|-------|-------|-------|
| 多路召回 | Embedding召回 | ItemCF | UserCF |
| 粗排模型 | LightGBM | XGBoost | 规则打分 |
| 重排多样性 | MMR | DPP | 规则打散 |
| 缓存策略 | LRU | LFU | TTL随机 |

### 代码骨架

```python
# 策略接口
class RecallStrategy(ABC):
    @abstractmethod
    def recall(self, user_id: str, count: int) -> List[str]:
        pass

# 具体策略
class EmbeddingRecall(RecallStrategy):
    def recall(self, user_id: str, count: int) -> List[str]:
        # ...向量召回实现
        pass

class ItemCFRecall(RecallStrategy):
    def recall(self, user_id: str, count: int) -> List[str]:
        # ...ItemCF实现
        pass

# 上下文：使用策略，无需知道具体是哪个
class RecallEngine:
    def __init__(self, strategy: RecallStrategy):
        self._strategy = strategy

    def set_strategy(self, strategy: RecallStrategy):
        self._strategy = strategy  # 运行时切换

    def recommend(self, user_id: str) -> List[str]:
        return self._strategy.recall(user_id, count=100)
```

### 选型信号

- ✅ "能不能一键切换召回路？"
- ✅ "新策略要灰度上线，AB 测试"
- ✅ "不同用户用不同策略"
- ❌ 永远只有一种算法 → 不需要策略模式

## 二、工厂模式（Factory Pattern）⭐⭐ 较常用

### 核心问题：**对象创建逻辑复杂**，不想让调用方知道构造细节

### 推荐系统场景

| 场景 | 工厂创建什么 |
|------|-------------|
| 不同场景的推荐服务 | `RecommendServiceFactory.create("home")` / `create("detail")` |
| 多种模型推理客户端 | `ModelClientFactory.create("deepfm")` / `create("clip")` |
| 不同数据源的 Repository | `RepoFactory.create("mysql")` / `create("hive")` |

### 代码骨架

```python
class RecallStrategyFactory:
    _registry: Dict[str, Type[RecallStrategy]] = {}

    @classmethod
    def register(cls, name: str, strategy_cls: Type[RecallStrategy]):
        cls._registry[name] = strategy_cls

    @classmethod
    def create(cls, name: str, **kwargs) -> RecallStrategy:
        if name not in cls._registry:
            raise ValueError(f"未注册的召回策略: {name}")
        return cls._registry[name](**kwargs)

# 注册
RecallStrategyFactory.register("embedding", EmbeddingRecall)
RecallStrategyFactory.register("itemcf", ItemCFRecall)

# 使用
strategy = RecallStrategyFactory.create("embedding")
```

### 选型信号

- ✅ `__init__` 参数超过 5 个
- ✅ 创建逻辑有分支判断（if scene == "A"）
- ✅ 同一接口有多个实现，需要动态选择
- ❌ 对象创建很简单（直接 `ClassName()`）→ 不需要工厂

## 三、建造者模式（Builder Pattern）⭐ 推荐系统专用

### 核心问题：**对象属性很多**，且有些可选，一步构造不优雅

### 推荐系统场景

```python
# 推荐请求参数爆炸 —— 建造者解决
recommendation_request = (
    RecommendationRequestBuilder(user_id="u123")
    .with_count(20)
    .with_recall_strategies(["embedding", "itemcf"])
    .with_exclude_items(["i456", "i789"])
    .with_diversity_threshold(0.3)
    .with_ctr_boost(1.2)
    .with_category_filter(["数码", "图书"])
    .with_debug(True)
    .build()
)
```

对比不用 Builder：
```python
# 参数位置记不住，可读性差
req = RecommendationRequest(
    user_id="u123",
    count=20,
    strategies=["embedding"],  # 是 strategies 还是 recall_strategies？
    exclude=["i456"],
    diversity=0.3,
    boost=1.2,
    category=["数码"],
    debug=True,
    _reserved=None  # WTF is this?
)
```

### 选型信号

- ✅ 构造函数参数 > 5 个
- ✅ 参数有默认值，且可以组合
- ✅ 经常需要调整参数做实验
- ❌ 参数固定不变 → 直接构造函数

## 四、观察者模式（Observer Pattern）⭐⭐⭐ 事件驱动核心

### 核心问题：**一个事件触发多个处理**，且处理逻辑需要可扩展

### 推荐系统场景

```
用户点击商品
    │
    ├──► ProfileObserver   ──► 更新用户兴趣画像
    ├──► CacheObserver     ──► 清除该用户推荐缓存
    ├──► AnalyticsObserver ──► 上报Kafka → BI
    └──► PushObserver      ──► 触发相似商品推送
```

详见：[观察者模式实战：推荐系统事件监听体系](./观察者模式实战：推荐系统事件监听体系.md)

### 选型信号

- ✅ 一个动作触发 > 2 个后续处理
- ✅ 后续处理需要能被动态添加/移除
- ✅ 处理逻辑之间不应相互依赖
- ❌ 只有单一的后续处理 → 直接调用函数

## 五、装饰器模式（Decorator Pattern）⭐ 推荐系统专用

### 核心问题：**需要动态给对象加功能**，但不想改原类

### 推荐系统场景

```python
# 给推荐结果加解释
@explainable
class ExplainableRankingService:
    def rank(self, candidates: List[str]) -> List[ScoredItem]:
        ...

# 给服务加缓存
@cached(ttl=300)
class RankingService:
    ...

# 给请求加限流
@rate_limit(max_calls=100, window=60)
class RecommendationAPI:
    ...
```

Flask 中装饰器示例：
```python
def require_auth(func):
    @wraps(func)
    def wrapper(*args, **kwargs):
        token = request.headers.get("Authorization")
        if not verify_jwt(token):
            return jsonify({"error": "Unauthorized"}), 401
        return func(*args, **kwargs)
    return wrapper

def log_request(func):
    @wraps(func)
    def wrapper(*args, **kwargs):
        logger.info(f"📥 {request.path} user={g.user_id}")
        start = time.time()
        result = func(*args, **kwargs)
        logger.info(f"📤 {request.path} 耗时 {time.time()-start:.3f}s")
        return result
    return wrapper

# 叠加装饰器：认证 → 日志 → 业务逻辑
@app.route("/api/recommend")
@log_request
@require_auth
def recommend():
    return get_recommendations(g.user_id)
```

### 选型信号

- ✅ 横切关注点（日志/缓存/重试/限流）要复用
- ✅ 需要组合多个功能（装饰器叠加）
- ✅ 不能改原有类（第三方库）
- ❌ 功能耦合在类内部 → 重构优于装饰器

## 六、模板方法模式（Template Method Pattern）⭐

### 核心问题：**流程固定，但部分步骤实现不同**

### 推荐系统场景

```python
class RecommendationPipeline(ABC):
    """模板方法：推荐流程骨架"""

    def recommend(self, user_id: str, count: int) -> List[Item]:
        # 固定流程
        candidates = self.recall(user_id, count * 5)   # Step1: 召回
        candidates = self.filter(candidates)          # Step2: 过滤
        ranked = self.rank(candidates, user_id)        # Step3: 排序
        result = self.rerank(ranked, count)             # Step4: 重排
        return result

    @abstractmethod
    def recall(self, user_id: str, count: int) -> List[Item]:
        pass

    @abstractmethod
    def rank(self, items: List[Item], user_id: str) -> List[ScoredItem]:
        pass

    def filter(self, items: List[Item]) -> List[Item]:
        # 默认实现：通用过滤
        return [i for i in items if i.is_active]

    def rerank(self, items: List[ScoredItem], count: int) -> List[Item]:
        # 默认实现：简单截断
        return [i.item for i in items[:count]]


class HomePageRecommender(RecommendationPipeline):
    def recall(self, user_id, count):
        return self.embedding_recall(user_id, count)

    def rank(self, items, user_id):
        return self.deepfm_rank(items, user_id)

    # 重写rerank：加多样性
    def rerank(self, items, count):
        return self.mmr_diversify(items, count, lambda_=0.3)


class DetailPageRecommender(RecommendationPipeline):
    def recall(self, user_id, count):
        return self.itemcf_recall(user_id, count)  # 详情页用ItemCF

    def rank(self, items, user_id):
        return self.lightgbm_rank(items, user_id)
```

### 选型信号

- ✅ 多个推荐场景共享同一流程（首页/详情页/搜索页）
- ✅ 流程步骤固定，但每步实现因场景而异
- ❌ 各场景流程完全不同 → 策略模式或直接分开写

## 七、代理模式（Proxy Pattern）⭐ 模型服务必备

### 核心问题：**不能或不想直接访问对象**，需要拦截/缓存/延迟

### 推荐系统场景

| 代理类型 | 场景 | 说明 |
|---------|------|------|
| **远程代理** | 模型推理 | 调用远程 TF-Serving / Triton 服务 |
| **缓存代理** | 推荐结果缓存 | Redis 命中则直接返回，不调模型 |
| **保护代理** | 鉴权/限流 | 请求先过保护层 |
| **虚拟代理** | 大图/Embedding | 延迟加载，不一次加载所有向量 |

```python
class ModelProxy:
    """模型推理代理：缓存 + 保护 + 监控"""

    def __init__(self, model_service: ModelService, redis: Redis):
        self.model = model_service
        self.cache = redis
        self.stats = Counter()

    def predict(self, features: dict) -> dict:
        cache_key = self._make_cache_key(features)

        # 缓存代理：命中则返回缓存
        cached = self.cache.get(cache_key)
        if cached:
            self.stats["cache_hit"] += 1
            return json.loads(cached)

        self.stats["cache_miss"] += 1

        # 保护代理：超时控制
        try:
            result = self.model.predict(features, timeout=2.0)
        except TimeoutError:
            self.stats["timeout"] += 1
            return self._fallback()

        # 写入缓存
        self.cache.setex(cache_key, ttl=300, value=json.dumps(result))
        return result
```

### 选型信号

- ✅ 需要缓存结果（避免重复调用）
- ✅ 需要拦截请求（日志/鉴权/限流）
- ✅ 对象创建代价高，需要延迟初始化
- ❌ 直接访问没问题 → 不需要代理

## 模式组合使用示例：推荐系统完整案例

```
用户请求 /api/recommend
│
├─ 【装饰器】@auth ────────────► JWT 鉴权
├─ 【装饰器】@rate_limit ───────► 限流保护
│
├─ 【控制器】recommend()
│   │
│   ├─ 【模板方法】Pipeline.recommend()
│   │   ├─ 【策略】recall() ───────────► EmbeddingRecall / ItemCFRecall
│   │   ├─ 【过滤器】filter() ──────────► 基础过滤
│   │   ├─ 【策略】rank() ──────────────► DeepFM / XGBoost
│   │   ├─ 【代理】ModelProxy.predict() ► 缓存+超时+fallback
│   │   └─ 【策略】rerank() ───────────► MMR / DPP
│   │
│   └─ 【观察者】UserEventBus.publish(event)
│       ├─ ProfileObserver ──► 更新画像
│       ├─ CacheObserver ─────► 清除缓存
│       └─ AnalyticsObserver ► 上报BI
│
└─ 【工厂】ModelClientFactory.create("deepfm") ──► TritonClient
```

## 快速参考表

| 需求 | 首选模式 | 备选模式 |
|------|---------|---------|
| 切换算法（召回路/排序） | **策略模式** | 工厂模式 |
| 创建复杂对象（模型客户端/推荐服务） | **工厂模式** | 抽象工厂 |
| 构建复杂请求对象（参数多） | **建造者模式** | — |

## 最重要的忠告

> **不要为了用模式而用模式。**

| 问自己 | 判断标准 |
|--------|---------|
| 只有一种实现？ | → 不需要策略模式，直接调 |
| 调用方不需要切换实现？ | → 不需要工厂，直接 `ClassName()` |
| 永远只有一种后续处理？ | → 不需要观察者，直接调函数 |
| 逻辑很简单？ | → 用模式反而增加复杂度 |

**模式是解决问题的工具，不是代码水平的证明。** 能用简单代码解决的问题，就不要引入模式。

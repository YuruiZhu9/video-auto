# 知识点 — 重构技巧：从"能跑"到"优雅"

## 概述

重构（Refactoring）是在**不改变外部行为**的前提下，改进代码的内部结构。
重构不是重写，是一步步改善。核心原则：**小步前进，每步测试**。

---

## 一、识别代码坏味道（Code Smell）

在动手重构之前，先学会识别问题。

### 常见坏味道清单

| 坏味道 | 特征 | 危险程度 |
|--------|------|----------|
| **重复代码** | 同样的逻辑出现 3 次以上 | 🔴 高 |
| **过长函数** | 一个函数超过 50 行 | 🔴 高 |
| **过大类** | 一个类超过 500 行 | 🔴 高 |
| **过长参数列表** | 参数超过 3 个 | 🟡 中 |
| **霰弹式修改** | 改一个功能要改多个类 | 🔴 高 |
| **特性依赖** | 类依赖了不该依赖的东西 | 🟡 中 |
| **数据泥团** | 同样的几个字段一起出现 | 🟡 中 |
| **夸夸其谈的通用性** | 过度抽象，实际用不上 | 🟡 中 |

## 二、重构基本手法

### 1. 提取函数（Extract Method）

**何时用**：一个函数干了多件事，或者一个文件超过 200 行。

#### 案例：Flask 路由中的泥团代码

```python
# ── 重构前：一个大函数塞所有逻辑 ─────────────────────────
@app.route("/orders/<int:order_id>", methods=["PUT"])
def update_order(order_id):
    # 1. 参数校验
    data = request.get_json()
    if not data:
        return jsonify({"error": "请求体为空"}), 400
    if "status" not in data:
        return jsonify({"error": "缺少 status 字段"}), 400
    if data["status"] not in ["pending", "paid", "shipped", "delivered"]:
        return jsonify({"error": "无效状态"}), 400

    # 2. 查找订单
    order = Order.query.get(order_id)
    if not order:
        return jsonify({"error": "订单不存在"}), 404

    # 3. 更新状态
    old_status = order.status
    order.status = data["status"]
    db.session.commit()

    # 4. 发通知
    send_notification(order.user_id, f"订单状态从 {old_status} 变为 {data['status']}")

    return jsonify({"message": "更新成功", "order_id": order.id})


# ── 重构后：提取各步骤为独立函数 ─────────────────────────
def validate_status_update(data: dict):
    """参数校验"""
    if not data:
        raise ValueError("请求体为空")
    if "status" not in data:
        raise ValueError("缺少 status 字段")
    if data["status"] not in ["pending", "paid", "shipped", "delivered"]:
        raise ValueError("无效状态")
    return data["status"]

def update_order_status(order_id: int, new_status: str) -> Order:
    """业务逻辑"""
    order = Order.query.get(order_id)
    if not order:
        raise ValueError("订单不存在")
    order.status = new_status
    db.session.commit()
    return order

def notify_status_change(order: Order, old_status: str, new_status: str):
    """通知"""
    send_notification(order.user_id, f"订单状态从 {old_status} 变为 {new_status}")

@app.route("/orders/<int:order_id>", methods=["PUT"])
def update_order(order_id):
    try:
        new_status = validate_status_update(request.get_json())
        order = Order.query.get(order_id)
        if not order:
            return jsonify({"error": "订单不存在"}), 404
        old_status = order.status
        order.status = new_status
        db.session.commit()
        notify_status_change(order, old_status, new_status)
        return jsonify({"message": "更新成功", "order_id": order.id})
    except ValueError as e:
        return jsonify({"error": str(e)}), 400
```

**效果**：
- 每个函数职责单一，可单独测试
- 出错时能快速定位问题
- 后续加验证规则不影响主逻辑

### 2. 移动函数（Move Method）

**何时用**：某个函数和它的宿主类关系不大，反而和另一个类更紧密。

#### 案例：报表逻辑搬家

```python
# ── 重构前：报表逻辑放在 User 类里 ──────────────────────
class User:
    def __init__(self, name, orders):
        self.name = name
        self.orders = orders  # 列表

    def generate_monthly_report(self, year, month):
        # 筛选本月的订单 → 这是订单相关逻辑，不是用户相关
        monthly = [o for o in self.orders
                   if o.date.year == year and o.date.month == month]
        total = sum(o.amount for o in monthly)
        return {"user": self.name, "month": f"{year}-{month}", "total": total}
```

```python
# ── 重构后：移到 ReportService ──────────────────────────
class ReportService:
    def generate_monthly_report(self, user: User, year: int, month: int):
        monthly = [o for o in user.orders
                   if o.date.year == year and o.date.month == month]
        total = sum(o.amount for o in monthly)
        return {"user": user.name, "month": f"{year}-{month}", "total": total}

# User 保持简洁
class User:
    def __init__(self, name, orders):
        self.name = name
        self.orders = orders
```

### 3. 替换条件语句（Replace Conditional with Polymorphism）

**何时用**：一堆 if-else/switch 处理不同类型的行为。

#### 案例：支付方式

```python
# ── 重构前：switch/if 地狱 ──────────────────────────────
def process_payment(order, method):
    if method == "alipay":
        result = alipay_api.pay(order.amount)
        if result.success:
            order.status = "paid"
        else:
            order.status = "failed"
    elif method == "wechat":
        result = wechat_api.pay(order.amount)
        if result.success:
            order.status = "paid"
        else:
            order.status = "failed"
    elif method == "card":
        result = card_api.charge(order.card_token, order.amount)
        if result.success:
            order.status = "paid"
        else:
            order.status = "failed"
    # ...再加10种支付方式？
    return order
```

```python
# ── 重构后：策略模式 + 工厂 ──────────────────────────────
from abc import ABC, abstractmethod

class PaymentStrategy(ABC):
    @abstractmethod
    def pay(self, order) -> bool:
        pass

    def handle_result(self, order, success: bool):
        order.status = "paid" if success else "failed"
        return order

class AlipayStrategy(PaymentStrategy):
    def pay(self, order):
        result = alipay_api.pay(order.amount)
        return self.handle_result(order, result.success)

class WechatPayStrategy(PaymentStrategy):
    def pay(self, order):
        result = wechat_api.pay(order.amount)
        return self.handle_result(order, result.success)

class CardStrategy(PaymentStrategy):
    def pay(self, order):
        result = card_api.charge(order.card_token, order.amount)
        return self.handle_result(order, result.success)

# 工厂：根据方法名返回对应策略
class PaymentFactory:
    _strategies = {
        "alipay": AlipayStrategy,
        "wechat": WechatPayStrategy,
        "card": CardStrategy,
    }

    @classmethod
    def get(cls, method: str) -> PaymentStrategy:
        cls_name = cls._strategies.get(method)
        if not cls_name:
            raise ValueError(f"不支持的支付方式: {method}")
        return cls_name()

# 简化后的使用方
def process_payment(order, method):
    strategy = PaymentFactory.get(method)
    return strategy.pay(order)
```

### 4. 引入参数对象（Introduce Parameter Object）

**何时用**：多个参数总是一起出现。

#### 案例：报表查询参数

```python
# ── 重构前：参数列表过长 ─────────────────────────────────
def get_sales_report(
    start_date: str,
    end_date: str,
    region: str,
    product_category: str,
    sales_channel: str,
    page: int,
    page_size: int
):
    ...

# 调用时：参数顺序容易搞错
get_sales_report("2024-01-01", "2024-12-31", "华东", "电子产品", "线上", 1, 20)
```

```python
# ── 重构后：参数对象 ─────────────────────────────────────
from dataclasses import dataclass
from typing import Optional

@dataclass
class SalesReportQuery:
    start_date: str
    end_date: str
    region: Optional[str] = None
    product_category: Optional[str] = None
    sales_channel: Optional[str] = None
    page: int = 1
    page_size: int = 20

def get_sales_report(query: SalesReportQuery):
    ...

# 调用时：参数名清晰，不会传错
get_sales_report(SalesReportQuery(
    start_date="2024-01-01",
    end_date="2024-12-31",
    region="华东",
    page=1,
))
```

### 5. 重命名（Rename）

**何时用**：变量名/函数名/类名不能清晰表达意图。

```python
# ── 重构前：神秘缩写 ────────────────────────────────────
def calc(a, b, t):
    return a * b * (1 + t)

# ── 重构后：清晰表达 ────────────────────────────────────
def calculate_total_price(quantity: float, unit_price: float, tax_rate: float):
    subtotal = quantity * unit_price
    tax = subtotal * tax_rate
    return subtotal + tax
```

## 三、重构安全规则

### 🔒 黄金法则

```
1. 重构前：确保有测试或能手动验证
2. 重构时：小步进行，每步不超过 5-10 行变动
3. 重构后：立即运行测试确认行为不变
4. 每次重构后：git commit（原子性）
```

### 重构优先级

```
优先重构：
🔴 重复代码（Bug 的温床）
🔴 核心业务逻辑中的坏味道（风险最高）
🔴 经常修改的代码

可以暂缓：
🟡 一次性脚本
🟡 稳定的底层库
🟡 即将废弃的代码
```

## 四、实际重构流程示例

### 场景：从"一个文件打天下"到"模块化结构"

**初始状态**：一个 `app.py` 塞了 800 行代码，所有路由、模型、工具函数混在一起。

**目标**：拆分为清晰的三层架构。

```
步骤：
1. 识别模块边界（哪些是 User 相关，哪些是 Order 相关）
2. 创建目录结构
3. 逐个提取函数/类到新文件
4. 建立 import 关系
5. 验证功能正常
6. 删除旧文件
```

```python
# 初始：app.py 的一部分
@app.route("/users")
def get_users(): ...

@app.route("/orders")
def get_orders(): ...

# 步骤1：创建结构
# app/
#   __init__.py
#   routes/
#     user_routes.py
#     order_routes.py
#   models/
#     user.py
#     order.py

# 步骤2：提取到 routes/user_routes.py
user_bp = Blueprint("users", __name__)

@user_bp.route("/users")
def get_users(): ...

# 步骤3：在 app/__init__.py 重新注册蓝图
def create_app():
    app = Flask(__name__)
    from routes.user_routes import user_bp
    from routes.order_routes import order_bp
    app.register_blueprint(user_bp)
    app.register_blueprint(order_bp)
    return app

# ✅ 结果：每个文件不超过 100 行，职责清晰
```

## 五、常见重构反模式

| 反模式 | 描述 | 对策 |
|--------|------|------|
| **重写式重构** | 一次性重写整个模块，耗时且风险高 | 小步渐进，用测试保护 |
| **抽象癖** | 所有东西都要抽象一层，导致过度设计 | YAGNI，先有具体再抽 |
| **拆分强迫症** | 文件稍长就拆，不考虑内聚性 | 同一模块的代码内聚优先 |
| **重构不提交** | 重构很多步骤后才提交，出问题难以回滚 | 每完成一个小步骤就 commit |

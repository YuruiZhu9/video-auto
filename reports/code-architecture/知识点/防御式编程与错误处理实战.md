# 防御式编程与错误处理实战

> "任何一个傻瓜都能写出计算机能懂的代码，但只有能写出人类能理解的代码，才是真正的工程师。"
> —— Martin Fowler

## 概念解释

### 什么是防御式编程？

防御式编程（Defensive Programming）是一种编程思想：**假设调用者的输入不可信，假设外部服务不可靠，假设任何操作都可能失败**。在此基础上，通过一系列技术手段，确保程序在这些"意外"发生时能：
- **优雅降级**：不影响主流程，或给出合理兜底
- **快速失败**：尽早发现问题，避免错误扩散
- **清晰表达**：错误信息有意义，能定位问题

### 推荐系统场景的特殊性

推荐系统是**多层协作**的系统：
- 上游：客户端传入 user_id、context 参数
- 中游：召回→排序→重排，每个阶段都可能出错
- 下游：MySQL/Redis/Milvus/Kafka，任何一个都可能出现网络抖动

推荐系统的错误处理失误，后果往往是**静默的**：不报错，但推荐结果质量下降（如召回路全部超时→返回空列表→用户体验为"没有推荐"）。这类错误比直接崩溃更难发现。

### 防御式编程 vs 异常处理

| 维度 | 传统异常处理 | 防御式编程 |
|------|------------|-----------|
| 态度 | 假设正常，异常是少数 | 假设任何地方都可能出错 |
| 边界 | 一般到 API/框架层 | 渗透到每一行业务代码 |
| 降级 | 抛异常→上层处理 | 快速失败→合理兜底 |
| 日志 | 简单记录 | 结构化日志 + 上下文 |

**核心原则**：防御式编程不排斥异常机制，而是在异常机制的基础上，加上"信任边界"的概念——来自外部的输入必须校验，来自内部的逻辑可以通过断言确保。

## 一、输入校验：不要相信任何调用者

### 1.1 函数参数校验

**反例（坏味道）**：
```python
def get_recommendations(user_id: int, top_k: int) -> list[dict]:
    # 没有任何校验
    results =召回_engine.recall(user_id)
    results = sort_model.rank(results)
    return results[:top_k]  # top_k 可能是负数、可能是 None
```

**问题**：
- `user_id` 传入 `"abc"` → 类型错误（Python 动态类型不会报错，但逻辑出错）
- `top_k` 传入 `-1` → 返回全部结果，超出预期
- `user_id` 传入 `None` → NPE 风险
- `top_k` 传入 `10000` → 性能问题

**正例（改进后）**：
```python
from pydantic import BaseModel, validator
from typing import Optional

class RecommendRequest(BaseModel):
    user_id: int
    top_k: int = 10
    scene: str = "home"
    context: Optional[dict] = None

    @validator("user_id")
    def user_id_must_be_positive(cls, v):
        if v <= 0:
            raise ValueError("user_id must be positive")
        return v

    @validator("top_k")
    def top_k_must_be_reasonable(cls, v):
        if v <= 0:
            raise ValueError("top_k must be positive")
        if v > 1000:  # 防止性能问题
            raise ValueError("top_k too large, max is 1000")
        return v

    @validator("scene")
    def scene_must_be_valid(cls, v):
        valid_scenes = {"home", "detail", "search", "cart", "order"}
        if v not in valid_scenes:
            raise ValueError(f"scene must be one of {valid_scenes}")
        return v


def get_recommendations(request: RecommendRequest) -> list[dict]:
    # 进入函数时，数据已经校验过了
    results =召回_engine.recall(request.user_id)
    results = sort_model.rank(results)
    return results[:request.top_k]
```

## 二、返回值规范：让错误状态显式化

### 2.1 不要返回 None 表示"没有结果"

**反例**：
```python
def recall_items(user_id: int) -> list[Item]:
    results = self.milvus.search(user_embedding)
    if not results:
        return None  # ❌ 调用者很容易忘记检查 None
```

**正例（三种策略）**：

```python
# 策略一：返回空列表（最推荐，符合 Liskov 替换）
def recall_items(user_id: int) -> list[Item]:
    results = self.milvus.search(user_embedding)
    return results if results else []

# 调用方无需检查 None
items = recall_items(user_id)
for item in items:  # 空列表直接跳过
    pass


# 策略二：返回 Result 包装（明确区分"有结果但为空"和"出错"）
from dataclasses import dataclass
from typing import TypeVar, Generic

T = TypeVar("T")

@dataclass
class Result(Generic[T]):
    success: bool
    data: Optional[T] = None
    error: Optional[str] = None

    @staticmethod
    def ok(data: T) -> "Result":
        return Result(success=True, data=data)

    @staticmethod
    def fail(error: str) -> "Result":
        return Result(success=False, error=error)


def recall_items(user_id: int) -> Result[list[Item]]:
    try:
        results = self.milvus.search(user_embedding)
        return Result.ok(results)
    except MilvusException as e:
        logger.error("recall_failed", user_id=user_id, error=str(e))
        return Result.fail(f"召回失败: {e}")

# 调用方必须处理失败情况
result = recall_items(user_id)
if not result.success:
    logger.warning("recall_fallback_triggered", user_id=user_id)
    return get_popular_items()  # 降级到热门兜底
```

### 2.2 推荐系统场景：三层返回值规范

```python
from dataclasses import dataclass
from enum import Enum

class RecallTier(Enum):
    NORMAL = "normal"      # 正常召回
    PARTIAL = "partial"    # 部分召回（如有过滤导致减少）
    EMPTY = "empty"        # 空召回
    ERROR = "error"        # 召回异常

@dataclass
class RecallResult:
    tier: RecallTier
    items: list[Item]
   召回_source: str  # "embedding" / "item_cf" / "popular"
    count: int
    latency_ms: float

    def is_usable(self) -> bool:
        """判断召回结果是否可用（用于后续排序）"""
        return self.tier in (RecallTier.NORMAL, RecallTier.PARTIAL)

    def get_fallback_score(self) -> float:
        """不同召回质量的置信度（排序层权重参考）"""
        if self.tier == RecallTier.NORMAL:
            return 1.0
        elif self.tier == RecallTier.PARTIAL:
            return 0.8
        elif self.tier == RecallTier.EMPTY:
            return 0.5
        else:
            return 0.0  # ERROR 层不参与排序


def召回_engine.recall(request: RecommendRequest) -> list[RecallResult]:
    """多路召回主入口，每路独立捕获异常"""
    tasks = []
    for strategy in self.strategies:
        try:
            # 每路独立执行，不互相影响
            task = asyncio.create_task(self._recall_one(strategy, request))
            tasks.append(task)
        except Exception as e:
            logger.error("strategy_creation_failed", 
                        strategy=strategy.name, error=str(e))

    results = await asyncio.gather(*tasks, return_exceptions=True)

    valid_results = []
    for i, result in enumerate(results):
        if isinstance(result, Exception):
            logger.error("recall_tier_error", 
                         tier=i, error=str(result))
            continue
        if result.is_usable():
            valid_results.append(result)

    return valid_results
```

## 三、异常设计：分类、分层、有意义

### 3.1 推荐系统异常分类体系

```python
# exceptions.py —— 统一的异常定义
class RecommenderException(Exception):
    """推荐系统基础异常（所有异常的基类）"""
    code: str = "RECOMMENDER_ERROR"
    
    def __init__(self, message: str, details: dict = None):
        super().__init__(message)
        self.message = message
        self.details = details or {}


# ── 数据层异常 ──────────────────────────────
class DataSourceException(RecommenderException):
    """数据源（MySQL/Redis/Milvus）不可用"""
    code = "DATA_SOURCE_ERROR"


class CacheException(RecommenderException):
    """缓存异常（Redis 连接失败等）"""
    code = "CACHE_ERROR"


class VectorDBException(RecommenderException):
    """向量数据库异常"""
    code = "VECTOR_DB_ERROR"


# ── 算法层异常 ──────────────────────────────
class RecallException(RecommenderException):
    """召回层异常（所有召回策略失败）"""
    code = "RECALL_ERROR"


class RankingException(RecommenderException):
    """排序层异常"""
    code = "RANKING_ERROR"


# ── 超时异常（特殊处理）─────────────────────
class TimeoutException(RecommenderException):
    """超时异常（调用方可以根据类型决定是否重试）"""
    code = "TIMEOUT_ERROR"
    retryable = True

    def __init__(self, operation: str, timeout_ms: int):
        super().__init__(
            message=f"{operation} 超时（{timeout_ms}ms）",
            details={"operation": operation, "timeout_ms": timeout_ms}
        )
```

### 3.2 异常处理的黄金法则

```python
# ❌ 错误示范：bare except 吞掉所有异常
def recommend(request: RecommendRequest):
    try:
        return do_recommend(request)
    except:  # 所有异常全部吞掉，完全不知道发生了什么
        return []

# ✅ 正确示范：精确捕获 + 结构化日志
def recommend(request: RecommendRequest):
    try:
        return do_recommend(request)
    except DataSourceException as e:
        # 数据源错误，降级到缓存或静态推荐
        logger.error("datasource_error",
                     user_id=request.user_id,
                     error=e.message,
                     details=e.details)
        return get_fallback_recommendations(request.user_id)
    except RankingException as e:
        # 排序层错误，召回结果直接返回（不排序）
        logger.error("ranking_error",
                    user_id=request.user_id,
                    error=e.message)
        return get_unranked_fallback(request)
    except TimeoutException as e:
        # 超时异常，可能值得重试
        logger.warning("recommend_timeout",
                       user_id=request.user_id,
                       operation=e.details.get("operation"))
        if e.retryable:
            raise  # 让上层决定是否重试
        return get_fallback_recommendations(request.user_id)
    except Exception as e:
        # 未知异常，记录完整上下文，向上传播
        logger.exception("unexpected_error",
                         user_id=request.user_id,
                         error=str(e))
        # 不要 bare return []，让问题暴露出来
        raise RecommenderException(f"推荐服务异常: {e}") from e
```

## 四、防御式编程在推荐系统的核心场景

### 4.1 场景一：外部模型推理

```python
import httpx
from tenacity import retry, stop_after_attempt, wait_exponential

class ModelInferenceClient:
    """模型推理客户端 —— 防御式编程完整示例"""

    def __init__(self, endpoint: str, timeout: float = 3.0):
        self.endpoint = endpoint
        self.timeout = timeout

    @retry(
        stop=stop_after_attempt(3),
        wait=wait_exponential(multiplier=0.5, min=0.5, max=5),
        reraise=True
    )
    async def predict(self, features: list[dict]) -> list[float]:
        """
        防御式调用模型推理服务
        - 超时保护（防止拖垮整个推荐流程）
        - 重试机制（应对瞬时网络抖动）
        - 输入校验（防止传入异常数据导致推理崩溃）
        - 降级策略（推理失败时的兜底）
        """
        # 第一层：输入校验
        if not features:
            logger.warning("model_inference_empty_features")
            return []

        if len(features) > 5000:
            raise RankingException(
                "batch_size too large",
                details={"batch_size": len(features), "max": 5000}
            )

        # 第二层：超时控制（connect + read 双超时）
        async with httpx.AsyncClient(
            timeout=httpx.Timeout(
                connect=1.0,   # 连接超时 1s
                read=self.timeout  # 读取超时可配置，默认 3s
            )
        ) as client:
            try:
                response = await client.post(
                    f"{self.endpoint}/predict",
                    json={"features": features}
                )
                response.raise_for_status()
                result = response.json()

                # 第三层：输出校验（防御模型服务返回异常数据）
                if "scores" not in result:
                    raise RankingException(
                        "invalid_model_response",
                        details={"response_keys": list(result.keys())}
                    )

                scores = result["scores"]
                if len(scores) != len(features):
                    logger.error("score_length_mismatch",
                                features=len(features),
                                scores=len(scores))
                    # 长度不匹配，用规则兜底（不抛异常，避免整个推荐链路中断）
                    return [0.5] * len(features)

                return scores

            except httpx.TimeoutException as e:
                logger.error("model_inference_timeout",
                            timeout=self.timeout,
                            features_count=len(features))
                raise TimeoutException("模型推理", int(self.timeout * 1000)) from e

            except httpx.HTTPStatusError as e:
                logger.error("model_inference_http_error",
                            status=e.response.status_code,
                            body=e.response.text[:200])
                raise RankingException(f"模型服务 HTTP {e.response.status_code}") from e

            except Exception as e:
                logger.exception("model_inference_unknown_error")
                raise RankingException(f"模型推理未知错误: {e}") from e
```

### 4.2 场景二：数据库连接与查询

```python
import aiomysql
from contextlib import asynccontextmanager

class UserProfileRepository:
    """数据访问层 —— 防御式编程完整示例"""

    def __init__(self, pool: aiomysql.Pool):
        self.pool = pool

    @asynccontextmanager
    async def _get_conn(self):
        """连接获取的防御式封装"""
        conn = await self.pool.acquire()
        try:
            yield conn
        finally:
            await self.pool.release(conn)

    async def find_by_id(self, user_id: int) -> Optional[dict]:
        # 第一层：参数防御
        if user_id is None:
            logger.warning("repo_find_by_id_none_user_id")
            return None

        try:
            async with self._get_conn() as conn:
                async with conn.cursor(aiomysql.DictCursor) as cursor:
                    # 第二层：参数化查询（防 SQL 注入）
                    await cursor.execute(
                        "SELECT * FROM user_profile WHERE user_id = %s",
                        (user_id,)
                    )
                    result = await cursor.fetchone()
                    return result

        except aiomysql.OperationalError as e:
            # 第三层：数据库连接错误 → 降级策略
            logger.error("mysql_connection_error",
                        user_id=user_id,
                        error=str(e),
                        errno=e.args[0] if e.args else None)
            # 不抛出，让调用方使用缓存兜底
            return None

        except aiomysql.IntegrityError as e:
            # 第四层：数据完整性错误（不该在查询时发生，但防御一下）
            logger.error("mysql_integrity_error",
                        user_id=user_id,
                        error=str(e))
            return None

    async def batch_find(self, user_ids: list[int]) -> dict[int, dict]:
        """批量查询 —— 防御 N+1 问题"""
        if not user_ids:
            return {}

        if len(user_ids) > 1000:
            logger.warning("batch_find_too_large",
                          size=len(user_ids))
            user_ids = user_ids[:1000]  # 截断，防止查询过大

        try:
            async with self._get_conn() as conn:
                async with conn.cursor(aiomysql.DictCursor) as cursor:
                    # 第三层：IN 查询用 %s 占位符，防止注入
                    # 批量查询防止 N+1
                    format_strings = ','.join(['%s'] * len(user_ids))
                    await cursor.execute(
                        f"SELECT * FROM user_profile WHERE user_id IN ({format_strings})",
                        tuple(user_ids)
                    )
                    rows = await cursor.fetchall()

                    return {row["user_id"]: row for row in rows}

        except Exception as e:
            logger.exception("batch_find_failed",
                           user_ids_count=len(user_ids))
            return {}  # 返回空字典，让调用方走降级逻辑
```

### 4.3 场景三：异步事件发布（Kafka）

```python
import json
from aiokafka import AIOKafkaProducer

class KafkaEventPublisher:
    """事件发布 —— 防御式编程完整示例"""

    def __init__(self, bootstrap_servers: str):
        self.bootstrap_servers = bootstrap_servers
        self.producer: Optional[AIOKafkaProducer] = None

    async def start(self):
        self.producer = AIOKafkaProducer(
            bootstrap_servers=self.bootstrap_servers,
            # 防御式配置
            acks="all",            # 等待所有副本确认（可靠性优先）
            retries=3,            # 重试 3 次
            retry_backoff_ms=100, # 重试间隔
            max_in_flight_requests_per_connection=1,  # 保证有序
            value_serializer=lambda v: json.dumps(v, 
                                                   default=str).encode(),
        )
        await self.producer.start()

    async def publish_click(self, user_id: int, item_id: int, 
                           scene: str, timestamp: datetime):
        """发布点击事件 —— 防御式异步发布"""

        # 第一层：输入校验（事件数据不能为空）
        if not user_id or not item_id:
            logger.warning("kafka_invalid_event_data",
                          user_id=user_id, item_id=item_id)
            return False

        # 第二层：字段类型防御（Kafka 不接受 None）
        event = {
            "event_type": "click",
            "user_id": int(user_id),  # 确保是 int
            "item_id": int(item_id),
            "scene": str(scene),
            "timestamp": timestamp.isoformat() if timestamp else datetime.now().isoformat(),
        }

        try:
            # 第三层：带超时的发送（不阻塞主流程）
            future = await asyncio.wait_for(
                self.producer.send_and_wait(
                    "user-behavior",
                    value=event,
                    key=str(user_id).encode()  # 同用户消息有序
                ),
                timeout=2.0
            )
            record_metadata = future
            logger.debug("kafka_event_published",
                        topic=record_metadata.topic,
                        partition=record_metadata.partition,
                        offset=record_metadata.offset)
            return True

        except asyncio.TimeoutError:
            # 第四层：超时降级（事件发送超时不影响推荐主流程）
            logger.error("kafka_publish_timeout",
                        user_id=user_id,
                        item_id=item_id,
                        event_type="click")
            # 降级：写入本地队列，等待后续重发
            await self._enqueue_local_fallback(event)
            return False

        except Exception as e:
            logger.exception("kafka_publish_error")
            await self._enqueue_local_fallback(event)
            return False

    async def _enqueue_local_fallback(self, event: dict):
        """本地兜底队列 —— Kafka 发送失败时的容灾"""
        # 可以写入 Redis 列表或本地文件，后续补偿任务重发
        logger.warning("event_fallback_queue",
                     event_type=event.get("event_type"),
                     event_size=len(event))
```

## 五、空值防御：Python 的特殊挑战

Python 是动态类型语言，`None` 可以赋值给任何变量，导致空指针错误（AttributeError）比静态类型语言更常见。推荐系统中的数据来源多（MySQL/Redis/Milvus），空值风险尤其高。

### 5.1 链式调用空安全

```python
from functools import singledispatch

# ❌ 链式调用没有空防御
user = get_user(user_id)
score = user.profile.preference.categories[0].score  # 任何一环是 None 就崩溃

# ✅ 使用 getattr 防御
user = get_user(user_id)
if user is None:
    return get_default_score()

profile = getattr(user, "profile", None)
if profile is None:
    return get_default_score()

categories = getattr(profile, "categories", None) or []
score = categories[0].score if categories else get_default_score()

# ✅ 更优雅：使用 Optional + walrus 运算符（Python 3.8+）
user = get_user(user_id)
if user is None:
    return get_default_score()

# walrus := 赋值表达式
if (profile := getattr(user, "profile", None)) is None:
    return get_default_score()

if (categories := getattr(profile, "categories", None)):
    score = categories[0].score
else:
    score = get_default_score()
```

## 六、并发场景的防御式编程

### 6.1 竞态条件防御

```python
import asyncio
from contextlib import asynccontextmanager

class RecommendationCache:
    """推荐结果缓存 —— 并发场景下的防御式编程"""

    def __init__(self, redis_client):
        self.redis = redis_client
        self._locks: dict[str, asyncio.Lock] = {}
        self._lock_guard = asyncio.Lock()  # 保护 _locks 字典本身

    async def _get_lock(self, key: str) -> asyncio.Lock:
        """延迟创建锁（按需创建，避免预创建大量锁）"""
        if key not in self._locks:
            async with self._lock_guard:
                # 双重检查（并发场景下防止重复创建锁）
                if key not in self._locks:
                    self._locks[key] = asyncio.Lock()
        return self._locks[key]

    async def get_or_compute(self, key: str, 
                              compute_fn, 
                              ttl: int = 300) -> list[dict]:
        """
        缓存获取或计算 —— 并发场景下的防御式双检锁
        防止缓存击穿（大量并发请求同时穿透到 DB/模型）
        """
        # 第一层：快速路径（无锁读）
        cached = await self.redis.get(key)
        if cached is not None:
            return json.loads(cached)

        # 第二层：获取锁（防止缓存击穿）
        lock = await self._get_lock(key)
        async with lock:
            # 第三层：双重检查（获取锁后其他协程可能已经写入）
            cached = await self.redis.get(key)
            if cached is not None:
                return json.loads(cached)

            # 第四层：计算（此时才真正查询 DB/模型）
            try:
                result = await asyncio.wait_for(
                    compute_fn(),
                    timeout=5.0  # 计算超时保护
                )
            except asyncio.TimeoutError:
                logger.error("cache_compute_timeout", key=key)
                return []  # 超时返回空，不阻塞

            # 第五层：写入缓存（失败不影响返回）
            try:
                await self.redis.setex(
                    key, ttl,
                    json.dumps(result, default=str)
                )
            except Exception as e:
                logger.warning("cache_set_failed", key=key, error=str(e))
                # 写入失败不影响返回（缓存没有，数据是对的就行）

            return result
```

## 七、结构化日志：错误的可见性保障

防御式编程的核心前提是：**你能看到错误**。没有日志的防御式编程是不完整的。

```python
import structlog
from structlog.contextvars import bind_contextvars

# 配置结构化日志
structlog.configure(
    processors=[
        structlog.contextvars.merge_contextvars,
        structlog.processors.add_log_level,
        structlog.processors.TimeStamper(fmt="iso"),
        structlog.processors.JSONRenderer()
    ]
)

def log_error(operation: str, error: Exception, **kwargs):
    """统一错误日志格式"""
    structlog.get_logger().error(
        "recommender_error",
        operation=operation,
        error_type=type(error).__name__,
        error_message=str(error),
        **kwargs
    )

# 使用示例
def recommend(request: RecommendRequest):
    try:
        return do_recommend(request)
    except RecommenderException as e:
        log_error(
            "recommend",
            e,
            user_id=request.user_id,
            scene=request.scene,
            error_code=e.code,
            details=e.details
        )
        return get_fallback_recommendations(request.user_id)
    except Exception as e:
        log_error(
            "recommend",
            e,
            user_id=request.user_id,
        )
        raise  # 未知异常向上传播
```

## 九、常见误区

### 误区一：过度防御

```python
# ❌ 过度防御：防御到业务逻辑里全是 if-not-None
def process(user_id):
    if user_id is None:
        return None
    name = get_name(user_id)
    if name is None:
        return None
    age = get_age(user_id)
    if age is None:
        age = 0
    return {"name": name, "age": age}

# ✅ 正确：在边界层防御，内部信任已校验的数据
def process(request: RecommendRequest) -> dict:
    # 入参在 API 层已校验，函数内部直接信任
    profile = user_service.get_profile(request.user_id)
    return profile.to_dict()  # profile 为 None 时的行为在 service 层统一处理
```

### 误区二：静默降级

```python
# ❌ 静默降级：错误被吞掉，用户和监控都不知道
try:
    result = recall(user_id)
except:
    pass  # ❌ 完全不知道召回失败了
return popular_items  # 默默返回兜底结果

# ✅ 正确：降级时明确记录和告警
try:
    result = recall(user_id)
except RecallException as e:
    logger.warning("recall_fallback",
                  user_id=user_id,
                  error=e.message,
                  fallback="popular_items")
    # 发送降级监控指标（Prometheus counter）
    RECALL_FALLBACK_TOTAL.labels(reason="recall_error").inc()
return popular_items
```

### 误区三：把异常用于正常业务逻辑

```python
# ❌ 错误：用异常控制正常业务流程
try:
    item = find_item_by_id(item_id)
except ItemNotFoundError:
    # 这是正常情况（用户浏览不存在的商品），不是异常！
    return []

# ✅ 正确：用返回值表达正常状态
item = find_item_by_id(item_id)
if item is None:  # 或 Result.ok(item)
    return []  # 正常业务路径，不是异常
```

### 误区四：重试所有异常

```python
# ❌ 错误：重试非幂等操作或不可恢复的错误
@retry(stop=after_3_attempts())
async def create_order(order_id):
    await db.insert(order_id)  # 重复插入会导致重复订单！
    return "created"

# ✅ 正确：只重试瞬时错误，且操作本身是幂等的
@retry(
    stop=after_3_attempts(),
    retry=retry_if_exception_type(TimeoutException)
)
async def get_recommendations(user_id):
    # GET 请求天然幂等，可以安全重试
    return await http_client.get(f"/recommend/{user_id}")
```

## 十、推荐系统防御式编程自查清单

上线前对照检查：

**输入边界**
- [ ] 所有 API 请求参数有 Pydantic/参数校验
- [ ] 数值参数有合理范围限制（如 top_k ≤ 1000）
- [ ] 外部服务返回数据有非空检查

**异常处理**
- [ ] 每层（召回/排序/重排）独立 try-except，互不影响
- [ ] 异常有结构化日志，包含 user_id/scene/error_type
- [ ] 降级路径有监控指标（Prometheus Counter）
- [ ] bare except 已全部消除

**超时保护**
- [ ] 每个外部调用有 connect + read 双超时
- [ ] 批量调用有总超时（如 asyncio.wait_for）
- [ ] 超时异常能区分是否值得重试

**降级兜底**
- [ ] 每层都有降级预案（召回路全挂→热门兜底）
- [ ] 降级后用户无感知（不报错，只降质量）
- [ ] 降级事件有日志和告警

**并发安全**
- [ ] 多协程访问共享资源有锁保护
- [ ] 缓存击穿有双检锁保护
- [ ] 没有暴露 `await` 在同步函数中

---

## 总结

防御式编程的核心是**三个态度**：

1. **对外部输入**：不信任 → 必须校验
2. **对外部服务**：不可靠 → 必须降级
3. **对未知错误**：不知道会发生什么 → 必须有日志和兜底

推荐系统因为涉及多个外部数据源和多层算法协作，防御式编程尤为重要。最关键的习惯：**永远不要 bare except，永远不要静默降级**。

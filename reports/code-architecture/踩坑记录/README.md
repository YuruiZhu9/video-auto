### 技术债识别与偿还策略

**四象限分类**：
```
有意识 + 慎重决策 = 明智的债（值得保留）
有意识 + 匆忙决定 = 鲁莽的债（避免）
无意识 + 疏忽    = 疏忽的债（Code Review 预防）
无意识 + 衰退    = 衰退的代码（持续重构应对）
```

**6 种还债方法**：
1. Boy Scout Rule — 顺手还，不积累
2. Strangler Fig — 绞杀者模式，渐进替换老模块
3. Expand-Contract — 安全改 API，不破坏现有调用
4. 抽象隔离墙 — Bridge Pattern，切断依赖
5. ADR 记账 — 决策记录，到期还债
6. 保姆式重构（陷阱）— ⚠️ 不要专门花整块时间还债

**推荐系统典型债**：
- Embedding 服务耦合（换模型要重启）
- 特征线上线下不一致（训练-服务 Skew）
- 硬编码召回策略（无法动态切换）
- 缓存无失效机制（用户行为更新慢）

### 重构实战：从单文件到分层架构

**渐进式 4 步重构**：
```
Step 1：安全优先（不动业务逻辑，先止血）
        → 修复 SQL 注入 + 连接生命周期
Step 2：提取 Service 层（业务逻辑与 Flask 解耦）
        → 推荐服务独立，可单元测试
Step 3：提取 Repository 层（数据访问抽象）
        → MySQL/Redis 替换无需改业务代码
Step 4：引入 Domain 层（四层架构完成）
        → 算法工程师可独立维护领域逻辑
```

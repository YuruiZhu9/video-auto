# 踩坑记录 — 常见架构错误与应对

## 记录说明

本文档记录代码架构实践中的真实踩坑经验，持续更新。

---

## 坑1：Controller 变成了"万能胶水"

### 症状
- Controller 里写了大段业务逻辑（数据库操作、计算、验证全塞在一起）
- Service 层几乎为空，只是简单转发
- 单测时 Controller 和 Service 都需要 mock 一堆东西

### 踩坑经历
```python
# ❌ 踩坑代码：Controller 干了 Service + Repository 的活
@router.post("/orders")
def create_order():
    data = request.get_json()
    # 验证
    if not data.get("user_id"):
        return {"error": "缺少 user_id"}, 400
    if data["amount"] <= 0:
        return {"error": "金额必须大于0"}, 400
    # 业务逻辑：检查用户存在
    user = db.session.query(User).filter(User.id == data["user_id"]).first()
    if not user:
        return {"error": "用户不存在"}, 404
    # 扣库存
    product = db.session.query(Product).filter(Product.id == data["product_id"]).first()
    if product.stock < data["quantity"]:
        return {"error": "库存不足"}, 400
    product.stock -= data["quantity"]
    # 创建订单
    order = Order(user_id=data["user_id"], product_id=data["product_id"], quantity=data["quantity"])
    db.session.add(order)
    db.session.commit()
    # 发通知
    send_notification(user.email, "订单创建成功")
    return {"order_id": order.id}
```

### 解决方案
严格按三层架构分层，每层各司其职：
```
Controller → 只做参数解析 + 调用 Service + 包装响应
Service → 处理业务规则（验证、计算、组合）
Repository → 数据存取（纯粹的 CRUD）
```

### 预防措施
- Code Review 时检查 Controller 代码行数，超过 50 行重点审查
- Service 层必须有单测，Controller 主要靠集成测试

## 坑2：过早抽象（Over-abstraction）

### 症状
- 一个小项目里搞了泛型基类、抽象工厂、策略模式全集
- 实际代码中每种实现只出现一次
- 新人接手时完全看不懂

### 踩坑经历
```typescript
// ❌ 踩坑代码：为"可能的扩展"写了一大套抽象
abstract class DataSource<T> {
  abstract fetch(query: Query): Promise<T[]>;
  abstract insert(data: T): Promise<T>;
  abstract update(id: string, data: T): Promise<T>;
  abstract delete(id: string): Promise<void>;
}

class UserDataSource extends DataSource<User> { ... }  // 只有一个实现
class ProductDataSource extends DataSource<Product> { ... }  // 只有一个实现

// 项目里从头到尾只用到 UserDataSource，但花了3倍时间写这套抽象
```

### 解决方案
- **YAGNI 原则**：先写简单实现，等真正需要扩展时再重构
- **Rule of Three**：同一模式出现 3 次以上才抽象

## 坑3：Service 层不依赖注入，改用全局变量/单例

### 症状
- Service 里直接 import 一个全局 db 连接
- 测试时无法 mock 数据
- Service 单测变成集成测试

### 踩坑经历
```python
# ❌ 踩坑代码：Service 直接 import 全局 db
from database import db  # 全局 db 对象

class OrderService:
    def get_order(self, order_id):
        # 直接用全局 db，无法 mock
        return db.session.query(Order).get(order_id)

# 测试时：必须创建真实数据库
def test_get_order():
    db = create_test_db()  # 慢，且不稳定
    ...
```

### 解决方案
- 依赖注入：构造函数接收 db 实例
- 测试时传入 Mock 对象

```python
# ✅ 正确做法：注入依赖
class OrderService:
    def __init__(self, db: Session):
        self.db = db

# 测试时：
mock_db = MagicMock()
svc = OrderService(mock_db)
mock_db.query.return_value.get.return_value = Order(...)
```

## 坑4：循环依赖（Circular Dependency）

### 症状
- 项目启动时报 `ImportError: circular import`
- 改 A 文件时 B 文件报错，改 B 时 A 报错
- 越拆越多，最后一团糟

### 常见场景

```python
# ❌ a.py → b.py → a.py 循环
# a.py
from b import B
class A:
    def use_b(self): return B().do()

# b.py
from a import A   # ❌ 循环导入
class B:
    def do(self): return "done"
```

### 解决方案
1. **延迟导入**：在函数内部 import
2. **提取公共接口**：把共享的类型/抽象放到单独的 `interfaces.py`
3. **依赖倒置**：依赖抽象（接口/基类）而非具体类

```python
# ✅ 解决方案：抽离到 interfaces.py
# interfaces.py
class IB:
    def do(self): pass

# a.py
from interfaces import IB
class A:
    def __init__(self, b: IB): self._b = b
    def use_b(self): return self._b.do()

# b.py
from interfaces import IB
class B(IB):
    def do(self): return "done"
```

## 坑5：把"贫血模型"当成"好设计"

### 症状
- Model 类只有数据字段 + getter/setter，没有任何业务逻辑
- 所有业务逻辑都堆在 Service/Manager/Utils 类里
- Model 类变成了"数据容器"，丧失面向对象的意义

### 踩坑经历
```python
# ❌ 贫血模型：Order 只有字段，逻辑全在外面的 OrderManager
class Order:
    def __init__(self):
        self.id = None
        self.user_id = None
        self.amount = 0

class OrderManager:
    def calculate_discount(self, order):  # 本该属于 Order
        ...

    def validate_order(self, order):  # 本该属于 Order
        ...
```

### 解决方案
- **领域驱动设计（DDD）**：把业务逻辑放到实体（Entity）里
- Model 既要有数据，也要有行为

```python
# ✅ 充血模型：Order 包含核心业务逻辑
class Order:
    def __init__(self, items: list[OrderItem], user: User):
        self.items = items
        self.user = user

    @property
    def amount(self) -> float:
        return sum(i.price * i.quantity for i in self.items)

    def apply_discount(self, code: str):
        if code == "SAVE10":
            self._discount = self.amount * 0.1
        ...

    def validate(self):
        if not self.items:
            raise ValueError("订单不能为空")
        ...
```

## 坑6：忽视分层边界，跨层直接调用

### 症状
- Router 直接调用 Repository，跳过 Service 层
- Service 层被架空，逐渐消亡
- 业务规则分散，难以维护

```
❌ Router → Repository（跳过 Service）
✅ Router → Service → Repository
```

### 解决方案
- 约定：禁止跨层调用，Router 只能调用 Service
- 如果发现"不需要 Service"的场景，很可能是业务逻辑太简单，不需要抽象

---

## 坑7：重构后不跑测试，直接上线

### 症状
- 重构后自信满满，直接部署
- 运行时才发现某个边界条件没考虑到
- 回滚成本高，影响用户

### 解决方案
1. 重构前确保有单测覆盖
2. 重构后运行全部测试
3. 小步部署，观察监控
4. 保留快速回滚能力

---

## 经验总结

| 序号 | 坑名 | 预防方法 |
|------|------|----------|
| 1 | Controller 变胖 | 保持 Service 层充盈，Controller ≤ 50 行 |
| 2 | 过早抽象 | YAGNI，等需要时再重构 |
| 3 | 全局依赖 | 坚持依赖注入 |
| 4 | 循环依赖 | 延迟导入 + 依赖倒置 |
| 5 | 贫血模型 | 业务逻辑尽量放在 Model 层 |
| 6 | 跨层调用 | 严格遵守分层约定 |
| 7 | 重构不测 | 每步重构 + 测试 + commit |

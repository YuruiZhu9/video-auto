# 代码架构踩坑记录

## 1. 过度设计

### 问题
为了"未来扩展"预留太多抽象，结果代码复杂度飙升，实际需求却很简单。

### 教训
- **YAGNI**：不要预先设计你不需要的东西
- 先简单实现，等需求明确后再重构
- 简单的代码优于复杂的代码

### 案例
```python
# 过度设计
class Animal(ABC):
    @abstractmethod
    def speak(self): pass

class Dog(Animal): ...
class Cat(Animal): ...
class Bird(Animal): ...

# 实际只需要
def make_speak(animal_type):
    sounds = {'dog': '汪', 'cat': '喵', 'bird': '吱'}
    return sounds.get(animal_type, '')
```

## 2. 过度拆分

### 问题
为了单一职责，把简单函数拆得到处都是，反而增加理解成本。

### 教训
- 单一职责不是越细越好
- 考虑代码的可读性和团队熟悉度
- 一致性比完美更重要

### 案例
```python
# 过度拆分
def calculate_total(items):
    return _sum_prices(items)

def _sum_prices(items):
    return sum(_get_prices(items))

def _get_prices(items):
    return [item.price for item in items]

# 简单明了
def calculate_total(items):
    return sum(item.price for item in items)
```

## 3. 教条化遵循原则

### 问题
为了遵循"依赖倒置"硬套接口，结果引入不必要的复杂度。

### 教训
- 原则是指导，不是教条
- 小项目不需要过度抽象
- 权衡成本和收益

### 案例
```python
# 小项目不需要
class IUserRepository(ABC):
    @abstractmethod
    def get_user(self, id): ...

class MySQLUserRepo(IUserRepository): ...

# 简单项目直接用
class UserService:
    def __init__(self):
        self.repo = UserRepository()  # 直接实例化就好
```

## 4. 忽视团队能力

### 问题
用了很"高级"的架构，但团队不会维护。

### 教训
- 架构要考虑团队实际情况
- 渐进式引入新技术
- 文档和培训跟得上

---

## 5. 过早优化

### 问题
在还不知道性能瓶颈在哪时就做各种"优化"。

### 教训
- 先跑起来，再优化
- 用数据说话，不是猜测
- 优化有代价：增加复杂度

---

## 6. 接口滥用

### 问题
每个类都加接口，即使只有一个实现。

### 教训
- 只有一个实现时，不需要接口
- 等到需要Mock测试时再加
- 接口是契约，不是装饰

---

## 7. 分层过细

### 问题
Service、Repository、Manager、Helper...分太多层。

### 教训
- 3-4层足够
- 每层要有真正价值
- 不要为了分层而分层

---

## 8. 命名随意

### 问题
方法名、类名不清晰，代码难以理解。

### 教训
- 好的命名是最好的文档
- 名字要能表达意图
- 团队统一命名规范

---

## 9. 不写测试

### 问题
重构没有安全网，不敢改代码。

### 教训
- 单元测试是重构的基础
- 从关键业务开始覆盖
- 测试不是越多越好

---

## 10. 一步到位心态

### 问题
想一次设计完美的架构。

### 教训
- 架构是演进的，不是设计出来的
- 小步快跑，持续改进
- 接受"不够好"，追求"刚刚好"

---

## 总结

| 坑 | 教训 |
|---|------|
| 过度设计 | YAGNI |
| 过度拆分 | 平衡复杂度 |
| 教条原则 | 权衡收益 |
| 忽视团队 | 务实优先 |
| 过早优化 | 数据驱动 |
| 接口滥用 | 需求驱动 |
| 分层过细 | 够用就好 |
| 命名随意 | 自文档 |
| 不写测试 | 测试护航 |
| 一步到位 | 持续演进 |

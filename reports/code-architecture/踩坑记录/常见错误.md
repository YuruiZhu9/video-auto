# 踩坑记录

## 1. 过度设计

### 问题
为了"扩展性"设计过度，导致代码复杂度激增。

### 教训
- 不要过度设计，YAGNI原则
- 先让代码跑起来，再逐步优化
- 简单优于复杂

### 案例
```python
# 过度设计
class AbstractUserFactory:
    @abstractmethod
    def create_user(self): pass

class VIPUserFactory(AbstractUserFactory):
    def create_user(self): pass

# 够用就好
class UserService:
    def create_user(self, user_type='normal'):
        pass
```

## 2. 教条化遵循原则

### 问题
为了遵循单一职责，把简单类拆得七零八落。

### 教训
- 原则是指导，不是教条
- 平衡复杂度与可维护性
- 经验判断何时拆分

### 案例
```python
# 教条化拆分
class UserName: pass
class UserEmail: pass
class UserAge: pass
# 这是过度拆分！

# 合理做法
class User:
    def __init__(self, name, email, age):
        self.name = name
        self.email = email
        self.age = age
```

## 3. 忽略依赖注入

### 问题
直接在类内部创建依赖，导致难以测试和替换。

### 教训
- 使用依赖注入
- 便于单元测试（Mock）
- 降低模块耦合

### 错误示例
```python
class OrderService:
    def __init__(self):
        self.email_service = EmailService()  # 内部创建！
```

---

## 4. 接口设计过大

### 问题
设计一个"万能接口"，强迫用户实现不需要的方法。

### 教训
- 接口要小而专注
- 按需分离接口
- 遵循接口隔离原则

---

## 5. 重构时不写测试

### 问题
重构过程中破坏功能，导致线上bug。

### 教训
- 重构前先有测试覆盖
- 小步前进
- 改完立即验证

---

## 6. 三层架构流于形式

### 问题
创建了分层目录，但业务逻辑仍然散落各处。

### 教训
- 分层是思维方式，不只是目录结构
- 每层有明确的职责边界
- 表现层不应包含业务逻辑

---

## 7. 过早优化

### 问题
在代码还没跑通时就考虑性能优化。

### 教训
- 先让代码工作，再考虑优化
- 性能问题通过profiling定位
- 不要预判性能瓶颈

---

## 8. 忽视代码可读性

### 问题
追求技巧性代码，导致难以理解。

### 教训
- 代码首先是给人看的
- 清晰的命名很重要
- 注释解释"为什么"，不解释"是什么"

---

## 经验总结

1. **原则是工具，不是枷锁**
2. **小步迭代优于大而全**
3. **测试是重构的保障**
4. **简单清晰优先于技巧**
5. **实践出真知，多看开源项目**

# 踩坑记录

记录学习代码架构过程中遇到的典型问题及解决方案。

---

## 1. 分层过度

### 问题
为了"架构"而架构，分了太多层，导致简单功能要写很多文件。

### 教训
- 小项目（<1000行代码）不需要严格分层
- 渐进式重构：先写简单代码，发现问题再拆分
- 记住：**简单 > 教条**

---

## 2. 过度设计

### 问题
用了很多设计模式，但实际场景根本不需要。

### 教训
- 设计模式是解决特定问题的，不是装饰品
- "先让它跑起来，再考虑优化"
- YAGNI原则：You Aren't Gonna Need It

---

## 3. 循环依赖

### 问题
```
A 导入 B
B 导入 A
→ 死循环，启动报错
```

### 常见场景
- Service 之间相互依赖
- Module 之间相互导入

### 解决方案
- 用事件/消息解耦
- 把共享代码提取到第三个模块
- NestJS：使用 forwardRef()

---

## 4. 数据库事务忘记提交

### 问题
```python
def transfer_money(from_id, to_id, amount):
    conn = get_connection()
    conn.execute("UPDATE accounts SET balance -= ? WHERE id = ?", 
                 (amount, from_id))
    conn.execute("UPDATE accounts SET balance += ? WHERE id = ?", 
                 (amount, to_id))
    # 忘记 conn.commit()
```
钱可能没到账！

### 教训
- 使用 with 语句自动 commit/rollback
- 或使用 ORM 的事务装饰器

---

## 5. 接口设计不稳定

### 问题
经常改 API 接口，导致前端跟着改。

### 教训
- 接口即契约，设计要慎重
- 使用版本号：/api/v1/users
- 考虑向前兼容

---

## 6. 硬编码配置

### 问题
```python
class EmailService:
    def send(self):
        smtp = smtplib.SMTP('smtp.qq.com', 587)  # 硬编码
```
换环境要改代码。

### 教训
- 使用配置文件或环境变量
- 依赖注入配置

---

## 7. 忽略错误处理

### 问题
```python
def get_user(user_id):
    user = db.query(user_id)
    return user.name  # user 可能是 None
```
→ 崩溃！

### 教训
- 永远检查空值
- 统一错误处理中间件
- 日志记录

---

## 8. 单元测试难写

### 问题
代码耦合严重，无法单独测试。

### 教训
- 依赖注入让测试更容易
- 先写测试再重构（TDD）
- 测试替身（Mock）隔离依赖

---

## 9. 命名不规范

### 问题
```python
def do():
    a = get_data()
    b = process(a)
    return c
```
鬼知道这些变量是什么。

### 教训
- 命名要表达意图
- 团队统一命名规范
- 优先使用完整的英文单词

---

## 10. 忘记索引

### 问题
查询慢：
```sql
SELECT * FROM users WHERE email = 'test@example.com'
-- email 没有索引，全表扫描
```

### 教训
- 根据查询条件添加索引
- 分析慢查询日志
- 权衡：索引不是越多越好

---

## 总结

| 坑 | 关键词 | 解决方案 |
|----|--------|----------|
| 过度分层 | 简单>教条 | 渐进式重构 |
| 过度设计 | YAGNI | 先跑起来 |
| 循环依赖 | 解耦 | forwardRef/事件 |
| 事务遗漏 | 自动提交 | with/装饰器 |
| 接口改来改去 | 契约 | 版本号 |
| 硬编码 | 配置 | 环境变量 |
| 空值崩溃 | 防御 | 检查+统一处理 |
| 测试难写 | 依赖注入 | 解耦+Mock |
| 命名乱 | 意图 | 规范+英文 |
| 查询慢 | 索引 | EXPLAIN 分析 |

# 代码架构踩坑记录

## 1. 过度设计

### 踩坑经历
早期学习架构模式时，什么都想用最好的设计。做一个简单的CRUD系统，非要上领域驱动设计（DDD），引入充血模型、领域服务、仓储模式等，导致：
- 代码量翻倍
- 学习成本高
- 维护困难

### 教训
- **根据项目规模选择架构**
- 小项目：MVC足够
- 中型项目：三层架构
- 大型项目：DDD
- **YAGNI原则**：不要过度设计

---

## 2. 分层不彻底

### 踩坑经历
```python
# ❌ 看起来分层了，但业务逻辑散落各处
class UserController:
    def create_user(self, data):
        # 这里既有验证
        if not data.get('email'):
            raise ValueError("Email required")
        
        # 又有数据库操作
        db.execute("INSERT INTO users...")
        
        # 还有业务逻辑
        if data.get('is_admin'):
            self.send_admin_welcome_email()
        
        return user
```

### 教训
- **每一层必须有明确的职责**
- Controller：接收请求，返回响应
- Service：业务逻辑
- Repository：数据访问
- **不要跨层调用**

## 3. 依赖关系混乱

### 踩坑经历
```python
# ❌ 循环依赖
from services.user_service import UserService
from repositories.user_repository import UserRepository

class UserService:
    def __init__(self):
        self.repo = UserRepository()

class UserRepository:
    # 某些情况下需要调用Service
    def delete_user(self, user_id):
        user = self.get_by_id(user_id)
        # 调用Service做业务处理
        notification = NotificationService()  # 临时创建
        notification.send_deletion_email(user)
```

### 教训
- **依赖方向必须统一**：高层→低层（抽象）
- **使用依赖注入**：不要在类内部创建依赖
- **避免循环依赖**：用接口解耦

## 4. 接口定义过大

### 踩坑经历
```typescript
// ❌ 胖接口，所有实现都要实现所有方法
interface IDataManager {
    read(): any;
    write(data: any): void;
    delete(id: string): void;
    search(query: string): any[];
    backup(): void;
    restore(backup: string): void;
}

// 只想读数据的类也要实现所有方法
class ReadOnlyDataSource implements IDataManager {
    read() { /* ... */ }
    write() { throw new Error("Not supported"); }
    delete() { throw new Error("Not supported"); }
    search() { /* ... */ }
    backup() { throw new Error("Not supported"); }
    restore() { throw new Error("Not supported"); }
}
```

### 教训
- **接口隔离原则**：使用小接口
- **按需定义**：只暴露需要的方法
- **组合优于继承**：多个小接口 > 一个大接口

## 5. 忽略单元测试

### 踩坑经历
项目重构时，因为没有测试覆盖，改一行代码都提心吊胆：
- 不敢改
- 改了不敢上线
- 上线后疯狂回滚

### 教训
- **重构前先写测试**
- **测试金字塔**：单元测试 > 集成测试 > E2E测试
- **CI/CD集成测试**

---

## 6. 数据库模型 = 领域模型

### 踩坑经历
```python
# ❌ 直接把数据库表映射到Model
class UserModel:
    """数据库表结构"""
    id: int
    name: str
    email: str
    password_hash: str
    created_at: datetime
    updated_at: datetime
    is_deleted: bool
    
    # 业务方法混在Model里
    def send_welcome_email(self):
        send_mail(self.email, "Welcome!")
    
    def calculate_discount(self):
        # 业务逻辑也在Model里
        return 0.1
```

### 教训
- **数据库模型 ≠ 领域模型**
- 数据库模型：数据结构
- 领域模型：业务概念
- **使用DTO做转换**

## 7. 忽略异常处理

### 踩坑经历
```python
# ❌ 吞掉所有异常
def process_data(data):
    try:
        # 处理逻辑
        result = do_something(data)
        return result
    except Exception:
        pass  # 静默忽略！
    
    return None
```

### 教训
- **区分可恢复和不可恢复异常**
- **记录日志**
- **给用户友好的错误提示**
- **不要吞掉异常**

## 8. 配置硬编码

### 踩坑经历
```python
# ❌ 硬编码配置
class PaymentService:
    def process_payment(self, amount):
        api_key = "sk_live_xxxxx"  # 硬编码！
        webhook_url = "https://example.com/webhook"
        
        # 调用支付API
        response = requests.post(
            "https://payment.example.com/api",
            headers={"Authorization": f"Bearer {api_key}"},
            json={"amount": amount, "webhook": webhook_url}
        )
```

### 教训
- **使用配置文件或环境变量**
- **敏感信息使用密钥管理服务**
- **区分开发和生产配置**

## 9. 不重视代码审查

### 踩坑经历
- 觉得自己代码写得不错
- 不想被人review
- 导致问题积累，后期难以维护

### 教训

- **至少找一个人review**

## 10. 为了架构而架构

### 踩坑经历
- 引入所有"最佳实践"
- 过度使用设计模式
- 项目复杂度爆炸

### 教训
- **架构服务于业务**
- **简单 > 复杂**
- **重构是迭代的**
- **先让它工作，再让它更好**

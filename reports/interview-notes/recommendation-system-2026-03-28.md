### Q1: 双塔模型（DSSM）工作原理是什么？为什么底层不做特征交叉？

**参考答案：**

**原理：** 双塔模型全称为 Deep Structured Semantic Model，将用户和物品分别输入两个独立的深度神经网络（Tower），输出固定维度的 Embedding 向量。线上服务时，通过计算两个向量的内积或余弦相似度来衡量匹配程度。

```
用户塔: User Features → DNN → User Embedding (128/256维)
物品塔: Item Features → DNN → Item Embedding (128/256维)
在线服务: score(u, i) = <User_Embedding, Item_Embedding>
```

**物品向量可离线预计算**存入 Faiss/Milvus 等向量索引，线上只需实时计算一次 User Embedding，然后做 ANN 检索，延迟可控制在 50ms 以内。

**为什么底层不做特征交叉：**
1. **计算约束**：召回层候选集通常百万~千万量级，若底层有交互，需实时将用户特征与每个物品逐一组合计算，O(N) 复杂度不可接受
2. **向量检索前提**：双塔结构使物品向量可以预计算、离线建好索引，是 ANN 检索的必要条件
3. **总结**：牺牲底层特征交叉的精度，换取全库检索效率——这是精度与延迟的经典权衡

**面试加分点：** 提及"对偶增强"（Dual Augmented）或者 SIM 等改进方案如何扩展双塔的能力边界。

### Q2: 双塔模型负样本如何选择？曝光未点击能做负样本吗？

**参考答案：**

**核心结论：不能用曝光未点击直接做负样本。**

**深层原因——样本选择偏差（Sample Selection Bias, SSB）：**
- 召回层的目标是从全量库（百万/千万级）中筛选
- "曝光未点击"仅来自上一轮精排筛选出的"精选集"（通常仅几百到几千个）
- 若只用曝光未点击训练，模型无法学习对全库中真正无关物品的鉴别力
- 模型会学到"精选集中没被点击的物品不该被召回"，而非"全库中不该被召回的物品不该被召回"

**正确做法：**

| 负样本类型 | 说明 | 适用场景 |
|-----------|------|---------|
| **全局随机负样本** | 从全量物品库随机采样（不含正样本） | 必做，让模型有全库视野 |
| **Batch内负样本** | 同一Batch内其他用户的正样本作为自己的负样本 | 高效，适合大规模训练 |
| **Hard Negative Mining** | 选取"被召回了但未被点击"的物品 | 进阶，提升区分能力 |

**代码级实现示意：**
```python
# 全局随机负采样
neg_items = random.sample(all_items - user_pos_items, k=num_neg)
# Hard Negative（离线统计召回但未点击的物品）
hard_neg_items = get_hard_negatives(user_id, top_k_recalled, not_clicked=True)
```

**面试追问：** "为什么Hard Negative要控制在正样本的5~10倍比例？" 答：比例太高会让模型过拟合困难样本，伤害整体泛化性。

### Q3: 多路召回如何融合？固定配额对不对？

**参考答案：**

**固定配额是错误的。** 不同召回源在不同场景、用户群体下表现差异巨大，固定配额会丢弃高质量召回结果，保留低质量结果。

**正确融合方案：**

**方案一：归一化加权**
- Min-Max 归一化或 Z-Score 标准化各路召回得分
- 缺点：受异常值影响大，不够鲁棒

**方案二：基于转化率的静态加权（推荐入门方案）**
```python
Final_Score = α_channel × Normalized_Score
# α_channel = 各路召回过去7天 CTR/CVR 作为权重
```

**方案三：轻量级融合模型（工业界主流）**
- 使用 LR 或 GBDT 模型预测粗略 CTR，将各路召回得分作为特征输入
- 本质是"粗排"阶段，提前做多路融合
- 优势：自动学习各路召回的相对重要性，且能适应不同用户群体

**兜底策略：**
- **去重**：按 Item ID 去重，避免同一物品被多路召回重复出现
- **强插补足**：热门物品队列或新品队列直接强插，保证基本曝光

**面试加分：** 提到"分层融合"——先按类别融合（语义召回+行为召回），再按权重融合。

### Q4: ANN（近邻检索）原理，HNSW vs ScaNN 各有何优劣？

**参考答案：**

**核心思想：** 不做全库逐个比较，而通过建立索引结构实现近似最近邻搜索，将 O(N) 降低为 O(log N) 或 O(n^0.5)。

**HNSW（Hierarchical Navigable Small World）：**
- 基于图的多层跳表结构，构建时随机选择层数，越高层越稀疏
- 搜索时从最高层开始贪心，向下逐层收敛
- **优点**：无需训练，插入效率高，对动态更新的物品库友好
- **缺点**：内存占用大（HNSW图需要额外存储邻居关系），高维时性能下降

**ScaNN（Google，量化方法）：**
- 对向量做量化（Product Quantization，PQ），将高维向量压缩为短编码
- 搜索时计算压缩后的距离，精度取决于量化质量
- **优点**：内存效率极高，适合内存受限场景；精度可调
- **缺点**：需要离线训练量化器，插入新向量需要重建索引或近似更新

**选型建议：**
- 物品库动态更新频繁 → HNSW
- 内存资源紧张、物品库相对静态 → ScaNN
- 实际工业场景也常用两者的混合方案

### Q5: 多路召回的截断与去重策略

**参考答案：**

**截断策略：**
- 每路召回设定最大候选数量（如协同过滤取Top200，语义召回取Top100）
- 防止某一召回源垄断候选池，保证多样性

**去重策略：**
- **Item级去重**：按 Item ID Hash 去重，多路合并后同一 Item 只保留得分最高的
- **类目去重**：同品类物品去重（如同一店铺、同一品牌），保证曝光多样性
- **语义去重**：用 Embedding 相似度做去重（相似度>阈值则去重），处理内容重复

**融合时序：**
```
各路召回并行 → 分别取TopN → 去重合并 → 融合打分 → 取TopK送精排
```

### Q6: Wide&Deep vs DeepFM 核心区别是什么？

**参考答案：**

| 维度 | Wide & Deep | DeepFM |
|------|------------|--------|
| **核心结构** | Wide（LR） + Deep（DNN）并联 | FM + Deep（DNN）共享输入 |
| **特征工程依赖** | 依赖人工构造交叉特征（如"用户+类目+性别"） | 端到端自动学习二阶交叉 |
| **低阶交互建模** | Wide 部分负责记忆（Memorization） | FM 通过隐向量内积显式建模 |
| **参数共享** | Wide 和 Deep 的 Embedding 通常不共享 | FM 和 Deep 共享相同 Embedding |
| **表达能力** | 只能建模人工指定的高阶特征组合 | 自动捕获所有二阶交叉 + 高阶交叉 |

**DeepFM 优势总结：**
1. **端到端**：无需人工特征工程，FM 自动建模二阶交叉
2. **Embedding 效率高**：FM 和 Deep 共享 Embedding，CTR 任务中 Embedding 训练最困难，共享使两者同时被梯度更新，训练更充分
3. **Wide&Deep 的 Wide 部分是"手动的"，DeepFM 的 FM 部分是"自动的"**——这是本质区别

### Q7: 既然DNN拟合能力强，为何还需要Wide或FM部分？

**参考答案：**

**三个核心理由：**

**① "过度泛化"风险**
- DNN 对从未出现的特征组合可能给出非零预测值
- 但某些稀疏组合代表极强的正/负反馈（如"高消费用户+深夜时段=高转化"）
- 这些模式需要"死记硬背"，Wide/FM 可以精确记住

**② 学习效率问题**
- DNN 擅长加性特征（每个特征的独立贡献）
- 但对显式的乘法关系（特征交叉）需要极深网络和海量数据才能逼近
- Wide/FM 以 O(1) 参数复杂度显式建模交叉，远比 DNN 的隐式学习高效

**③ 梯度利用效率**
- DeepFM 通过 FM 和 Deep 共享 Embedding，使 Embedding 同时接受：
  - 来自 FM 的**显式二阶交互**梯度
  - 来自 Deep 的**隐式高阶交互**梯度
- 两者互补，Embedding 训练更充分

**面试加分：** 提及"记忆（Memorization）与泛化（Generalization）的平衡"——Wide 负责记忆明确规律，Deep 负责泛化未知模式，这是 Google 提出 Wide&Deep 的核心 insight。

### Q8: DIN的Target Attention机制原理，序列变长后如何优化？

**参考答案：**

**背景痛点：** 传统方法对用户历史行为做 Sum Pooling 或 Average Pooling——无论当前推荐什么商品，输出都是同一个混合向量，无法区分用户的具体兴趣点。

**DIN 解法（Target Attention）：**
```python
# 候选商品是"鼠标"时：
weights = Attention(User_History, Candidate_Item)
# "键盘"历史行为 → 高权重
# "洗面奶"历史行为 → 权重接近0

# 候选商品是"毛巾"时：
weights = Attention(User_History, Candidate_Item)
# 权重分配完全相反
```
- 用候选商品向量 Q 作为 Query，用户历史行为序列作为 Key/Value
- 通过加权求和输出用户对当前候选商品的兴趣向量
- **实现"千物千面"的用户表达**

**公式：**
```
a(query, key) = softmax(V^T · tanh(W · key + U · query))
output = Σ(a_i · value_i)
```

**序列变长优化：**
- Attention 计算复杂度为 O(N × Candidate_Size)
- 50个历史行为 × 1000个候选商品 = 50,000次交互
- **解决方案**：截断用户序列（保留最近50~100个行为）

### Q9: DIEN/SIM如何处理超长用户行为序列（10k+行为）？

**参考答案：**

| 方案 | 核心思路 | 适用场景 |
|------|---------|---------|
| **截断** | 保留最近N个行为（50~200） | 低频场景（电商） |
| **记忆网络** | 用GRU/LSTM压缩历史序列 | 中等长度（500~1000） |
| **检索式建模** | 先检索相关子序列，再建模 | 超长序列（10k+） |

**DIEN（Deep Interest Evolution Network）：**
- 引入 Interest Extractor 层（用GRU从序列中抽取兴趣表示）
- 引入 Interest Evolving 层（用带Attention的GRU建模兴趣演化）
- 将序列建模从 O(N) 压缩为固定长度向量

**SIM（Search-based Interest Model，阿里）：**
- **Hard Search**：利用商品的 Category/Brand ID 建立倒排索引，直接取同类历史行为
- **Soft Search**：用向量索引（ALIAS/HNSW）检索最相关的历史子序列
- **收益**：将 O(N) 复杂度降低为 O(log N) 或 O(K)

**面试追问：** "SIM的Hard Search和Soft Search如何融合？" 答：加权融合，Soft Search 产出 K 个候选，加上 Hard Search 的精确匹配，一起送入下游Attention。

### Q10: ESMM如何解决样本选择偏差（SSB）和数据稀疏（DS）问题？

**参考答案：**

**问题背景：**
- 直接训练 CVR 模型只在"点击"样本上训练
- 但推断时需要对所有"曝光"样本打分
- 训练空间与推断空间分布不一致 → SSB
- 点击样本稀疏，转化样本更少 → DS

**ESMM（Entire Space Multi-task Model，阿里）核心思想：**
不直接训练CVR，而是利用概率链式法则引入两个辅助任务。

```
P(CTCVR) = P(CTR) × P(CVR)
CTCVR = CTR任务 × CVR任务（共享Embedding）
```

**解决 SSB：**
- 在**整个曝光空间**上训练 CTR 和 CTCVR 任务
- 不再局限于点击样本空间，避开了只在点击样本上训练导致的分布偏差

**解决 DS：**
- CVR 网络共享 CTR 网络的 Embedding 层
- CTR 样本量远大于 CVR，底层特征表达得到充分训练
- CVR 任务通过共享 Embedding 间接"借用"了 CTR 的大规模数据

**面试加分：** ESMM 的 loss = Loss(CTR) + Loss(CTCVR)，CVR 本身不单独建模，而是在多任务框架下隐式学习。

### Q11: MMOE中梯度冲突如何解决？

**参考答案：**

**问题现象：**
- 简单任务（如点击）梯度幅值远大于困难任务（如转化）
- 共享层参数更新被简单任务主导，困难任务得不到有效学习

**MMOE（Multi-gate Mixture-of-Experts）解法：**
- 通过门控机制（Gate）让不同任务动态选择 Expert 组合
- 每个任务有独立的 Gate：$g^k(x) = softmax(W_{gk} · x)$
- 每个 Expert 对任务的贡献由 Gate 加权决定

**工程解法（梯度平衡）：**

**① Uncertainty Weighting**
- 为每个任务引入可学习的噪声参数 σ_k
- Loss = Σ Loss_k / (2σ_k²) + log(σ_k)
- σ_k 越大，该任务权重越低，自动平衡

**② GradNorm**
- 动态调整各任务梯度范数，使梯度量级趋向一致
- 梯度量级正则化：$‖G_W^{(i)}(t) - G_W^{(avg)}(t) × r(t)‖$

**③ PLE（Progressive Layer Extraction，腾讯）**
- 引入"共享 Expert"和"任务独有 Expert"分离
- 底层共享表征，上层任务特有参数分别优化
- 本质是从架构层面减少梯度冲突，而非在 Loss 层对抗

### Q12: 多目标学习的Loss平衡策略

**参考答案：**

**主流策略对比：**

| 方法 | 原理 | 优缺点 |
|------|------|--------|
| **Equal Weighting** | 各任务 Loss 等权重相加 | 简单但效果差，任务间量级不一致 |
| **Grid Search** | 离线搜索固定权重组合 | 耗时，不适应动态场景 |
| **Uncertainty Weighting** | 为每个任务引入可学习噪声参数 | 自动平衡，实现简单 |
| **GradNorm** | 梯度范数正则化 | 效果好，计算开销中等 |
| **Dynamic Weighting** | 根据训练进度动态调整权重 | 适合长周期训练 |
| **PLE** | 架构层面分离共享/独有 Expert | 从根本上减少冲突，效果最好 |

**工程实践建议：**
- 小团队/快速迭代：Uncertainty Weighting（实现简单，效果好）
- 大厂/长期优化：PLE（架构优化，长期收益大）
- 不建议：Equal Weighting 和 Grid Search

### Q13: DPP/MMR在多样性重排中的应用？

**参考答案：**

**严格按精排pCTR排序的问题：**
- 信息茧房、内容同质化
- 短期CTR可能提升，但长期用户满意度和留存下降

**MMR（Maximal Marginal Relevance）：**
```python
MMR = argmax[ λ × Rel(item, query) - (1-λ) × max_Sim(item, selected_items) ]
# 选择下一个物品时：考虑与查询的相关性，同时惩罚与已选物品的相似度
```
- λ ∈ [0,1] 控制相关性 vs 多样性的权衡
- λ=1 时退化为纯相关性排序

**DPP（Determinantal Point Process，行列式点过程）：**
- 数学上保证集合整体多样性最优
- 核心思想：行列式即体积，采样使选中集合的体积最大 → 覆盖空间最大
- 适合精确建模：既保证整体相关性高，又保证列表内多样性最大
- 工业实现：贪心DPP（用Cholesky分解近似求解）

**面试追问：** "DPP和MMR哪个更好？" 答：MMR实现简单、延迟低，适合线上；DPP精度更高但计算复杂度高，适合离线生成候选列表再做在线融合。

### Q14: 上了多样性策略后CTR跌了怎么办？

**参考答案：**

**面试正确姿态：** 承认短期损失，论证长期收益。

**标准答法（四步）：**

1. **承认短期代价**
   - 强行提升多样性必然导致CTR下跌1%~3%，这是正常的
   - 不要因为短期指标下跌就回滚

2. **引入长期指标**
   - 关注次日/7日留存率，而非当次CTR
   - 关注惊喜度（Serendipity）和用户发现新兴趣的比例

3. **细化评估指标**
   - 除 CTR/CVR 外，引入：
     - ILD（列表内平均距离）：衡量内容多样性
     - 类目覆盖率：列表覆盖了多少个不同类目
     - 探索率：新物品曝光占比

4. **分层重排策略**
   - 先保证基础相关性（Top80%位置给高置信度物品）
   - 后N%位置做多样性探索
   - 用A/B测试找到最优平衡点

### Q16: UCB/Thompson Sampling在冷启动探索中的应用？

**参考答案：**

**UCB（Upper Confidence Bound）：**
```python
UCB(i) = estimated_CTR(i) + √(2·ln(T) / N_i)
# 不仅看点击率预估均值，还考虑置信区间
# 给曝光次数少、新不确定性高的物品额外加分
```
- 置信区间宽度与曝光次数成反比：曝光越少，上界越高
- 自然平衡 exploitation（利用高CTR物品）和 exploration（探索新物品）

**Thompson Sampling（贝叶斯方法）：**
```python
# 为每个物品维护Beta分布（适合二值奖励）
theta_i ~ Beta(alpha_i + clicks, beta_i + non_clicks)
# 每次从Beta分布采样产生CTR，按采样值排序
```
- 比UCB更优雅地处理不确定性，适合实时更新
- 贝叶斯框架天然支持后验更新

**对比：**
| 维度 | UCB | Thompson Sampling |
|------|-----|-----------------|
| 理论基础 | 置信区间 | 贝叶斯后验 |
| 实现复杂度 | 低 | 中等 |
| 收敛速度 | 快 | 更快（通常） |
| 适合场景 | 静态物品库 | 动态/新物品频繁上线 |

### Q17: 离线AUC提升但上线CTR下跌，可能原因是什么？

**参考答案：**

**四大常见原因（必背）：**

**① 特征线上线下不一致（Feature Inconsistency）**
- 离线训练用数据仓库（延迟小时级~天级）
- 线上用实时流数据（毫秒级）
- 同一特征的定义/计算方式/更新时间不一致

**② 样本选择偏差（SSB）**
- 在"曝光→点击"样本上训练，但在线需要对海量候选集预测
- 模型学到的"点击 vs 未点击"区分力在全库上不成立

**③ 特征穿越（Feature Leakage）**
- 使用了"未来信息"——如当次请求的转化标签、session内后续行为
- 表现为某特征重要性异常高且无业务解释

**④ 评估目标与业务目标不匹配**
- AUC衡量排序能力，但热门物品天然排名靠前
- 模型可能过度学习"热门效应"而非真实偏好

**排查清单（面试加分项）：**
```
1. 特征一致性校验：开启Feature Log，逐条比对离线和线上特征
2. COPCC校准：检查模型预估均值与实际CTR是否接近
3. 穿越特征排查：特征重要性分析，警惕异常高的新特征
4. 测试集分布校验：检查离线测试集与线上实际流量分布是否一致
```

### Q18: 特征穿越（Feature Leakage）问题如何排查？

**参考答案：**

**常见穿越场景：**

| 穿越类型 | 具体案例 | 危害 |
|---------|---------|------|
| **标签穿越** | 用当次曝光的转化结果作为特征 | 离线虚高，上线崩盘 |
| **时间穿越** | 用未来时间点的统计数据 | 离线虚高 |
| **交叉穿越** | user_click_count = 统计包含了label时间窗口内的点击 | 隐蔽性强 |
| **曝光穿越** | 训练时用了测试集的曝光样本 | 分布偏移 |

**排查方法：**

**① 时间对齐校验（最重要）**
```sql
-- 错误写法
SELECT user_id, item_id, click_label,
       user_30d_click_cnt  -- 这个统计包含了label时间窗口内的点击！
FROM train_data

-- 正确写法：特征统计必须早于label
SELECT user_id, item_id, click_label,
       user_before_30d_click_cnt  -- label时刻之前的统计
FROM train_data
```

**② 特征重要性异常检测**
- 某特征重要性突然飙升（异常于其他特征）
- 检查该特征是否与标签有直接或间接关联

**③ 时序留出验证**
- 按时间切分训练/验证/测试集
- 不使用时序打乱的K-Fold（会引入未来信息）

**④ 线上特征逐条记录（Feature Log）**
- 将模型 inference 时每个请求的特征记录下来
- 与离线特征逐条比对，统计不一致率

### Q19: 精排模型延迟超标（SLA不满足）如何优化？

**参考答案：**

**工业级优化手段（按优先级）：**

**① 并发计算（最有效）**
- 召回、特征提取、模型预测并行化
- 独立路径并行执行，总延迟 = max(各路径延迟) 而非 sum

**② 模型轻量化**
- 知识蒸馏：用大模型（Teacher）训练小模型（Student）
- 结构简化：减少DNN层数/宽度，用更高效的激活函数
- 量化：FP32 → INT8，减少推理计算量

**③ 超时截断与降级**
```
if timeout > SLA:
    use_rough_rank_result  # 切换到粗排结果
    fallback_to_popular    # 极端情况下用热门兜底
```

**④ 缓存策略**
- Redis 缓存热门用户推荐列表（TTL=5min）
- 缓存高频特征（如物品统计特征）
- 缓存模型预测结果的 top items

**⑤ 候选集截断**
- 粗排→精排的候选数量优化（从500→200，减少精排压力）
- 与业务方协商可接受的候选数量下界

**⑥ 预估精度降级**
- 高峰期自动切换到简单模型（Logistic Regression）
- 低峰期切回深度模型

### Q21: 为什么不能用LLM直接做精排？业界解决方案是什么？

**参考答案：**

**三大瓶颈：**

| 瓶颈 | 具体数据 | 影响 |
|------|---------|------|
| **时延** | LLM推理在毫秒~秒级，精排要求<100ms | 无法上线 |
| **成本** | LLM推理成本是传统ID模型的数千倍 | 商业不可行 |
| **动态性** | 推荐系统候选集实时变化，LLM无法快速更新 | 效果差 |

**解决方案：**

**方案一：离线特征生成 + 缓存（主流）**
```
LLM离线处理 → 生成物品语义向量 → 存入向量库
线上精排模型 → 读取LLM生成的向量作为特征 → 毫秒级完成
```

**方案二：知识蒸馏（深度优化）**
- 用 LLM 生成大量软标签数据
- 训练轻量级 Student 模型（如 DeepFM、DCN）
- Student 模型学习 Teacher（LVM）的泛化能力

**方案三：RAG架构（前沿探索）**
- 将推荐候选物品作为上下文注入 LLM
- LLM 做多候选的语义排序（仅适合候选数<100的粗排场景）

**ID特征 vs 文本语义的融合趋势：**
- 传统模型擅长"协同过滤"信号（ID编号的共现规律）
- LLM 强项是"泛化"和"零样本推理"
- **未来趋势**：ID Embedding 作为 Prompt 一部分注入 LLM，或两者通过 Adapter 融合

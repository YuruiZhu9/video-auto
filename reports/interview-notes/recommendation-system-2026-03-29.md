### A1. 双塔模型（DSSM）原理与工程优势

#### 原理

双塔模型（Two-Tower Model，又称 DSSM 变体）的核心思想是**将用户和物品分别编码为独立向量**，两个塔在模型推断前互不干扰：

```
用户塔（User Tower）  →  e_u ∈ R^d
物品塔（Item Tower）  →  e_i ∈ R^d
匹配分数 = cosine(e_u, e_i) 或 dot(e_u, e_i)
```

**在线服务流程**：
1. 离线：所有物品向量 e_i 提前算好，存入 FAISS/Milvus 等向量索引
2. 在线：实时过用户塔得到 e_u，用 ANN 检索从全量库中找出 Top-K 相似物品
3. 延迟：用户塔计算（~10ms）+ ANN 检索（~20ms）= 毫秒级

#### 工程优势

| 优势 | 说明 |
|------|------|
| **解耦** | 用户塔和物品塔独立，可分别优化 |
| **离线建索引** | 物品向量提前算好，节省在线计算资源 |
| **可扩展** | 通过 ANN 索引支持亿级物品库 |
| **多目标复用** | 同一套物品向量可服务多个业务场景 |

#### 面试加分话术
> "双塔模型本质上是用**精度换效率**——牺牲了用户-物品的底层交互信号，换取了全库毫秒级检索能力。在工业界，这是在'召回候选集规模'与'计算延迟'之间做权衡的必然选择。"

### A2. 召回层负样本构造——为何不能用"曝光未点击"？

#### 核心问题：样本选择偏差（SSB）

**"曝光未点击"≠ 真正的负样本**。理由：

- **数据来源不同**：曝光数据是经过上一轮推荐系统筛选出的"精选集"，已经过粗排/精排过滤
- **学习目标扭曲**：模型若只用曝光未点击训练，学到的是"如何区分精选集中的好坏"，而非"如何从海量噪声中找出好物品"
- **对全库随机非相关物品缺乏鉴别力**

#### 正确策略：三类负样本组合

| 类型 | 构造方法 | 作用 |
|------|---------|------|
| **随机负采样** | 从全量库随机选未曝光物品 | 教会模型识别完全不相关物品 |
| **困难负样本** | 选"召回了但未点击"或"相关性分高但业务判定为负" | 提升模型细粒度区分能力 |
| **曝光未点击** | 作为补充，但**不能作为唯一负样本** | 贴合线上分布 |

#### 困难负样本的具体做法

```
正样本：点击序列中的 item（target item）
负样本A（随机）：从未被该用户任何序列中出现的 item 中随机采样
负样本B（困难）：选被 user embedding 召回但未点击的 item（Hard Negatives）
```

**采样比例经验**：正:随机负:困难负 ≈ 1 : 100 : 10（具体比例依场景调整）

### A3. 多路召回融合与截断策略

#### 问题场景

系统有 I2I、U2I、向量召回、热门召回、地理召回等 5 路，最终给排序层输出 500 个商品，每路取多少？

#### 三大融合方案

**方案一：归一化（Normalization）**
- 用 Min-Max 或 Z-Score 将各路分数映射到 [0,1]
- `Final Score = α × norm(score)`
- 缺点：各路分数物理意义不同，归一化后可比性仍有限

**方案二：基于转化率的渠道加权（推荐主流）**
- 离线统计各路过去 7 天 CTR/CVR 作为权重
- 若物料被多路召回，将加权分数相加（体现"多路共识"）
- `Final Score = Σ(weight_channel × norm(score_channel))`

**方案三：轻量级模型融合（Stacking）**
- 用 LR/GBDT 将各路原始分 + 来源标签 + 基础特征输入，预测粗排 CTR
- 本质上把"召回融合"升级为"粗排"阶段

#### 截断后的兜底策略
- **去重**：按 Item ID 去重，取最大分
- **强插补足**：热门/新品队列强插补足，防止下游空转
- **多样性保护**：按类目分桶，滑动窗口保证窗口内不重复

### A4. 双塔模型为何不在底层做用户-物品特征交叉？

#### 工程约束分析

**双塔的核心假设**：物品向量必须可**离线预计算**

| 约束 | 影响 |
|------|------|
| 若底层做特征交叉 | 物品向量 = f(user_features, item_features)，无法提前算 |
| 若物品向量无法预计算 | 在线Serving需实时对百万候选计算，延迟爆炸 |
| 计算复杂度 | 特征交叉 O(n²) → 对百万候选不可能在50ms内完成 |

#### 精度与效率的权衡

- DNN 隐式学习高阶交互需要极深网络 + 海量数据，对稀疏 ID 特征效率低
- 双塔牺牲了细粒度交互，换取了**全库检索能力**
- 精排阶段再做特征交叉（DeepFM/DIN 等），即"粗召回+精排序"分工

### B1. Wide&Deep vs DeepFM 本质区别

| 维度 | Wide & Deep | DeepFM |
|------|------------|--------|
| **Wide 部分** | LR（人工构造交叉特征） | FM（自动学习二阶特征交叉） |
| **Deep 部分** | DNN（隐式高阶交互） | DNN（隐式高阶交互） |
| **特征工程依赖** | 高（需专家构造wide特征） | 低（端到端自动） |
| **低阶交互建模** | 依赖人工 wide 特征 | FM 显式建模二阶交互 |
| **参数共享** | Wide 和 Deep 通常不共享 Embedding | FM 和 Deep 共享 Embedding |
| **参数效率** | 较低 | 更高（共享减少过拟合） |

#### 核心结论
> **DeepFM = Wide&Deep 的改进版**：用 FM 替换 Wide，去掉了人工特征工程，同时通过参数共享让 Embedding 同时受 FM（显式二阶）和 DNN（隐式高阶）双重梯度更新，训练更充分。

### B2. DeepFM 如何避免 Embedding Collapse？

#### 什么是 Embedding Collapse？

当不同特征的 Embedding 被强制共享训练时，简单任务（高梯度任务）的梯度可能主导更新，导致所有 Embedding 趋于一致，失去区分能力。

#### DeepFM 的对策

**共享 Embedding 机制**：
- FM 部分：通过隐向量内积计算二阶交互
- Deep 部分：通过 DNN 前向传播
- **两者共用同一套 Embedding**，所以 Embedding 同时接受两条路径的梯度更新

```python
# 伪代码示意
embedding = EmbeddingLayer(features)  # 共享

fm_output = FMLayer(embedding)       # 显式二阶交互梯度
deep_output = DNNLayer(embedding)    # 隐式高阶交互梯度

# 两个梯度共同更新 Embedding，避免单一路径主导
loss = BCE(fm_output + deep_output, label)
```

**效果**：显式 + 隐式双路监督，Embedding 训练更均衡，不易 collapse。

### B3. 单纯 DNN 做排序的致命弱点

#### 弱点一：过度泛化（Over-Generalization）
- DNN 倾向于将 Embedding 映射到稠密空间
- 对**极少出现的特征组合**，即使完全无关，DNN 也可能给出非零预测
- 例如：用户从未点过"婴儿用品"，DNN 可能误给高分

#### 弱点二：乘法关系逼近效率低
- 特征交叉本质是**乘法关系**（特征 A × 特征 B）
- DNN 用多层 ReLU 逼近乘法，需要极深网络 + 大量数据
- **FM 直接用内积显式建模二阶交互**，效率远高于 DNN 隐式逼近

#### 弱点三：稀疏 ID 特征处理弱
- 推荐系统大量使用稀疏 ID 特征（如 item_id, category_id）
- DNN 的 Embedding + ReLU 组合对稀疏 ID 的稀疏交互建模能力有限
- FM 的隐向量内积天然适合稀疏特征交互

### B4. DIN 为何用注意力机制而非简单 Pooling？

#### 传统 Pooling 的局限

| 方法 | 问题 |
|------|------|
| Sum Pooling | 所有历史行为等权重，无法区分当前候选 |
| Average Pooling | 同上，且会稀释重要信号 |
| **DIN (Target Attention)** | 根据当前候选商品动态加权历史行为 |

#### DIN 原理

```python
# 用户历史行为序列: [item1, item2, ..., item_n]
# 当前候选商品: target_item

# 计算每个历史 item 与 target 的注意力权重
attention_weight_i = softmax(MLP(concat([V_item_i, V_target])))
weighted_behavior = sum(attention_weight_i * V_item_i)

# 当 target 是"鼠标"时，"键盘"权重高，"洗面奶"权重接近0
```

#### 工程代价
- Attention 计算量：50 历史行为 × 1000 候选 = 50,000 次交互
- 随序列长度线性增长，需要截断或压缩策略

### B5. 超长序列（10k+）处理：SIM 模型原理

#### 背景
用户行为序列可能超长（10k+），全量 Attention O(N²) 不可接受。

#### SIM（Search-based Interest Model）两阶段方案

| 阶段 | 方法 | 复杂度 |
|------|------|--------|
| **Hard Search** | 用 item Category/Brand ID 建倒排索引，只取同类历史 | O(1) |
| **Soft Search** | 用向量 ANN 检索从历史中找 Top-K 相似的子序列 | O(log N) |

```python
# SIM 流程
long_history = user's 10k+ behaviors

# Stage 1: 从 10k 中检索相关子序列
relevant_subseq = search(long_history, target_item_id)  # Hard 或 Soft

# Stage 2: 对子序列做 Attention（DIN/DIEN）
final_embedding = Attention(relevant_subseq, target_item)
```

#### 与 DIEN 的区别

| 模型 | 核心思路 | 适用场景 |
|------|---------|---------|
| DIEN | 用 GRU 压缩历史，保留序列演化信息 | 中等长度序列（<1000） |
| SIM | 从长历史中检索相关子集，再精细建模 | 超长序列（10k+） |

### C1. CVR 预估中 SSB 与 DS 问题

#### SSB（Sample Selection Bias，样本选择偏差）

- **现象**：CVR 模型只在"点击"样本上训练，但推断时需要对所有"曝光"样本打分
- **后果**：训练空间（点击样本）与推断空间（曝光样本）分布不一致
- **本质**：用"条件分布 p(z=1|y=1, x)"替代了"边缘分布 p(z=1|x)"

#### DS（Data Sparsity，数据稀疏）

- 曝光 → 点击 → 转化，逐层漏斗递减
- 转化正样本极其稀疏，模型难以充分拟合
- 以电商为例：曝光100万，可能点击10万，转化仅1000

---

### C2. ESMM 如何同时解决 SSB 和 DS？

#### 核心思想：不直接训练 CVR，用概率链式法则引入辅助任务

```
pCTR  = P(click=1 | x)      ← 在全量曝光空间训练
pCTCVR = P(click=1, conv=1 | x) = pCTR × pCVR
pCVR  = pCTCVR / pCTR        ← 通过辅助任务间接得到
```

#### ESMM 网络结构

```
Input Features
    ↓
Shared Embedding Layer（同时给 CTR 和 CVR 共享）
    ↓                    ↓
  CTR Tower          CVR Tower
    ↓                    ↓
pCTR               pCVR
    ↓                    ↓
           ↓
    pCTCVR = pCTR × pCVR
           ↓
      Loss = Loss_CTR + Loss_CTCVR
```

#### 如何同时解决两个问题

| 问题 | 解法 |
|------|------|
| **SSB** | CTR 和 CTCVR 在**全量曝光空间**训练，不只在点击空间 |
| **DS** | CVR 共享 CTR 的 Embedding，底层特征表达得到充分训练（CTR 样本多） |

### C3. MMOE 中梯度冲突/"跷跷板"现象

#### 问题现象

- 简单任务（如CTR，点击样本多，梯度幅值大）的梯度主导共享层
- 困难任务（如时长预测，样本少，梯度幅值小）的梯度被淹没
- 共享层被简单任务"带偏"，难以同时优化多目标

#### MMOE 的门控对策

```python
# MMOE: Multi-gate Mixture of Experts
experts = [Expert1, Expert2, ..., ExpertN]  # 多个 Expert 网络

gate_ctr  = Softmax(W_ctr * user_features)   # CTR 任务专属门控
gate_dur  = Softmax(W_dur * user_features)   # 时长任务专属门控

output_ctr = sum(gate_ctr[i] * experts[i](x))
output_dur = sum(gate_dur[i] * experts[i](x))
```

**效果**：不同任务动态选择 Expert 组合，简单任务不会完全淹没困难任务。

#### 工程解法

| 方法 | 说明 |
|------|------|
| **Uncertainty Weighting** | 动态调整 Loss 权重，样本方差大的任务自动降低权重 |
| **GradNorm** | 梯度归一化，强制各任务梯度幅度相近 |
| **PLE（推荐进阶）** | 分离"共享 Expert"和"任务独有 Expert"，避免相互干扰 |

---

### C4. PLE 与 MMOE 的区别

| 维度 | MMOE | PLE（Progressive Layered Extraction） |
|------|------|--------------------------------------|
| **Expert 分类** | 所有 Expert 完全共享 | 分"共享 Expert"和"任务独有 Expert" |
| **信息流动** | 各任务直接从 Expert 选择 | 先经过共享 Expert，再进入任务专属 Expert |
| **梯度保护** | 无 | 任务独有 Expert 受到保护，不被其他任务破坏 |
| **效果** | 适合任务相关性高时 | 适合任务冲突严重时（更稳定） |

```
MMOE:  Expert1 --┬─→ gate_ctr  ──→ output_ctr
                 ├─→ gate_dur  ──→ output_dur

PLE:   Expert1_share ──┬─→ Expert1_ctr  ──→ output_ctr
                      ├─→ Expert1_dur  ──→ output_dur
```

### D1-D4. 冷启动完整解法

| 层级 | 核心思路 | 典型方法 |

### E1. 精排模型 P99 延迟超标优化

#### 问题场景

精排模型（如 DeepFM）P99 > 200ms，SLA 要求 100ms，如何优化？

#### 四大优化策略

| 策略 | 操作 | 收益 |
|------|------|------|
| **并发计算** | 召回、特征提取、模型预测并行化 | 延迟 ÷ N |
| **超时截断** | 规定时间内未返回则用粗排结果兜底 | 保障 P99 |
| **降级策略** | 负载高时自动切换到 LR/GBDT 简单模型 | 保护系统 |
| **缓存** | Redis 缓存热门用户推荐列表或高频特征 | 减少重复计算 |

#### 模型侧优化
- **模型蒸馏**：大模型（Teacher）蒸馏到小模型（Student）
- **结构简化**：减少 DNN 层数 / Embedding 维度
- **量化**：FP16/INT8 量化加速推理

### E2. 离线 AUC 涨但线上 A/B 下跌——归因分析

#### 四大原因

| 原因 | 说明 | 排查方法 |
|------|------|---------|
| **特征穿越** | 用了当次请求转化率或未来时间的行为 | 特征重要性分析，警惕异常高的新特征 |
| **特征不一致** | 离线用数仓数据，线上用实时流数据 | 线上特征日志逐条比对 |
| **样本选择偏差** | 模型只在"曝光点击"上训练，对全库候选缺乏区分力 | 检查测试集负样本分布 |
| **评估指标不匹配** | AUC 衡量排序能力，无法反映业务价值 | 引入业务指标（GMV、时长） |

#### 核心公式

```
离线 Recall@100 涨 ≠ 在线 CTR 涨
原因：Recall 衡量"候选集里有没有好东西"
      CTR 衡量"排序靠不靠谱 + 候选集够不够新鲜"
```

### E3. 特征穿越（Data Leakage）排查

#### 常见穿越场景

| 穿越类型 | 举例 | 危害 |
|---------|------|------|
| **时间穿越** | 用了样本时间点之后的行为 | 线上效果崩塌 |
| **当次请求穿越** | 用了当次曝光后用户是否点击的反馈 | 离线虚假繁荣 |
| **画像穿越** | 用了未来才知道的用户标签 | 严重违规 |

#### 排查清单

1. **时间戳审计**：检查所有特征的生成时间是否在样本时间之前
2. **特征重要性异常检测**：某特征异常高 → 高度怀疑穿越
3. **留一法验证**：去掉可疑特征后离线 AUC 是否仍合理
4. **线上特征日志**：逐条比对离线训练特征 vs 线上 Serving 特征

### E4. 重排层多样性控制——MMR vs DPP

#### MMR（Maximal Marginal Relevance）

```python
score_i = λ × relevance(u, i) - (1-λ) × max_sim(i, selected_items)
# 核心思想：每次选一个物品，既考虑自身相关性，也考虑与已选列表的差异性
# λ 越小 → 越倾向于选不同类目（高多样性）
```

**优点**：简单高效，贪心选法
**缺点**：贪心不保证全局最优

#### DPP（Determinantal Point Process）

- 用**行列式**计算选中集合的"体积"
- 体积越大 → 集合内物品越多样
- 保证**全局最优**的多样性选择

```python
# DPP 核心：选出的集合 S 使得 det(K_S) 最大
# K 是物品间相似度矩阵
# 体积大 = 物品之间相似度低 = 多样性高
```

| 指标 | MMR | DPP |
|------|-----|-----|
| 多样性 | 贪心最优 | 全局最优 |
| 计算复杂度 | O(K²) | O(K³) |
| 适用场景 | 实时性要求高 | 候选集不大（Top-100） |

### F1-F3. 大模型（LLM）在推荐系统中的应用

#### 三大落地点

| 场景 | 具体应用 | 工程可行性 |
|------|---------|----------|
| **内容理解** | 用 LLM 提取物品描述/评论中的高质量 Tags | ✅ 已落地（离线批处理） |
| **生成式推荐理由** | 生成自然语言推荐理由，提升点击率 | ✅ 已落地（生成式特征） |
| **数据增强** | 用 LLM 生成用户兴趣模拟数据辅助小模型训练 | ⚠️ 探索中 |

#### 为何不能用 LLM 直接做精排

| 约束 | 说明 |
|------|------|
| **时延** | 精排需几十毫秒内处理数百候选，LLM 推理无法满足 |
| **成本** | LLM 推理成本是传统 ID 模型的数千倍 |
| **信号差异** | LLM 强于文本语义，推荐系统需要的是协同过滤信号（ID特征） |

#### ID 特征 vs 文本语义的鸿沟

```
传统推荐核心：稀疏 ID 特征 → 协同过滤信号
LLM 强项：稠密文本语义 → 泛化能力

融合方案：
1. 将 ID Embedding 作为 Prompt 注入 LLM
2. RAG 架构：用推荐模型的结果作为 LLM 的上下文
3. 知识蒸馏：大模型作为 Teacher，蒸馏到轻量 Student 模型
```

### G1. AUC、NDCG@K、MAP@K 适用场景

| 指标 | 适用场景 | 特点 |
|------|---------|------|
| **AUC** | 排序能力评估（不关心顺序，只关心相对顺序） | 对正负样本比例不敏感 |
| **NDCG@K** | 有分级相关性（0-4 分）时，Top-K 排序质量 | 考虑位置折扣，奖励把高相关物品排前面 |
| **MAP@K** | 二元相关性（相关/不相关），Top-K | 无法利用分级信息 |

**面试重点**：NDCG 的 gain 函数 = 2^rel_i - 1，对相关性分级天然友好；MAP 将所有相关物品视为等价，无法区分 4 分物品和 1 分物品。

### G2. 位置偏差（Position Bias）纠正

#### 问题建模

```
P(click | item, position) = P(examine | position) × P(click | examine, item)
```

- examination probability 只和 position 有关（用户必须先看到才能点）
- relevance probability 只和 item 特征有关

#### 训练阶段
- 将 position 作为输入特征加入模型，让模型学会解耦
- 用一个额外网络建模 P(examine | position)

#### Serving 阶段
- **固定 position** = 1（或者直接去掉 position 特征）
- 此时模型输出的是 pure relevance score

#### 无偏数据收集
- 偶尔做 **Randomized Experiment**（随机打乱排序），收集无偏标签
- 用无偏标签校准 position bias 模型

### G3. 离线 NDCG 涨但在线 engagement 持平——诊断流程

#### 诊断流程图

```
Step 1: 检查 Recall@K 是否真的提升了候选集质量
        ↓（如果候选集变了，但 ranker 不认识 → engagement 不变）
Step 2: 检查 Ranker Top-10 是否真的被新候选占据
        ↓
Step 3: 分用户分群分析，看改进是否集中于特定人群
        ↓
Step 4: 检查离线标签（人工标注）是否与用户真实点击行为一致
        ↓
Step 5: 验证特征线上线下一致性（最重要！）
```

#### 核心原因总结

| 原因 | 说明 |
|------|------|
| **候选集变了但 ranker 不会打** | 新召回的物品特征分布与老物品不同，ranker 泛化能力不足 |
| **标签与行为不一致** | 人工标注的"相关性"≠用户真实点击偏好 |
| **特征穿越（最常见）** | 新特征在线下有效但线上无法获取，导致线上退化 |

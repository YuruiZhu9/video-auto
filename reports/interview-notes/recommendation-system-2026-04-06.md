#### Q1：双塔模型（DSSM）为什么这样设计？底层特征为什么不交叉？

**参考解析：**

**架构设计动机：**
- 推荐系统召回层面临的核心矛盾是：候选集规模巨大（百万~亿级），要求**毫秒级响应**（通常50ms以内），但模型推理需要计算用户与所有物品的交互得分
- 双塔模型将用户塔和物品塔**完全解耦**：
  - **物品塔**：离线预计算所有Item的Embedding，存入Faiss/Milvus等向量索引
  - **用户塔**：在线实时计算User Embedding，用ANN检索最近邻

```
User Tower: User Features → DNN → User Embedding
Item Tower: Item Features → DNN → Item Embedding
Online Serving: User Embedding × ANN → Top-K Items
```

**为什么不在底层交叉（双塔的核心权衡）：**
- 若在底层交叉，则用户特征需要与物品特征在同一次前向传播中同时出现
- 这意味着：无法预计算物品向量，所有推理都变成在线计算，延迟不可接受
- 双塔通过**牺牲底层细粒度特征交叉的精度**，换取**全库召回的效率**

**面试加分点：**
> "双塔的核心洞察是：召回阶段不需要精确的个性化交叉，交叉的精确性交给下游精排模型来完成。召回只需要'大海捞针'——把相关物品从海量候选中筛选出来，粗粒度的语义匹配足矣。"

---

#### Q2：召回负采样：曝光未点击能直接当负样本吗？样本选择偏差（SSB）是什么？

**参考解析：**

**直接用"曝光未点击"作为负样本的问题——样本选择偏差（SSB）：**

召回层的目标是**从全量候选库中找出相关物品**。但"曝光未点击"的样本来自：
- 经过上一轮推荐系统筛选后的"精选集"（通常数百~数千条）
- 这些物品本身就是系统认为有潜力的，并非随机采样的

如果只用这些数据训练，模型学到的是：

> "如何区分精选集中的物品谁更好"，而不是"如何从海量噪声中识别相关物品"

这导致模型在真实全量候选上的**泛化能力极差**。

**工业界负采样策略（三级体系）：**

| 负样本类型 | 采样方式 | 作用 |
|-----------|---------|------|
| **随机负样本（Easy Neg）** | 全库随机采样，与用户无关 | 教模型识别完全不相关物品 |
| **困难负样本（Hard Neg）** | 被召回了但未点击，或语义相似但业务负 | 提升模型判别能力 |
| **Hardest Neg** | 粗排/精排打分高但业务负的样本 | 防止"伪正例"混淆模型 |

**公式化：**
```
负采样优化目标：
min Σ [max(0, 1 - s(u,i+) + s(u,i-))] + λ·Regularization
其中 i- 是采样负样本，s(·) 是双塔相似度分数
```

**工程实现注意点：**
- 随机负采样比例通常是正样本的10~100倍（正负比失衡）
- Hard Negative挖掘要与业务方联合定义（如"曝光>1000但CTR<0.5%"）
- 定期更新负采样池，防止模型对旧负样本过拟合

#### Q3：多路召回如何融合？归一化方法有哪些？

**参考解析：**

多路召回的融合本质是**分数对齐问题**——各路召回的分数含义不同（协同过滤的cosine sim、粗排的CTR概率、规则的boost分数等），不能直接相加。

**方法一：Min-Max归一化（最简单）**
```
score_norm_i = (score_i - min_i) / (max_i - min_i)
```
- 优点：线性映射，物理意义清晰
- 缺点：受单点异常值影响大；若某路只有1个样本，失效

**方法二：Z-Score标准化**
```
score_norm_i = (score_i - μ_i) / σ_i
```
- 优点：考虑整体分布，适合近似正态分布的分数
- 缺点：需要离线统计，且同样受异常值影响

**方法三：基于转化率的加权融合（工业界主流）**
```python
Final_Score = Σ (α_channel · Normalized_Score_channel)
# α由离线CTR/CVR实验确定，定期更新
```
- 各路权重通过A/B测试调优
- 不同通道可设不同曝光配额上限

**方法四：粗排轻量级模型融合**
- 用LR或GBDT，以各路召回分+通道ID作为特征，预测CTR
- 本质是"让模型学习哪些路更可信"
- 比固定加权更灵活，适合通道数量多时

**兜底策略：**
- 去重：Item ID去重，防止重复候选
- 强插：热门/新品队列强插补足，防止下游空转

#### Q4：物品冷启动：新品没有行为数据如何做召回？

**参考解析：**

**分层解决思路（系统化）：**

**阶段一：内容特征驱动（核心手段）**
- 利用NLP/CV模型提取新品内容向量：
  - 文本描述 → BERT/Sentence-BERT Embedding
  - 图片封面 → ResNet/ViT Visual Embedding
  - 音频/视频 → 对应模态Encoder
- 通过向量检索，找到内容相似的高热已有物品
- 新品可复用相似品的协同信号（"相似品被哪些用户喜欢"）

**阶段二：探索策略（Exploitation & Exploration）**
- UCB（Upper Confidence Bound）：给不确定性高的新品更多展示机会
- Thompson Sampling：为每个物品维护Beta分布，采样CTR排序
- 保证新品有"探索预算"（通常曝光占比5%~15%）

**阶段三：跨域迁移**
- 利用其他平台/场景中已有的行为信号
- 例如：抖音新视频可通过创作者在今日头条的历史表现推断潜力

**阶段四：用户引导**
- 新品优先推给有明确搜索意图的用户
- 标签匹配：新品标签与用户近期搜索/点击标签对齐

**面试加分点：**
> "物品冷启动的衡量指标是'长期价值'而非短期CTR。新品如果有潜力但短期数据稀疏，需要容忍短期损失。因此业务上通常设定'冷启动流量池'，新品在此池内享受保护性曝光，待积累足够数据后出池。"

#### Q5：ANN索引原理：HNSW vs ScaNN 选哪个？

**参考解析：**

**HNSW（Hierarchical Navigable Small World）：**
- 核心思想：多层跳跃式搜索图（类似高速路网络）
- 构建：按概率随机将节点分配到不同层，高层稀疏、低层稠密
- 搜索：从顶层最远节点出发，逐层向下贪心搜索
- 复杂度：O(log n)，内存占用较高（每条向量都存）
- 优点：对动态插入友好（新品随时可加）
- 缺点：内存占用大，召回精度上限略低

**ScaNN（Google）：**
- 核心思想：VaQ量化（Vector Quantization）+ 残差学习
- 将高维向量压缩为有限codebook中的某个编码
- 搜索时比较量化中心+解码头，不直接比较原向量
- 优点：内存压缩比高（10~50倍），搜索速度极快
- 缺点：不支持动态更新，需要重建索引

**选型建议：**
```
场景选型：
- 物品更新频繁（新品每日大量入库）→ HNSW（支持增量）
- 超大规模（亿级+）且追求速度 → ScaNN（量化压缩）
- 精度要求极高（召回率>95%）→ HNSW（暴力ANN）
- 内存受限场景 → ScaNN
```

#### Q6：Wide&Deep vs DeepFM：本质区别是什么？为什么还需要Wide/FM？

**参考解析：**

| 维度 | Wide & Deep | DeepFM |
|------|-------------|--------|
| **核心结构** | Wide（LR线性）+ Deep（DNN） | FM（自动化二阶）+ Deep（DNN） |
| **特征交叉** | 依赖人工：`AND(UserInstall=Netflix, ImpApp=Pandora)` | 端到端自动：FM隐向量内积自动学二阶交互 |
| **参数效率** | Wide稀疏，Deep稠密 | FM+Deep共享Embedding，参数效率高 |
| **表达能力** | 低阶靠人工，高阶靠DNN | 低阶+高阶同时自动学习 |

**为什么还需要Wide或FM部分？（面试高频追问）**

**DNN的"过度泛化"问题：**
- DNN将Embedding映射到稠密连续空间，对**从未出现的特征组合**可能给出非零预测
- 但某些稀疏组合代表**极强反馈**（如"深夜+游戏+未成年"），需要精确记忆
- 纯DNN需要极深网络+海量数据才能逼近这种乘法关系，效率极低

**Wide&Deep中Wide的价值：**
- 线性模型天然适合记忆（memorization）：直接记住哪些特征共现有效
- 与Deep的泛化（generalization）能力互补

**DeepFM的进化：**
- 用FM替换Wide，无需人工设计交叉特征
- FM通过隐向量内积高效建模所有二阶特征交互
- DeepFM = **一阶（Embedding Sum）+ 二阶（FM内积）+ 高阶（DNN隐式）** 三路并行

**工业选型：**
- 有充足人工特征工程经验 → Wide&Deep
- 希望端到端自动学习 → DeepFM（当前更主流）

#### Q7：DIN模型：为什么引入注意力机制？传统Pooling有什么问题？

**参考解析：**

**传统Pooling的问题：**

用户历史行为：[篮球、球鞋、游戏鼠标、键盘、洗面奶、饮料]

候选目标商品：运动T恤

传统Sum/Average Pooling：
```
User Embedding = mean([E(篮球), E(球鞋), E(游戏鼠标), E(键盘), E(洗面奶), E(饮料)])
```
- 所有历史行为被**等权重**对待
- 洗面奶与T恤完全不相关，但贡献了同等权重
- 结果：用户表达被大量噪声稀释

**DIN的解法——Target Attention（目标注意力）：**

核心洞察：**当前候选商品，是激活相关历史行为的"开关"**

```
Attention Score = softmax(MLP([E_target, E_history, E_target ⊙ E_history]))
User Embedding = Σ(Attention_i × E_history_i)
```

当候选=T恤时：
- E(篮球) · E(T恤) → 高权重（运动相关）
- E(洗面奶) · E(T恤) → 低权重（日用品无关）

**工程注意点：**

注意力计算复杂度：O(H × C)，H=历史行为数，C=候选数
- 50个历史行为 × 1000个候选 = 50,000次交互
- 工业解法：限制候选打分batch并行，或用sampled softmax

**DIN vs DIEN：**
- DIN：静态权重（每个历史行为的重要性固定）
- DIEN：引入 GRU 序列建模，能捕捉**兴趣演化**（从浏览→点击→购买的心理路径）

#### Q8：序列超长（10k+行为）怎么处理？SIM模型原理是什么？

**参考解析：**

**问题本质：**
- Attention复杂度 O(H × C)，H超长时不可行
- 超过计算预算（通常50~200个行为）

**三级解决体系：**

| 阶段 | 方法 | 适用场景 | 复杂度 |
|------|------|---------|--------|
| **截断** | 保留最近N个行为（50~200） | 低频场景 | O(N) |
| **压缩** | GRU/LSTM将历史压缩为固定向量（DIEN） | 中频场景 | O(N) |
| **检索** | 从长历史中检索相关子序列（SIM/ATAM） | 高频/长序列 | O(log N) |

**SIM（Search-based Interest Model）核心原理：**

```
两步检索：
1. Hard Search（精确匹配）：
   - 用商品Category/Brand建立倒排索引
   - 从10k历史中找同类目商品

2. Soft Search（语义匹配）：
   - 用向量索引（ALIAS/HNSW）
   - 从10k历史中找Embedding最相似的Top-K
   - 融合：Score = α·Hard + β·Soft

3. 再做Target Attention（精排的最后一步）
```

**为什么SIM有效：**
- 不是所有历史行为对当前候选都有用
- 引入检索层，将 O(H) 降为 O(log H + K)，K << H
- 过滤噪声，保留真正相关的长期兴趣信号

#### Q9：ESMM如何解决CVR预估中的SSB和数据稀疏问题？

**参考解析：**

**两个核心问题：**

**样本选择偏差（SSB）：**
- 传统CVR只在「点击」样本上训练
- 但服务时需要对「曝光」全集打分
- 训练空间 ⊂ 推断空间，分布不一致

**数据稀疏（DS）：**
- 曝光 >> 点击 >> 转化（通常 100:10:1）
- CVR正样本极少，直接训练模型欠拟合

**ESMM解法（Entire Space Multi-Task Model）：**

核心思想：**不直接训练CVR，通过概率链式法则引入辅助任务**

```
p(转化|曝光) = p(点击|曝光) × p(转化|点击)
CTCVR = CTR × CVR
```

**三个关键设计：**

1. **共享Embedding层**：CTR任务样本多（曝光→点击），CVR网络复用CTR的Embedding，相当于用海量CTR数据给CVR做预训练

2. **CTCVR Loss反向传CVR梯度**：CVR网络没有独立损失函数，其梯度来自CTCVR的损失传播，间接利用了曝光空间的监督信号

3. **全空间训练**：CTR和CTCVR都在「曝光全集」上训练，CVR间接具备了对全空间的泛化能力

**公式：**
```
L = Σ L_CTR(y, pCTR) + Σ L_CTCVR(y, pCTR × pCVR)
pCVR = Sigmoid(MLP_CVR(E_shared))
```

#### Q10：MMOE的门控机制是什么？如何解决梯度冲突？

**参考解析：**

**MMOE（Multi-Gate Mixture-of-Experts）架构：**

```
输入 X
  ├── Expert 1 (共享底层专家网络 E1)
  ├── Expert 2 (E2)
  ├── ...
  └── Expert K (EK)
  │
  ├── Gate_Task1: softmax(W_g1 · X) → 任务1对各Expert的权重
  ├── Gate_Task2: softmax(W_g2 · X) → 任务2对各Expert的权重
  └── Gate_Task3: ...

输出 Task_i = Σ (gate_i_k × Expert_k(X))
```

**门控机制的本质：**
- 每个任务有自己的Gate，决定从哪些Expert提取信息
- 不同任务对同一输入可以有不同的"关注重点"
- 实现了任务间解耦与共享的自适应平衡

**梯度冲突的成因：**
- 不同任务梯度方向/幅值差异大
- 简单任务（如CTR）梯度幅值 >> 困难任务（如CVR）
- 共享层被简单任务主导，困难任务得不到有效更新

**MMOE解决思路：**
- 门控允许任务忽略不相关的Expert
- 但当Expert不足或任务冲突严重时，仍会相互干扰

**工业解法（PLE/CGC）：**

在MMOE基础上，引入**任务独有Expert**：

```
PLE（Progressive Layered Extraction）：
  - 共享Expert层（抽取共同知识）
  - 任务独有Expert层（保护任务特性）
  - 跨层融合：底层独有 → 顶层共享 → 任务输出
```

**Loss平衡方法：**
- Uncertainty Weighting：根据任务不确定性自动加权（不确定任务给高权重）
- GradNorm：梯度幅值归一化
- DWA（Dynamic Weight Average）：用loss变化率动态调整

#### Q11：推荐系统全链路——各模块职责和时延预算？

**参考解析：**

```
[全链路漏斗]  亿级候选 → 百级召回(5-10ms) → 千级粗排(3-5ms) → 数十精排(20-50ms) → 十级重排(5ms)

总延迟预算：< 100ms（移动端通常要求更低）
```

| 模块 | 候选规模 | 模型复杂度 | 时延预算 | 核心职责 |
|------|---------|-----------|---------|---------|
| **召回** | 百万~亿级 | 轻量（双塔） | 5~10ms | 从全量中粗筛相关候选（200~2000条） |
| **粗排** | 200~2000 | 中等（LR/GBDT） | 3~5ms | 召回结果初排序，过渡层 |
| **精排** | 数十~百级 | 重（DNN多目标） | 20~50ms | 精确打分，多目标优化 |
| **重排** | 10~20条 | 轻量规则/小模型 | 5ms | 多样性、业务规则、体验优化 |

**工程优化技巧：**
- 并行化：召回、特征读取并行，减少等待
- 缓存：热门用户/物品的Embedding预计算，Redis缓存
- 降级：超时使用粗排结果兜底
- 批处理：精排batch推理，GPU利用率提升

#### Q12：特征穿越（Feature Leakage）是什么？如何排查？

**参考解析：**

**特征穿越的定义：**
训练时使用了**不该在推理时获得**的特征，导致模型"偷看答案"。

**常见类型：**

| 类型 | 例子 | 后果 |
|------|------|------|
| **时间穿越** | 用当次曝光后用户点击的物品作为特征 | 离线指标虚高，上线崩盘 |
| **未来信息** | 特征中包含session结束后的行为 | 模型"作弊"，无真实预测能力 |
| **ID穿越** | 用当次曝光的唯一ID做特征 | 模型记住特定item而非学习规律 |
| **统计穿越** | 实时计算CTR时包含当前曝光本身 | 自循环强化 |

**排查方法（工业实践）：**

```
排查清单：
1. 特征日志：线上线下特征逐条对比（Training-Serving Skew）
2. 特征重要性：XGB/线性模型分析，异常高的特征值得怀疑
3. 时间戳审计：检查所有特征是否有"未来数据"混入
4. COPCC校准：离线预测均值 vs 在线实际CTR对比
5. 盲测验证：遮蔽疑似穿越特征，离线指标下跌则确认穿越
```

**COPCC（Calibration of Predictions and Clicks）：**
- 若离线pCTR均值=8%，但在线实际CTR=4%，说明离线有穿越特征"虚胖"了分数

#### Q13：离线AUC提升但在线CTR不涨，如何诊断？

**参考解析：**

这是推荐算法面试中**经典高频问题**，考察候选人对离线/在线差异的系统分析能力。

**五步诊断法：**

**Step 1：检查候选集重叠（Recall层面）**
- Recall@100提升≠Top-K排序改变
- 验证：新候选是否真正进入了精排的Top-K

**Step 2：排名器适配性（Rank层面）**
- 新召回候选可能与历史候选分布不同
- 精排模型是在"旧候选"上训练的，对新候选打分不准

**Step 3：特征穿越排查**
- 新模型可能恰好拟合了某个穿越特征
- 参考Q12排查清单

**Step 4：标签不匹配**
- 离线相关性标签（人工标注）≠ 在线点击行为
- 标签体系本身是偏差来源

**Step 5：按用户群细分**
- 提升可能集中在某个子群体
- 其他群体可能是平的甚至下降

**面试加分话术：**
> "这个问题的本质是离线评估空间与在线服务空间的差异。召回改变了候选集的分布，精排模型还没来得及适应；或者精排的特征工程没有覆盖新候选的特有特征。建议做一次全链路特征覆盖率审计，并设计分人群、分内容的A/B测试来定位问题。"

#### Q14：重排序——MMR和DPP区别？如何平衡多样性与CTR？

**参考解析：**

**MMR（Maximal Marginal Relevance，最大边际相关）：**
```
Score(i) = λ·Rel(u,i) - (1-λ)·max_{j∈S} Sim(i, j)
```
- 贪心算法：每步选一个"既相关又不重复"的物品
- λ越大越偏重相关性，越小越偏重多样性
- 简单易实现，但贪心有局部最优风险

**DPP（行列式点过程，Determinantal Point Process）：**
- 用行列式体积衡量集合多样性
- 保证选出的集合整体多样性最优（非贪心）
- 计算复杂度高，但数学上更优雅

**CTR下跌怎么办？**

| 策略 | 说明 |
|------|------|
| 短期容忍 | 多样性通常带来Session CTR下跌1~3%，但长期留存升 |
| 流量分层 | 一部分用户体验多样性策略，另一部分保持相关性优先 |
| 渐进调整 | λ参数从小到大逐渐调，给用户适应时间 |
| 新增指标 | 除CTR/CVR外，引入ILD（类目覆盖）、NDCG、长期留存 |

#### Q16：位置偏差（Position Bias）如何纠正？

**参考解析：**

**问题建模（谷歌经典范式）：**

```
P(click | item, pos) = P(examine | pos) × P(click | examine, item)
```

假设：用户是否检查某个位置只与位置有关，与物品内容无关（Examination Hypothesis）

**训练时纠正：**
- 将位置作为输入特征加入模型
- 或使用position-debiased pooling（将position信息剥离到独立网络分支）

**服务时纠正：**
- 推理时将位置特征设为常数（通常 pos=1 或所有位置置零）
- 让模型只基于内容相关性打分

**无偏数据收集：**
- 随机化实验（Randomized Position Experiment）：
  - 小比例流量（5%）强制随机排序
  - 收集无偏的曝光-点击数据作为校准ground truth
  - 用倾向分数（propensity score）加权训练样本

#### Q17：流行度偏差（Popularity Bias）如何诊断与缓解？

**参考解析：**

**马太效应形成路径：**
```
热门物品 → 更多曝光 → 更多点击 → 模型更倾向 → 更多曝光 → 循环
```

**诊断方法：**
- 覆盖率指标：Top-K物品占总物品库的比例（健康值应 > 5%）
- 基尼系数：物品曝光分布的均匀程度（越接近1越不均匀）
- 长尾分布分析：头部物品占比是否异常高

**缓解策略（三类）：**

| 类别 | 方法 | 原理 |
|------|------|------|
| **损失重加权** | 逆倾向评分（IPS） | 曝光多的物品降低权重，反之提升 |
| **正则化** | Popularity Penalty | 在损失中加入覆盖率正则项 |
| **探索机制** | 确定性保量（Ensure popular items don't dominate） | 重排时为长尾物品保留曝光槽位 |
| **因果去偏** | Causal Embedding | 将流行度效应与真实相关性分离 |

**面试核心话术：**
> "流行度偏差的根因是反馈循环：数据产生的过程本身就是有偏的（热门物品天然获得更多数据），模型在这个有偏数据上训练，又强化了这种偏差。解法不能只在模型层打补丁，需要在数据生成机制层面干预（如随机化探索），因果推断提供了一套理论框架。"

#### Q19：ID特征 vs 文本语义Gap怎么桥接？

**参考解析：**

**问题本质：**

传统推荐系统以物品ID为核心：
- 优势：ID Embedding能编码"协同过滤信号"（哪些用户喜欢过这个物品）
- 劣势：对新物品泛化差，语义完全未知

LLM以文本语义为核心：
- 优势：零样本语义理解，对新品友好
- 劣势：缺乏ID协同信号（"这个物品ID曾被高活用户大量点击"这类信息LLM不知道）

**桥接方案（三条路）：**

**方案一：异构Embedding融合**
```
最终Embedding = concat(ID_Embedding, Text_Embedding)
或：Final_Score = α·Score_ID + β·Score_Text
```

**方案二：Prompt注入ID协同信号**
- 将历史点击物品ID序列作为Prompt的一部分
- 例："用户历史点击：[ID_1023, ID_8841, ID_2309]，候选物品描述：XXX"
- LLM能从历史ID序列中"推理"用户协同偏好

**方案三：RAG增强推荐**
- 构建物品知识库（属性、评论、标签）
- 检索增强：从知识库中检索与候选相关的上下文
- LLM基于检索结果做推荐判断

**面试核心话术：**
> "ID特征和文本语义代表两种信息：协同信号和语义信号。两者不是替代关系，而是互补。2026年的主流架构是多路召回——用ID协同信号做主召回通道（因为协同信号对用户行为预测更精准），用LLM语义信号做补充通道（特别是在冷启动和跨域场景）。最终通过加权融合让两种信号各展所长。"

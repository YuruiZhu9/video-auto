## 1.1 架构解析：128专家 + Top-2路由的几何秘密

### MoE数学公式

Mistral Small 4的MoE层输出定义为：

```
y = ∑_{i=1}^{top_k} Gate_i(x) · Expert_i(x)
```

其中：
- **x** ∈ R^d：输入Token的隐藏向量（d=4096）
- **Gate_i(x) = softmax(W_g x)_i**：第i个专家的门控权重
- **Expert_i(x)**：第i个FFN专家网络（共128个）
- **top_k = 2**：每个Token只激活2个专家

总参数量 = 119B，但每次前向只经过2/128 = **1.56%的专家参数**。

**稀疏度计算**：
```
稀疏度 = 1 - (激活参数 / 总参数)
       = 1 - (6.5B / 119B)
       = 94.5%  （每处理一个Token，94.5%的参数处于闲置状态）
```

**对比同期竞品MoE稀疏度**：
| 模型 | 总参数量 | 激活参数 | 稀疏度 |
|------|---------|---------|--------|
| Mistral Small 4 | 119B | 6.5B | **94.5%**（最高） |
| Qwen3.5-397B | 397B | 17B | 95.7% |
| GLM-5 | 744B | 40B | 94.6% |
| Nemotron 3 Super | 120B | 12B | 90.0% |
| GPT-oss 120B | 117B | 5.1B | 95.6% |

Mistral Small 4以**仅5.5%的激活率**刷新了同期开源MoE的稀疏度纪录（与Qwen3.5-397B并列顶级）。

### 专家数量设计的工程权衡

为什么是128个专家？以下是128 vs 64 vs 32专家的对比：

```
专家数 = 128：
  - 优点：专家多样性高，每个专家专业化程度高
  - 缺点：路由复杂度O(E)，内存开销大（专家Embedding）
  - 适用：任务类型丰富的场景（推理+视觉+编码）

专家数 = 64：
  - 优点：平衡效率和多样性
  - 缺点：专家容量有限，高负载时可能溢出
  - 适用：单一任务场景

专家数 = 32：
  - 优点：调度简单，通信开销低
  - 缺点：专家容量压力大，容易过载
  - 适用：简单任务或资源受限场景
```

**128专家的容量问题**：当某个Token路由到某专家时，该专家必须有能力处理。容量因子（Capacity Factor）定义为：

```
Capacity = (tokens_per_device × top_k) / num_experts_per_device
```

Mistral Small 4通过**容量因子动态调整**处理专家过载：当某专家被过度激活时，超出容量的Token被强制路由到次优专家（由softmax第二位决定）。

### 共享专家 + 路由专家的混合设计

Mistral Small 4很可能采用了**共享专家机制**（类似DeepSeek-V3）：

```
输出 = Shared_Experts(x) + ∑_{i=1}^{top_k} Gate_i(x) · Routed_Expert_i(x)
```

- **共享专家**（如8个）：始终激活，提供语言理解的基础能力
- **路由专家**（120个）：由Gate网络选择激活，提供任务特定能力

这样设计的好处是：即使路由失败，共享专家也能保证基础语言能力不降级。

## 1.2 能力统一：推理 + 视觉 + 编码的三合一魔法

Mistral Small 4最令人印象深刻的设计决策是**用一个模型覆盖三个能力维度**，而不是像以前那样每个能力一个专用模型。

### 能力路由的底层机制

在MoE框架下，不同能力通过不同的专家组合实现：

```
推理任务（如数学证明）：
  → 激活：逻辑推理专家 + 符号计算专家 + 长程依赖专家

视觉任务（如图表理解）：
  → 激活：视觉编码专家 + 空间推理专家 + OCR专家

编码任务（如代码补全）：
  → 激活：语法专家 + API调用专家 + 测试验证专家
```

这意味着**同一个MoE模型内部存在隐式的"能力路由"**——不同任务激活不同的专家子集。这种设计与推荐系统的"多目标学习"高度相似：推荐模型也需要同时考虑点击率、转化率、用户满意度等多个目标。

### 推理模式：快速推理 vs 深度推理

Mistral Small 4支持**两种推理模式切换**：

**快速推理模式**（Low Latency）：
- 禁用CoT（Chain of Thought），直接输出答案
- 适用：简单查询、闲聊、实时交互
- 延迟：毫秒级

**深度推理模式**（Deep Think）：
- 启用显式CoT，展示推理过程
- 适用：数学证明、复杂代码调试、多步逻辑推理
- 延迟：秒级，但答案质量显著更高

```python
# 推理模式伪代码实现
def generate_with_mode(prompt, mode="fast"):
    if mode == "deep_think":
        # 强制模型输出思考过程
        prompt = "Please think step by step and then answer."
    elif mode == "fast":
        # 禁用长思考
        prompt = "Answer directly and concisely."
    
    response = model.generate(prompt, max_new_tokens=...)
    return response
```

### 256K上下文窗口的工程实现

256K上下文（≈ 64万汉字）是目前开源MoE中最长的之一。实现这个能力需要解决两个核心问题：

**问题1：Attention的O(n²)复杂度**

标准Attention的计算复杂度：
```
O(seq_len² × d_head × n_heads)
```

对于256K Token：
```
256K² = 655亿次计算（仅Attention）
```

**解决方案：Sliding Window Attention + Global Attention**

```python
class HybridAttention(nn.Module):
    def __init__(self, window_size=4096, global_size=256):
        self.window_size = window_size  # 局部窗口
        self.global_size = global_size  # 全局Token数
    
    def forward(self, x):
        # 局部：每个Token只看前后window_size个Token
        local_attn = sliding_window_attention(x, window=self.window_size)
        
        # 全局：特殊[Global] Token与所有Token交互
        global_attn = full_attention(x[:, :self.global_size])
        
        return local_attn + global_attn
```

**问题2：KV Cache显存爆炸**

256K上下文的KV Cache（FP16）：
```
= 40层 × 2(K+V) × 256,000 × 8头 × 128维 × 2字节
≈ 40 GB VRAM（仅KV Cache）
```

Mistral Small 4采用**分组KV Cache + 量化**双重优化：
- 按4或8个Token一组共享KV
- KV量化到INT8或更低
- 实际KV Cache降至 < 10 GB

> 💡 **核心洞察**：GLM-5以77.8%的SWE-bench分数刷新了开源模型在真实软件Bug修复任务上的纪录。SWE-bench的独特之处在于：模型需要在真实GitHub仓库中定位Bug根因、生成修复补丁、并通过单元测试验证。这是生产级代码能力的试金石——不仅考验代码生成，更考验对大型代码库的理解和调试能力。

## 2.1 SWE-bench的独特价值：为何它比HumanEval更难

传统代码基准的局限：
- **HumanEval**：164道编程题，模型只需写函数体，平均代码长度 ~ 50行
- **MBPP**：974道Python基础题，测试用例简单，侧重语法正确性

**SWE-bench的革命性设计**：
```
任务：从真实开源仓库（scikit-learn、Django、pytest等）中提取
      已知的Bug Issue，模型需要：
      1. 理解Issue描述和错误信息
      2. 在数百万行代码中找到问题位置
      3. 生成精确的补丁文件（diff格式）
      4. 通过完整的单元测试套件验证

难度：代码库平均 > 100万行，Patch平均修改 < 10行
```

SWE-bench 77.8%意味着GLM-5在真实仓库中可以**自主修复近8成的实际Bug**——这已经接近初级工程师水平。

### GLM-5的代码能力技术分析

GLM-5（744B参数，40B激活）的代码能力来源于几个关键设计：

**1. 超长上下文理解**：
- 真实Bug修复需要理解多个文件之间的依赖关系
- GLM-5支持超长上下文，可以一次性读入完整代码仓库
- 这对于推荐系统也很重要：推荐系统的特征工程同样需要理解跨表的业务逻辑

**2. 架构优化（推测为GLM-4V的延续））：
```python
# GLM代码能力的推测架构
class GLMCodeExpert(nn.Module):
    def __init__(self):
        self.syntax_parser = TreeSitterParser()  # 语法树解析
        self.api_retriever = BM25Retriever()    # API文档检索
        self.test_executor = SandboxExecutor()  # 测试执行环境
    
    def fix_bug(self, issue: str, repo_code: str) -> str:
        # Step 1: 理解Bug描述
        bug_summary = self.summarize(issue)
        
        # Step 2: 定位相关代码片段
        relevant_files = self.retrieve(repo_code, bug_summary)
        
        # Step 3: 生成修复方案
        patch = self.generate_patch(relevant_files, bug_summary)
        
        # Step 4: 验证修复
        test_result = self.execute_tests(patch)
        
        return patch if test_result.passed else self.revise(patch)
```

# 四、Grok 4.20 Beta：幻觉率22%的秘密

> 💡 **核心洞察**：Grok 4.20以22%的幻觉率创下历史最低纪录（此前最佳约30%）。幻觉率衡量模型输出中包含事实性错误或无中生有信息的比例。22%意味着每回答100个问题约22个存在事实错误——这对需要高可靠性的场景（医疗、法律、金融推荐）意义重大。背后可能采用了"检索增强置信度"机制和更严格的采样温度控制。

---

## 4.1 幻觉率的测量方法

**IFBench（xAI自有基准）**：测量模型在Infobox信息提取任务中的准确率
- 任务：从用户问题中提取Infobox字段值
- 例如："特斯拉CEO是谁？" → 答案应为"Elon Musk"
- IFBench 82.9%意味着82.9%的实体提取是正确的

**幻觉率与IFBench的关系**：
```
幻觉率 ≈ 1 - IFBench准确率 = 17.1%（理论值）
实际幻觉率22% = 考虑到了推理链路中的传播误差
```

### 降低幻觉的技术路径

**方法1：检索增强置信度（RAG-Enhanced Confidence）**
```python
def low_hallucination_generate(query: str, retrieval_db: KnowledgeBase):
    # 检索相关事实
    facts = retrieval_db.search(query, top_k=10)
    
    # 高置信度路径：检索到强相关事实
    if facts[0].relevance > 0.95:
        return direct_answer_from_facts(facts)
    
    # 低置信度路径：检索信号弱，启用谨慎模式
    else:
        return cautious_answer_with_citations(query, facts)
```

**方法2：多候选验证（Self-Verification）**
```
Step 1: 生成初始答案A
Step 2: 让模型反过来验证A中的每个事实声明
Step 3: 如果验证失败，修正A
Step 4: 重复直到稳定
```

**方法3：低温采样 + 截断高方差Token**
- 将采样温度降至0.1~0.3
- 截断概率分布尾部的高方差Token
- 减少"凭空编造"的随机性

# 八、本周技术论文精选

## 论文1：MoE负载均衡的数学原理

**标题**：（推测）Auxiliary-Loss-Free MoE训练的新进展

**核心公式**：传统MoE的辅助损失函数
```
L_aux = α · ∑_i |f_i - P| / E
```

其中：
- f_i：被路由到专家i的Token比例
- P：目标专家比例（= 1/E，E=专家数）
- α：辅助损失权重（通常0.01~0.1）

**新方向**：去掉辅助损失，用路由器噪声（Router Z-Loss）替代：
```
L_z = log(∑_i exp(Gate_i(x)))²
```
这避免了辅助损失对主任务loss的干扰，让模型自己学到更好的负载均衡。

## 论文2：稀疏注意力机制的进阶

**标题**：（推测）Hawk的线性注意力 + Ring Attention混合架构

**核心思想**：
```
传统Attention：O(n²)全连接
线性Attention：O(n)但精度损失
Ring Attention：O(n²)但分布式

Hawk方案：长程用线性注意力 + 短程用全注意力
分段阈值：|i-j| < 512 → 全注意力
           |i-j| ≥ 512 → 线性注意力（Mamba风格）

精度损失：< 1%（在LRA基准上）
内存节省：> 60%（100K上下文）
```

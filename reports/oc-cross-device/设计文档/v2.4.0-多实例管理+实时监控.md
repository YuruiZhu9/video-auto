# OpenClaw 跨设备控制方案 — v2.4.0 设计文档
## 多实例管理与实时监控告警系统

---

## 一、需求背景

随着 OpenClaw 部署场景越来越复杂，用户开始出现以下需求：

1. **多机器部署**：主实例 + 灾备实例分布在不同机房，需要统一管理
2. **负载分流**：不同类型的任务（轻量查询 / 深度分析）分发到不同实例
3. **故障自愈**：某个实例挂了，自动切换到健康实例，用户无感知
4. **容量规划**：想知道每个实例的负载情况、响应时间、错误率
5. **告警通知**：CPU / 内存飙高，或者错误率异常时，主动推送告警

## 二、系统设计

### 2.1 多实例管理器（Multi-Instance Manager）

#### 核心概念

- **InstanceInfo**：每个 OpenClaw 实例的元数据
  - 静态信息：`id`、`name`、`base_url`、`api_key`、`group`、`tags`
  - 运行时状态：`status`、`active_tasks`、`avg_response_time`、`failure_rate`
- **CircuitBreaker**：熔断器，防止故障实例继续接收请求
- **LoadBalanceStrategy**：三种路由策略
  - `ROUND_ROBIN`：轮询，公平分发
  - `LEAST_LOADED`：选择当前负载最低的实例
  - `FAILOVER`：主备模式，优先主实例，故障自动切换

#### 健康检查机制

```
每 15 秒：
  遍历所有注册实例 → GET /api/status
  → 成功：更新 last_heartbeat / avg_response_time
          连续失败 ≥ 3 次 → 熔断器打开 → status = FAILED
  → 失败：failed_requests++
          记录 last_error
          触发 on_unhealthy 回调
          
熔断后 60 秒：进入半开状态，放行 1 个测试请求
  → 测试成功：自动恢复 HEALTHY
  → 测试失败：重新熔断
```

#### 路由决策流程

```
请求进入 → 检查实例分组 → 过滤启用实例
→ 熔断器状态过滤（排除 OPEN 的）
→ 按策略选择：
  ROUND_ROBIN：计数器 % 候选数 = 选中
  LEAST_LOADED：min(active_tasks)
  FAILOVER：优先 primary 标签 > min(active_tasks)
→ 执行任务 → 更新 active_tasks 计数
```

### 2.2 实时监控系统（Monitoring & Alerting）

#### 指标体系

| 类别 | 指标 | 数据源 | 用途 |
|------|------|--------|------|
| 系统 | cpu_percent | psutil | 容量规划 |
| 系统 | memory_percent | psutil | 容量规划 |
| 系统 | disk_percent | psutil | 磁盘告警 |
| OpenClaw | active_tasks | 外部注入 | 任务负载 |
| OpenClaw | avg_response_ms | 外部注入 | 性能监控 |
| OpenClaw | error_rate | 外部注入 | SLA 监控 |
| OpenClaw | instances_healthy | 内部计算 | 可用性 |
| API | api_latency_p95 | 请求追踪 | P95 延迟 |
| API | api_requests_per_min | 请求计数 | QPM |

#### 告警规则

```python
AlertRule(
    metric="cpu_percent", condition="gt", threshold=80,
    severity="warning", cooldown=300, channels=["dingtalk"]
)
```

**条件表达式**：`gt` / `lt` / `gte` / `lte` / `eq`

**告警等级**：
- `info`：信息通知
- `warning`：警告，需要关注
- `critical`：紧急，需立即处理

**冷却机制**：同一规则触发后，`cooldown` 秒内不重复告警

#### 数据存储

- 内存 `deque`：滑动窗口，每个指标保留 720 个点（约 1 小时 @ 5s）
- SQLite（可选）：持久化历史数据，供长期趋势分析

### 2.3 通知通道

| 通道 | 实现 | 配置 |
|------|------|------|
| 钉钉 | 群机器人 Webhook + 加签 | `DINGTALK_TOKEN` / `DINGTALK_SECRET` |
| Telegram | Bot 发送消息 | `TELEGRAM_BOT_TOKEN` / `TELEGRAM_CHAT_ID` |
| 邮件 | SMTP | `SMTP_HOST` / `SMTP_USER` / `SMTP_PASS` |
| 控制台 | Python logging | 内置，无需配置 |

告警消息格式：
```
🔴 [CRITICAL] CPU 过高
机器：北京-生产-01
指标：cpu_percent = 96.5%
阈值：> 95%
时间：2026-04-06 13:52:00
操作：/api/v1/monitor/alerts/{rule_id}/ack
```

## 三、API 设计

### 3.1 多实例 API

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/v1/monitor/instances` | 列出所有实例 |
| POST | `/api/v1/monitor/instances` | 注册新实例 |
| GET | `/api/v1/monitor/instances/{id}` | 实例详情 |
| PATCH | `/api/v1/monitor/instances/{id}` | 更新实例配置 |
| DELETE | `/api/v1/monitor/instances/{id}` | 注销实例 |
| POST | `/api/v1/monitor/instances/health-check` | 手动触发健康检查 |
| POST | `/api/v1/monitor/instances/select` | 策略选择最优实例 |

### 3.2 监控 API

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/v1/monitor/snapshot` | 系统快照 |
| GET | `/api/v1/monitor/series/{metric}` | 指标时序 |
| GET | `/api/v1/monitor/dashboard` | Dashboard 汇总 |
| GET | `/api/v1/monitor/current/{metric}` | 当前指标值 |

### 3.3 告警 API

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/v1/monitor/alerts/rules` | 列出规则 |
| POST | `/api/v1/monitor/alerts/rules` | 添加规则 |
| DELETE | `/api/v1/monitor/alerts/rules/{id}` | 删除规则 |
| GET | `/api/v1/monitor/alerts/active` | 当前告警 |
| GET | `/api/v1/monitor/alerts/history` | 告警历史 |
| POST | `/api/v1/monitor/alerts/{id}/ack` | 确认告警 |

## 四、部署配置

### 4.1 配置文件示例

```yaml
# config.yaml

multi_instance:
  enabled: true
  health_check_interval: 15    # 秒
  strategies:
    default: "round_robin"   # 全局默认策略
    production: "failover"    # production 分组用主备模式

  instances:
    - id: "prod-beijing"
      name: "生产-北京"
      base_url: "http://192.168.1.10:18789"
      api_key: "${OPENCLAW_API_KEY_BJ}"
      group: "production"
      tags: ["primary", "fast"]
      max_concurrent: 10
    - id: "prod-ningbo"
      name: "生产-宁波"
      base_url: "http://192.168.1.11:18789"
      api_key: "${OPENCLAW_API_KEY_NB}"
      group: "production"
      tags: ["backup"]
      max_concurrent: 10

monitoring:
  enabled: true
  collection_interval: 5      # 秒
  retention_minutes: 60

  alert_rules:
    - id: "high-cpu"
      name: "CPU 过高"
      metric: "cpu_percent"
      condition: "gt"
      threshold: 80
      severity: "warning"
      cooldown: 300
      channels: ["dingtalk", "telegram"]

    - id: "critical-cpu"
      name: "CPU 紧急"
      metric: "cpu_percent"
      condition: "gt"
      threshold: 95
      severity: "critical"
      cooldown: 60
      channels: ["dingtalk", "telegram", "email"]

    - id: "high-memory"
      name: "内存过高"
      metric: "memory_percent"
      condition: "gt"
      threshold: 85
      severity: "warning"
      cooldown: 300
      channels: ["dingtalk"]

    - id: "error-rate"
      name: "错误率异常"
      metric: "error_rate"
      condition: "gt"
      threshold: 5
      severity: "warning"
      cooldown: 180
      channels: ["dingtalk"]

    - id: "slow-response"
      name: "响应超时"
      metric: "avg_response_ms"
      condition: "gt"
      threshold: 5000
      severity: "warning"
      cooldown: 300
      channels: ["dingtalk"]

notification:
  dingtalk:
    enabled: true
    token: "${DINGTALK_TOKEN}"
    secret: "${DINGTALK_SECRET}"
  telegram:
    enabled: false
    bot_token: "${TELEGRAM_BOT_TOKEN}"
    chat_id: "${TELEGRAM_CHAT_ID}"
  email:
    enabled: false
    smtp_host: "smtp.example.com"
    smtp_port: 587
    smtp_user: "${SMTP_USER}"
    smtp_pass: "${SMTP_PASS}"
    from_addr: "alert@example.com"
    to_addrs:
      - "admin@example.com"
```
